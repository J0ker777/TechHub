JSON

  "customerId": 123,

}

Команда Service C вирішує трохи «покращити» структуру відповіді:

{

    "id": 123,
    "fullName": "Ivan"
  }
}

Unit Tests:

✅ PASSED

✅ SUCCESS

✅ SUCCESS

Health Check:

🟢 Healthy

Начебто все чудово.

А через кілька хвилин:

Service B ❌
Service A ❌
Frontend ❌

І починається Production Incident.

01

💥 Що сталося?

Service C дійсно працює правильно.

Проблема в іншому.

Service B очікував:

JSON
{
  "customerId": 123,
  "name": "Ivan"
}

а отримав:

JSON
{
  "customer": {
    "id": 123,
    "fullName": "Ivan"
  }
}

З точки зору команди Service C:

↳
«Ми просто змінили DTO».

З точки зору всієї системи:

↳
Ми порушили контракт.

І ось тут починається одна з головних проблем мікросервісної архітектури.

02

🤝 API — це контракт між командами

Коли один сервіс викликає інший:

між ними фактично існує домовленість:

Request
Response
HTTP Codes
Headers
Data Types
Required Fields
Optional Fields
Possible Values
Semantics

І змінити цей контракт в односторонньому порядку — приблизно те саме, що змінити сигнатуру методу, який використовують десятки інших проєктів.

Тільки компілятор про це вже не попередить.

03

🔨 Що таке Breaking Change?

Очевидний приклад.

Було:

JSON
{
  "customerId": 123
}

Стало:

JSON
{
  "id": 123
}

Consumer очікує:

CSHARP
customer.CustomerId

але поля більше немає.

Це breaking change.

04

⚠️ Зміна типу — теж Breaking Change

Було:

JSON
{
  "customerId": 123
}

Стало:

JSON
{
  "customerId": "123"
}

Людина бачить практично те саме.

А для strongly typed consumer:

CSHARP
public int CustomerId { get; set; }

це вже може закінчитися помилкою десеріалізації.

05

➕ А додати поле можна?

Було:

JSON
{
  "id": 123,
  "name": "Ivan"
}

Стало:

JSON
{
  "id": 123,
  "name": "Ivan",
  "email": "ivan@example.com"
}

Зазвичай це вважається backward-compatible change.

Старий consumer просто проігнорує email.

Але…

Не завжди.

06

💣 Навіть нове поле може щось зламати

Уявімо consumer, який використовує strict schema validation.

Він очікує:

JSON
{
  "id": 123,
  "name": "Ivan"
}

і конфігурація говорить:

additionalProperties = false

Приходить:

JSON
{
  "id": 123,
  "name": "Ivan",
  "email": "ivan@example.com"
}

Validator:

❌ Unknown property: email

Provider зробив начебто non-breaking change.

А consumer усе одно зламався.

Саме тому в distributed systems є корисний принцип:

↳
Be conservative in what you send and tolerant in what you accept.

Consumer не повинен ламатися лише тому, що provider додав інформацію, яка йому не потрібна.

07

🧨 А тепер цікавіший приклад

API повертає:

JSON
{
  "id": 123,
  "status": "ACTIVE"
}

Документація говорить:

status:

ACTIVE
BLOCKED

Consumer пише:

CSHARP
switch (customer.Status)
{
    case "ACTIVE":
        ProcessActive();
        break;

    case "BLOCKED":
        ProcessBlocked();
        break;

    default:
        throw new Exception(
            "Unknown status");
}

Через пів року бізнес додає новий статус:

DELETED

Response:

JSON
{
  "id": 123,
  "status": "DELETED"
}

JSON валідний.

Endpoint той самий.

Поле status залишилось string.

Swagger працює.

Health Check зелений.

А consumer:

💥 Unknown status

То чи був це Breaking Change?

08

🧠 Контракт — це не тільки JSON

Це важливий момент.

API contract — це не лише:

field name
field type
required / optional

Це ще й семантика.

Наприклад:

status = ACTIVE

раніше означав:

↳
«Користувач може виконувати всі операції».

Після зміни бізнес-логіки ACTIVE означає:

↳
«Користувач активний, але деякі операції можуть бути заборонені».

JSON взагалі не змінився.

А поведінка системи змінилася.

І consumer може продовжувати технічно працювати, але вже приймати неправильні бізнес-рішення.

Це набагато небезпечніше, ніж звичайний 500.

09

📄 А Swagger/OpenAPI нас врятує?

OpenAPI дуже корисний.

Він дозволяє описати:

YAML
Customer:
  type: object
  required:
    - id
    - status
  properties:
    id:
      type: integer
    status:
      type: string
      enum:
        - ACTIVE
        - BLOCKED

Можна генерувати:

  • документацію;
  • SDK;
  • клієнти;
  • validators;
  • mocks.

Але OpenAPI сам по собі не гарантує, що команда випадково не зробить breaking change.

Для цього потрібна автоматична перевірка контракту.

10

🧪 Contract Testing

Уявімо:

Service B фактично говорить:

↳
«Для моєї роботи мені потрібно, щоб Service C повертав id та status у такому форматі».

Перед deployment Service C можна перевірити:

Якщо ні:

❌ Pipeline Failed

І це набагато краще, ніж:

11

🔄 Consumer-Driven Contracts

Можна піти ще далі.

Provider не просто сам визначає, яким повинен бути API.

Consumers описують, яку частину контракту вони реально використовують.

Наприклад:

Service C перед релізом може перевірити:

↳
Чи не зламаю я когось із своїх consumers?

Для цього існують інструменти на кшталт Pact та інші підходи до contract testing.

12

🔢 А може просто зробити API Versioning?

Наприклад:

/api/v1/customers

Потрібна breaking change:

/api/v2/customers

Старі consumers залишаються на:

v1

нові переходять на:

v2

Це хороший механізм.

Але тут є пастка.

Через декілька років можна отримати:

v1
v2
v3
v4
v5

і кожну версію потрібно:

support
monitor
secure
test
document

Тому versioning — це не заміна backward compatibility.

↳
Нова версія API потрібна для дійсно несумісних змін, а не для кожного нового поля.
13

🚀 Як безпечніше змінювати API?

Припустимо, ми хочемо замінити:

JSON
{
  "name": "Ivan"
}

на:

JSON
{
  "fullName": "Ivan"
}

Не обов'язково одразу видаляти name.

Крок 1

Додаємо нове поле:

JSON
{
  "name": "Ivan",
  "fullName": "Ivan"
}

Крок 2

Consumers переходять на:

fullName

Крок 3

Перевіряємо, що name більше ніхто не використовує.

Крок 4

Позначаємо:

Крок 5

І тільки після узгодженого періоду прибираємо його або робимо це в новій версії контракту.

Це називають expand and contract.

Спочатку розширюємо контракт.

Потім мігруємо consumers.

І лише після цього прибираємо стару частину.

14

🕵️ А як дізнатися, хто взагалі використовує API?

Ось ще одна проблема великих систем.

Команда Service C хоче змінити endpoint.

Питаємо:

↳
«Хто його використовує?»

Відповідь:

🤷

Можливо:

Frontend
Service A
Service B
Mobile App
Old Integration
Some Script
External System

І тут питання вже не лише про код.

Потрібні:

  • документація;
  • ownership сервісів;
  • dependency map;
  • API catalog;
  • telemetry;
  • tracing;
  • version/deprecation policy.

Інакше навіть маленька зміна перетворюється на:

↳
«Задеплоїмо і подивимось, хто перший напише».

Це теж спосіб знайти dependencies.

Але не найкращий. 🙂

15

🧩 Мікросервіси додають організаційну складність

У моноліті зміна DTO може закінчитися:

Compilation Error

і розробник побачить проблему ще до запуску.

У distributed system:

Service A repository
Service B repository
Service C repository

усі три можуть:

Build ✅
Tests ✅
Deploy ✅

і при цьому разом:

System ❌

Тому чим більше незалежних сервісів і команд, тим важливішими стають:

contracts, ownership, compatibility та автоматичне тестування взаємодій.

16

Словник термінів простими словами

  • Мікросервіс — окремий компонент із власною відповідальністю та інтерфейсом.
  • API contract — погоджені запити, відповіді, типи, статуси, помилки й правила поведінки.
  • Consumer / Provider — сервіс, який викликає API, і сервіс, який його надає.
  • Breaking change — зміна, після якої чинний consumer більше не може працювати.
  • Backward compatibility — здатність нової версії API обслуговувати старих клієнтів.
  • OpenAPI / Swagger — машинний опис HTTP-контракту та інструменти навколо нього.
  • Contract test — автоматична перевірка, що provider і consumer однаково розуміють контракт.
  • Consumer-Driven Contract — очікування, сформовані реальними consumer-ами й перевірені на provider-і.
  • Versioning — паралельна підтримка несумісних версій контракту.
  • Deprecation — оголошений період відмови від старого поля чи endpoint.
  • Observability — логи, метрики й трасування для пошуку реальних споживачів і помилок.
17

👶 Якщо зовсім просто

API між мікросервісами — це домовленість двох команд. Навіть маленька зміна назви, типу, обов’язковості поля або коду помилки може зламати чужий сервіс.

OpenAPI описує форму контракту, а contract tests перевіряють, чи справді обидві сторони її виконують. Безпечні зміни спочатку додають, потім переводять consumer-ів і лише після цього прибирають стару поведінку.

Версія API допомагає з несумісними змінами, але не замінює комунікацію. Команда повинна знати споживачів, строки міграції та фактичне використання старого контракту.

18

🧠 Що варто запам'ятати

API — це не просто endpoint.

Це контракт між системами та командами.

І змінюючи API, потрібно думати не лише:

↳
«Чи працює мій сервіс?»

а:

↳
«Чи продовжать працювати всі, хто від мене залежить?»

Тому хороша еволюція API — це зазвичай:

Backward Compatibility
        +
Contract Testing
        +
Deprecation Policy
        +
Versioning
        +
Consumer Awareness

А головна думка:

↳
У distributed system сервіс може бути повністю Healthy і при цьому успішно ламати всю систему.
