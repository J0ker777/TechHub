Вступ

Коли ми говоримо: «сайт протестований», що саме це означає?

Часто перевірка виглядає приблизно так:

↳
Відкрив сайт → авторизувався → натиснув кілька кнопок → дані збереглися → помилок немає → можна релізити.

Але вебзастосунок — це не тільки те, що ми бачимо в браузері.

За звичайною кнопкою «Зберегти» може стояти цілий ланцюжок:

Користувач
    ↓
Браузер
    ↓
Frontend
    ↓
HTTP-запит
    ↓
Backend API
    ↓
База даних
    ↓
Інша система

І проблема може виникнути на будь-якому з цих рівнів.

Тому сьогодні спробуємо подивитися на тестування вебзастосунку не як на «поклікати сайт», а як на перевірку всієї системи.

01

1. Візьмемо простий приклад

Уявімо особистий кабінет споживача.

Користувач може передати показання лічильника.

В інтерфейсі все дуже просто:

Лічильник №123456

Поточне показання:
[ 15432 ]

[ Передати показання ]

Користувач вводить:

15432

натискає кнопку і бачить:

Показання успішно передано

Здається, що тест простий:

  1. Ввести число.
  2. Натиснути кнопку.
  3. Побачити повідомлення.

Якщо повідомлення з'явилося — функціональність працює.

Але насправді ми перевірили лише один позитивний сценарій, або так званий happy path.

02

2. Починаємо з позитивного сценарію

Позитивний сценарій потрібен завжди.

Спочатку потрібно переконатися, що система взагалі виконує свою основну функцію.

Наприклад:

Користувач авторизувався
        ↓
Відкрив свій лічильник
        ↓
Ввів коректне показання
        ↓
Натиснув "Передати"
        ↓
Отримав повідомлення про успіх
        ↓
Показання з'явилося в історії

Це хороший початок.

Але це тільки початок тестування.

Тепер спробуємо зробити щось не так.

03

3. Негативні сценарії

Якщо система очікує число, потрібно перевірити не тільки правильне число.

Що буде, якщо передати:

порожнє значення
0
-100
999999999999999
15.5
"hello"
"<script>"

Або вставити пробіли:

" 15432 "

Або дуже довгий рядок.

Хороший тестувальник перевіряє не тільки:

↳
Чи працює система, коли користувач робить усе правильно?

А й:

↳
Що станеться, коли користувач, браузер або інша система передасть те, чого ми не очікували?
04

4. Frontend validation — це ще не перевірка системи

Frontend може не дозволяти вводити неправильні дані.

Наприклад:

HTML
<input type="number" max="99999">

У браузері все виглядає добре.

Користувач не може ввести:

hello

або:

999999999

Але frontend — це лише клієнт.

Запит до API можна відправити без вашого інтерфейсу.

Наприклад:

HTTP
POST /api/meters/123/readings
Content-Type: application/json

{
    "value": 999999999
}

Якщо backend прийняв це значення — frontend validation нас не врятувала.

Тому важливе правило:

↳
Усе, що приходить від клієнта, backend повинен перевіряти самостійно.

Frontend validation покращує UX.

Backend validation захищає дані та бізнес-логіку.

05

5. Відкриваємо DevTools

Один із найкорисніших інструментів під час тестування вебзастосунку вже знаходиться у браузері.

Відкриваємо:

F12 → Network

Натискаємо «Передати показання» і дивимося, що реально відбулося.

Можемо побачити приблизно такий запит:

HTTP
POST /api/meters/123/readings HTTP/1.1
Content-Type: application/json
Authorization: Bearer eyJ...

{
    "value": 15432
}

А сервер відповідає:

HTTP
HTTP/1.1 201 Created
Content-Type: application/json

{
    "id": 84721,
    "meterId": 123,
    "value": 15432
}

Тепер ми бачимо значно більше.

Можемо перевірити:

  • URL;
  • HTTP method;
  • request headers;
  • request body;
  • cookies;
  • authorization;
  • response body;
  • HTTP status;
  • час виконання запиту.

І тут тестування переходить з рівня «кнопка працює» на рівень розуміння того, як працює система.

06

6. HTTP status теж потрібно перевіряти

Уявімо ситуацію.

Backend повернув:

HTTP
HTTP/1.1 500 Internal Server Error

але frontend через помилку показав:

Показання успішно передано

Якщо дивитися тільки на UI, можна вирішити, що все працює.

Тому потрібно дивитися і на HTTP.

Наприклад:

СитуаціяМожлива відповідь
Показання створено201 Created
Некоректний запит400 Bad Request
Користувач не автентифікований401 Unauthorized
Немає необхідного доступу403 Forbidden
Лічильник не знайдений404 Not Found
Конфлікт зі станом ресурсу409 Conflict
Дані не проходять семантичну валідацію422 Unprocessable Content
Неочікувана помилка сервера500 Internal Server Error

Конкретні коди залежать від контракту API.

Важливо не просто отримати «якусь помилку», а перевірити, що API поводиться передбачувано і відповідно до контракту.

07

7. А тепер обійдемо UI

Якщо ми знаємо endpoint:

POST /api/meters/123/readings

ми можемо перевірити його окремо через Postman, Bruno, Swagger UI або інший API-клієнт.

Наприклад:

JSON
{
    "value": null
}

потім:

JSON
{
    "value": -100
}

потім:

JSON
{
    "value": "hello"
}

потім:

JSON
{
    "value": 999999999999999
}

UI міг ніколи не дозволити сформувати такі запити.

А API — може їх отримати.

Це принципова різниця між:

тестуванням інтерфейсу

та

тестуванням системи.

08

8. Не довіряємо ID, який передав клієнт

Подивимося ще раз на наш URL:

HTTP
POST /api/meters/123/readings

123 — ID лічильника.

Припустимо, це мій лічильник.

А що буде, якщо я зміню:

123

на:

124

і відправлю:

HTTP
POST /api/meters/124/readings

Якщо 124 належить іншому користувачу, сервер повинен перевірити:

Хто виконує запит?
        ↓
Чи має цей користувач доступ до meterId=124?
        ↓
Так → продовжуємо
Ні  → відмовляємо

Сам факт того, що користувач знає ID об'єкта, не дає йому права працювати з ним.

Саме тут під час тестування починають проявлятися проблеми класу IDOR / Broken Object Level Authorization.

09

9. Авторизація — це не тільки login

Ще одна поширена помилка:

↳
Користувач авторизований, отже він може виконувати запит.

Ні.

Authentication відповідає на питання:

↳
Хто ти?

Authorization:

↳
Що тобі дозволено робити?

Наприклад:

User A → meter 123
User B → meter 124
Admin  → meter 123, 124, ...

Тому варто перевіряти запити:

без токена
з неправильним токеном
з простроченим токеном
з токеном іншого користувача
з недостатньою роллю
з правильним токеном

Причому перевіряти це потрібно на backend.

Прихована кнопка у frontend — не контроль доступу.

10

10. Перевіряємо не тільки GET

Часто права перевіряють приблизно так:

HTTP
GET /api/meters/123

Чужий лічильник отримати не можна.

Добре.

А що з:

HTTP
POST
PUT
PATCH
DELETE

Наприклад:

HTTP
DELETE /api/meters/123

може використовувати зовсім іншу backend-логіку.

Тому доступ потрібно перевіряти для кожної операції, а не тільки для перегляду даних.

11

11. XSS, CSRF, CORS — тепер дивимося на них практично

Ми вже можемо знати, що таке XSS, CSRF та CORS.

Тепер питання інше:

↳
Де їх шукати під час тестування конкретного застосунку?

Наприклад, є поле:

Коментар

Спробували ввести дані, які містять HTML/JavaScript.

Потрібно перевірити не тільки момент збереження.

Коментар може потім відображатися:

в особистому кабінеті
в адміністративній панелі
в історії
у звіті
в іншому застосунку

Тобто небезпечне значення може бути збережене зараз, а проявитися пізніше в іншому місці.

Для cookie-based authentication окремо дивимося на CSRF-захист, SameSite, CSRF-токени та критичні state-changing операції.

А якщо frontend і API знаходяться на різних origin — перевіряємо CORS.

12

12. Перевіряємо, що реально сталося з даними

Повернемося до повідомлення:

Показання успішно передано

Що означає «успішно»?

Frontend отримав 200/201?

Backend виконав операцію?

Дані записалися в БД?

У БД вони правильні?

Інтеграція отримала їх?

Уявімо запис:

reading_id: 84721
meter_id:   123
value:      15432
created_by: 567
status:     NEW

Варто перевірити:

meter_id правильний?
value правильний?
created_by правильний?
час правильний?
status правильний?
запис один?

Особливо цікаве останнє питання.

13

13. А що буде, якщо натиснути кнопку двічі?

Користувач натиснув:

[ Передати ]

Сайт задумався.

Через секунду користувач натиснув ще раз.

У Network бачимо:

POST /readings
POST /readings

Що буде в БД?

84721 | meter=123 | value=15432
84722 | meter=123 | value=15432

Це нормально?

Можливо.

А можливо — серйозна помилка.

Для показань це залежить від бізнес-правил.

А тепер замінимо операцію:

Передати показання

на:

Оплатити 500 грн

Тепер повторна операція вже може мати зовсім інші наслідки.

Саме тому під час тестування важливо перевіряти повторні запити та ідемпотентність.

14

14. А якщо відповідь загубилася?

Ще цікавіший сценарій:

Client
   │
   │ POST /payment
   ▼
Server
   │
   │ платіж виконано
   ▼
Database

Server
   │
   X ← connection lost

Client не отримав response

Для клієнта результат невідомий.

Він повторює:

HTTP
POST /payment

Що тепер?

Саме такі сценарії показують, чому недостатньо тестувати систему лише за нормального з'єднання та ідеальних умов.

15

15. Перевіряємо інтеграції

Наш backend не обов'язково працює сам.

Наприклад:

Browser
   ↓
Frontend
   ↓
Backend
   ↓
Billing
   ↓
Database

У happy path:

Billing → 200 OK

А що буде, якщо Billing поверне:

400
401
404
500
503

Або взагалі не відповість?

timeout

Що робить наша система?

Показує користувачу зрозумілу помилку?

Повторює запит?

Ставить операцію в чергу?

Записує дані в БД?

Відкочує транзакцію?

Залишає операцію в проміжному статусі?

Це вже перевірка не окремої кнопки, а поведінки системи при частковій відмові.

16

16. Помилка теж повинна працювати правильно

Ми часто перевіряємо успішний результат:

200 OK

Але помилка — теж результат роботи системи.

Користувач не повинен бачити:

NullReferenceException at MeterService.cs:184

або:

SQLSTATE[23000]

або stack trace.

Краще:

Не вдалося передати показання.
Спробуйте ще раз пізніше.

При цьому в логах має залишитися достатньо інформації, щоб команда могла зрозуміти причину.

Тобто:

Користувач → зрозуміле повідомлення
Розробник  → технічна інформація в логах
17

17. Логи — частина тестування

21

21. Не забуваємо про браузер і екран

22

22. Регресія: ми тестуємо не тільки те, що змінили

Припустимо, розробник змінив:

Передачу показань

Логічно перевірити цю функцію.

Але ці дані можуть використовувати:

Історія показань
        ↓
Графік
        ↓
Billing
        ↓
Мобільний застосунок
        ↓
Звіти

Тому зміна одного endpoint може вплинути на кілька функцій.

Це і є одна з причин регресійного тестування.

Потрібно запитувати:

↳
Що ще могло змінитися через цю зміну?
23

23. Не все потрібно перевіряти вручну

Після такого списку може виникнути логічне питання:

↳
Це ж скільки часу потрібно на один реліз?

Саме тому існує автоматизація тестування.

Умовно:

        E2E
       /   \
 Integration
 /         \
API tests
─────────────
 Unit tests

Unit-тести можуть швидко перевіряти окрему бізнес-логіку.

API-тести — контракт та поведінку endpoint.

Integration-тести — взаємодію компонентів.

E2E — ключові користувацькі сценарії через систему.

Ручне тестування залишається важливим, але людина не повинна перед кожним релізом вручну повторювати сотні однакових перевірок.

24

24. Практичний checklist

Перед тим як сказати:

↳
«Функціональність протестована»

корисно пройти хоча б такий список.

Функціональність

□ Happy path працює
□ Негативні сценарії перевірені
□ Граничні значення перевірені
□ Обов'язкові поля перевірені
□ Бізнес-правила виконуються

Frontend

□ UI правильно відображає результат
□ Помилки зрозумілі користувачу
□ Подвійне натискання обробляється
□ Refresh / Back / Forward не створюють проблем
□ Перевірені необхідні браузери та розміри екрана

API

□ Method правильний
□ Request відповідає контракту
□ Response відповідає контракту
□ HTTP status правильний
□ Backend самостійно валідовує дані
□ Некоректні параметри обробляються

Authentication / Authorization

□ Запит без authentication перевірений
□ Прострочена/некоректна сесія або token перевірені
□ Ролі перевірені
□ Доступ до чужих об'єктів перевірений
□ Backend перевіряє authorization

Security

□ Перевірені потенційні XSS-точки
□ Перевірений CSRF там, де він релевантний
□ Перевірені object-level permissions / IDOR
□ CORS налаштований відповідно до архітектури
□ Технічні помилки не розкривають зайву інформацію

Дані

□ Дані реально записані
□ Дані записані правильно
□ Немає неочікуваних дублікатів
□ Повторний запит перевірений
□ Конкурентні зміни враховані

Інтеграції

□ Успішна відповідь перевірена
□ Помилка зовнішньої системи перевірена
□ Timeout перевірений
□ Повторний запит не створює неконсистентних даних

Експлуатація

□ Помилки логуються
□ Є можливість знайти проблемний запит
□ Логи не містять зайвих секретів
□ Систему можна діагностувати після релізу

Регресія

□ Визначено, на що могла вплинути зміна
□ Критичні суміжні сценарії перевірені
□ Автоматизовані тести пройшли

25. Головна думка

Тестування вебзастосунку — це не перевірка того, чи натискається кнопка.

Це перевірка всього сценарію:

Користувач
    ↓
UI
    ↓
HTTP
    ↓
Authentication
    ↓
Authorization
    ↓
API
    ↓
Validation
    ↓
Business Logic
    ↓
Database
    ↓
Integration
    ↓
Logs

І для кожного рівня потрібно поставити два питання:

↳
Що повинно відбутися, якщо все добре?

і

↳
Що повинно відбутися, якщо щось піде не так?

Саме друге питання часто знаходить найбільш цікаві помилки.

Тому наступного разу, коли після тестування хтось скаже:

↳
«Я поклікав — усе працює».

можна поставити лише одне запитання:

↳
А що саме ти перевірив?
