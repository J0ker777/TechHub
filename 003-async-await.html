💻 Async/Await: чому async не означає паралельно?

Вступ

async/await сьогодні є практично стандартом для backend-розробки.

HTTP-запити, робота з БД, файлами, чергами — всюди бачимо:

CSHARP
await SomeOperationAsync();

Через це іноді виникає дуже просте припущення:

↳
Якщо метод async — значить він виконується паралельно.

Але це не так.

Async ≠ Parallel ≠ Multithreading

І нерозуміння різниці між ними може призвести як до повільного коду, так і до проблем у Production.

01

🐌 Async-код, який усе одно працює послідовно

Уявімо API, якому потрібно отримати три незалежні набори даних:

CSHARP
var user = await GetUserAsync();
var orders = await GetOrdersAsync();
var balance = await GetBalanceAsync();

return new Result(user, orders, balance);

Усі методи асинхронні.

Але подивімось, що реально відбувається:

Наступна операція запускається тільки після завершення попередньої.

Якщо кожна займає приблизно 1 секунду:

Загальний час:

≈ 3 секунди

Код асинхронний.

Але операції виконуються послідовно.

02

🚀 А якщо операції незалежні?

Якщо GetOrdersAsync() не потребує результату GetUserAsync(), а GetBalanceAsync() не залежить від GetOrdersAsync(), їх можна запустити одночасно:

CSHARP
var userTask = GetUserAsync();
var ordersTask = GetOrdersAsync();
var balanceTask = GetBalanceAsync();

await Task.WhenAll(
    userTask,
    ordersTask,
    balanceTask);

return new Result(
    await userTask,
    await ordersTask,
    await balanceTask);

Тепер картина приблизно така:

Якщо кожна операція займає близько 1 секунди, загальний час буде приблизно:

≈ 1 секунда, а не 3.

Ми нічого не прискорили всередині самих операцій.

Ми просто перестали без необхідності чекати завершення кожної перед запуском наступної.

03

🧠 Але це все ще не означає три потоки

Ось тут важлива різниця.

Коли ми пишемо:

CSHARP
await httpClient.GetAsync(url);

це не означає:

↳
«Створи новий Thread і нехай він сидить та чекає відповіді».

Для нормальної асинхронної I/O-операції потік не повинен блокуватися на весь час очікування мережі.

У спрощеному вигляді:

Поки віддалений сервер думає 2 секунди, нашому CPU немає сенсу тримати Thread заблокованим лише для очікування.

Саме тому async особливо ефективний для I/O-bound операцій.

Наприклад:

  • HTTP;
  • SQL;
  • файлові операції;
  • мережеві запити;
  • робота з зовнішніми API.
04

⚙️ I/O-bound vs CPU-bound

Це дуже важливе розділення.

I/O-bound

Програма переважно чекає:

CPU у цей час майже нічого не робить.

Тут async/await дуже доречний.

CPU-bound

Наприклад:

CSHARP
CalculateHash();
ResizeImage();
ProcessVideo();
RunMLInference();
CalculateSomethingVeryHeavy();

Тут CPU реально виконує обчислення.

Якщо написати:

CSHARP
await CalculateSomethingAsync();

CPU від цього магічно швидшим не стане.

async не додає процесорних ядер.

05

🧵 А що тоді робить Task.Run()?

Можна зустріти код:

CSHARP
await Task.Run(() =>
{
    HeavyCalculation();
});

Task.Run() передає роботу в ThreadPool.

Це може бути корисно, наприклад, у desktop/UI-застосунку, щоб важкі CPU-обчислення не блокували UI thread.

Але в ASP.NET Core ситуація інша.

Якщо всередині Web API зробити:

CSHARP
await Task.Run(() => SomeDatabaseCall());

ми не зробили операцію швидшою.

Фактично ми сказали:

↳
«Не виконуй це на одному ThreadPool thread — дай мені інший ThreadPool thread».

Під великим навантаженням надмірне використання такого підходу може тільки погіршити масштабованість.

Тому:

↳
Task.Run — не чарівний спосіб зробити Web API асинхронним.

Якщо бібліотека має справжній async API — зазвичай краще використовувати саме його.

06

⚠️ Ще одна популярна пастка

Подивімось на такий код:

CSHARP
items.ForEach(async item =>
{
    await ProcessAsync(item);
});

На вигляд усе нормально.

Але List<T>.ForEach() очікує звичайний Action<T>.

У результаті async-лямбда фактично поводиться як async void.

А це означає, що зовнішній код не має нормального Task, який можна очікувати.

Можемо отримати ситуацію:

Start processing
Processing item 1...
Processing item 2...
Processing item 3...

Method finished!

...а ProcessAsync ще працюють

Краще явно працювати з Task:

CSHARP
var tasks = items.Select(ProcessAsync);

await Task.WhenAll(tasks);

Тепер ми реально очікуємо завершення всіх операцій.

07

💣 Тоді запускаємо все через Task.WhenAll?

Теж ні.

Уявімо, що маємо:

10 000 users

і для кожного потрібно викликати API:

CSHARP
var tasks = users.Select(x =>
    SendRequestAsync(x));

await Task.WhenAll(tasks);

Що ми щойно зробили?

Потенційно спробували одночасно запустити 10 000 операцій.

І проблема може виникнути вже не у нашому коді.

Можна впертися в:

  • connection pool;
  • socket limits;
  • rate limits;
  • SQL connection pool;
  • memory;
  • downstream service;
  • зовнішній API.

Тобто:

↳
Concurrency без обмежень може перетворитися на DoS, який система влаштувала сама собі.
08

🚦 Bounded Concurrency

Іноді правильніше сказати:

↳
У мене 10 000 задач, але одночасно я хочу виконувати максимум 20.

Наприклад:

CSHARP
using var semaphore = new SemaphoreSlim(20);

var tasks = items.Select(async item =>
{
    await semaphore.WaitAsync();

    try
    {
        await ProcessAsync(item);
    }
    finally
    {
        semaphore.Release();
    }
});

await Task.WhenAll(tasks);

Тепер:

Total operations:     10 000
Concurrent operations:    20

Завершилась одна операція — запускається наступна.

Ми отримуємо контрольовану concurrency замість:

🔥 FIRE EVERYTHING AT ONCE 🔥

У сучасному .NET для багатьох подібних сценаріїв також зручно використовувати Parallel.ForEachAsync з обмеженням MaxDegreeOfParallelism.

09

📈 Чому це особливо важливо для Web API?

Уявімо сервер, який обробляє:

1 000 одночасних HTTP-запитів.

Кожен запит виконує SQL query, яка відповідає 500 ms.

При синхронному блокуванні можна отримати багато потоків, які фактично просто сидять:

При справжньому async I/O потоки можуть використовуватися для іншої роботи, поки БД або мережа готують відповідь.

Саме тому головна перевага async у backend часто не:

«Один запит стане швидшим».

А:

↳
«Система зможе ефективніше обслуговувати багато одночасних запитів».

Це принципова різниця.

10

Словник термінів простими словами

  • Async / await — спосіб не блокувати потік під час очікування асинхронної операції.
  • Task — об’єкт, що представляє роботу, яка завершиться пізніше.
  • Sequential execution — наступна операція починається після попередньої.
  • Concurrency — кілька операцій перебувають у роботі в один період.
  • Parallelism — обчислення реально виконуються одночасно на кількох ядрах або потоках.
  • I/O-bound переважно чекає мережу, диск чи БД; CPU-bound використовує процесор.
  • Task.Run переносить CPU-роботу до thread pool; він не прискорює зовнішнє I/O.
  • Task.WhenAll очікує завершення групи вже запущених tasks.
  • Fire-and-forget — запуск без коректного очікування результату й помилки.
  • Bounded concurrency — обмеження кількості одночасних операцій.
  • Thread pool starvation — нестача потоків через блокування або надмірні задачі.
11

👶 Якщо зовсім просто

await означає: «призупини операцію, поки результат не готовий, і не тримай потік без потреби». Якщо кожен await стоїть перед запуском наступної операції, робота все одно послідовна.

Незалежні I/O-операції можна спочатку запустити, а потім разом очікувати через Task.WhenAll. Вони одночасно чекають зовнішні системи, хоча окремий потік не потрібен для кожної.

Необмежений запуск тисяч tasks може перевантажити базу, API або connection pool. Bounded concurrency задає безпечну кількість одночасної роботи.

12

🧠 Що варто запам'ятати

async — не означає parallel.

await — не означає new Thread.

Task — не означає Thread.

Task.Run() — не робить I/O магічно швидшим.

Task.WhenAll() — корисний для незалежних операцій, але безконтрольна concurrency може створити нові проблеми.

А головне:

↳
Async потрібен не стільки для того, щоб CPU працював швидше, скільки для того, щоб не витрачати ресурси на блокуюче очікування.

    user,

500 ms

У нас не три операції, а:

10 000 HTTP-запитів.

❓ Що насправді має визначати цей ліміт — кількість CPU, connection pool, можливості нашого сервісу чи можливості системи, яку ми викликаємо?
