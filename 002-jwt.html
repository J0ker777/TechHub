👀 JWT можна прочитати 🧠 Що варто запам'ятати
Вступ

JWT сьогодні зустрічається майже всюди: API, мікросервіси, мобільні застосунки, OAuth/OIDC.

Виглядає він приблизно так:

eyJhbGciOiJSUzI1NiIs...

Довгий набір незрозумілих символів.

І через це легко подумати:

«Дані всередині JWT зашифровані».

Але це не так.

01

👀 JWT можна прочитати

Типовий JWT складається з трьох частин:

HEADER.PAYLOAD.SIGNATURE

Наприклад:

xxxxx.yyyyy.zzzzz

Header і Payload — це фактично JSON, закодований у Base64URL.

У payload може бути щось на кшталт:

JSON
{
  "sub": "12345",
  "name": "Ivan",
  "role": "admin",
  "exp": 1787000000
}

І для того, щоб це прочитати, секретний ключ не потрібен.

Base64 — це encoding, а не encryption.

Тому правило просте:

↳
Не кладіть у звичайний JWT інформацію лише тому, що не хочете показувати її користувачу.

Паролі, API keys, connection strings та інші секрети там точно не повинні опинятися.

✍️ Тоді навіщо потрібен Signature?

Підпис потрібен не для приховування інформації.

Він дозволяє перевірити:

чи змінював хтось токен після того, як його видав довірений сервер.

Наприклад, користувач бачить:

JSON
"role": "user"

і вирішує змінити на:

JSON
"role": "admin"

Payload змінити він може.

Але старий signature після цього вже не відповідатиме новому payload.

При коректній перевірці сервер відхилить такий токен.

Тобто:

Encryption → приховує дані

Signature → підтверджує цілісність та походження даних

Це різні задачі.

🚨 Але що, якщо JWT викрали?

Ось тут починається найцікавіше.

Припустимо, у користувача є валідний access token.

Зловмисник якимось чином отримав його.

Йому не потрібно:

  • знати пароль;
  • розшифровувати JWT;
  • генерувати новий signature;
  • ламати алгоритм підпису.

Він може просто відправляти викрадений токен.

Для API це буде той самий валідний credential, доки не спрацюють механізми обмеження його використання.

Це одна з причин, чому access token зазвичай має бути короткоживучим.

Наприклад:

Access Token → 5–15 хв

а для продовження сесії використовується:

Refresh Token → довший термін

Конкретні значення залежать від ризиків і архітектури системи.

🚪 А як працює Logout?

Тут у JWT є цікава особливість.

Уявімо, сервер видав токен:

exp = 12:00

О 10:00 користувач натиснув Logout.

Застосунок видалив токен.

Але якщо хтось скопіював його до logout?

Сам по собі JWT не отримує магічне повідомлення:

«Користувач вийшов — більше не працюй».

Якщо сервер перевіряє лише signature та exp, токен потенційно залишатиметься валідним до 12:00.

Тому залежно від вимог використовують:

  • короткий lifetime access token;
  • refresh token rotation;
  • token revocation;
  • denylist;
  • перевірку стану сесії.

Але тут є компроміс.

Одна з переваг JWT — можливість stateless authentication.

Якщо для кожного запиту ми починаємо перевіряти token/session у центральній БД або Redis, частину цієї переваги ми втрачаємо.

🔎 Signature правильний. Цього достатньо?

Ні.

Уявімо, API отримав JWT.

Signature успішно перевірено.

exp ще не минув.

Можна виконувати запит?

Не обов'язково.

У JWT є важливі claims.

Наприклад:

iss — Issuer

Хто видав токен?

JSON
"iss": "https://identity.company.com"

API повинен переконатися, що довіряє саме цьому issuer.

aud — Audience

Для кого був створений токен?

JSON
"aud": "billing-api"

Токен, створений для:

reporting-api

не повинен автоматично давати доступ до:

billing-api

навіть якщо обидва API довіряють одному Identity Provider.

exp — Expiration

До якого моменту токен дійсний.

nbf — Not Before

До якого моменту токен ще не повинен прийматися.

🔑 А звідки API бере ключ для перевірки?

У сучасних системах часто використовуються асиметричні алгоритми, наприклад RSA або ECDSA.

Identity Provider має:

Private Key

і ним підписує токени.

API використовує:

Public Key

для перевірки signature.

Public keys можуть публікуватися через JWKS — JSON Web Key Set.

У header JWT при цьому може бути:

JSON
{
  "alg": "RS256",
  "kid": "key-2026-01"
}

kid допомагає API визначити, який public key потрібно використати.

Це також дозволяє Identity Provider робити key rotation без необхідності вручну роздавати новий ключ кожному сервісу.

🖥 А де зберігати JWT на клієнті?

Ще одне питання, на яке немає універсальної відповіді:

localStorage?

sessionStorage?

cookie?

memory?

Наприклад, токен у localStorage доступний JavaScript.

При успішній XSS атаці зловмисник потенційно може його отримати.

HttpOnly Cookie недоступна JavaScript, що допомагає проти прямого викрадення токена через XSS.

Але cookie автоматично додається браузером до відповідних запитів — і тоді потрібно правильно враховувати CSRF, SameSite, Secure та інші параметри.

Тому питання:

«Де краще зберігати JWT?»

насправді починається з іншого:

«Яка модель загроз у нашого застосунку?»

02

🧠 Що варто запам'ятати

JWT — це не просто:

Login → отримали token → перевірили signature → дозволили запит

Мінімально потрібно думати про:

Signature + Issuer + Audience + Lifetime + Permissions + Key Management + Token Storage

І головне:

↳
Валідний JWT ще не означає, що цьому запиту потрібно дозволити виконати конкретну операцію.

Authentication відповідає на питання:

«Хто ти?»

Authorization:

«Що тобі дозволено робити?»

І це вже зовсім інша перевірка.
