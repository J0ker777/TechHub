Ми щодня відкриваємо десятки вебсайтів.

Вводимо адресу:

https://cabinet.example.com/profile

натискаємо Enter — і через секунду бачимо сторінку.

На перший погляд усе просто.

Але між натисканням Enter і появою сторінки браузер, операційна система, DNS, мережа, засоби безпеки, вебсервер, backend і база даних встигають виконати цілий ланцюжок операцій.

І коли користувач каже:

↳
«Не працює сайт»

це насправді майже нічого не говорить про причину проблеми.

Спробуємо пройти весь шлях одного запиту і зрозуміти, що насправді відбувається після натискання Enter.

01

1. Що взагалі таке вебсайт

Почнемо з важливого моменту.

Вебсайт — це не обов'язково один сервер, на якому лежать HTML-файли.

Сучасний вебзастосунок може складатися з багатьох компонентів:

Браузер
   │
   ▼
DNS
   │
   ▼
WAF / Reverse Proxy
   │
   ▼
Frontend
   │
   ▼
API Gateway
   │
   ▼
Backend
   │
   ├──► Database
   │
   ├──► Redis
   │
   ├──► RabbitMQ
   │
   └──► Інші системи/API

При цьому користувач бачить лише одну адресу:

https://cabinet.example.com

Уся внутрішня архітектура від нього прихована.

02

2. Користувач вводить URL

Припустимо, ми відкриваємо:

https://cabinet.example.com/profile

Це URL — Uniform Resource Locator.

Розберемо його:

https://cabinet.example.com/profile
│       │                   │
│       │                   └── path
│       └────────────────────── host
└────────────────────────────── scheme

https

Протокол, який буде використовувати браузер.

HTTPS означає, що HTTP працює через захищене TLS-з'єднання.

cabinet.example.com

Ім'я сервера, до якого потрібно звернутися.

Але мережа не працює з такими іменами напряму.

Їй потрібна IP-адреса.

/profile

Ресурс, який ми хочемо отримати.

Наприклад:

/

головна сторінка,

/profile

профіль,

/payments

платежі.

03

3. DNS: де знаходиться cabinet.example.com?

Браузеру потрібно зрозуміти:

cabinet.example.com → ?

Наприклад, результатом може бути:

cabinet.example.com → 203.0.113.25

Для цього використовується DNS — Domain Name System.

Спрощено DNS можна уявити як телефонну книгу Інтернету:

example.com → IP
google.com  → IP
github.com  → IP

Але браузер не обов'язково відразу звертається до зовнішнього DNS-сервера.

Спочатку можуть перевірятися кеші:

Browser DNS cache
       ↓
Operating System cache
       ↓
Configured DNS resolver
       ↓
DNS infrastructure

Якщо IP вже відомий — частину цього шляху можна пропустити.

04

4. DNS знайшов IP. Що далі?

Припустимо:

cabinet.example.com
        ↓
203.0.113.25

Тепер браузер знає, куди потрібно підключитися.

Але HTTP-запит ще не відправлено.

Спочатку потрібно встановити мережеве з'єднання.

Для класичного HTTP/1.1 або HTTP/2 зазвичай використовується TCP.

Для HTTPS типовим портом є:

443

Отже, логічно маємо:

203.0.113.25:443
05

5. TCP: встановлюємо з'єднання

Перед передаванням HTTP-даних клієнт і сервер встановлюють TCP-з'єднання.

Спрощено:

Browser                         Server
   │                               │
   │ -------- SYN ---------------->│
   │                               │
   │ <----- SYN + ACK -------------│
   │                               │
   │ -------- ACK ---------------->│
   │                               │

Це називається TCP three-way handshake.

Після цього між сторонами існує TCP-з'єднання.

Але ми відкриваємо:

https://

Тому потрібен ще один важливий етап.

06

6. TLS: створюємо захищений канал

HTTPS — це не окремий HTTP.

Спрощено:

HTTPS = HTTP + TLS

TLS забезпечує:

  • шифрування;
  • цілісність даних;
  • перевірку автентичності сервера.

Під час TLS handshake браузер і сервер домовляються про параметри захищеного з'єднання.

Сервер також передає сертифікат.

Браузер перевіряє, зокрема:

  • чи не закінчився термін його дії;
  • чи відповідає сертифікат доменному імені;
  • чи можна довіряти центру сертифікації;
  • чи коректний ланцюжок сертифікатів.

Тому ситуація:

↳
«Сайт доступний по IP, але через HTTPS не відкривається»

може взагалі не мати стосунку до frontend або backend.

Проблема може бути на рівні TLS або сертифіката.

07

7. Нарешті HTTP-запит

Тепер браузер може відправити запит.

Наприклад:

HTTP
GET /profile HTTP/1.1
Host: cabinet.example.com
User-Agent: Chrome/...
Accept: text/html
Cookie: session=abc123

Тут уже бачимо знайомий HTTP.

Запит говорить приблизно наступне:

↳
Дай мені ресурс /profile для cabinet.example.com.

Але є важливий нюанс.

Запит зовсім не обов'язково потрапляє безпосередньо на сервер застосунку.

08

8. На шляху може стояти WAF

У корпоративних системах зовнішні вебзастосунки часто захищаються за допомогою WAF — Web Application Firewall.

Схема може виглядати так:

Internet
   │
   ▼
 WAF
   │
   ▼
Reverse Proxy
   │
   ▼
Application

WAF аналізує HTTP-запити та може блокувати потенційно небезпечний трафік.

Наприклад:

Browser
   │
   │ GET /profile
   ▼
 WAF
   │
   ├── suspicious → BLOCK
   │
   └── allowed
          │
          ▼
      Application

Тому ще одна ситуація:

↳
«Frontend працює, backend працює, але з Інтернету запит отримує 403».

Причина може бути не в коді застосунку.

Запит може блокувати WAF.

09

9. Reverse Proxy / Web Server

Далі запит може потрапити, наприклад, на:

  • Nginx;
  • Apache;
  • IIS;
  • інший reverse proxy.

Його задача — визначити, куди направити запит.

Наприклад:

/              → frontend
/api/          → API Gateway
/static/       → static files

Отже:

GET /profile

може піти на frontend,

а:

GET /api/profile

— на backend.

Для користувача все це може залишатися одним доменом:

cabinet.example.com
10

10. Сервер повертає HTML

Припустимо, браузер запросив:

HTTP
GET /profile

і сервер відповів:

HTTP
HTTP/1.1 200 OK
Content-Type: text/html

а в body прийшло:

HTML
<!DOCTYPE html>
<html>
<head>
    <title>Особистий кабінет</title>
    <link rel="stylesheet" href="/app.css">
</head>
<body>

    <div id="app"></div>

    <script src="/app.js"></script>

</body>
</html>

Чи означає це, що сторінка вже завантажена?

Ні.

Браузер отримав лише перший документ.

11

11. HTML породжує нові запити

Браузер починає читати HTML.

І знаходить:

HTML
<link rel="stylesheet" href="/app.css">

Отже, потрібен CSS.

Відправляється ще один запит:

HTTP
GET /app.css

Далі браузер бачить:

HTML
<script src="/app.js"></script>

Ще один запит:

HTTP
GET /app.js

Потім:

HTML
<img src="/logo.svg">

Ще один:

HTTP
GET /logo.svg

У реальному застосунку таких ресурсів може бути багато.

Тому відкриття однієї сторінки — це зовсім не обов'язково один HTTP-запит.

Це можуть бути десятки або сотні запитів.

12

12. HTML, CSS і JavaScript — хто за що відповідає?

Дуже спрощено можна запам'ятати так.

HTML — структура

HTML
<button>Оплатити</button>

Визначає, що є на сторінці.

CSS — вигляд

CSS
button {
    border-radius: 8px;
}

Визначає, як це виглядає.

JavaScript — поведінка

JAVASCRIPT
button.addEventListener("click", pay);

Визначає, що відбувається.

Умовно:

HTML       CSS       JavaScript
 │          │             │
 ▼          ▼             ▼
структура   вигляд       поведінка
13

13. Але звідки беруться дані?

Наш користувач відкрив:

/profile

На сторінці потрібно показати:

Ім'я
Особовий рахунок
Адресу
Баланс
Останні покази

Цих даних може не бути в HTML.

Frontend повинен отримати їх від backend.

Наприклад JavaScript виконує:

HTTP
GET /api/profile

І backend повертає:

JSON
{
  "name": "Іван Петренко",
  "account": "12345678",
  "balance": 245.30
}

Frontend отримує JSON і показує його користувачу.

14

14. Frontend і Backend

Тут важливо розділяти два поняття.

Frontend

Це частина застосунку, з якою безпосередньо взаємодіє користувач.

Наприклад:

HTML
CSS
JavaScript
React
Angular
Vue

Вона виконується переважно у браузері.

Backend

Це серверна частина.

Наприклад:

.NET
Java
PHP
Node.js
Python

Backend реалізує бізнес-логіку.

Наприклад:

GET /api/profile

може означати:

  1. перевірити користувача;
  2. визначити його account ID;
  3. звернутися до БД;
  4. отримати дані;
  5. перевірити права;
  6. сформувати JSON;
  7. повернути відповідь.
15

15. Backend звертається до бази

Тепер наша схема стає цікавішою.

Browser
   │
   │ GET /api/profile
   ▼
Frontend
   │
   ▼
API
   │
   ▼
Backend
   │
   ▼
Database

Backend може виконати SQL-запит:

SQL
SELECT
    name,
    account,
    balance
FROM customers
WHERE id = 12345;

База повертає результат:

Іван Петренко
12345678
245.30

Backend перетворює його на JSON:

JSON
{
  "name": "Іван Петренко",
  "account": "12345678",
  "balance": 245.30
}

і повертає браузеру.

16

16. Але backend може бути не один

У сучасній системі /api/profile зовсім не означає один сервер.

Наприклад:

Browser
   │
   ▼
API Gateway
   │
   ▼
Profile Service
   │
   ├────► Customer DB
   │
   ├────► Billing API
   │
   └────► Redis

Profile Service може отримати основні дані з однієї БД, баланс — з білінгу, а частину інформації — з кешу Redis.

У результаті один простий екран:

↳
«Мій профіль»

може залежати від роботи кількох систем.

17

17. А де тут авторизація?

Більшість кабінетів не дозволяють просто виконати:

HTTP
GET /api/profile

Потрібно знати, хто саме виконує запит.

Для цього можуть використовуватися:

  • cookies;
  • sessions;
  • access tokens;
  • JWT;
  • OAuth 2.0 / OpenID Connect.

Наприклад:

HTTP
GET /api/profile
Authorization: Bearer eyJhbGciOi...

Backend перевіряє token.

Якщо все добре:

200 OK

Якщо користувач не автентифікований:

401 Unauthorized

Якщо користувач відомий, але не має необхідних прав:

403 Forbidden

Це важлива різниця.

19

19. Що таке DOM?

Коли браузер отримує HTML, він не просто показує текст файлу.

Він будує структуру документа — DOM (Document Object Model).

Наприклад:

HTML
<body>
    <h1>Кабінет</h1>
    <button>Оплатити</button>
</body>

перетворюється приблизно на дерево:

Document
   │
   └── html
        │
        └── body
             ├── h1
             │    └── "Кабінет"
             │
             └── button
                  └── "Оплатити"

JavaScript може змінювати це дерево.

Наприклад:

JAVASCRIPT
document.querySelector("h1").innerText =
    "Вітаємо, Іване!";

І браузер оновить сторінку без повного перезавантаження.

20

20. Чому сучасний сайт може працювати без перезавантаження?

У класичному вебсайті перехід:

/profile → /payments

міг означати отримання нового HTML-документа.

У сучасному SPA — Single Page Application — часто завантажується основний JavaScript-застосунок.

Далі frontend сам звертається до API:

GET /api/profile

GET /api/payments

GET /api/meters

і змінює потрібну частину сторінки.

Тому користувач натискає:

↳
«Платежі»

і бачить новий екран, хоча браузер не завантажував повністю нову HTML-сторінку.

21

21. Що відбувається після натискання кнопки?

Припустимо, користувач натиснув:

«Передати покази»

Frontend може виконати:

HTTP
POST /api/readings
Content-Type: application/json
Authorization: Bearer ...

{
  "meterId": "12345",
  "value": 15432
}

Далі:

Browser
   │
   ▼
API Gateway
   │
   ▼
Backend
   │
   ├── перевірка token
   ├── validation
   ├── business logic
   ├── запис у DB
   └── можлива інтеграція

Backend повертає:

HTTP
HTTP/1.1 200 OK
JSON
{
  "status": "accepted"
}

І frontend показує:

✓ Покази успішно передані

Одна кнопка на екрані приховує цілий ланцюжок операцій.

22

22. Тепер фраза «сайт не працює» звучить інакше

Уявімо звернення:

↳
«Не працює особистий кабінет».

Де проблема?

Варіантів багато.

DNS

cabinet.example.com → не резолвиться

Сайт взагалі не буде знайдений.

Network

IP відомий, але з'єднання не встановлюється.

TLS

Наприклад, проблема із сертифікатом.

WAF

Запит блокується правилами безпеки.

Frontend

HTML відкрився, але JavaScript падає з помилкою.

API

Frontend працює, але:

GET /api/profile → 500

Авторизація

GET /api/profile → 401

Права

GET /api/profile → 403

Backend

Виникла внутрішня помилка.

Database

Backend не може підключитися до БД.

Інтеграція

Backend працює, але зовнішня система недоступна.

Тому хороше технічне питання — не:

↳
«Чому сайт не працює?»

а:

↳
«На якому етапі перестає працювати ланцюжок?»
23

23. HTTP status code вже багато про що говорить

Під час діагностики варто дивитися на HTTP status.

Наприклад:

200 OK

Запит успішний.

301 / 302

Redirect.

400 Bad Request

Проблема із запитом.

401 Unauthorized

Проблема з автентифікацією.

403 Forbidden

Доступ заборонений.

404 Not Found

Ресурс не знайдений.

429 Too Many Requests

Забагато запитів.

500 Internal Server Error

Помилка на сервері.

502 Bad Gateway

Proxy/Gateway не отримав коректної відповіді від upstream.

503 Service Unavailable

Сервіс тимчасово недоступний.

504 Gateway Timeout

Gateway не дочекався відповіді.

Це ще не готовий діагноз, але вже дуже хороший напрямок пошуку.

24

24. Як побачити все це самому?

У браузері Chrome або Edge натискаємо:

F12

і відкриваємо:

Developer Tools → Network

Оновлюємо сторінку.

І раптом те, що до цього було приховано, стає видимим.

Можна побачити:

Name             Status      Type
--------------------------------------
profile          200         document
app.css          200         stylesheet
app.js           200         script
logo.svg         200         image
api/profile      200         fetch
api/payments     200         fetch
api/meters       500         fetch

І вже бачимо цікаву картину.

Сайт не впав.

HTML завантажився.

CSS завантажився.

JavaScript завантажився.

Profile API працює.

Payments API працює.

А ось:

api/meters → 500

не працює.

Тобто проблема значно локальніша, ніж:

↳
«Сайт лежить».
25

25. Що дивитися в Network?

Натиснувши на конкретний запит, можна побачити багато корисної інформації.

Headers

Наприклад:

HTTP
Request URL:
https://cabinet.example.com/api/profile

Request Method:
GET

Status Code:
200

Також можна побачити request headers:

HTTP
Authorization: Bearer ...
Content-Type: application/json

та response headers.

Payload

Для POST-запиту можна побачити, що саме frontend відправив.

Наприклад:

JSON
{
  "meterId": "12345",
  "value": 15432
}

Це особливо корисно під час тестування.

Питання вже не:

↳
«Я натиснув кнопку, але воно не працює».

А:

↳
«Frontend після натискання кнопки відправив POST /api/readings, передав такі дані й отримав 400».

Це зовсім інший рівень діагностики.

Response

Можна побачити, що повернув backend.

Наприклад:

JSON
{
  "error": "Reading must be greater than previous value"
}

І тоді причина проблеми може стати очевидною навіть без доступу до серверних логів.

Timing

Також можна побачити, скільки часу займає запит.

Наприклад:

DNS              5 ms
Connection      20 ms
TLS             30 ms
Waiting         850 ms
Download         5 ms

Якщо основний час:

Waiting 850 ms

це вже може підказувати, що браузер довго чекає саме відповіді від серверної сторони.

26

26. Console — другий корисний інструмент

Поруч із Network є вкладка:

Console

Там можна побачити JavaScript-помилки.

Наприклад:

Uncaught TypeError:
Cannot read properties of undefined

Тобто API може працювати нормально, але frontend не зміг правильно обробити отримані дані.

З точки зору користувача:

↳
«Не працює сайт».

З точки зору діагностики:

HTML       OK
CSS        OK
API        OK
Backend    OK
Database   OK
Frontend   ERROR

Різниця величезна.

27

27. Один екран — багато систем

Повернемося до нашого кабінету.

Користувач бачить одну сторінку:

┌───────────────────────────────┐
│       Особистий кабінет       │
│                               │
│ Іван Петренко                 │
│ Баланс: 245,30 грн            │
│                               │
│ Лічильник: 15432              │
│                               │
│ [Передати покази]             │
└───────────────────────────────┘

А технічно за нею може стояти:

                     ┌──────────────┐
                     │ Customer DB  │
                     └──────▲───────┘
                            │
Browser → WAF → Gateway → Backend
                            │
              ┌─────────────┼─────────────┐
              ▼             ▼             ▼
           Billing        Redis        Meter API

І якщо хоча б одна критична залежність недоступна, частина функціональності може перестати працювати.

28

28. Головна думка

Вебсайт — це не просто:

HTML + CSS + JavaScript

Сучасний вебзастосунок — це цілий ланцюжок взаємодій.

Спрощено:

URL
 ↓
DNS
 ↓
Network
 ↓
TCP
 ↓
TLS
 ↓
HTTP
 ↓
WAF
 ↓
Reverse Proxy
 ↓
Frontend
 ↓
API
 ↓
Backend
 ↓
Database / Redis / інші системи
 ↓
JSON
 ↓
JavaScript
 ↓
DOM
 ↓
Screen

І знати напам'ять усі деталі цього ланцюжка потрібно далеко не кожному.

Але розуміти, що цей ланцюжок існує, дуже корисно кожному, хто працює з вебсистемами.

Розробнику це допомагає шукати проблеми.

QA — точніше локалізувати дефекти.

BA — краще розуміти поведінку системи та інтеграції.

DevOps та Support — швидше визначати проблемний компонент.

PM — розуміти, чому фраза «треба просто зробити сторінку» іноді приховує зміни одразу в декількох системах.

29

🧪 Маленький експеримент

Відкрийте будь-який вебсайт.

Натисніть:

F12 → Network

Оновіть сторінку.

Подивіться:

  • скільки запитів було виконано;
  • які з них мають тип document;
  • де завантажуються JS та CSS;
  • які запити мають тип Fetch/XHR;
  • які HTTP status codes повертаються;
  • що знаходиться в Request;
  • що знаходиться в Response;
  • скільки часу займають різні запити.

А потім відкрийте якусь сторінку або натисніть кнопку без перезавантаження браузера.

І подивіться, які нові API-запити з'являться в Network.

Після цього вебсайт уже складно сприймати просто як «сторінку в браузері». 🙂

30

📌 Що варто запам'ятати

1. URL — це лише початок.

Після введення адреси запускається цілий ланцюжок мережевих і серверних взаємодій.

2. DNS перетворює ім'я на IP.

Без цього браузер не знає, куди підключатися.

3. HTTPS використовує TLS.

Тому сертифікат і TLS — окремі потенційні точки проблем.

4. Одна сторінка ≠ один HTTP-запит.

Сучасна сторінка може виконувати десятки або сотні запитів.

5. Frontend і backend — різні частини системи.

Frontend може працювати, коли backend уже не працює — і навпаки.

6. Один API може залежати від багатьох систем.

БД, кеш, черги, білінг та зовнішні API можуть бути частиною одного користувацького сценарію.

7. HTTP status code — хороший початок діагностики.

401, 403, 404, 500, 502, 503, 504 означають дуже різні речі.

8. DevTools → Network — один із найпростіших способів побачити реальну роботу вебзастосунку.

І найголовніше:

↳
Коли «не працює сайт», перше питання — не «хто винен?», а «на якому етапі ланцюжка виникла проблема?»
