01

🐇 Що таке RabbitMQ?

Якщо дуже спростити, RabbitMQ — це посередник між системами, який приймає повідомлення від одних компонентів та доставляє їх іншим.

Наприклад:

Order Service говорить:

↳
Замовлення №987 створено.

А Notification Service може обробити цю інформацію окремо.

Головна відмінність від звичайного HTTP — Hypertext Transfer Protocol (протоколу обміну запитами й відповідями у вебі):

Order Service безпосередньо залежить від доступності та швидкості Notification Service.

З RabbitMQ:

Order Service може передати повідомлення брокеру і не чекати, поки Notification Service завершить свою роботу.

04

✅ ACK — одна з найважливіших речей у RabbitMQ

Тепер уявімо:

Consumer отримав message.

Але звідки RabbitMQ знає, що message успішно оброблений?

Для цього існує Acknowledgement — ACK (підтвердження доставки).

Спрощено:

Consumer говорить:

↳
Я успішно обробив message.

Після цього broker може вважати доставку завершеною.

Тут і далі припускаємо manual acknowledgement (ручне підтвердження): ACK надсилається після успішної обробки. Automatic acknowledgement (автоматичне підтвердження) не чекає завершення бізнес-операції. Publisher confirms (підтвердження брокера відправнику) — окремий механізм: він не підтверджує виконання роботи Consumer. Документація RabbitMQ про підтвердження.

05

💥 А що буде, якщо Consumer впаде?

Наприклад:

ACK не був відправлений.

RabbitMQ бачить:

і за відповідних умов message може бути доставлений повторно.

У ручному режимі незавершені доставки повертаються в чергу після закриття каналу або з’єднання обробника. Сама відсутність ACK не означає миттєвої повторної доставки.

І тут починається найцікавіше.

08

🛡 Тут повертається Idempotency

Ми вже зустрічали цю проблему з HTTP:

POST /payments

Client не отримав response і зробив retry.

У RabbitMQ проблема дуже схожа.

Тому Consumer повинен уміти розпізнавати повторну обробку. Idempotency (ідемпотентність) означає, що повторення тієї самої операції не створює додаткового бізнес-ефекту: друге повідомлення не повинно спричинити друге списання.

Наприклад, message має:

JSON
{
  "messageId": "4f3a...",
  "orderId": 987,
  "amount": 1000
}

Consumer може перевірити:

messageId already processed?

Якщо:

NO

→ обробити.

Якщо:

YES

→ не виконувати бізнес-операцію повторно.

Спрощено:

Уже успішно оброблений дубль теж потрібно підтвердити ACK. Перевірку ідентифікатора та збереження результату потрібно узгодити з бізнес-операцією й паралельною обробкою. Для зовнішнього платежу потрібен захист від повтору на стороні платіжного API: одного запису «бачили повідомлення» недостатньо.

Конкретна реалізація залежить від системи, але принцип важливий:

↳
Consumer повинен бути готовий до повторної доставки message.

11

☠️ Dead Letter Queue

Що робити, якщо message не вдається обробити навіть після retries?

Наприклад:

Можна перемістити його в Dead Letter Queue — DLQ (окрему чергу повідомлень, які не вдалося обробити).

DLQ дозволяє окремо працювати з проблемними messages.

Це потребує налаштування Dead Letter Exchange — DLX (маршрутизатора для повідомлень, які виводять з основної черги) та прив’язки до DLQ. Наприклад, відхилення без повернення в основну чергу може спрямувати повідомлення через DLX; без такого налаштування його можуть відкинути. Помилка застосунку сама по собі не запускає цей механізм. Ліміти повторів і паузи теж визначають явно. Документація RabbitMQ про dead lettering.

Наприклад:

Invalid Data
External System Error
Unknown Customer
Unsupported Message Version
Application Bug

15

🗄 RabbitMQ — це не Database (база даних)

Іноді виникає логіка:

↳
Ми поклали message у RabbitMQ — тепер він там надійно зберігається.

Не зовсім.

RabbitMQ — насамперед message broker, а не заміна основної бази даних.

Для надійності доставки мають значення, зокрема:

Queue durability — збереження визначення черги після перезапуску; Message persistence — налаштування збереження повідомлень; Correct topology — правильні маршрутизатори, черги та прив’язки. Exactly Once Processing — обробка рівно один раз. Гарантії залежать також від типу черги й налаштувань.

Queue durability
Message persistence
Publisher confirms
Acknowledgements
Correct topology

Але навіть правильно налаштований RabbitMQ не означає:

Exactly Once Processing Guaranteed

17

🧩 RabbitMQ не вирішує Distributed Transactions (розподілені транзакції) магічно

Можна було б подумати:

BEGIN TRANSACTION

Save Order
Publish RabbitMQ Message

COMMIT

Але Database та RabbitMQ — дві різні системи.

Звичайна DB transaction сама по собі не робить їх однією атомарною операцією.

Для таких сценаріїв існують окремі patterns.

Один із відомих:

Transactional Outbox Pattern.

Transactional Outbox — збереження бізнес-даних і запису майбутньої події в одній транзакції бази даних. Транзакція — група змін, які фіксуються або скасовуються разом.

Спрощено:

Потім окремий publisher:

Обидва записи фіксуються разом: або є і замовлення, і запис події, або немає жодного. Окремий publisher (компонент публікації) читає Outbox та надсилає події брокеру. Повторні спроби теж можуть створювати дублікати: ідемпотентність Consumer залишається потрібною.

Але це вже хороша тема для окремої статті.

RabbitMQ може розподіляти messages між consumers однієї queue. Блок групи означає чотири паралельні обробники: вони ділять роботу, а не отримують кожен копію кожного повідомлення.

Так messaging допомагає згладжувати пікове навантаження та масштабувати обробку.

Але тут з'являються нові питання:

Concurrency — паралельна робота; Ordering — порядок повідомлень; Prefetch — обмеження кількості доставок без ACK, які можна видати обробнику; Database load — навантаження на базу; External API limits — обмеження зовнішніх API. Bottleneck — вузьке місце продуктивності.

👶 Якщо зовсім просто

🛒 Замовлення прийняли — решту роботи можна виконати окремо

Уявіть магазин. Ви оформили замовлення, а магазину потрібно надіслати лист, підготувати документ і передати інформацію аналітиці. Якщо все робити під час натискання кнопки, повільний сервіс листів змусить вас чекати. Його збій може навіть зіпсувати відповідь про вже створене замовлення.

RabbitMQ допомагає передати частину роботи на подальшу обробку. Сервіс замовлень залишає повідомлення «Замовлення №987 створено», а інші компоненти виконують свою роботу окремо. Це ще не означає, що лист надіслано чи платіж завершено. Прийняте замовлення та виконання всіх наступних кроків — різні стани.

📮 Хто за що відповідає?

Producer — відправник. Exchange нагадує сортувальний пункт: за правилами визначає потрібні черги. Queue — місце, де повідомлення очікує обробки. Consumer — виконавець, який отримує завдання й робить потрібну дію.

Якщо подія цікава і сервісу листів, і аналітиці, їм потрібні окремі черги: кожен процес отримує свою копію. Якщо одну чергу обслуговують чотири однакові виконавці, вони ділять роботу між собою. Це різні способи використання черг.

✅ Навіщо підтверджувати виконання?

Отримати завдання — ще не означає виконати його. Після успішної роботи виконавець надсилає ACK: «Цю доставку можна вважати завершеною». У ручному режимі, якщо він упав і з’єднання закрилося до підтвердження, повідомлення можуть передати повторно.

Виконавець міг уже списати гроші й упасти за мить до ACK. RabbitMQ не знає, чи завершився платіж. Тому повторне повідомлення не повинно автоматично спричиняти друге списання. Захист від дублювання потрібно будувати в платіжному сервісі, базі та взаємодії з платіжним API.

🔁 Що робити з помилками?

Якщо зовнішній сервіс тимчасово недоступний, можна спробувати пізніше. Пауза дає йому шанс відновитися. Безперервні повтори без обмеження лише збільшують навантаження.

Постійно проблемне повідомлення можна спрямувати в налаштовану DLQ. Це черга для розслідування: хтось має знайти причину, виправити її та вирішити, як завершити операцію. Потрапляння до DLQ не означає вирішення проблеми.

📊 Чому зеленого індикатора замало?

Працюючий RabbitMQ схожий на відкритий пункт приймання замовлень: двері відчинені, але це нічого не говорить про швидкість виконання. Якщо щосекунди приходить 1000 завдань, а завершуються 500, черга зростає на 500 щосекунди.

Потрібно знати і кількість завдань, і час очікування найстарішого. Сто нових повідомлень та сто повідомлень, які чекають чотири години, — різні ситуації. Для бізнесу важливо, коли клієнт отримає результат.

🗄 Навіщо ще й база даних?

RabbitMQ передає роботу між компонентами, а база зберігає стан замовлень і платежів. Черга не замінює це сховище й не робить зміни в різних системах однією неподільною операцією.

Якщо замовлення збережене, а застосунок упав до публікації повідомлення, наступний сервіс може не дізнатися про нього. Outbox допомагає: замовлення та запис майбутньої події зберігаються разом у базі. Окремий компонент потім надсилає подію RabbitMQ. Повтори при цьому все одно можливі.

🧭 Коли потрібна черга, а коли HTTP?

Черга корисна для листів, документів, фонових завдань, реакції кількох сервісів на подію та згладжування пікового навантаження. Вона розділяє момент появи роботи й момент її виконання. Але накопичення завдань не додає продуктивності: для тривалого зростання навантаження потрібні ресурси та достатня швидкість обробки.

Коли потрібна відповідь зараз — наприклад, відкрити дані клієнта — HTTP часто простіший. RabbitMQ варто додавати за конкретної користі від окремої обробки, коли команда готова підтримувати черги, контракти, повтори й моніторинг.

👥 Що потрібно різним ролям?

PM/BA: узгодити, що означає «операція прийнята», коли очікується результат, як користувач побачить затримку чи помилку й хто розбирає невиконані завдання.

QA: перевіряти кінцевий бізнес-результат, повторну доставку, падіння до ACK, недоступність залежностей і DLQ. Зелений індикатор брокера не доводить, що платіж проведено рівно один раз.

Dev/Architect: узгодити контракти подій, маршрутизацію, збереження повідомлень, підтвердження, ідемпотентність, повтори, порядок і спостережуваність. Черга організовує передачу роботи, а надійність залежить від усього процесу.
