Вступ

Уявімо звичайний процес створення замовлення.

Користувач натискає:

«Оформити замовлення»

Frontend викликає:

TEXT
POST /orders

А далі починається цілий ланцюжок:

TEXT
Client
  ↓
Order Service
  ↓
Payment Service
  ↓
Notification Service
  ↓
Document Service

Order Service створив замовлення.

Потім потрібно:

  • провести платіж;
  • відправити повідомлення;
  • сформувати документ.

Здається логічним просто викликати відповідні API.

Але що буде, якщо:

TEXT
Notification Service ❌

або він відповідає 30 секунд?

Чи повинен користувач чекати?

Чи повинно створення замовлення завершитися помилкою тільки тому, що зараз не працює сервіс повідомлень?

А якщо Order Service зробить retry?

А якщо одночасно таких замовлень 10 000?

Саме тут з'являється інший спосіб взаємодії між системами — Messaging.

І один із найвідоміших message brokers — RabbitMQ.

01

🐇 Що таке RabbitMQ?

Якщо дуже спростити, RabbitMQ — це посередник між системами, який приймає повідомлення від одних компонентів та доставляє їх іншим.

TEXT
Producer
   ↓
RabbitMQ
   ↓
Consumer

Наприклад:

TEXT
Order Service
   ↓
RabbitMQ
   ↓
Notification Service

Order Service говорить:

↳
Замовлення №987 створено.

А Notification Service може обробити цю інформацію окремо.

Головна відмінність від звичайного HTTP-виклику:

TEXT
Order Service
     │
     │ HTTP
     ▼
Notification Service
     │
     ▼
Response

Order Service безпосередньо залежить від доступності та швидкості Notification Service.

З RabbitMQ:

TEXT
Order Service
     ↓
  RabbitMQ
     ↓
Notification Service

Order Service може передати повідомлення брокеру і не чекати, поки Notification Service завершить свою роботу.

🔄 Synchronous vs Asynchronous

HTTP-взаємодія часто виглядає так:

TEXT
Service A
   │
   │ Request
   ▼
Service B
   │
   │ Processing
   ▼
Response
   │
   ▼
Service A

Service A чекає.

Це synchronous interaction.

Наприклад:

TEXT
GET /customers/123

Нам потрібна інформація про customer прямо зараз.

Тут HTTP чудово підходить.

Але уявімо:

↳
Замовлення створене. Треба відправити email.

Чи обов'язково користувачу чекати email перед тим, як отримати:

TEXT
201 Created

Не обов'язково.

Можна зробити:

TEXT
Order Service
      ↓
 ORDER_CREATED
      ↓
   RabbitMQ
      ↓
Notification Service

Це вже asynchronous interaction.

🧠 RabbitMQ потрібен не для того, щоб замінити HTTP

Це важливий момент.

Іноді після знайомства з RabbitMQ виникає бажання:

↳
А давайте тепер усі сервіси з'єднаємо через RabbitMQ.

Це не мета.

HTTP добре підходить, коли потрібна відповідь зараз:

TEXT
Client
  ↓
GET /customers/123
  ↓
Customer Service
  ↓
Customer

Messaging добре підходить, коли система може сказати:

↳
Подія сталася. Обробіть її.

Наприклад:

TEXT
ORDER_CREATED
PAYMENT_COMPLETED
CUSTOMER_BLOCKED
DOCUMENT_GENERATED

Тому в реальній системі часто одночасно існують:

TEXT
HTTP
+
RabbitMQ

📦 Що таке Message?

Уявімо, що створено order:

TEXT
Order ID = 987

Order Service може опублікувати повідомлення:

JSON
{
  "event": "ORDER_CREATED",
  "orderId": 987,
  "customerId": 123
}

RabbitMQ доставить його consumer.

Наприклад:

TEXT
Notification Service

який побачить:

TEXT
ORDER_CREATED

і відправить повідомлення клієнту.

⚠️ Message — це теж контракт

У попередніх статтях ми говорили, що API має контракт.

Наприклад:

TEXT
POST /orders

має:

TEXT
Request
Response
Status Codes
Headers

У messaging ситуація така сама.

Було:

JSON
{
  "orderId": 987
}

А provider вирішив змінити:

JSON
{
  "order": {
    "id": 987
  }
}

Consumer очікує:

TEXT
orderId

і раптом отримує зовсім іншу структуру.

TEXT
Producer 🟢
RabbitMQ 🟢
Consumer 🔴

RabbitMQ працює чудово.

А система — ні.

Тому message schema та semantics — це теж контракт між системами.

02

🧩 Як RabbitMQ працює всередині?

На практиці схема трохи цікавіша, ніж:

TEXT
Producer → Queue → Consumer

У RabbitMQ базова модель виглядає приблизно так:

TEXT
Producer
   ↓
Exchange
   ↓
Queue
   ↓
Consumer

Тут з'являються три важливі поняття:

TEXT
Exchange
Queue
Consumer

Розберемо кожне.

📤 Producer

Producer — система, яка публікує message.

Наприклад:

TEXT
Order Service

створив order і повідомляє:

TEXT
ORDER_CREATED
TEXT
Order Service
      │
      │ message
      ▼
   RabbitMQ

Producer при цьому не обов'язково повинен знати, хто саме обробить повідомлення.

🔀 Exchange

Важливий момент:

Producer зазвичай публікує message в Exchange.

TEXT
Producer
   ↓
Exchange

Exchange вирішує:

↳
Куди направити це повідомлення?

Далі message може потрапити в одну або декілька queues.

TEXT
             ┌→ Queue A
Producer → Exchange
             └→ Queue B

Для маршрутизації використовуються bindings та, залежно від типу exchange, routing keys.

📬 Queue

Queue — це черга повідомлень, які очікують обробки.

TEXT
Queue

┌─────────────┐
│ Message 1   │
│ Message 2   │
│ Message 3   │
│ Message 4   │
└─────────────┘
       ↓
    Consumer

Consumer забирає messages та обробляє їх.

Якщо Producer створює повідомлення швидше, ніж Consumer їх обробляє:

TEXT
Producer
████████████████████ →
             Queue
        █████████████
             ↓
          Consumer
             ██ →

queue починає рости.

І це вже дуже важлива Production-метрика.

👷 Consumer

Consumer — компонент, який отримує message та виконує потрібну роботу.

Наприклад:

TEXT
Notification Worker

отримує:

JSON
{
  "event": "ORDER_CREATED",
  "orderId": 987
}

і виконує:

TEXT
Load customer
      ↓
Prepare notification
      ↓
Send email
03

🔀 Навіщо взагалі Exchange?

Уявімо подію:

TEXT
ORDER_CREATED

Її хочуть отримувати:

TEXT
Notification Service
Analytics Service
Document Service

Тоді можна побудувати:

TEXT
                     ┌→ Notification Queue
                     │
Order → Exchange ────┼→ Analytics Queue
                     │
                     └→ Document Queue

Одна подія може запустити декілька незалежних процесів.

Order Service при цьому не повинен знати:

TEXT
Notification Service URL
Analytics Service URL
Document Service URL

Він просто публікує подію.

🛣 Exchange Types

У RabbitMQ є кілька типів Exchange.

Основні:

TEXT
Direct
Topic
Fanout
Headers

У першій статті не будемо занурюватися в усі деталі, але загальна ідея така.

Direct

Routing відбувається за точним routing key.

TEXT
routing key = order.created
TEXT
Producer
   ↓
Exchange
   ↓
order.created
   ↓
Queue

Topic

Дозволяє використовувати patterns.

Наприклад:

TEXT
order.created
order.cancelled
order.completed

Consumer може бути підписаний на:

TEXT
order.*

Fanout

Повідомлення відправляється в усі прив'язані queues.

TEXT
              ┌→ Queue A
              │
Exchange ─────┼→ Queue B
              │
              └→ Queue C

Це корисно, коли одна подія цікава кільком незалежним consumers.

04

✅ ACK — одна з найважливіших речей у RabbitMQ

Тепер уявімо:

TEXT
RabbitMQ
   ↓
Message
   ↓
Consumer

Consumer отримав message.

Але звідки RabbitMQ знає, що message успішно оброблений?

Для цього існує Acknowledgement — ACK.

Спрощено:

TEXT
RabbitMQ
   │
   │ Message
   ▼
Consumer
   │
   │ Processing
   ▼
Success
   │
   │ ACK
   ▼
RabbitMQ

Consumer говорить:

↳
Я успішно обробив message.

Після цього broker може вважати доставку завершеною.

05

💥 А що буде, якщо Consumer впаде?

Наприклад:

TEXT
RabbitMQ
   ↓
Payment Message
   ↓
Consumer
   ↓
Processing
   ↓
💥 Crash

ACK не був відправлений.

RabbitMQ бачить:

TEXT
Message delivered
ACK ❌

і за відповідних умов message може бути доставлений повторно.

І тут починається найцікавіше.

06

🔁 Message може прийти більше одного разу

Це фундаментальна річ, яку потрібно враховувати при проектуванні messaging.

Consumer не повинен думати:

↳
Якщо я отримав message — я гарантовано бачу його вперше.

У реальній distributed system можливий сценарій:

TEXT
RabbitMQ
   ↓
Message #987
   ↓
Consumer
   ↓
Operation completed ✅
   ↓
Consumer crashes 💥
   ↓
ACK не дійшов

RabbitMQ:

↳
Я не отримав підтвердження.

І доставляє message ще раз.

TEXT
Message #987
   ↓
Consumer
07

💳 А тепер уявімо Payment Service

Message:

JSON
{
  "orderId": 987,
  "amount": 1000
}

Consumer отримує його:

TEXT
Create Payment
     ↓
1000 грн списано ✅

А потім:

TEXT
💥 Consumer crashed

до ACK.

RabbitMQ доставляє message повторно.

Consumer знову виконує:

TEXT
Create Payment

І що тепер?

TEXT
Payment #1 → 1000 грн
Payment #2 → 1000 грн

Клієнт може заплатити двічі.

08

🛡 Тут повертається Idempotency

Ми вже зустрічали цю проблему з HTTP:

TEXT
POST /payments

Client не отримав response і зробив retry.

У RabbitMQ проблема дуже схожа.

Тому Consumer повинен уміти розпізнавати повторну обробку.

Наприклад, message має:

JSON
{
  "messageId": "4f3a...",
  "orderId": 987,
  "amount": 1000
}

Consumer може перевірити:

TEXT
messageId already processed?

Якщо:

TEXT
NO

→ обробити.

Якщо:

TEXT
YES

→ не виконувати бізнес-операцію повторно.

Спрощено:

TEXT
Message
   ↓
Check Message ID
   ↓
┌───────────────┐
│ Already seen? │
└───────────────┘
   │          │
  YES         NO
   │          │
   ↓          ↓
 Skip      Process
              ↓
             ACK

Конкретна реалізація залежить від системи, але принцип важливий:

↳
Consumer повинен бути готовий до повторної доставки message.
09

🔁 Retry

А тепер інша ситуація.

Consumer отримав:

TEXT
ORDER_CREATED

і повинен викликати зовнішній API:

TEXT
Consumer
   ↓
External API

А API тимчасово недоступний:

TEXT
503 Service Unavailable

Чи потрібно одразу відмовлятися від message?

Не обов'язково.

Можна зробити retry.

TEXT
Message
   ↓
Consumer
   ↓
External API ❌
   ↓
Retry

Через деякий час:

TEXT
Retry
  ↓
External API ✅

Операція завершилась.

10

💣 Але Retry теж може зламати систему

Поганий варіант:

TEXT
API ❌
 ↓
Retry
 ↓
Retry
 ↓
Retry
 ↓
Retry
 ↓
Retry
 ↓
Retry

А тепер таких messages:

TEXT
100 000

Ми можемо буквально добити систему, яка й так має проблеми.

Тому retry policy повинна визначати:

TEXT
How many retries?
How often?
What errors are retryable?
What happens after retries?

Наприклад:

TEXT
Retry #1 → 5 sec
Retry #2 → 30 sec
Retry #3 → 2 min

А не:

TEXT
while(true)
{
    Retry();
}
11

☠️ Dead Letter Queue

Що робити, якщо message не вдається обробити навіть після retries?

Наприклад:

TEXT
Message
   ↓
Consumer
   ↓
Error
   ↓
Retry
   ↓
Error
   ↓
Retry
   ↓
Error

Можна перемістити його в Dead Letter Queue.

TEXT
Main Queue
    ↓
 Consumer
    ↓
  Error
    ↓
 Retries
    ↓
   DLQ

DLQ дозволяє окремо працювати з проблемними messages.

Наприклад:

TEXT
Invalid Data
External System Error
Unknown Customer
Unsupported Message Version
Application Bug
12

⚠️ DLQ — це не смітник

Погана практика:

TEXT
Message failed
     ↓
DLQ
     ↓
забули назавжди

Якщо DLQ існує, хтось повинен:

TEXT
Monitor DLQ
Investigate
Fix reason
Replay / Resolve

Інакше це просто місце, де система тихо накопичує невиконані бізнес-операції.

TEXT
Healthy 🟢

14

⏱ Особливо цікава метрика — Age

У queue:

TEXT
100 messages

Це багато чи мало?

Незрозуміло.

Якщо oldest message:

TEXT
Age = 200 ms

можливо, все чудово.

А якщо:

TEXT
Age = 4 hours

у нас явно проблема.

Тому іноді:

TEXT
Oldest Message Age

говорить про стан бізнес-процесу більше, ніж просто кількість messages.

15

🗄 RabbitMQ — це не Database

Іноді виникає логіка:

↳
Ми поклали message у RabbitMQ — тепер він там надійно зберігається.

Не зовсім.

RabbitMQ — насамперед message broker, а не заміна основної бази даних.

Для надійності доставки мають значення, зокрема:

TEXT
Queue durability
Message persistence
Publisher confirms
Acknowledgements
Correct topology

Але навіть правильно налаштований RabbitMQ не означає:

TEXT
Exactly Once Processing Guaranteed
16

📤 А що, якщо Producer думає, що message відправив?

Ще один цікавий сценарій.

Order Service:

TEXT
Order saved to DB ✅

Після цього:

TEXT
Publish ORDER_CREATED

А між цими операціями application падає:

TEXT
Order saved ✅

💥 CRASH

Message published ❌

У Database order є.

А RabbitMQ нічого про нього не знає.

TEXT
Database
Order #987 ✅

RabbitMQ
ORDER_CREATED ❌

Notification Service ніколи не отримає message.

17

🧩 RabbitMQ не вирішує Distributed Transactions магічно

Можна було б подумати:

TEXT
BEGIN TRANSACTION

Save Order
Publish RabbitMQ Message

COMMIT

Але Database та RabbitMQ — дві різні системи.

Звичайна DB transaction сама по собі не робить їх однією атомарною операцією.

Для таких сценаріїв існують окремі patterns.

Один із відомих:

Transactional Outbox Pattern.

Спрощено:

TEXT
Order Service
     ↓
DB Transaction
     │
     ├── Save Order
     │
     └── Save Outbox Message
             ↓
           COMMIT

Потім окремий publisher:

TEXT
Outbox
   ↓
Publisher
   ↓
RabbitMQ

Але це вже хороша тема для окремої статті.

18

🔀 RabbitMQ і масштабування

Уявімо queue:

TEXT
Orders Queue

і одного consumer:

TEXT
Queue
 ↓
Consumer 1

Він обробляє:

TEXT
100 msg/sec

А Producer генерує:

TEXT
500 msg/sec

Черга росте.

Один із варіантів:

TEXT
            ┌→ Consumer 1
            │
Queue ──────┼→ Consumer 2
            │
            ├→ Consumer 3
            │
            └→ Consumer 4

RabbitMQ може розподіляти messages між consumers однієї queue.

Так messaging допомагає згладжувати пікове навантаження та масштабувати обробку.

Але тут з'являються нові питання:

TEXT
Concurrency
Ordering
Prefetch
Idempotency
Database load
External API limits

Тобто:

↳
Більше consumers ≠ автоматично швидша система.

Якщо всі вони підуть одночасно в одну Database, bottleneck просто переміститься туди.

19

🔢 А як щодо порядку повідомлень?

Припустимо:

TEXT
ORDER_CREATED
ORDER_PAID
ORDER_CANCELLED

Може бути важливо, щоб consumer побачив їх саме в такому порядку.

Але distributed messaging, retry та паралельні consumers можуть ускладнювати ordering.

Тому якщо бізнес-логіка залежить від суворого порядку подій, це потрібно проектувати окремо, а не просто припускати:

↳
RabbitMQ усе доставить саме так, як мені потрібно.
20

🧠 RabbitMQ змінює архітектуру системи

Без broker:

TEXT
Order Service
  │
  ├──HTTP→ Payment
  │
  ├──HTTP→ Notification
  │
  └──HTTP→ Documents

Order Service знає про всіх.

З messaging:

TEXT
                 ┌→ Payment Queue → Payment
                 │
Order → Exchange ┼→ Notification Queue → Notification
                 │
                 └→ Document Queue → Documents

Зменшується пряма зв'язаність між компонентами.
