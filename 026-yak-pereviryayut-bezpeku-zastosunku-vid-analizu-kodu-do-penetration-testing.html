Але застосунок має серйозну проблему з контролем доступу.

Саме тому питання:

↳

Спочатку потрібно уточнити:

↳

Для різних рівнів застосунку існують різні підходи: SAST, SCA, DAST та Penetration Testing (тестування на проникнення).

Вони не є альтернативами один одному.

Кожен відповідає на своє питання.

01

1. Один застосунок — багато потенційних проблем

Сучасний застосунок — це значно більше, ніж код, написаний командою розробки.

У ньому є власний код, сторонні бібліотеки, фреймворки, налаштування, API, механізми автентифікації та авторизації, база даних і бізнес-логіка.

Проблема може виникнути практично на будь-якому рівні.

Розробник може допустити SQL Injection (SQL-ін'єкцію).

Стороння бібліотека може містити відому критичну вразливість.

Сервер може бути неправильно налаштований.

API може неправильно перевіряти права доступу.

Бізнес-логіка може дозволяти виконати операцію, яку користувач виконувати не повинен.

Тому не існує одного універсального security scanner (сканера безпеки), який однаково добре перевірить усе.

Почнемо з власного коду.

02

2. SAST — аналізуємо власний код

SAST — Static Application Security Testing (статичне тестування безпеки застосунку).

SAST аналізує вихідний код або його представлення без необхідності атакувати запущений застосунок.

Наприклад:

PHP
$id = $_GET['id'];

$sql = "SELECT * FROM users WHERE id = " . $id;

Статичний аналізатор може побачити приблизно такий data flow (потік даних):

Дані, які контролює користувач, потрапляють безпосередньо в SQL-запит.

Це потенційний SQL Injection (SQL-ін'єкція).

Важлива перевага SAST полягає в тому, що проблему можна знайти ще до розгортання застосунку.

Чим раніше знайдена проблема, тим простіше й дешевше її зазвичай виправити.

03

3. Що може знаходити SAST

Залежно від мови, фреймворку та конкретного інструмента статичний аналіз може допомагати знаходити:

  • SQL Injection (SQL-ін'єкцію);
  • Cross-Site Scripting, XSS (міжсайтовий скриптинг);
  • Command Injection (ін'єкцію команд);
  • Path Traversal (несанкціонований доступ до шляхів файлової системи);
  • небезпечну десеріалізацію;
  • hardcoded credentials (облікові дані, записані безпосередньо в коді);
  • неправильне використання криптографії;
  • потенційний витік конфіденційних даних;
  • небезпечну роботу з файлами;
  • використання небезпечних API;
  • частину помилок валідації даних.

Одним із прикладів корпоративних SAST-рішень є Fortify.

Але важливо розділяти технологію та конкретний продукт:

Тому правильніше говорити:

↳
«Код проходить SAST»

а вже після цього уточнювати, який саме інструмент використовується.

04

4. Але SAST не знає всього про систему

Повернемося до:

HTTP
GET /api/contracts/1251

У коді може бути цілком нормальний виклик:

contractService.getContract(contractId)

Проблема полягає не в самому виклику.

Перед поверненням договору система повинна перевірити, чи має поточний користувач право працювати саме з цим договором.

Якщо перевіряється лише факт авторизації користувача, але не його право працювати саме з цим об'єктом, виникає Broken Access Control (порушення контролю доступу), зокрема можливий IDOR — Insecure Direct Object Reference (небезпечне пряме посилання на об'єкт).

Статичному аналізатору складно знати бізнес-правило:

↳
Користувач повинен бачити лише договори своєї організації.

Код може бути технічно коректним.

А логіка доступу — ні.

Це одне з важливих обмежень автоматичного статичного аналізу.

Але є ще одна проблема.

05

5. Ми пишемо далеко не весь код застосунку

Навіть невеликий сучасний застосунок може використовувати десятки або сотні сторонніх компонентів.

Наприклад:

Причому залежності можуть мати власні залежності.

Команда могла ніколи безпосередньо не додавати Library C.

Але її код усе одно є частиною програмного продукту.

Такі непрямі залежності називають transitive dependencies (транзитивними залежностями).

Якщо в Library C знайдуть критичну вразливість, проблема потенційно стосуватиметься й нашого застосунку.

Так ми переходимо до SCA.

06

6. SCA — перевіряємо те, що ми використали

SCA — Software Composition Analysis (аналіз складу програмного забезпечення).

Якщо максимально спростити різницю:

↳
SAST: що небезпечного ми написали?
↳
SCA: що небезпечного ми використали?

Припустимо, застосунок використовує:

some-library 2.4.1

У цій версії знаходять відому вразливість.

Наш код при цьому може бути написаний абсолютно правильно.

Проблема знаходиться в компоненті, який ми підключили.

07

7. CVE — спільна мова для відомих вразливостей

Тут з'являється поняття CVE — Common Vulnerabilities and Exposures (загальновідомі вразливості та загрози).

Публічно відомій вразливості може бути присвоєний ідентифікатор:

CVE-YYYY-NNNNN

Він дозволяє різним security-системам однозначно посилатися на одну й ту саму проблему.

Але для цього спочатку потрібно знати:

↳
З яких компонентів взагалі складається наш застосунок?
08

8. SBOM — склад програмного продукту

SBOM — Software Bill of Materials (перелік компонентів програмного забезпечення).

Це машинозчитуваний опис компонентів, які входять до складу програмного продукту.

Наприклад:

SBOM допомагає відповісти на дуже важливе питання:

↳
Що саме знаходиться всередині нашого програмного продукту?

Це особливо важливо, коли інформація про нову вразливість з'являється вже після релізу.

09

9. Dependency-Track як практичний приклад

Одним із рішень для роботи з компонентами та SBOM є OWASP Dependency-Track.

Типовий процес може виглядати приблизно так:

Важливо не плутати підхід із конкретним інструментом.

SCA / Component Analysis (аналіз компонентів) — це підхід.

Dependency-Track — одна з платформ, яка може використовуватися для контролю компонентів, SBOM і відомих вразливостей.

10

10. Кейс №1. Код не змінився, але ризик змінився

Припустимо, 1 вересня ми випустили нову версію застосунку.

Вона використовує:

Application 4.2
└── Library X 3.2

На момент релізу критичних відомих CVE немає.

Застосунок працює.

Нових release (релізів) немає.

Нових commit (змін у репозиторії) немає.

А 15 вересня дослідники публікують інформацію про нову критичну вразливість у Library X 3.2.

У репозиторії не змінився жоден рядок.

Але ризик для системи змінився.

Саме тому SCA не повинна бути лише одноразовою перевіркою перед релізом.

Потрібен Continuous Vulnerability Monitoring (постійний моніторинг вразливостей):

Саме тут SBOM стає особливо цінним.

11

11. CVSS і реальний ризик — не одне й те саме

Поруч із CVE часто можна побачити CVSS — Common Vulnerability Scoring System (систему оцінювання критичності вразливостей).

Наприклад:

CVSS: 9.8
Severity: Critical

CVSS допомагає стандартизовано оцінити технічну тяжкість вразливості.

Але:

↳
CVSS ≠ реальний ризик для конкретної системи.

Для оцінки реального ризику потрібно враховувати контекст.

У компонента може бути критична CVE, але вразлива функція взагалі не використовується нашим застосунком або недосяжна в конкретній конфігурації.

І навпаки — проблема з нижчим CVSS може стосуватися критичного бізнес-процесу або дуже чутливих даних.

Тому CVSS допомагає з пріоритизацією, але не замінює аналіз ризику.

12

12. Код і залежності перевірили. Але застосунок ще не атакували

На цьому етапі маємо:

Ми перевірили власний код та сторонні компоненти.

Але майже не перевіряли, як система поводиться після запуску.

Так ми переходимо до DAST.

13

13. DAST — тестуємо працюючий застосунок

DAST — Dynamic Application Security Testing (динамічне тестування безпеки застосунку).

На відміну від SAST, DAST працює не з вихідним кодом, а із запущеним застосунком.

DAST поводиться ближче до зовнішнього клієнта або атакувальника.

Він може змінювати параметри запитів, надсилати різні payloads (спеціально сформовані дані запиту), аналізувати відповіді та шукати ознаки вразливостей.

Залежно від інструмента та конфігурації DAST може допомагати знаходити:

  • XSS;
  • SQL Injection;
  • частину проблем authentication/session management (автентифікації та керування сесіями);
  • неправильні security headers (HTTP-заголовки безпеки);
  • information disclosure (витік технічної або конфіденційної інформації);
  • помилки конфігурації;
  • частину проблем API;
  • інші вразливості, що проявляються під час роботи системи.

SAST і DAST дивляться на систему принципово по-різному.

14

14. Кейс №2. Усі компоненти безпечні, але бізнес-процес — ні

Уявімо систему погодження платежів.

Бізнес-правило:

Розробники реалізували API:

HTTP
POST /api/payments/7821/approve

У коді:

  • немає SQL Injection;
  • немає XSS;
  • немає hardcoded password (пароля в коді);
  • залежності не мають відомих критичних CVE;
  • HTTP-запит валідний;
  • endpoint (кінцева точка API) захищений автентифікацією.

Але виявляється, що менеджер може викликати певну послідовність API-запитів і перевести платіж у статус APPROVED, не отримавши підтвердження фінансового контролера.

Технічно кожен окремий endpoint працює.

А бізнес-процес можна обійти.

Автоматичному сканеру складно самостійно зрозуміти правило:

↳
«Платіж понад 10 000 повинен пройти два незалежні погодження».

Тут потрібне розуміння системи та її бізнес-логіки.

І ми підходимо до Penetration Testing.

15

15. Що таке Penetration Testing

Penetration Testing (тестування на проникнення), або пентест, — це контрольована перевірка безпеки системи шляхом моделювання реальних сценаріїв атаки в погодженому scope (обсязі та межах тестування).

Pentester (спеціаліст із тестування на проникнення) дивиться не лише на окрему потенційну вразливість.

Його цікавить:

↳
Що можна зробити із системою, використовуючи її поведінку не так, як передбачали розробники?

Тобто спеціаліст намагається зрозуміти систему як єдине ціле.

16

16. Кейс №3. Звичайний користувач і IDOR

Повернемося до прикладу на початку статті.

Користувач відкриває:

HTTP
GET /api/contracts/1251
Authorization: Bearer ...

Отримує свій договір.

Pentester ставить дуже просте питання:

↳
Що буде, якщо змінити ID?
HTTP

Сервер відповідає:

HTTP

і повертає чужий договір.

Подивимося, що могло статися на backend (серверній частині).

Якщо перевірка ACCESS відсутня, система знає:

↳
користувач авторизований,

але не перевіряє:

↳
чи має цей користувач право бачити саме цей об'єкт.

Для знаходження такої проблеми потрібно розуміти модель доступу:

Саме тому проблеми Broken Access Control часто потребують контексту.

17

17. Pentest — це не «запустити сканер»

Іноді Penetration Testing уявляють так:

Але якісний pentest значно ширший.

Автоматизовані інструменти при цьому активно використовуються.

Наприклад, для вебзастосунків та API часто застосовують Burp Suite.

Але інструмент допомагає спеціалісту проводити тестування — він не замінює сам процес.

18

18. DAST і Pentest — не одне й те саме

Межа тут важлива.

DAST — технологія динамічного аналізу запущеного застосунку.

Penetration Testing — ширший процес перевірки того, як систему реально можна атакувати в межах погодженого scope.

Pentester може використовувати:

  • proxy (проксі для перехоплення та зміни запитів);
  • vulnerability scanner (сканер вразливостей);
  • browser developer tools (інструменти розробника браузера);
  • API clients (клієнти для роботи з API);
  • scripts (скрипти);
  • fuzzing (автоматичне надсилання великої кількості різних або некоректних даних);
  • manual HTTP requests (ручні HTTP-запити);
  • DAST;
  • спеціалізовані security-інструменти.

Тобто DAST може бути одним із методів, які використовуються під час пентесту, але це не одне й те саме.

19

19. Ще одна перевага Pentest — Attack Chain

Attack Chain (ланцюжок атаки) — це ситуація, коли декілька окремих проблем комбінуються в один сценарій.

Наприклад:

Окремо перша проблема може мати невисокий пріоритет.

Друга — середній.

Третя теж може виглядати обмеженою.

Але разом вони утворюють реальний сценарій компрометації.

Тому security findings (знайдені проблеми безпеки) важливо розглядати не лише як незалежні рядки у звіті, а й як потенційні частини одного сценарію атаки.

21

21. Збираємо все в один SDLC

SDLC — Software Development Life Cycle (життєвий цикл розробки програмного забезпечення).

Тепер можна скласти весь процес.

Це не означає, що кожен commit повинен проходити pentest.

Автоматизовані SAST/SCA-перевірки можна запускати регулярно в CI/CD — Continuous Integration / Continuous Delivery (безперервна інтеграція та доставка).

DAST — після розгортання відповідного середовища.

Повний pentest може виконуватися залежно від:

  • критичності системи;
  • типу даних;
  • масштабу змін;
  • появи нового зовнішнього інтерфейсу;
  • суттєвих архітектурних змін;
  • регуляторних вимог;
  • внутрішньої security-політики.

Головне — щоб перевірки були частиною процесу, а не випадковою активністю перед PROD.

22

22. Security Gate: знайти проблему недостатньо

Security Gate (контрольна точка безпеки) — це правило, яке визначає, чи може зміна рухатися далі за результатами security-перевірок.

Уявімо, що pipeline показав:

SAST
Critical: 1
High:     3

SCA
Critical: 0
High:     2

Сам факт запуску сканера не робить процес безпечним.

Найгірший сценарій:

Потрібен процес роботи з findings.

Тобто результат security-сканера — це вхід у процес управління вразливістю, а не кінцевий результат.

23

23. False Positive не означає «сканеру не можна довіряти»

False Positive (хибне спрацювання) — ситуація, коли інструмент повідомляє про потенційну проблему, але після аналізу виявляється, що реальної вразливості немає.

Наприклад, SAST бачить:

і створює finding про потенційний SQL Injection.

Але між input та SQL може існувати безпечна обробка, яку конкретний аналізатор неправильно інтерпретував.

Правильна реакція:

Неправильна реакція:

↳
«Сканер іноді помиляється, тому його результати можна не дивитися».
24

24. Кейс №4. Знайшли одну проблему — перевіряємо весь клас

Припустимо, pentest знайшов IDOR:

HTTP
GET /api/contracts/{id}

Команда додає перевірку authorization (авторизації).

Проблему виправлено.

Але в системі також можуть бути:

/api/contracts/{id}
/api/invoices/{id}
/api/documents/{id}
/api/orders/{id}
/api/customers/{id}

Якщо всі endpoints створювалися за однаковим архітектурним принципом, та сама проблема може існувати й там.

Тому краще шукати root cause (першопричину).

Це важлива різниця між:

↳
«виправити одну vulnerability (вразливість)»

та

↳
«усунути причину появи такого класу вразливостей».
25

25. Security не повинна починатися перед PROD

Погана модель виглядає так:

У цей момент частина проблем може вимагати значних змін.

Особливо якщо причина знаходиться в архітектурі або моделі авторизації.

Значно ефективніше включати security-контролі протягом усього життєвого циклу.

Частину security-контролів ми переносимо ближче до початку життєвого циклу.

Це одна з ідей Shift Left Security (перенесення перевірок безпеки на ранні етапи розробки).

Але Shift Left не означає:

↳
«Усі security-перевірки потрібно виконувати до deployment».

Деякі проблеми принципово проявляються тільки у працюючій системі.

Тому практична модель:

26

26. Один функціонал очима чотирьох перевірок

А тепер подивимося на один і той самий функціонал повністю.

Команда реалізувала можливість:

↳
Користувач може завантажувати та переглядати документи в особистому кабінеті.

Крок 1 — SAST

Аналізуємо власний код.

Можемо знайти:

  • Unsafe File Handling (небезпечну роботу з файлами);
  • Path Traversal;
  • Injection;
  • Hardcoded Secret (секрет, записаний у коді).

Крок 2 — SCA

Аналізуємо сторонні компоненти.

Наприклад:

Крок 3 — DAST

Перевіряємо запущений застосунок.

Наприклад:

  • що буде при завантаженні неочікуваного типу файлу;
  • як система реагує на некоректні дані;
  • чи правильно налаштовані HTTP security headers;
  • чи не розкриває сервер зайву технічну інформацію.

Крок 4 — Penetration Testing

Pentester дивиться на функціонал як на частину всієї системи.

Користувач B отримав документ користувача A.

Функціонал один.

А проблеми на кожному рівні можуть бути абсолютно різними.

Саме це і є головною причиною використовувати кілька рівнів security testing.

27

27. Не шукайте «сканер, який знайде все»

Питання:

↳
«Який security scanner знайде всі вразливості?»

не зовсім правильне.

Корисніше запитати:

↳
«Які класи ризиків ми перевіряємо і яким способом?»

Кожен рівень закриває свою частину ризиків.

28

28. Що варто запам'ятати

SAST — Static Application Security Testing (статичне тестування безпеки) аналізує власний код і дозволяє знаходити частину проблем ще під час розробки.

Fortify — один із прикладів SAST-рішень.

SCA — Software Composition Analysis (аналіз складу програмного забезпечення) допомагає контролювати сторонні компоненти та відомі вразливості в них.

SBOM — Software Bill of Materials (перелік компонентів програмного забезпечення) дозволяє розуміти, з чого складається програмний продукт.

Dependency-Track — один із прикладів платформ для роботи з SBOM та ризиками компонентів.

CVE — Common Vulnerabilities and Exposures використовується для ідентифікації відомих вразливостей.

CVSS — Common Vulnerability Scoring System допомагає оцінювати їхню технічну критичність, але не замінює оцінку реального ризику.

DAST — Dynamic Application Security Testing (динамічне тестування безпеки) перевіряє поведінку запущеного застосунку.

Penetration Testing (тестування на проникнення) допомагає перевіряти реальні сценарії атаки, авторизацію, бізнес-логіку та комбінації різних проблем.

А після знаходження вразливості потрібен повний цикл:

29

Висновок

Безпека застосунку не визначається результатом одного сканування.

Якщо SAST не знайшов критичних проблем, це ще не означає, що застосунок безпечний.

Якщо в залежностях немає відомих CVE, це не означає, що немає проблем у власному коді.

DAST може перевірити поведінку працюючого застосунку, але не знає всіх правил бізнесу.

Pentest може знайти складний сценарій атаки, але успішний pentest сьогодні не означає, що через місяць у сторонній бібліотеці не з'явиться нова критична вразливість.

Кожен підхід відповідає на своє питання:

Тому SAST, SCA, DAST та Penetration Testing не потрібно протиставляти один одному.

Це різні рівні одного процесу Application Security.

Зрілий процес починається не з питання:

↳
«Який security-сканер ми використовуємо?»

А з трьох інших:

↳
Що ми перевіряємо?
↳
Коли ми це перевіряємо?
↳
Що відбувається після того, як проблему знайдено?

Саме відповіді на ці питання перетворюють набір security-інструментів на процес безпеки розробки.

30

Якщо зовсім просто

Уявімо, що застосунок — це будинок.

Ми хочемо переконатися, що в цей будинок не зможе потрапити стороння людина.

Але перевіряти його можна по-різному.

SAST — перевіряємо, як ми побудували будинок

SAST дивиться на наш власний код.

Це приблизно як перевірити креслення та процес будівництва:

↳
Чи правильно встановлені двері? Чи не забули ми замок? Чи немає очевидної помилки в конструкції?

Якщо розробник зробив небезпечну конструкцію в коді, SAST може допомогти її знайти.

SCA — перевіряємо матеріали, які ми купили

Будинок складається не тільки з того, що ми зробили власноруч.

Ми купили:

  • двері;
  • замки;
  • вікна;
  • сигналізацію;
  • інші готові компоненти.

У програмному забезпеченні це сторонні бібліотеки та пакети.

Може виявитися, що ми все встановили правильно, але виробник замка повідомив:

↳
«У моделі замка 3.2 знайдена серйозна проблема — його можна відкрити без ключа».

Це приблизно те, що відбувається, коли в сторонній бібліотеці з'являється нова CVE.

Саме тому потрібно знати, які компоненти ми використовуємо, і продовжувати стежити за ними навіть після релізу.

DAST — перевіряємо вже готовий будинок

Будинок побудований.

Тепер ми підходимо до нього ззовні й перевіряємо:

↳
Що буде, якщо неправильно використати двері?
↳
Що буде, якщо відправити системі неочікувані дані?
↳
Чи не залишили ми відкритим вікно?

DAST не обов'язково знає, як будинок побудований усередині.

Він дивиться на його реальну поведінку.

Pentest — просимо спеціаліста спробувати проникнути всередину

Тут задача стає ширшою.

Спеціаліст може побачити:

↳
Через головні двері пройти не можна.

Але потім помітити:

↳
На другому поверсі відкрите вікно.

Потім:

↳
До вікна можна дістатися через дах гаража.

А на гараж:

↳
можна потрапити через сусідню будівлю.

Окремо кожна проблема могла здаватися незначною.

Разом вони створили шлях усередину.

У безпеці це називається Attack Chain (ланцюжок атаки).

Чому потрібні всі ці перевірки

Тому що вони відповідають на різні питання.

Одна перевірка не замінює іншу.

І ще одна важлива річ

Навіть якщо сьогодні всі перевірки пройдені успішно, це не означає:

↳
«Тепер застосунок безпечний назавжди».

Завтра може з'явитися інформація про нову вразливість у бібліотеці.

Після нового релізу розробники можуть випадково створити нову проблему.

Після зміни бізнес-процесу може з'явитися спосіб обійти авторизацію.

Тому безпека — це не одна перевірка перед PROD.

Це постійний процес:

І якщо запам'ятати з усієї статті лише одну думку, нехай вона буде такою:

↳
Немає однієї перевірки, яка доводить, що застосунок безпечний. Ми перевіряємо власний код, сторонні компоненти, поведінку працюючої системи та реальні сценарії атаки — і продовжуємо робити це протягом усього життя застосунку.
