XSS — Cross-Site Scripting (міжсайтове виконання сценаріїв) — вразливість, за якої недовірений вміст може спричинити виконання коду у браузері користувача. JavaScript — мова програмування, якою вебсторінка керує своєю поведінкою. Назва XSS історична: для такої атаки не обов’язково потрібні два різні сайти.

Уявімо звичайний вебзастосунок.

Спочатку домовимося про назви компонентів: Backend (серверна частина) обробляє запити, Database, або DB (база даних) зберігає записи, а API — Application Programming Interface (програмний інтерфейс взаємодії) дає компонентам спосіб обмінюватися даними. Frontend (клієнтська частина) показує сторінку та обробляє дії користувача. Далі application означає застосунок, а browser — браузер.

Користувач може залишити коментар:

Дякую, усе працює!

Backend зберігає його в Database:

Потім інший користувач відкриває сторінку.

У наступних прикладах JSON — JavaScript Object Notation (текстовий формат обміну структурованими даними) передає коментар, а HTML — HyperText Markup Language (мова розмітки вебсторінок) задає спосіб його відображення. Дані у форматі JSON самі собою не виконуються: важливо, як їх використає frontend.

Frontend отримує:

JSON
{
  "comment": "Дякую, усе працює!"
}

і показує:

HTML
<div>
  Дякую, усе працює!
</div>

Все нормально.

А тепер уявімо, що замість звичайного тексту користувач передав HTML, який містить JavaScript-обробник:

Event handler (обробник події) — код, який запускається у відповідь на подію. У цьому прикладі onerror реагує на помилку завантаження зображення, а alert показує діалогове повідомлення. Це демонстрація виконання коду, а не весь можливий вплив XSS.

HTML
<img src="x" onerror="alert('XSS')">

Backend чесно зберіг його в Database.

Frontend чесно отримав його через API.

А браузер раптом...

XSS виникає, коли недовірені дані потрапляють у сторінку таким чином, що браузер починає сприймати їх не просто як дані, а як HTML або JavaScript.

04

💻 Простий приклад

У нас є:

HTML
<div id="username"></div>

Frontend отримує username з API:

JAVASCRIPT
const username = response.username;

І робить:

JAVASCRIPT
document.getElementById("username").innerHTML = username;

Якщо:

username = "Denis"

отримаємо:

HTML
<div>
  Denis
</div>

Все добре.

Але якщо username містить HTML:

HTML
<img src="x" onerror="alert('XSS')">

то innerHTML говорить браузеру приблизно:

↳
Це HTML. Розбери його та додай у DOM.

DOM — Document Object Model (об’єктна модель документа) — представлення сторінки як дерева об’єктів, з яким працює JavaScript. innerHTML розбирає рядок як HTML і змінює вміст елемента. Доданий цим способом тег script сам собою зазвичай не виконується, але це не робить innerHTML безпечним: обробники подій залишаються одним зі способів виконати код.

І браузер починає його інтерпретувати.

05

🛡 А якщо використати textContent?

Тепер змінимо код:

JAVASCRIPT

Тоді значення:

HTML
<img src="x" onerror="alert('XSS')">

буде показане користувачу саме як текст.

Браузер не повинен інтерпретувати його як HTML.

Це дуже добре демонструє головний принцип:

↳
Дані повинні залишатися даними.
06

⚠️ Проблема не тільки в <script>

Іноді XSS намагаються вирішити так:

Заборонимо <script>

Але цього недостатньо.

JavaScript може запускатися не лише через:

HTML
<script>...</script>

Існують event handlers, небезпечні DOM API, URL-контексти та багато інших способів перетворити неправильно оброблені дані на виконуваний контент.

Тут DOM API (програмні засоби роботи зі сторінкою) — зокрема властивості й методи її елементів. URL — Uniform Resource Locator (адреса ресурсу) може потрапляти, наприклад, у посилання. Контекст — місце та спосіб вставлення даних, які визначають, як браузер їх прочитає. Blacklist (список заборонених конструкцій) відсікає окремі небезпечні варіанти, але не гарантує, що всі інші безпечні.

Тому blacklist:

<script> ❌

не є повноцінним XSS-захистом.

07

🗄 Stored XSS

Stored XSS (збережена XSS), також Persistent XSS (стійка, збережена в системі XSS), означає, що шкідливий вміст зберігається й пізніше потрапляє на сторінки інших користувачів. Payload (вміст, що реалізує атаку) у нашому прикладі — переданий користувачем HTML із небезпечною поведінкою.

Тепер найцікавіший сценарій.

Уявімо систему підтримки клієнтів.

Користувач вводить ім'я:

John Smith

Але атакуючий замість імені передає шкідливий HTML.

Database зберігає його.

Через деякий час адміністратор відкриває:

Admin Panel

Frontend завантажує customer:

Тут customer означає запис клієнта, а Admin Panel (панель адміністратора) — інтерфейс для керування системою.

і небезпечно вставляє значення в HTML.

Це називається:

або:

Тому що атакуючому не обов'язково змушувати кожного користувача відкривати спеціальне посилання.

Payload уже знаходиться в системі.

UI — User Interface (користувацький інтерфейс) — сторінки й елементи керування, через які людина працює із системою.

09

🔄 Reflected XSS

Reflected XSS (відображена XSS) — сценарій, у якому небезпечний вміст із request (запиту) повертається у response (відповіді) й виконується через небезпечне відображення.

Інший сценарій — коли payload не зберігається в Database.

Наприклад:

/search?q=iphone

Application показує:

Search results for: iphone

Уявімо, що параметр q безпечним чином не обробляється перед вставкою в HTML.

Тоді спеціально сформований URL може змусити сторінку відобразити передане значення як активний HTML.

Схема:

Це називається:

Reflected XSS

Payload не обов'язково зберігається на сервері.

Він приходить із request і повертається у response.

10

🧩 DOM-based XSS

DOM-based XSS (XSS через небезпечну роботу з DOM) виникає в коді клієнтської частини, який читає недовірені дані й небезпечно вставляє їх у сторінку. У прикладі location.hash — фрагмент адреси після символу #; браузер не передає цей фрагмент серверу у звичайному HTTP-запиті. HTTP — HyperText Transfer Protocol (протокол обміну запитами й відповідями у вебі) визначає цей обмін.

А тепер ще цікавіше.

Backend може взагалі не брати участі у проблемі.

Наприклад, JavaScript читає параметр URL:

JAVASCRIPT
const message = location.hash.substring(1);

і вставляє його:

JAVASCRIPT
element.innerHTML = message;

Але в усіх випадках фундаментальна проблема дуже схожа:

↳
Недовірені дані потрапили в небезпечний контекст і стали виконуваним контентом.

Ця трійка корисна для навчання, але категорії не завжди взаємовиключні. Stored / reflected описують, як вміст потрапляє до жертви, а DOM-based — де відбувається небезпечна обробка. Наприклад, збережений коментар може спричинити XSS саме через клієнтський innerHTML.

12

🔐 А тепер згадаємо JWT

JWT — JSON Web Token (формат токена з даними та механізмом перевірки їхньої цілісності) може використовуватися як Access Token (токен доступу). Не кожен токен доступу є JWT. Token (токен) у цьому контексті — значення для підтвердження права доступу. localStorage (локальне сховище браузера для даних сайту) доступне JavaScript цього сайту.

У попередніх статтях ми говорили про Access Token.

Наприклад, frontend зберігає token:

JAVASCRIPT
localStorage.setItem("access_token", token);

Тепер уявімо, що на сторінці є XSS.

Шкідливий JavaScript виконується всередині application.

Якщо token доступний JavaScript:

Тобто XSS потенційно може перетворитися з:

дивний alert на сторінці

на:

Session / Token compromise

Session / Token compromise (компрометація сесії або токена) означає втрату контролю над даними чи механізмом, які дозволяють діяти від імені користувача. Сесія пов’язує наступні запити з уже виконаним входом.

13

🍪 Тоді давайте покладемо token в HttpOnly Cookie?

Cookie (невеликий запис, який браузер зберігає та надсилає із запитами за відповідними правилами) може містити ідентифікатор сесії. Credential (дані для підтвердження доступу) — загальна назва для таких значень. Authentication (автентифікація) перевіряє, хто користувач, а authorization (авторизація) визначає, що йому дозволено.

Це дійсно змінює ситуацію.

Cookie можна зробити:

HttpOnly (недоступність cookie для читання через JavaScript), Secure (передавання cookie захищеним HTTPS-з’єднанням) і SameSite (правила надсилання cookie у міжсайтових запитах) виконують різні задачі. HTTPS — HTTP із шифруванням з’єднання. Самі прапорці не виправляють небезпечне вставлення HTML.

HttpOnly
Secure
SameSite

HttpOnly означає, що JavaScript не може просто прочитати значення cookie.

Тобто:

JAVASCRIPT
document.cookie

не поверне HttpOnly cookie.

Це суттєво ускладнює пряме викрадення такого credential через XSS.

Але тут є важлива пастка.

14

⚠️ HttpOnly Cookie не лікує XSS

Уявімо:

XSS exists

Шкідливий JavaScript виконується всередині вашого application.

Навіть якщо він не може прочитати authentication cookie, він усе ще може взаємодіяти зі сторінкою та, залежно від архітектури застосунку, ініціювати запити від імені користувача.

Наприклад, якщо користувач має право виконати певну операцію, injected JavaScript може спробувати використати вже авторизований браузерний контекст.

Тому:

але:

І це принципово важливо.

15

👤 XSS виконується з можливостями користувача

Уявімо:

Regular User

має доступ лише до:

/profile
/orders

XSS виконується в його browser context.

Browser context (контекст виконання у браузері) тут означає сторінку, її доступні дані та можливості поточного користувача. Impact (наслідки або масштаб впливу) залежить від цих можливостей. Впроваджений код — injected code — не отримує автоматично права адміністратора операційної системи.

Можливий вплив обмежений тим, що доступно цьому користувачу та самому застосунку.

А тепер XSS запускається у:

Admin Browser

Admin має:

/users
/payments
/configuration
/admin

Потенційний impact стає значно більшим.

Тому одна й та сама XSS-вразливість може мати зовсім різний ризик залежно від того, у браузері якого користувача виконується payload.

Тобто символи, які мають спеціальне значення в конкретному контексті, не повинні раптом перетворювати дані на код.

19

3️⃣ HTML Sanitization

HTML Sanitization (очищення HTML від небезпечних конструкцій) потрібне, коли частину розмітки дозволено зберегти. Sanitizer (очищувач HTML) застосовує політику дозволених тегів, атрибутів та адрес. Plain text (звичайний текст без розмітки) і HTML із дозволеним форматуванням — різні вимоги до поля.

Іноді HTML від користувача справді потрібен.

Rich Text Editor (редактор форматованого тексту) може використовуватися у blog (блозі), knowledge base (базі знань) або comments with formatting (коментарях із форматуванням).

Наприклад:

Rich Text Editor
Blog
Knowledge Base
Comments with formatting

Користувачу дозволяють:

HTML
<b>Bold</b>
<i>Italic</i>
<p>Paragraph</p>

Тоді просто перетворити все на plain text не можна.

У такому випадку потрібна HTML Sanitization.

Ідея:

Sanitizer повинен прибрати або нейтралізувати небезпечні конструкції відповідно до політики дозволеного HTML.

Використовуйте підтримуваний спеціалізований очищувач, наприклад DOMPurify, і оновлюйте його. Саморобний пошук небезпечних рядків не замінює розбір HTML. Подальша небезпечна зміна вже очищеного HTML може звести результат очищення нанівець.

20

4️⃣ Framework protections

Framework protections (вбудовані захисні механізми фреймворку) допомагають безпечно формувати сторінку. Framework (фреймворк) — набір засобів для розробки застосунку; rendering (формування відображення) — побудова інтерфейсу, а escaping (екранування) — подання спеціальних символів у безпечній для відповідного контексту формі. Raw HTML (необроблена HTML-розмітка) означає вставлення рядка саме як розмітки.

Сучасні frontend frameworks часто автоматично escaping/encoding значення при звичайному rendering.

Наприклад, концептуально:

{user.name}

зазвичай безпечніше, ніж явне:

render this string as raw HTML

Але практично кожен framework має спосіб сказати:

↳
Я знаю, що роблю. Встав цей HTML як є.

Саме такі механізми потребують особливої уваги.

Framework допомагає.

Але:

↳
Framework не може захистити від коду, який свідомо обходить його захист.
21

5️⃣ Content Security Policy — CSP

CSP — Content Security Policy (політика безпеки вмісту) задає браузеру обмеження для ресурсів і виконання коду. Policy (політика) — набір правил; HTTP headers (заголовки HTTP) — службові поля запиту чи відповіді. Inline scripts (вбудовані сценарії) — код безпосередньо в HTML; обробники подій в атрибутах також потребують уваги до правил CSP.

Ще один рівень захисту:

Content Security Policy

Server може передати браузеру policy через HTTP headers.

Концептуально CSP може визначати:

звідки дозволено JavaScript
чи дозволено inline scripts
звідки можна завантажувати ресурси

Наприклад, policy може суттєво ускладнити виконання injected script.

Але важливий момент:

↳
CSP — Defense in Depth, а не заміна правильного Output Encoding та Sanitization.

Defense in Depth (багаторівневий захист) означає, що додаткові механізми зменшують ризик, але не скасовують потреби виправити причину вразливості.

Не треба будувати логіку:

🚫 Input Validation ≠ Output Encoding

Ці речі часто плутають.

Input Validation

Перевіряє:

↳
Чи допустимі ці дані для нашого бізнес-поля?

Наприклад:

age = -500

очевидно невалідне.

Або:

countryCode = "UA"

має відповідати визначеному формату.

Output Encoding

Вирішує іншу проблему:

↳
Як безпечно вставити ці дані в конкретний output context?

Це різні задачі.

25

⚠️ Контекст має значення

Безпечна обробка залежить від того, куди саме вставляються дані.

HTML body (вміст HTML-документа), HTML attribute (атрибут елемента), JavaScript, URL та CSS — Cascading Style Sheets (каскадні таблиці стилів) мають різні правила обробки. Output context означає контекст виведення. Значення, безпечне як текст, не стає автоматично безпечним кодом чи адресою.

Наприклад:

HTML body
HTML attribute
JavaScript
URL
CSS

— це різні контексти.

Тому універсальна функція:

MakeEverythingSafe()

яку можна застосувати один раз до будь-яких даних, — небезпечна ілюзія.

Якщо зовсім просто

Уявімо службу підтримки, яка приймає відвідувачів і читає їхні записки. Людина пише: «Будь ласка, перевірте моє замовлення». Працівник має прочитати ці слова як повідомлення клієнта. Але якщо він почне виконувати будь-які інструкції з записки так, наче їх видав керівник, клієнт отримає можливість керувати чужою роботою.

У вебзастосунку роль такого працівника виконує браузер. Сайт передає йому і вміст, який треба показати, і інструкції, як побудувати сторінку та як вона має працювати. XSS виникає там, де вміст від користувача помилково перетворюється на такі інструкції.

Чому збережений коментар може стати проблемою

База даних може правильно зберегти рядок, а сервер — правильно повернути його. Це ще не означає, що його безпечно показали. Вирішальний момент настає, коли сторінка вставляє рядок у браузер: як звичайний текст чи як HTML, який браузер розбиратиме.

textContent для звичайного текстового поля означає: «Покажи ці символи». innerHTML означає: «Сприйми цей рядок як розмітку». Якщо користувач контролює такий рядок, а належної обробки немає, разом із видимим повідомленням він може передати небезпечну поведінку.

Звичайні поля імені, назви чи коментаря без форматування не потребують виконання HTML. Для них важливо зберегти текст текстом. Якщо ж продукт справді дозволяє форматовану статтю чи коментар, потрібне спеціальне очищення HTML: залишити дозволене форматування й прибрати небезпечні конструкції. Просто заборонити слово script недостатньо.

Три способи доставити проблему

Збережена XSS схожа на небезпечну записку, яку поклали в картку клієнта: кожен працівник, що відкриє картку через вразливий інтерфейс, може постраждати. Відображена XSS схожа на повідомлення, яке принесли разом із конкретним зверненням: небезпечні дані приходять у запиті й потрапляють у відповідь. DOM-based XSS означає, що сам код сторінки бере дані, наприклад з адреси, і вставляє їх небезпечним способом.

Ці назви допомагають зрозуміти шлях проблеми. Вони не змінюють головного питання: у якому місці чужі дані почали сприйматися як код?

Чому важливо, хто відкрив сторінку

Якщо шкідливий код запустився у браузері адміністратора, він може спробувати скористатися доступними цьому адміністратору діями. Тому поле, яке заповнює звичайний клієнт, може становити ризик для панелі керування або служби підтримки. Зловмиснику не обов’язково самому мати адміністративний обліковий запис.

Приховати cookie від JavaScript через HttpOnly корисно: це ускладнює пряме викрадення такого значення. Але браузер користувача вже авторизований, а шкідливий код може взаємодіяти зі сторінкою. Тому «не вдалося прочитати cookie» не означає «атака нічого не може зробити».

Як виглядає практичний захист

Спочатку визначаємо, що поле повинно містити: звичайний текст чи дозволений форматований HTML. Перевіряємо дані за правилами цього поля. Під час відображення вибираємо безпечний для конкретного місця спосіб вставлення; HTML, якщо він потрібен, очищуємо відповідним інструментом. Використовуємо захист фреймворку й не обходимо його без потреби. CSP і налаштування cookie додають інші рівні захисту.

Для PM — Project Manager (керівника проєкту) та BA — Business Analyst (бізнес-аналітика) важливо явно описати, чи потрібне форматування і хто бачитиме введені дані. Для QA — перевірити весь цей шлях, включно з адміністративними екранами. Для Dev (розробника) та Architect (архітектора) — знайти конкретні місця вставлення даних і забезпечити правильну обробку в кожному контексті.

Перевірка лише відповіді API або лише бази даних не дає повної картини. Заявка може успішно зберегтися сьогодні, а небезпечний код запуститися завтра, коли її відкриє інша людина.

Головна думка проста: користувач має право передати застосунку дані, але це не дає йому права передавати інструкції браузеру іншого користувача. Надійне оформлення та обробка вмісту зберігають цю межу.
