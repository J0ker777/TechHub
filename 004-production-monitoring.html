Вступ

Уявімо звичайний ранок.

Моніторинг показує:

API          🟢 Healthy
Database     🟢 Healthy
Redis        🟢 Healthy
RabbitMQ     🟢 Healthy
CPU          🟢 25%
RAM          🟢 42%

Начебто все чудово.

Але в підтримку вже пишуть користувачі:

↳
«Не працює оформлення замовлення».

Відкриваємо:

GET /health

200 OK

{
  "status": "Healthy"
}

Сервіс живий.

Інфраструктура жива.

Health Check зелений.

А система не працює.

Як так?

01

🟢 Що насправді означає 200 OK від /health?

Розглянемо найпростіший Health Check:

CSHARP
app.MapGet("/health", () =>
{
    return Results.Ok(new
    {
        status = "Healthy"
    });
});

Що ми перевірили?

Фактично лише:

↳
ASP.NET Core зміг прийняти HTTP-запит і повернути відповідь.

Це корисна інформація.

Але вона нічого не говорить про те, чи може система виконувати свою реальну роботу.

Наприклад:

Client
  │
  ▼
 API 🟢
  │
  ▼
 DB 🔴

/health може продовжувати відповідати:

200 OK

А будь-який реальний endpoint:

POST /orders

500 Internal Server Error

Тому поняття «сервіс живий» і «сервіс працює» — не одне й те саме.

02

❤️ Liveness — ти взагалі живий?

Liveness відповідає на максимально просте питання:

↳
Процес працює чи завис/помер?

Наприклад:

GET /health/live

відповідає:

200 OK

Це означає приблизно:

«Я живий і можу відповідати на запити».

Liveness не обов'язково має перевіряти:

  • Database;
  • Redis;
  • RabbitMQ;
  • зовнішні API;
  • сторонні сервіси.

І це важливо.

03

🚦 Readiness — ти готовий працювати?

Інше питання:

↳
Чи готовий сервіс прямо зараз обробляти реальний трафік?

Для цього можна мати:

GET /health/ready

Наприклад, процес уже запустився:

Application 🟢

але ще:

DB connection       🔴
Configuration       🔴
Required dependency 🔴

Тоді:

Liveness  → Healthy
Readiness → Unhealthy

Сервіс живий.

Але направляти на нього користувацькі запити поки що не варто.

04

💣 Чому не можна просто перевірити всі залежності?

Здається, рішення очевидне.

Давайте /health перевірятиме все:

API
 │
 ├── Database
 ├── Redis
 ├── RabbitMQ
 ├── Payment API
 ├── Notification API
 └── External Service

Якщо хоч одна залежність не працює:

Unhealthy

Звучить логічно.

Але тут можна створити ще більшу проблему.

05

🔥 Redis упав — вбиваємо весь API?

Уявімо:

Client
  │
  ▼
 API
  │
  ├── PostgreSQL 🟢
  │
  └── Redis 🔴

Redis використовується тільки для кешування.

Без нього API працює повільніше, але працює.

Якщо readiness check скаже:

Redis unavailable
      ↓
API Unhealthy

балансер може перестати направляти трафік на API.

Тобто через падіння необов'язкового кешу ми самі зробили недоступним сервіс, який міг продовжувати працювати.

Можливо, правильний стан тут:

API → Degraded

а не:

API → Unhealthy

Це і є одна з ідей graceful degradation:

↳
Якщо другорядна функція недоступна, основний бізнес-процес повинен по можливості продовжувати працювати.
06

🐇 А тепер цікавіше — RabbitMQ

Уявімо систему:

API → RabbitMQ → Worker → Database

Користувач створює заявку.

API кладе повідомлення в RabbitMQ:

POST /orders

202 Accepted

Все чудово.

Health Checks:

API          🟢
RabbitMQ     🟢
Worker       🟢
Database     🟢

Але користувачі кажуть:

↳
«Моя заявка вже годину в обробці».

Дивимось на RabbitMQ:

Queue: orders

Messages Ready: 1 240 000
Consumers:      10

RabbitMQ працює.

Worker працює.

Database працює.

А система не встигає обробляти повідомлення.

07

🕐 Queue Depth — вже цікавіше

Можна почати моніторити:

Queue Depth

Наприклад:

0–1 000       🟢
1 000–10 000  🟡
>10 000       🔴

Але навіть цього може бути недостатньо.

Уявімо дві черги:

Queue A: 50 000 messages
Queue B: 500 messages

Яка з них має проблему?

На перший погляд — Queue A.

Але подивімось глибше:

Queue A
50 000 messages
processing: 10 000 msg/sec
oldest message: 5 sec

Queue B
500 messages
processing: 1 msg/min
oldest message: 4 hours

Тепер ситуація зовсім інша.

Тому іноді набагато важливіша метрика:

↳
Age of oldest message

Тобто скільки часу найстаріше повідомлення чекає на обробку.

08

📈 Health Check ≠ Monitoring

Це важливий момент.

Health Check відповідає на питання:

↳
«Компонент зараз доступний?»

А monitoring повинен допомагати відповісти:

↳
«Система зараз поводиться нормально?»

Це значно ширше питання.

Наприклад, сервіс може бути:

HTTP 200 🟢
CPU 30% 🟢
RAM 40% 🟢
DB 🟢

але при цьому:

p95 latency       12 sec 🔴
Error rate        18%    🔴
Queue age         45 min 🔴
Processing rate   ↓80%   🔴

Технічно процес живий.

А для користувача система вже практично недоступна.

09

📊 Average latency теж може обманювати

Моніторинг показує:

Average response time: 180 ms

Виглядає чудово.

Але:

p50 = 100 ms
p95 = 4 sec
p99 = 15 sec

Це означає, що значна частина користувачів уже отримує зовсім інший досвід.

Тому в Production часто важливі:

p50 / p95 / p99

а не лише середнє значення.

10

💼 А де тут бізнес?

Можна піти ще далі.

Уявімо інтернет-магазин.

Моніторинг:

API        🟢
Database   🟢
RabbitMQ   🟢
Redis      🟢
CPU        🟢
RAM        🟢

Але метрика:

Orders created / minute

зазвичай:

120

а зараз:

2

Технічний моніторинг може нічого критичного не показувати.

А бізнес уже фактично стоїть.

Тому поряд із технічними метриками корисно мати business metrics:

Orders created
Payments completed
Documents processed
Messages delivered
Registrations completed

Тобто моніторити не тільки:

↳
«Чи працює сервер?»

а й:

↳
«Чи виконує система те, заради чого вона існує?»
11

🔍 Що тоді варто моніторити?

Умовно можна розділити спостереження на декілька рівнів.

1️⃣ Infrastructure

CPU
RAM
Disk
Network

2️⃣ Application

Availability
Error Rate
Latency
Throughput

3️⃣ Dependencies

Database
Redis
RabbitMQ
External APIs

4️⃣ Processing

Queue Depth
Message Age
Processing Rate
Failed Messages

5️⃣ Business

Orders/min
Payments/min
Documents/min
Successful operations
Failed operations

І тільки разом вони дають більш реальну картину стану системи.

12

🚨 І ще одна пастка — Health Check сам може створити проблему

Уявімо 20 екземплярів API.

Моніторинг перевіряє кожен кожні 5 секунд.

А кожен /health робить:

SELECT FROM Database
PING Redis
Check RabbitMQ
Call External API

Тепер Health Check сам генерує постійне навантаження на всі залежності.

А якщо зовнішній сервіс почав відповідати повільно, сотні health-check запитів можуть ще сильніше погіршити ситуацію.

Тому health endpoints повинні бути:

швидкими, прогнозованими і добре продуманими.

13

🧠 Що варто запам'ятати

200 OK від /health ще не означає:

↳
«Система працює нормально».

Liveness показує:

«Я живий».

Readiness:

«Я готовий приймати трафік».

Monitoring:

«Я працюю нормально».

Business monitoring:

«Я виконую свою реальну функцію».

Іноді найнебезпечніша Production-проблема виглядає саме так:

Everything is GREEN 🟢

поки користувачі вже пишуть:

«У нас нічого не працює».
