Ми постійно пишемо щось подібне:

JAVASCRIPT
fetch("/api/orders")

або:

CSHARP
await httpClient.GetAsync("/api/orders");

Але що насправді знаходиться всередині HTTP-запиту?

І що взагалі відбувається між натисканням кнопки користувачем та виконанням коду на сервері?

Спробуємо розібрати HTTP-запит буквально по частинах.

01

🌍 Почнемо з простого

Уявімо інтернет-магазин.

Користувач натискає:

«Створити замовлення»

Frontend відправляє:

HTTP
POST /api/orders HTTP/1.1
Host: api.company.com
Authorization: Bearer eyJ...
Content-Type: application/json
Accept: application/json

{
  "productId": 123,
  "quantity": 2
}

А сервер відповідає:

HTTP
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/orders/987

{
  "id": 987,
  "status": "CREATED"
}

Для більшості розробників це звична картина.

Але давайте розберемо, що означає кожен її елемент.

02

📦 Що таке HTTP?

HTTP — Hypertext Transfer Protocol.

Якщо дуже спростити, це набір правил, за якими Client та Server обмінюються повідомленнями.

TEXT
Client
   │
   │ HTTP Request
   ▼
Server
   │
   │ HTTP Response
   ▼
Client

Client може бути:

TEXT
Browser
Mobile Application
Backend Service
Postman
curl
IoT Device

Server може бути:

TEXT
Web Application
API
API Gateway
Microservice
Reverse Proxy

Тобто HTTP — це не тільки браузер і вебсторінки.

Це один із головних протоколів взаємодії сучасних систем.

04

🔨 Method

Першим бачимо:

HTTP
POST

HTTP method описує намір операції.

Найвідоміші:

TEXT
GET
POST
PUT
PATCH
DELETE

Наприклад:

HTTP
GET /api/orders/123

означає:

↳
Отримати інформацію про order 123.
HTTP
POST /api/orders

може означати:

↳
Створити новий order.
HTTP
DELETE /api/orders/123
↳
Видалити order 123.

Але важливий момент:

HTTP сам по собі не змусить ваш сервер поводитися правильно.

Технічно можна написати:

HTTP
GET /deleteEverything

і сервер справді все видалить.

Протокол цього магічно не заборонить.

Правильна семантика HTTP methods — це частина контракту та дизайну API.

До цього ще повернемось у темі REST.

07

📨 Headers

Тепер найцікавіше.

HTTP headers передають метадані про запит.

Наприклад:

HTTP
Authorization: Bearer eyJ...

говорить:

↳
Ось credential, який використовується для доступу до ресурсу.

Саме тут часто передається Access Token, про який ми говорили в статтях про JWT та OAuth 2.0.

Інший header:

HTTP
Content-Type: application/json

означає:

↳
Body, який я тобі відправляю, має формат JSON.

Наприклад:

JSON
{
  "productId": 123
}
08

🤔 Content-Type vs Accept

Ці два headers дуже часто плутають.

HTTP
Content-Type: application/json

означає:

↳
Я відправляю тобі JSON.

А:

HTTP
Accept: application/json

означає:

↳
Я хочу отримати відповідь у JSON.

Тобто:

TEXT
Content-Type
     ↓
ЩО Я ВІДПРАВЛЯЮ
TEXT
Accept
     ↓
ЩО Я ХОЧУ ОТРИМАТИ

Наприклад:

HTTP
POST /reports

Content-Type: application/json
Accept: application/pdf

Теоретично це може означати:

↳
Я передаю параметри звіту в JSON, але хочу отримати PDF.

11

🔐 HTTP vs HTTPS

HTTPS — це HTTP поверх захищеного TLS-з'єднання.

Спрощено:

TEXT
HTTP

Client
  │
  │ readable traffic
  ▼
Server

HTTPS:

TEXT
Client
  │
  │ 🔐 encrypted
  ▼
Server

TLS забезпечує, зокрема:

  • шифрування;
  • цілісність;
  • автентифікацію сервера через сертифікат.

Тому:

HTTP
Authorization: Bearer eyJ...

не повинен передаватися через незахищений HTTP.

Bearer token означає приблизно:

↳
Хто володіє цим token — той потенційно може ним скористатися.
12

🌐 Але що відбувається ДО HTTP?

Уявімо:

TEXT
https://api.company.com/orders

Перш ніж сервер взагалі побачить HTTP request, потрібно знайти:

TEXT
api.company.com

Для цього використовується DNS.

Спрощено:

TEXT
api.company.com
       │
       ▼
      DNS
       │
       ▼
10.20.30.40

Після цього Client встановлює мережеве з'єднання із сервером.

Для класичного HTTP/1.1 або HTTP/2 поверх TCP спрощена картина виглядає так:

TEXT
DNS
 ↓
TCP Connection
 ↓
TLS Handshake
 ↓
HTTP Request
 ↓
HTTP Response

Для HTTP/3 транспорт уже інший — QUIC поверх UDP.

Але головна думка:

↳
HTTP-запит — це лише один із рівнів взаємодії.
13

⏱ Чому API може відповідати довго?

Уявімо:

TEXT
Client
  │
  ▼
API
  │
  ├── Database
  ├── Redis
  └── Service B

Користувач бачить:

TEXT
Response Time = 5 seconds

Але ці 5 секунд можуть складатися з:

TEXT
DNS             20 ms
Connection      30 ms
TLS             40 ms
API             50 ms
Database       300 ms
Service B     4300 ms
Network        260 ms

Тому фраза:

↳
«API повільний»

ще нічого не говорить про причину.

Потрібно розуміти, де саме витрачається час.

Саме тут стають корисними tracing, metrics та logs.

14

🆔 Request ID / Correlation ID

У distributed system один HTTP request може пройти:

TEXT
Client
   ↓
API Gateway
   ↓
Service A
   ↓
Service B
   ↓
Service C

У кожного сервісу свої логи.

Як зрозуміти, які записи стосуються одного запиту?

Для цього часто використовується correlation/tracing information.

Умовно:

HTTP
X-Correlation-ID: a82f91

Тоді в логах:

TEXT
Service A
[a82f91] Request started

Service B
[a82f91] Calling database

Service C
[a82f91] Payment failed

Можна відстежити шлях одного запиту через систему.

У сучасному distributed tracing це зазвичай робиться через стандартизований tracing context, наприклад W3C Trace Context.

16

🚦 Status Code

HTTP
201 Created

означає:

↳
Запит успішно виконаний і створено новий ресурс.

HTTP status codes поділяються на групи:

TEXT
1xx → Informational
2xx → Success
3xx → Redirection
4xx → Client Error
5xx → Server Error
17

🟢 2xx — Success

Найвідоміші:

TEXT
200 OK
201 Created
202 Accepted
204 No Content

200 OK

Звичайна успішна операція.

HTTP
GET /orders/123

→ 200 OK

201 Created

Створено новий ресурс.

HTTP
POST /orders

→ 201 Created

При цьому server може повернути:

HTTP
Location: /orders/987

202 Accepted

Дуже цікавий статус.

Означає приблизно:

↳
Запит прийнятий, але обробка ще не завершена.

Наприклад:

TEXT
Client
  │
  │ POST /reports
  ▼
API
  │
  │ message
  ▼
Queue
  │
  ▼
Worker

API може відповісти:

HTTP
202 Accepted

а звіт сформується пізніше.

204 No Content

Операція успішна, але response body не потрібен.

HTTP
DELETE /orders/123

→ 204 No Content

🔐 401 vs 403

Це дуже часто плутають.

Спрощено:

401 Unauthorized

Насправді практичний зміст ближчий до:

↳
Необхідна коректна автентифікація.

Наприклад:

TEXT
Token missing
Token invalid
Token expired

403 Forbidden

↳
Ми знаємо, хто ти, але тобі не дозволено виконувати цю операцію.

Наприклад:

TEXT
User authenticated ✅

Required:
orders.delete

User has:
orders.read

→ 403 Forbidden

Тобто:

TEXT
401
→ Who are you?

403
→ I know who you are,
  but you can't do this.
20

🔴 5xx — проблема на стороні сервера

Наприклад:

TEXT
500 Internal Server Error
502 Bad Gateway
503 Service Unavailable
504 Gateway Timeout

500

Сервер отримав запит, але всередині сталася неочікувана помилка.

502

Gateway або proxy отримав некоректну відповідь від upstream.

Наприклад:

TEXT
Client
 ↓
API Gateway
 ↓
Service ❌

→ 502 Bad Gateway

503

Сервіс тимчасово недоступний.

Наприклад:

TEXT
maintenance
overload
dependency unavailable

504

Gateway не дочекався відповіді upstream service.

TEXT
Client
 ↓
Gateway
 ↓
Service B
   ...
   timeout

→ 504 Gateway Timeout

Тут ми вже повертаємося до нашої попередньої теми про timeout та каскадні відмови.

21

💣 «А ми завжди повертаємо 200»

Іноді API побудований так:

HTTP
HTTP/1.1 200 OK

{
  "success": false,
  "error": "Customer not found"
}

HTTP говорить:

TEXT
SUCCESS

Body говорить:

TEXT
FAILURE

Технічно такий контракт можливий.

Але він може створювати проблеми.

Наприклад, monitoring бачить:

TEXT
HTTP 200
HTTP 200
HTTP 200
HTTP 200

і робить висновок:

TEXT
Success Rate = 100%
🟢

А фактично:

TEXT
50% operations failed
🔴

Крім того, стандартні HTTP clients, API Gateway, retry policies та observability tooling часто орієнтуються саме на HTTP semantics.

Тому status code — це не просто декоративне число.

Це частина контракту API.

23

🧠 HTTP — це контракт

Коли Client викликає API, між ними існує домовленість:

TEXT
Method
URL
Headers
Body
Status Codes
Response Body

Наприклад:

TEXT
POST /orders

Input:
{
  productId,
  quantity
}

Success:
201 Created

Validation Error:
400 Bad Request

Not Authenticated:
401 Unauthorized

Not Allowed:
403 Forbidden

І Client будує свою поведінку навколо цього контракту.

Тому зміна HTTP semantics може ламати consumers так само, як зміна JSON structure.

24

🧩 А де тут REST?

Важливий момент:

↳
HTTP API і REST API — не зовсім одне й те саме.

Можна зробити:

HTTP
POST /getCustomer
POST /createCustomer
POST /deleteCustomer

Це HTTP API.

Воно може чудово працювати.

Але чи є воно RESTful — вже інше питання.

REST намагається використовувати ресурси та семантику HTTP:

HTTP
GET    /customers/123
POST   /customers
PATCH  /customers/123
DELETE /customers/123

Але це вже тема для окремої статті.
