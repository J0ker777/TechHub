📦 Що таке HTTP?

HTTP — Hypertext Transfer Protocol.

Якщо дуже спростити, це набір правил, за якими Client та Server обмінюються повідомленнями.

Client може бути:

Browser
Mobile Application
Backend Service

IoT Device

Server може бути:

Web Application
API
API Gateway
Microservice
Reverse Proxy

Тобто HTTP — це не тільки браузер і вебсторінки.

Це один із головних протоколів взаємодії сучасних систем.

04

🔨 Method

Першим бачимо:

HTTP
POST

HTTP method описує намір операції.

Найвідоміші:

GET
POST
PUT
PATCH
DELETE

Наприклад:

HTTP
GET /api/orders/123

означає:

↳
Отримати інформацію про order 123.
HTTP
POST /api/orders

може означати:

↳
Створити новий order.
HTTP
DELETE /api/orders/123
↳
Видалити order 123.

Але важливий момент:

HTTP сам по собі не змусить ваш сервер поводитися правильно.

Технічно можна написати:

HTTP
GET /deleteEverything

і сервер справді все видалить.

Протокол цього магічно не заборонить.

Правильна семантика HTTP methods — це частина контракту та дизайну API.

До цього ще повернемось у темі REST.

📨 Headers

Тепер найцікавіше.

HTTP headers передають метадані про запит.

Наприклад:

HTTP
Authorization: Bearer eyJ...

говорить:

↳
Ось credential, який використовується для доступу до ресурсу.

Саме тут часто передається Access Token, про який ми говорили в статтях про JWT та OAuth 2.0.

Інший header:

HTTP
Content-Type: application/json

означає:

↳

Наприклад:

JSON
{
  "productId": 123
}

🤔 Content-Type vs Accept

Ці два headers дуже часто плутають.

HTTP
Content-Type: application/json

означає:

↳
Я відправляю тобі JSON.

А:

HTTP
Accept: application/json

означає:

↳
Я хочу отримати відповідь у JSON.

Тобто:

Наприклад:

HTTP
POST /reports

Content-Type: application/json
Accept: application/pdf

Теоретично це може означати:

↳
Я передаю параметри звіту в JSON, але хочу отримати PDF.

🔐 HTTP vs HTTPS

HTTPS — це HTTP поверх захищеного TLS-з'єднання.

Спрощено:

HTTPS:

TLS забезпечує, зокрема:

  • шифрування;
  • цілісність;
  • автентифікацію сервера через сертифікат.

Тому:

HTTP
Authorization: Bearer eyJ...

не повинен передаватися через незахищений HTTP.

Bearer token означає приблизно:

↳
Хто володіє цим token — той потенційно може ним скористатися.

🆔 Request ID / Correlation ID

У distributed system один HTTP request може пройти:

У кожного сервісу свої логи.

Як зрозуміти, які записи стосуються одного запиту?

Для цього часто використовується correlation/tracing information.

Умовно:

Тоді в логах:

🟢 2xx — Success

Найвідоміші:

200 OK
201 Created
202 Accepted
204 No Content

200 OK

Звичайна успішна операція.

HTTP
GET /orders/123

→ 200 OK

201 Created

Створено новий ресурс.

HTTP
POST /orders

→ 201 Created

При цьому server може повернути:

HTTP

202 Accepted

Дуже цікавий статус.

Означає приблизно:

↳
Запит прийнятий, але обробка ще не завершена.

Наприклад:

а звіт сформується пізніше.

Операція успішна, але response body не потрібен.

25

Словник термінів простими словами

  • HTTP — правила обміну повідомленнями між клієнтом і сервером.
  • Client / Server — клієнт надсилає запит, а сервер виконує роботу та повертає відповідь.
  • Request / Response — повідомлення-запит і повідомлення-відповідь.
  • URL — адреса ресурсу зі схемою, доменом, шляхом і параметрами.
  • Method — намір запиту: отримати, створити, змінити або видалити дані.
  • Header — службова інформація про формат, авторизацію, кешування та інші умови.
  • Body — основні дані повідомлення, наприклад JSON із новим замовленням.
  • DNS знаходить IP-адресу за доменом; TCP створює з’єднання; TLS шифрує його для HTTPS.
  • API Gateway — вхідна точка, яка спрямовує запит до потрібного сервісу.
  • Latency — повний час очікування, включно з мережею, чергами, базою та іншими сервісами.
  • Request ID / Correlation ID — ідентифікатор для пошуку одного запиту в логах різних сервісів.
  • Status code — числовий підсумок результату: успіх, помилка клієнта або сервера.
26

👶 Якщо зовсім просто

HTTP схожий на розмову за чітким шаблоном. Клієнт каже серверу, що хоче зробити, з якими даними і в якому форматі очікує результат. Сервер відповідає статусом, заголовками та, за потреби, тілом.

До HTTP браузер знаходить сервер через DNS, встановлює з’єднання і для HTTPS домовляється про шифрування. Потім запит може пройти через gateway, сервіси, базу або чергу.

Тому повільна чи помилкова відповідь не завжди означає проблему в одному API. Request ID показує весь шлях, а status code пояснює категорію результату.
