Коли в архітектурі системи зʼявляється Redis, пояснення часто звучить приблизно так:

↳
«Це кеш. Він дуже швидкий».

Це правда, але лише частина картини.

Redis може кешувати результати запитів до бази даних, зберігати сесії користувачів, лічильники, тимчасові токени, використовуватися для rate limiting, координації декількох екземплярів сервісу, Pub/Sub та інших задач.

Але головна особливість Redis одночасно є його перевагою і причиною багатьох архітектурних помилок:

Redis дуже швидкий, тому його легко почати використовувати там, де він насправді не потрібен.

Розберемося, що це за технологія, навіщо вона потрібна і що необхідно враховувати перед появою Redis у системі.

01

1. Що таке Redis

Redis — це високопродуктивне сховище даних, яке переважно працює з даними в оперативній памʼяті.

У традиційній базі даних основне довготривале сховище — диск:

Redis побудований навколо іншої ідеї:

Оперативна памʼять значно швидша за постійне дискове сховище. Саме тому Redis здатний дуже швидко виконувати величезну кількість операцій.

Але називати Redis просто «базою даних у RAM» теж не зовсім правильно.

Він підтримує різні структури даних:

  • Strings;
  • Hashes;
  • Lists;
  • Sets;
  • Sorted Sets;
  • Streams та інші.

Наприклад:

user:123:name = "Anna"

або умовно:

user:123 = {
    name: "Anna",
    role: "manager",
    department: "sales"
}

Ключі зазвичай мають зрозумілу структуру:

user:123
session:a8f71c
product:458
otp:user:123
rate-limit:192.168.1.20

Це дозволяє швидко знаходити потрібні дані без складних SQL-запитів.

02

2. Навіщо Redis, якщо вже є база даних?

Уявімо звичайний API:

Клієнт викликає:

HTTP
GET /api/products/123

Backend виконує SQL:

SQL
SELECT *
FROM products
WHERE id = 123;

Якщо цей товар переглянуть 100 000 разів, база може виконати дуже схожий запит 100 000 разів.

При цьому товар, можливо, змінюється лише раз на день.

Тут зʼявляється Redis.

Backend спочатку перевіряє Redis:

GET product:123

Якщо значення є — отримуємо його з памʼяті.

Якщо немає — читаємо дані з БД і записуємо їх у Redis:

SET product:123 ...

Наступні запити вже можуть не звертатися до бази.

Важлива думка:

Redis не робить повільний SQL швидшим. Redis дозволяє не виконувати цей SQL кожного разу.

03

3. TTL: дані, які живуть певний час

Одна з найкорисніших можливостей Redis — TTL (Time To Live).

Можна сказати:

зберігати цей ключ 300 секунд

Наприклад:

product:123
TTL = 300 seconds

Через пʼять хвилин Redis автоматично видалить ключ.

Це дуже зручно для тимчасових даних.

Наприклад:

OTP code          → 2 хвилини
Password reset    → 15 хвилин
Cache             → 5 хвилин
Session           → 30 хвилин
Rate limit        → 1 хвилина

Не потрібно створювати окремий процес, який постійно шукає прострочені записи та видаляє їх.

04

4. Redis — це не тільки кеш

Кешування — найвідоміший сценарій використання Redis, але далеко не єдиний.

Сесії користувачів

Уявімо декілька екземплярів backend:

Користувач може потрапити на будь-який екземпляр backend.

Тому зберігати сесію лише в памʼяті конкретного сервера незручно.

Redis може виступати централізованим сховищем сесій:

session:f72ab91

Будь-який backend може отримати потрібні дані.

05

5. Лічильники

Redis дуже добре підходить для операцій типу:

+1

Наприклад:

views:article:123 = 1567

При кожному перегляді:

INCR views:article:123

Redis виконує таку операцію атомарно.

Це корисно для:

  • кількості переглядів;
  • статистики;
  • спроб авторизації;
  • кількості запитів;
  • різноманітних технічних метрик.
06

6. Rate Limiting

Припустимо, API дозволяє:

100 requests / minute

Для кожного користувача або IP можна створити ключ:

rate-limit:user:123

При кожному запиті збільшуємо значення:

1
2
3
...
99
100
101

І встановлюємо TTL:

60 seconds

Якщо значення перевищило 100:

HTTP
HTTP 429 Too Many Requests

Через хвилину ключ автоматично зникає.

Це один із класичних сценаріїв використання Redis.

07

7. Тимчасові токени та OTP

Redis зручний для даних, які за своєю природою повинні швидко зникнути.

Наприклад, користувачу надсилається OTP:

482193

У Redis:

otp:user:123 = 482193

TTL = 120 seconds

Через дві хвилини код автоматично перестає існувати.

Але важливо памʼятати: Redis не скасовує вимоги безпеки. Секретні значення не варто бездумно зберігати у відкритому вигляді лише тому, що вони мають короткий TTL.

Але тут є важливий нюанс.

Distributed lock — значно складніша задача, ніж просто створити ключ у Redis.

Потрібно враховувати:

  • TTL блокування;
  • що станеться при падінні сервісу;
  • хто є власником lock;
  • як безпечно його звільнити;
  • що буде, якщо операція працює довше за TTL.

Тому сам факт наявності Redis ще не означає, що distributed locking реалізований правильно.

09

9. Найскладніше питання кешу

Припустимо, у Redis знаходиться:

product:123
price = 100

А в базі даних ціну змінили:

price = 120

Тепер маємо:

Database
price = 120

Redis
price = 100

Що поверне API?

Якщо використовується кеш — потенційно 100.

Це називається stale data — застарілі дані.

І саме тут починається одна з найскладніших задач кешування:

cache invalidation.

Як система повинна зрозуміти, що кеш більше не актуальний?

10

10. Cache-Aside

Один із найпоширеніших підходів виглядає так:

1. Перевірити Redis
2. Якщо HIT → повернути результат
3. Якщо MISS → прочитати DB
4. Записати результат у Redis
5. Повернути результат

Умовний псевдокод:

data = redis.get(key)

if data exists:
    return data

data = database.get(id)

redis.set(key, data, TTL)

return data

Це називають Cache-Aside Pattern.

Він простий і дуже поширений.

Але при зміні даних потрібно визначити стратегію.

Наприклад:

UPDATE database
DELETE cache

Наступний запит отримає:

Cache MISS

прочитає актуальне значення з БД і знову заповнить кеш.

11. Cache Stampede

Уявімо популярний ключ:

Його одночасно використовують тисячі користувачів.

TTL закінчується.

Ключ зникає.

І майже одночасно приходять:

Усі вони можуть піти в базу даних.

І кеш, який мав захищати БД від навантаження, раптом сам створює величезний сплеск навантаження.

Це називають Cache Stampede.

Для боротьби з цим застосовують різні підходи:

  • distributed locking;
  • різний або випадковий TTL;
  • background refresh;
  • stale-while-revalidate;
  • попереднє прогрівання кешу.
12

12. Pub/Sub

Redis також має механізм Publish/Subscribe.

Наприклад:

Service A публікує повідомлення, а підписники його отримують.

Це може бути зручно для простих real-time сценаріїв.

Але тут важливо не зробити неправильний висновок:

Redis Pub/Sub ≠ RabbitMQ.

Класичний Redis Pub/Sub орієнтований на доставку активним підписникам. Якщо підписник був недоступний у момент публікації, не слід автоматично очікувати поведінки надійної брокерної черги.

Якщо бізнес-процес вимагає гарантованої обробки повідомлення, необхідно окремо проєктувати механізм доставки.

13

13. А як щодо Redis Streams?

Redis має і більш потужний механізм — Streams.

Він дозволяє зберігати потік повідомлень та працювати з consumer groups.

Тобто Redis може використовуватися не тільки для простого Pub/Sub.

Але звідси не випливає:

Redis Streams = RabbitMQ = Kafka

Ці технології мають різні моделі роботи, можливості та типові сценарії.

Тому вибір повинен починатися не з:

↳
«Яка технологія у нас вже встановлена?»

а з:

↳
«Яку проблему ми вирішуємо і які гарантії нам потрібні?»

15. Що станеться, якщо Redis впаде?

Це одне з найважливіших питань при проєктуванні.

Не:

↳
«Чи швидкий Redis?»

А:

↳
«Що станеться з нашою системою, якщо Redis стане недоступним?»

Відповідь залежить від того, для чого він використовується.

Якщо Redis — кеш

Можливо:

Система продовжить працювати, але база отримає більше навантаження.

Якщо Redis зберігає сесії

Користувачі можуть втратити доступ до своїх активних сесій або система не зможе їх перевірити.

Якщо Redis використовується для rate limiting

Потрібно заздалегідь визначити поведінку:

Це класичний вибір між fail-open та fail-closed, який залежить від конкретного ризику.

Якщо Redis використовується для lock

Недоступність Redis може вплинути вже не тільки на продуктивність, а й на коректність бізнес-операцій.

Тому Redis не можна автоматично вважати «просто кешем, який не страшно втратити».

16

16. А Redis взагалі зберігає дані на диск?

Так.

Хоча Redis орієнтований на роботу з RAM, він має механізми persistence.

Два важливих поняття:

RDB — періодичні snapshots стану Redis.

AOF (Append Only File) — журнал операцій зміни даних.

Спрощено:

Це дозволяє відновлювати дані після перезапуску.

Але persistence не означає автоматично:

↳
«Тепер Redis можна використовувати замість основної реляційної БД».

Вибір сховища визначається моделлю даних, гарантіями, транзакційністю, обсягами, доступністю та іншими вимогами.

17

17. А якщо сам Redis один?

Тоді він може стати Single Point of Failure.

Redis підтримує механізми побудови відмовостійкої інфраструктури.

Наприклад:

Для автоматичного failover може використовуватися Sentinel.

Для розподілу даних між декількома вузлами існує Redis Cluster.

Але це вже окрема інфраструктурна тема.

Головне розуміти:

якщо Redis критичний для роботи системи — його доступність також стає частиною архітектури системи.

20

20. Що потрібно запамʼятати

Redis — це значно більше, ніж просто кеш.

Він добре підходить для:

Cache
Sessions
Counters
Rate Limiting
TTL data
OTP
Distributed coordination
Pub/Sub
Streams

Але Redis не потрібно додавати до системи лише тому, що:

«Redis швидкий»

Перед його використанням варто відповісти щонайменше на пʼять питань:

1. Яку проблему вирішує Redis?

2. Які саме дані в ньому зберігатимуться?

3. Хто є Source of Truth — Redis чи інша система?

4. Як і коли дані будуть видалятися або оновлюватися?

5. Що станеться із системою, якщо Redis буде недоступний?

Якщо відповіді на ці питання зрозумілі — Redis може бути надзвичайно корисним компонентом архітектури.

Якщо ж єдина аргументація звучить як:

↳
«Давайте поставимо Redis, бо він швидкий»,

то, можливо, Redis поки що взагалі не потрібен.

Коротко

І, мабуть, найважливіша думка:

хороша архітектура — це не система, в якій використано якомога більше технологій. Це система, в якій кожна технологія має зрозумілу причину своєї появи.
