Коли в архітектурі системи зʼявляється Redis, пояснення часто звучить приблизно так:

↳
«Це кеш. Він дуже швидкий».

Це правда, але лише частина картини.

Redis може кешувати результати запитів до бази даних, зберігати сесії користувачів, лічильники, тимчасові токени, використовуватися для rate limiting (обмеження кількості запитів), координації декількох екземплярів сервісу, Pub/Sub — Publish/Subscribe (модель публікації та підписки) та інших задач.

Але головна особливість Redis одночасно є його перевагою і причиною багатьох архітектурних помилок:

Redis дуже швидкий, тому його легко почати використовувати там, де він насправді не потрібен.

Розберемося, що це за технологія, навіщо вона потрібна і що необхідно враховувати перед появою Redis у системі.

01

1. Що таке Redis

Redis — це високопродуктивне сховище даних, яке переважно працює з даними в оперативній памʼяті.

У традиційній базі даних основне довготривале сховище — диск:

Redis побудований навколо іншої ідеї:

RAM — Random Access Memory (оперативна памʼять) значно швидша за постійне дискове сховище. Саме тому Redis здатний дуже швидко виконувати величезну кількість операцій.

Але називати Redis просто «базою даних у RAM» теж не зовсім правильно.

Він підтримує різні структури даних:

  • Strings — рядки;
  • Hashes — набори полів і значень;
  • Lists — списки;
  • Sets — множини унікальних значень;
  • Sorted Sets — впорядковані множини;
  • Streams — потоки записів;
  • та інші.

Наприклад:

user:123:name = "Anna"

або умовно:

user:123 = {
    name: "Anna",
    role: "manager",
    department: "sales"
}

Ключі зазвичай мають зрозумілу структуру:

user:123
session:a8f71c
product:458
otp:user:123
rate-limit:192.168.1.20

Це дозволяє швидко знаходити потрібні дані без складних SQL-запитів.

02

2. Навіщо Redis, якщо вже є база даних?

Уявімо звичайний API — Application Programming Interface (програмний інтерфейс для взаємодії систем):

Клієнт викликає:

HTTP
GET /api/products/123

Backend виконує SQL — Structured Query Language (мова запитів до реляційних баз даних):

SQL
SELECT *
FROM products
WHERE id = 123;

Якщо цей товар переглянуть 100 000 разів, база може виконати дуже схожий запит 100 000 разів.

При цьому товар, можливо, змінюється лише раз на день.

Тут зʼявляється Redis.

Тут зʼявляються два важливі терміни:

  • Cache Hit (влучання в кеш) — потрібні дані вже є в Redis;
  • Cache Miss (промах кешу) — даних у Redis немає і потрібно звернутися до іншого джерела, наприклад до бази даних.

Backend спочатку перевіряє Redis:

GET product:123

Якщо значення є — отримуємо його з памʼяті.

Якщо немає — читаємо дані з БД і записуємо їх у Redis:

SET product:123 ...

Наступні запити вже можуть не звертатися до бази.

Важлива думка:

Redis не робить повільний SQL швидшим. Redis дозволяє не виконувати цей SQL кожного разу.

03

3. TTL: дані, які живуть певний час

Одна з найкорисніших можливостей Redis — TTL — Time To Live (час життя запису).

Можна сказати Redis:

зберігати цей ключ 300 секунд

Наприклад:

product:123
TTL = 300 seconds

Через пʼять хвилин Redis автоматично видалить ключ.

Це дуже зручно для тимчасових даних.

Наприклад:

OTP code          → 2 хвилини
Password reset    → 15 хвилин
Cache             → 5 хвилин
Session           → 30 хвилин
Rate limit        → 1 хвилина

OTP — One-Time Password (одноразовий пароль) — код, який можна використати для підтвердження операції протягом обмеженого часу.

Не потрібно створювати окремий процес, який постійно шукає прострочені записи та видаляє їх.

04

4. Redis — це не тільки кеш

Кешування — найвідоміший сценарій використання Redis, але далеко не єдиний.

Сесії користувачів

Уявімо декілька екземплярів backend:

Load Balancer (балансувальник навантаження) розподіляє запити між декількома екземплярами backend.

Користувач може потрапити на будь-який екземпляр.

Тому зберігати сесію лише в памʼяті конкретного сервера незручно.

Redis може виступати централізованим сховищем сесій:

session:f72ab91

Будь-який backend може отримати потрібні дані.

05

5. Лічильники

Redis дуже добре підходить для операцій типу:

+1

Наприклад:

views:article:123 = 1567

При кожному перегляді:

INCR views:article:123

Redis виконує таку операцію атомарно.

Атомарна операція — операція, яка виконується як єдине неподільне ціле. Інший процес не може побачити її «наполовину виконаною».

Це корисно для:

  • кількості переглядів;
  • статистики;
  • спроб авторизації;
  • кількості запитів;
  • різноманітних технічних метрик.
06

6. Rate Limiting

Rate Limiting (обмеження частоти запитів) захищає API від надмірної кількості звернень від одного користувача, клієнта або IP-адреси.

Припустимо, API дозволяє:

100 requests / minute

Для кожного користувача або IP можна створити ключ:

rate-limit:user:123

При кожному запиті збільшуємо значення:

1
2
3
...
99
100
101

І встановлюємо TTL:

60 seconds

Якщо значення перевищило 100:

HTTP
HTTP 429 Too Many Requests

HTTP 429 Too Many Requests означає, що клієнт виконав забагато запитів за визначений проміжок часу.

Через хвилину ключ автоматично зникає.

Це один із класичних сценаріїв використання Redis.

07

7. Тимчасові токени та OTP

Redis зручний для даних, які за своєю природою повинні швидко зникнути.

Наприклад, користувачу надсилається OTP:

482193

У Redis:

otp:user:123 = 482193

TTL = 120 seconds

Через дві хвилини код автоматично перестає існувати.

Але важливо памʼятати: Redis не скасовує вимоги безпеки. Секретні значення не варто бездумно зберігати у відкритому вигляді лише тому, що вони мають короткий TTL.

08

8. Distributed Lock

Тепер цікавіший сценарій.

Distributed Lock (розподілене блокування) — механізм, який допомагає декільком екземплярам системи домовитися, хто саме зараз має право виконувати певну операцію.

У нас працюють три екземпляри одного сервісу.

Два з них майже одночасно отримали команду виконати одну операцію.

Наприклад:

Generate monthly report

Без координації може статися так:

Для координації можна використовувати distributed lock у Redis.

Спрощено процес виглядає так:

Наприклад, Service A створює:

SET lock:report ...

Service B бачить, що lock вже існує, і не запускає ту саму операцію.

Але тут є важливий нюанс.

Distributed lock — значно складніша задача, ніж просто створити ключ у Redis.

Потрібно враховувати:

  • TTL блокування;
  • що станеться при падінні сервісу;
  • хто є власником lock;
  • як безпечно його звільнити;
  • що буде, якщо операція працює довше за TTL.

Тому сам факт наявності Redis ще не означає, що distributed locking реалізований правильно.

09

9. Найскладніше питання кешу

Припустимо, у Redis знаходиться:

product:123
price = 100

А в базі даних ціну змінили:

price = 120

Тепер маємо:

Це називається Stale Data (застарілі дані) — ситуація, коли кеш містить стару версію інформації, хоча основне джерело вже змінилося.

І саме тут починається одна з найскладніших задач кешування:

Cache Invalidation (інвалідація кешу) — визначення того, коли кешовані дані більше не можна вважати актуальними та їх потрібно оновити або видалити.

Як система повинна зрозуміти, що кеш більше не актуальний?

10

10. Cache-Aside

Один із найпоширеніших підходів — Cache-Aside Pattern (шаблон кешування, де застосунок сам перевіряє та заповнює кеш).

Процес виглядає так:

Умовний псевдокод:

data = redis.get(key)

if data exists:
    return data

data = database.get(id)

redis.set(key, data, TTL)

return data

Це простий і дуже поширений підхід.

Але при зміні даних потрібно визначити стратегію.

Наприклад:

Наступний запит отримає Cache Miss, прочитає актуальне значення з БД і знову заповнить кеш.

11

11. Cache Stampede

Уявімо популярний ключ:

catalog:popular

Його одночасно використовують тисячі користувачів.

TTL закінчується.

Ключ зникає.

І майже одночасно приходять тисячі запитів.

І кеш, який мав захищати БД від навантаження, раптом сам створює величезний сплеск навантаження.

Це називають Cache Stampede (лавина запитів після одночасного промаху кешу).

Для боротьби з цим застосовують різні підходи:

  • distributed locking;
  • різний або випадковий TTL;
  • background refresh (фонове оновлення кешу);
  • stale-while-revalidate (тимчасове повернення старого значення, поки кеш оновлюється у фоні);
  • попереднє прогрівання кешу.
12

12. Pub/Sub

Redis також має механізм Publish/Subscribe (публікація/підписка).

Один сервіс публікує повідомлення, а інші сервіси можуть бути на нього підписані.

Service A публікує повідомлення, а підписники його отримують.

Це може бути зручно для простих real-time сценаріїв (сценаріїв обміну даними майже в реальному часі).

Але тут важливо не зробити неправильний висновок:

Redis Pub/Sub ≠ RabbitMQ.

Класичний Redis Pub/Sub орієнтований на доставку активним підписникам. Якщо підписник був недоступний у момент публікації, не слід автоматично очікувати поведінки надійної брокерної черги.

Якщо бізнес-процес вимагає гарантованої обробки повідомлення, необхідно окремо проєктувати механізм доставки.

13

13. А як щодо Redis Streams?

Redis має і більш потужний механізм — Redis Streams (потоки повідомлень Redis).

Він дозволяє зберігати потік повідомлень та працювати з Consumer Groups (групами споживачів повідомлень).

Тобто Redis може використовуватися не тільки для простого Pub/Sub.

Але звідси не випливає:

Redis Streams = RabbitMQ = Kafka

Ці технології мають різні моделі роботи, можливості та типові сценарії.

Тому вибір повинен починатися не з:

↳
«Яка технологія у нас вже встановлена?»

а з:

↳
«Яку проблему ми вирішуємо і які гарантії нам потрібні?»

Вони вирішують різні задачі.

Тому архітектура цілком може містити всі ці компоненти одночасно:

І це нормально.

15

15. Що станеться, якщо Redis впаде?

Це одне з найважливіших питань при проєктуванні.

Не:

↳
«Чи швидкий Redis?»

А:

↳
«Що станеться з нашою системою, якщо Redis стане недоступним?»

Відповідь залежить від того, для чого він використовується.

Якщо Redis — кеш

Можливо:

Система продовжить працювати, але база отримає більше навантаження.

Якщо Redis зберігає сесії

Користувачі можуть втратити доступ до своїх активних сесій або система не зможе їх перевірити.

Якщо Redis використовується для rate limiting

Потрібно заздалегідь визначити поведінку:

Fail-Open (дозволити операцію при відмові захисного компонента) та Fail-Closed (заборонити операцію при такій відмові) — два різні підходи, вибір між якими залежить від конкретного ризику.

Наприклад, недоступність механізму rate limiting може бути менш небезпечною за повну недоступність критичного API — або навпаки, якщо цей API особливо чутливий до зловживань.

Якщо Redis використовується для lock

Недоступність Redis може вплинути вже не тільки на продуктивність, а й на коректність бізнес-операцій.

Тому Redis не можна автоматично вважати «просто кешем, який не страшно втратити».

16

16. А Redis взагалі зберігає дані на диск?

Так.

Хоча Redis орієнтований на роботу з RAM, він має механізми Persistence (збереження даних для можливості їх відновлення).

Два важливих поняття:

RDB — Redis Database snapshot (періодичний знімок стану Redis).

AOF — Append Only File (журнал операцій зміни даних).

Спрощено:

Це дозволяє відновлювати дані після перезапуску.

Але persistence не означає автоматично:

↳
«Тепер Redis можна використовувати замість основної реляційної БД».

Вибір сховища визначається моделлю даних, гарантіями, транзакційністю, обсягами, доступністю та іншими вимогами.

17

17. А якщо сам Redis один?

Тоді він може стати SPOF — Single Point of Failure (єдина точка відмови).

Redis підтримує механізми побудови відмовостійкої інфраструктури.

Наприклад:

Replication (реплікація) — копіювання даних з одного вузла на інші.

Для автоматичного Failover (перемикання на інший вузол при відмові основного) може використовуватися Redis Sentinel.

Для розподілу даних між декількома вузлами існує Redis Cluster.

Але це вже окрема інфраструктурна тема.

Головне розуміти:

якщо Redis критичний для роботи системи — його доступність також стає частиною архітектури системи.

18

18. Типова помилка: кешувати все

Після першого успішного використання Redis легко зʼявляється бажання:

↳
«А давайте кешувати ще й це».

А потім Redis поступово починає містити:

users
products
permissions
configuration
reports
reference data
sessions
...

І система поступово отримує дві версії реальності:

Тоді виникають питання:

Хто source of truth?

Коли оновлювати кеш?

Хто його видаляє?

Який TTL?

Що робити після зміни даних?

Що робити при недоступності Redis?

Source of Truth (основне достовірне джерело даних) — система, інформація в якій вважається правильною у випадку розбіжності між декількома копіями.

Тому правильне питання:

↳
«Що ми виграємо від кешування саме цих даних?»

Якщо база й так відповідає за 5 мс і має невелике навантаження, Redis може не прискорити систему настільки, щоб виправдати додаткову складність.

  • replication;
  • failover;
  • моніторинг;
  • доступність;
  • безпеку;
  • поведінку системи при відмові Redis.

Тобто Redis — це не «безкоштовна продуктивність».

Ми обмінюємо частину простоти системи на продуктивність і нові можливості.

І цей обмін має бути виправданим.

20

20. Що потрібно запамʼятати

Redis — це значно більше, ніж просто кеш.

Він добре підходить для:

  • Cache — кешування;
  • Sessions — сесій;
  • Counters — лічильників;
  • Rate Limiting — обмеження частоти запитів;
  • даних із TTL;
  • OTP;
  • Distributed Coordination — координації між декількома екземплярами системи;
  • Pub/Sub;
  • Streams.

Але Redis не потрібно додавати до системи лише тому, що:

↳
«Redis швидкий».

Перед його використанням варто відповісти щонайменше на пʼять питань:

1. Яку проблему вирішує Redis?

2. Які саме дані в ньому зберігатимуться?

3. Хто є Source of Truth — Redis чи інша система?

4. Як і коли дані будуть видалятися або оновлюватися?

5. Що станеться із системою, якщо Redis буде недоступний?

Якщо відповіді на ці питання зрозумілі — Redis може бути надзвичайно корисним компонентом архітектури.

Якщо ж єдина аргументація звучить як:

↳
«Давайте поставимо Redis, бо він швидкий»,

то, можливо, Redis поки що взагалі не потрібен.

21

Якщо зовсім просто

Уявімо звичайний магазин.

У магазину є великий склад. На ньому зберігаються всі товари, і саме інформація на складі вважається правильною.

У нашому випадку це база даних.

Але є проблема: якщо продавцю за кожною дрібницею потрібно бігати на склад, робота буде повільною.

Тому біля продавця можна поставити невелику полицю з речами, які потрібні найчастіше.

Ця полиця — приблизно те, чим часто є Redis.

Якщо потрібна інформація вже лежить поруч — ми беремо її дуже швидко.

Якщо її немає — йдемо до основної бази, отримуємо інформацію і можемо тимчасово покласти копію в Redis.

Саме тому Redis часто використовують як кеш.

Але Redis уміє значно більше.

Наприклад, нам потрібно запамʼятати код підтвердження лише на дві хвилини.

Можна записати його в Redis та встановити TTL:

OTP = 482193
TTL = 120 секунд

Через дві хвилини Redis сам видалить цей запис.

Або потрібно рахувати кількість запитів користувача:

1
2
3
...
100

Redis дуже добре вміє швидко збільшувати такі лічильники.

Тому на його основі часто реалізують rate limiting.

Або в нас працює декілька екземплярів одного сервісу і потрібно не дозволити двом із них одночасно виконати одну критичну операцію.

Тут Redis може допомогти з distributed lock.

А ще Redis може зберігати сесії, тимчасові дані, брати участь в обміні повідомленнями та вирішувати інші задачі.

Але тут зʼявляється важливе «але».

Якщо ми поклали в Redis копію даних із бази, тепер у нас фактично є дві копії:

Наприклад, у базі ціна товару вже 120 грн, а Redis памʼятає стару ціну — 100 грн.

Тому недостатньо просто сказати:

↳
«Давайте поставимо Redis — сайт стане швидшим».

Потрібно розуміти:

  • що саме ми кешуємо;
  • скільки часу ці дані можуть жити;
  • коли їх потрібно видаляти;
  • що робити після зміни даних у базі;
  • що станеться, якщо Redis перестане працювати.

Особливо важливо розуміти різницю між Redis, базою даних і RabbitMQ.

База даних зазвичай потрібна для надійного довготривалого зберігання бізнес-даних.

Redis особливо корисний там, де потрібні дуже швидкі або тимчасові дані.

RabbitMQ потрібен передусім для асинхронного обміну повідомленнями між системами з відповідними механізмами доставки.

Тому абсолютно нормально побачити в одній системі:

Це не три технології, які обовʼязково конкурують між собою.

Вони можуть вирішувати три різні задачі.

І головна ідея Redis дуже проста:

Redis потрібен не тому, що він модний або просто дуже швидкий. Він потрібен тоді, коли системі дійсно необхідно дуже швидко працювати з певними даними, зберігати тимчасову інформацію або координувати роботу декількох компонентів.

Якщо база даних і без Redis чудово справляється з навантаженням, додавати ще один компонент лише «для швидкості» може не мати сенсу.

Бо разом із Redis ми отримуємо не тільки швидкість.

Ми отримуємо ще один компонент, який потрібно:

  • розгорнути;
  • захистити;
  • моніторити;
  • резервувати;
  • правильно налаштувати;
  • оновлювати;
  • враховувати при відмовах;
  • і, найголовніше, правильно використовувати в коді.

Тому хороше архітектурне рішення звучить не так:

↳
«Давайте використаємо Redis».

А приблизно так:

↳
«У нас є конкретна проблема. Ось чому для її вирішення підходить Redis, ось які дані ми там зберігатимемо, ось скільки вони житимуть і ось що система робитиме, якщо Redis стане недоступним».

Якщо команда може відповісти на ці питання — Redis використовується усвідомлено.

Якщо відповідь лише:

↳
«Бо Redis швидкий»,

варто ще раз подумати, чи потрібен він системі взагалі.
