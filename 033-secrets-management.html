Пароль до бази даних, API-ключ, сертифікат або токен доступу — майже кожен застосунок використовує секрети. Але де їх правильно зберігати? Чому .env і appsettings.json не вирішують усіх проблем? І як HashiCorp Vault дозволяє керувати секретами без постійного зберігання паролів у застосунку?

Час читання: ~15 хвилин Для кого: Developers, DevOps, QA, Architects, Tech Leads, Security Engineers, Support, BA, PM/PO

01

1. Проблема, яку часто не помічають

Уявімо звичайний корпоративний застосунок — Orders API.

Він обробляє замовлення, підключається до Microsoft SQL Server, надсилає повідомлення через RabbitMQ і звертається до зовнішнього API.

Для цього йому потрібні облікові дані.

Розробник додає їх у appsettings.json:

JSON
{
  "ConnectionStrings": {
    "MainDb": "Server=sql01;Database=Orders;User Id=orders_user;Password=MyPassword123!"
  },
  "RabbitMQ": {
    "Username": "orders_service",
    "Password": "rabbit_password"
  },
  "ExternalApi": {
    "ApiKey": "example-secret-key"
  }
}

Усі секрети в прикладі вигадані.

Застосунок працює. Підключення успішні, запити виконуються, повідомлення надсилаються.

На перший погляд — усе добре.

Але виникає декілька запитань.

Що станеться, якщо цей файл потрапить до сторонніх?

Зловмисник може отримати облікові дані до БД, RabbitMQ та зовнішнього API.

Як змінити пароль?

Потрібно змінити облікові дані в цільовій системі, оновити конфігурацію й забезпечити, щоб застосунок почав використовувати нове значення.

А якщо пароль використовують десять сервісів?

Ротація одного пароля може спричинити помилки одночасно в декількох системах.

А хто взагалі має право знати цей пароль?

Розробник? DevOps? Адміністратор сервера? Кожен, хто має доступ до конфігурації?

Саме тут починається проблема Secrets Management.

Головний ризик — не тільки можливість викрадення секрету, а й відсутність керованого життєвого циклу доступу.

02

2. Що таке Secrets Management

Secret (секрет) — конфіденційне значення, яке дозволяє отримати доступ до ресурсу або виконати захищену операцію.

До секретів належать:

ТипПриклад
Database CredentialsЛогін і пароль до БД
API KeyКлюч доступу до API
Client SecretСекрет OAuth-клієнта
Access TokenТокен доступу
Private KeyПриватний криптографічний ключ
Encryption KeyКлюч шифрування
Certificate PasswordПароль до контейнера сертифіката

Не кожне конфігураційне значення є секретом.

Наприклад, адреса сервера, номер порту або назва бази даних зазвичай не потребують такого самого захисту, як пароль. Хоча й ці дані можуть бути внутрішньою службовою інформацією.

Secrets Management (керування секретами) — сукупність механізмів для захищеного зберігання, отримання, контролю доступу, оновлення та відкликання секретів.

Уявімо сейф із ключами від різних приміщень.

Замість того щоб роздати всім співробітникам копії ключів, організація використовує спеціальну систему, яка перевіряє особу, видає дозволений ключ і реєструє факт доступу.

Secrets Management працює за схожою логікою, але для програмних систем.

Життєвий цикл секрету

Тут важливі три терміни:

  • Rotation (ротація) — заміна секрету новим значенням.
  • Revocation (відкликання) — припинення можливості використовувати раніше видані облікові дані.
  • Audit (аудит) — фіксація подій доступу та адміністративних дій.

Система керування секретами повинна допомагати не тільки отримати пароль, а й відповісти на запитання: хто його отримував, чому мав доступ і як припинити цей доступ.

03

3. Чому звичайної конфігурації недостатньо

Секрети можуть зберігатися різними способами. Частина з них цілком прийнятна для локальної розробки, але потребує додаткових механізмів у production.

3.1. Секрет безпосередньо в коді

CSHARP
var password = "SuperSecretPassword";

Це Hardcoded Secret (секрет, вбудований у код).

Найбільша проблема — він може залишитися в Git навіть після видалення рядка з поточної версії файлу.

Також його можуть знайти інструменти аналізу коду або люди з доступом до репозиторію.

Якщо справжній секрет уже потрапив у Git, видалення коміту не гарантує безпеки. Секрет потрібно вважати потенційно скомпрометованим і замінити або відкликати.

3.2. Секрет у конфігураційному файлі

JSON
{
  "Database": {
    "Password": "example-password"
  }
}

Це вже дозволяє змінювати пароль без перекомпіляції.

Але конфігурація може потрапити в deployment package (пакет розгортання), резервні копії або на сервер із занадто широкими правами читання.

До того ж конфігураційний файл не забезпечує автоматичної ротації чи аудиту використання секрету.

3.3. Секрет у .env

BASH
DB_PASSWORD=example-password

Environment Variables (змінні середовища) — поширений спосіб передавання конфігурації застосунку.

Він дозволяє не включати секрет у вихідний код, але значення все ще може бути доступним через середовище виконання, засоби діагностики, помилково налаштовані журнали або адміністративні інструменти.

Важливо: .env — це спосіб зберігання та доставки конфігурації, а не повноцінна система керування секретами.

3.4. Секрет у CI/CD

Azure DevOps і подібні системи дозволяють зберігати секретні змінні.

Це корисний механізм для Pipeline (конвеєра збірки та розгортання), але не завжди найкраще місце для постійних runtime-секретів застосунку.

Наприклад, якщо секрет передається в застосунок під час кожного deployment, необхідно продумати, що відбудеться при його зміні між розгортаннями.

Порівняння підходів

ПідхідПеревагаОбмеження
Hardcoded у кодіПростотаВисокий ризик витоку
appsettings.jsonЗручна конфігураціяНемає керування життєвим циклом
.envВідокремлення від кодуНе забезпечує ротацію й аудит
CI/CD Secret VariablesЗручно для pipelineНе завжди оптимально для runtime
Secrets ManagerЦентралізовані правила, аудит, ротаціяПотребує інтеграції та експлуатаційної підтримки

Отже, справа не в тому, щоб повністю заборонити конфігураційні файли або змінні середовища.

Потрібно розділити конфігурацію застосунку та управління конфіденційними обліковими даними.

04

4. Як працює Secrets Manager

Замість зберігання пароля всередині застосунку використовується окремий сервіс — Secrets Manager.

Застосунок звертається до нього, підтверджує свою ідентичність та отримує тільки дозволені секрети.

Тут є два принципово різні механізми.

Authentication (автентифікація) — перевірка того, хто звертається.

Authorization (авторизація) — перевірка того, до яких секретів цей застосунок має право доступу.

Наприклад, сервіс Orders API повинен отримувати пароль до своєї бази даних, але не до бази даних зарплат.

Це принцип Least Privilege (мінімально необхідних привілеїв).

Навіть якщо один сервіс буде скомпрометований, його права не повинні автоматично відкривати доступ до всіх інших систем.

05

5. HashiCorp Vault — практичний приклад

HashiCorp Vault — платформа для керування секретами, їх видачею, контролем доступу та окремими криптографічними операціями.

Vault може:

  • зберігати статичні секрети;
  • створювати тимчасові облікові дані;
  • застосовувати політики доступу;
  • підтримувати різні способи автентифікації;
  • керувати строком дії виданих облікових даних;
  • підтримувати відкликання доступу;
  • вести аудит звернень.

У Vault є декілька основних компонентів.

КомпонентПризначення
Auth MethodПеревіряє ідентичність клієнта
PolicyВизначає дозволені операції
Secrets EngineЗберігає або генерує секрети
Vault TokenВикористовується для авторизованих звернень
LeaseОписує строк дії виданих облікових даних
Audit DeviceРеєструє звернення та події

Один із найпоширеніших механізмів — KV Secrets Engine (сховище пар «ключ — значення»).

Він дозволяє зберігати, наприклад, пароль БД та API-ключ.

KV v2 додатково підтримує версійність значень.

Але існує й інший режим роботи, який значно цікавіший з погляду безпеки.

06

6. Статичні та динамічні секрети

Static Secrets — статичні секрети

Статичний секрет створюється заздалегідь і зберігається у Vault.

Наприклад:

secret/orders/prod

DbUsername = orders_user
DbPassword = ********

Коли Orders API запускається, він отримує ці значення.

Перевага — пароль більше не потрібно зберігати в конфігураційному файлі застосунку.

Але сам пароль усе ще може бути довгостроковим.

Якщо його потрібно змінити, необхідно правильно оновити значення в цільовій системі та забезпечити отримання нового секрету застосунком.

Зберігання секрету у Vault не означає, що він автоматично змінюється.

Dynamic Secrets — динамічні секрети

Динамічний секрет створюється на вимогу.

Наприклад, застосунку потрібен доступ до SQL Server.

Vault може створити окремі тимчасові облікові дані до бази даних відповідно до попередньо налаштованої ролі.

Приклад відповіді:

JSON
{
  "lease_id": "database/creds/orders/abc123",
  "lease_duration": 3600,
  "renewable": true,
  "data": {
    "username": "v_orders_8472",
    "password": "generated-example-password"
  }
}

TTL — Time To Live (час життя) — строк, протягом якого виданий секрет вважається дійсним.

У цьому прикладі — 3600 секунд, тобто одна година.

Після завершення строку дії Vault може відкликати облікові дані за допомогою налаштованого механізму.

Однак фактичне припинення доступу залежить від інтегрованої системи. Наприклад, уже відкриті підключення до БД можуть потребувати окремої обробки.

Для Microsoft SQL Server Vault має відповідний database plugin, але його використання вимагає налаштування ролей, дозволів і команд створення та відкликання користувачів.

Що це дає?

Порівняймо два варіанти.

Звичайний пароль:

orders_user
Password = постійний

Його викрадення може залишатися небезпечним доти, доки пароль не змінять або доступ не заблокують.

Динамічний секрет:

v_orders_8472
TTL = 1 година

Час потенційного зловживання обмежений механізмами завершення строку дії та відкликання.

Це не робить систему невразливою, але суттєво зменшує ризики тривалого використання викрадених облікових даних.

07

7. Головне запитання: як застосунок отримує доступ до Vault?

Ми прибрали пароль БД із конфігурації.

Але як тепер застосунок авторизується у Vault?

Якщо просто записати в конфігурацію довгостроковий Vault Token, проблему вирішено лише частково.

Було:

Application → пароль БД → Database

Стало:

Application → пароль до Vault → Vault → пароль БД

Це називають Secret Zero Problem (проблема початкового секрету).

Ідея правильнішого підходу — використовувати ідентичність середовища, в якому працює застосунок.

Залежно від інфраструктури це може бути:

  • Azure Managed Identity — керована ідентичність ресурсу Azure;
  • Kubernetes Auth — автентифікація на основі ідентичності workload у Kubernetes;
  • AWS IAM Auth — використання ідентичності AWS;
  • AppRole — механізм автентифікації сервісів із захищеною доставкою початкових облікових даних;
  • інші підтримувані методи.

Приклад

Застосунок працює у середовищі Azure з налаштованою Managed Identity.

Він використовує ідентичність платформи для отримання відповідного токена, який Vault перевіряє через налаштований Azure Auth Method.

Після успішної перевірки Vault видає власний токен із потрібними правами.

Застосунок більше не повинен зберігати пароль до Vault у своєму коді.

Але ця схема працює лише за умови, що початкова ідентичність і довіра між системами налаштовані правильно.

Для on-premises середовищ, зокрема Windows Server та IIS, механізм початкової автентифікації потрібно проєктувати окремо. Сам факт запуску сервісу під певним Windows-акаунтом ще не означає, що Vault автоматично довірятиме цій ідентичності.

08

8. Практичний приклад: Orders API на .NET

Розглянемо повний сценарій роботи корпоративної системи.

Крок 1. Запуск застосунку

Orders API отримує звичайну конфігурацію:

JSON
{
  "Vault": {
    "Address": "https://vault.internal.example",
    "SecretPath": "secret/data/orders/prod"
  }
}

Тут немає пароля БД.

Крок 2. Автентифікація

Orders API або окремий Vault Agent підтверджує свою ідентичність за допомогою налаштованого методу.

Після успішної автентифікації застосунок отримує доступ до Vault API.

Крок 3. Отримання секрету

Приклад HTTP-запиту до KV v2:

HTTP
GET /v1/secret/data/orders/prod HTTP/1.1
Host: vault.internal.example
X-Vault-Token: <vault-token>

Токен у заголовку підтверджує право звернення до Vault. Його потрібно передавати через HTTPS і не записувати в application logs.

Vault перевіряє права доступу.

Приклад політики:

HCL
path "secret/data/orders/prod" {
  capabilities = ["read"]
}

Ця політика дозволяє читати конкретний шлях.

Вона не дає автоматичного доступу до інших секретів.

Якщо доступ дозволений, Vault повертає відповідь зі статусом 200 OK.

Спрощений приклад:

JSON
{
  "data": {
    "data": {
      "DbUsername": "orders_user",
      "DbPassword": "example-password"
    },
    "metadata": {
      "version": 3
    }
  }
}

У реальній відповіді KV v2 є також інші поля метаданих.

Якщо токен не має достатніх прав, Vault зазвичай відповість 403 Forbidden. Якщо автентифікація неуспішна або облікові дані недійсні, код відповіді залежатиме від конкретного endpoint та сценарію.

Крок 4. Використання в .NET

Отримані значення застосунок використовує для побудови підключення:

CSHARP
var connectionStringBuilder =
    new SqlConnectionStringBuilder
    {
        DataSource = "sql01",
        InitialCatalog = "Orders",
        UserID = credentials.Username,
        Password = credentials.Password,
        Encrypt = true
    };

await using var connection =
    new SqlConnection(connectionStringBuilder.ConnectionString);

await connection.OpenAsync();

Тут credentials — об'єкт із даними, отриманими через захищений компонент інтеграції з Vault.

Цей код показує тільки використання отриманих секретів. Автентифікація у Vault, поновлення токенів, кешування та обробка помилок повинні реалізовуватися окремо.

Важливі правила:

  • не записувати Connection String із паролем у логи;
  • не передавати секрет клієнтському застосунку;
  • не отримувати секрет із Vault на кожний бізнес-запит без потреби;
  • контролювати строк його дії та процедуру оновлення;
  • не вимикати перевірку TLS-сертифікатів заради спрощення підключення.

Vault використовується серверною частиною, а не безпосередньо браузером користувача для отримання внутрішніх паролів.

09

9. Що буде, якщо секрет викрадуть?

Уявімо, що під час діагностики розробник додав таке логування:

CSHARP
logger.LogInformation(
    "Database connection: {ConnectionString}",
    connectionString
);

Якщо connectionString містить пароль, він потрапить у журнал.

Далі журнал можуть отримувати централізовані системи моніторингу, наприклад ELK.

Таким чином доступ до пароля потенційно отримають люди або процеси, які мають право читати логи, але не повинні мати доступу до БД.

Як розвивається інцидент

Що потрібно зробити

Передусім — обмежити або припинити використання скомпрометованих облікових даних.

Потім забезпечити заміну секрету, перевірити журнали доступу, оцінити можливі наслідки та усунути канал витоку.

Видалення пароля з коду, Git чи логів саме по собі не анулює вже викрадені облікові дані.

Якщо секрет був статичним, його потрібно змінити або відкликати в цільовій системі.

Якщо він був динамічним, можна використовувати механізми відкликання lease у Vault.

Але й тут необхідно перевіряти, що доступ справді припинився на рівні цільової системи.

Secrets Manager зменшує ризики, але не компенсує необережне поводження з уже отриманими секретами.

10

10. Що відбувається, якщо Vault недоступний?

Це питання особливо важливе для production.

Уявімо ситуацію:

  • Orders API працює;
  • у нього вже є дійсні облікові дані до БД;
  • Vault тимчасово недоступний.

Чи повинен застосунок одразу припинити роботу?

Не обов'язково.

Якщо секрет ще дійсний, застосунок може продовжувати його використовувати відповідно до визначеної політики.

Але ситуація змінюється, якщо:

  • застосунок перезапустили;
  • завершився строк дії токена або lease;
  • потрібно отримати нові облікові дані;
  • відбулася ротація секрету.

Основні ризики

СитуаціяНаслідок
Vault недоступний під час запускуЗастосунок може не стартувати
Vault недоступний під час роботиНові секрети можуть бути недоступні
Завершився TTLМожлива втрата доступу до ресурсу
Змінився пароль БДСтарі підключення або нові з'єднання можуть перестати працювати
Відкликали Vault TokenНові звернення до Vault будуть заборонені

Як це враховувати

Архітектура повинна передбачати:

High Availability (високу доступність). Vault має працювати з урахуванням відмов серверів та мережевих компонентів.

Caching (кешування). Застосунок або спеціалізований агент може тимчасово зберігати дозволені секрети. Але це не означає, що прострочені або відкликані облікові дані можна використовувати без обмежень.

Renewal (поновлення). Для токенів і lease, які підтримують поновлення, потрібно передбачити відповідний механізм.

Retry (повторення запиту). Тимчасові мережеві помилки потрібно обробляти з обмеженням кількості спроб та затримками.

Fail Closed (безпечна відмова). Якщо застосунок не має дійсних облікових даних, він не повинен обходити механізми безпеки або автоматично переходити на адміністративний пароль.

Важливо також контролювати connection pooling (пул підключень). Після ротації облікових даних може знадобитися оновити налаштування пулу та закрити старі з'єднання.

Окреме архітектурне рішення — чи повинен застосунок читати секрет безпосередньо через Vault API, чи краще використати Vault Agent або інший перевірений механізм доставки секретів.

11

11. Vault, Azure Key Vault та Kubernetes Secrets — це одне й те саме?

Ні. Це різні інструменти, які частково вирішують схожі завдання.

РішенняОсновне призначення
HashiCorp VaultЦентралізоване керування секретами, динамічні облікові дані, політики, аудит
Azure Key VaultКерування секретами, ключами та сертифікатами в екосистемі Azure
AWS Secrets ManagerКерування секретами та підтримка сценаріїв автоматичної ротації
Kubernetes SecretsЗберігання та доставка секретних даних workload у Kubernetes
CI/CD Secret VariablesЗахищене передавання значень під час виконання pipeline

Наприклад, Kubernetes Secrets не варто автоматично вважати еквівалентом зовнішнього Secrets Manager. Значення в маніфестах часто подаються у форматі Base64, який є кодуванням, а не шифруванням.

Потрібно окремо налаштовувати захист etcd, RBAC (рольовий контроль доступу), механізми доставки й ротації.

Водночас не кожному застосунку обов'язково потрібен саме Vault.

Якщо система повністю працює в Azure, Azure Key Vault разом із Managed Identity може бути простішим рішенням.

Якщо потрібні різні середовища виконання, власні політики, підтримка багатьох платформ та динамічні секрети, HashiCorp Vault може бути доцільнішим.

Вибір залежить від вимог, а не від популярності інструмента.

12

12. Як це правильно тестувати

Secrets Management потрібно перевіряти не тільки на рівні «застосунок успішно підключився».

Позитивний сценарій

  1. Застосунок автентифікується у Vault.
  2. Отримує секрет, до якого має доступ.
  3. Встановлює підключення до цільової системи.
  4. Виконує бізнес-операцію.
  5. Не розкриває секрет у відповіді API чи журналі.

Негативні сценарії

ПеревіркаОчікувана поведінка
Токен без необхідних правVault повертає відмову в доступі, зазвичай 403
Секрет відсутнійЗастосунок обробляє помилку без розкриття деталей
Vault недоступнийКонтрольована відмова або дозволений режим роботи з дійсними даними
Токен відкликанийНові звернення з ним не виконуються
Пароль БД зміненийЗастосунок переходить на новий секрет згідно з визначеним механізмом
Секрет потрапив у текст виняткуВін не повинен відображатися в журналах або API response

Якщо відсутність секрету робить виконання операції неможливим, прикладною поведінкою може бути відповідь 503 Service Unavailable, без передачі користувачу внутрішньої помилки Vault.

Точний HTTP-статус зовнішнього API визначається контрактом сервісу. Не слід бездумно транслювати відповідь Vault 403 кінцевому користувачу, оскільки це різні рівні авторизації.

Security-тести

Потрібно перевірити, що:

  • один сервіс не може отримати секрет іншого;
  • TEST не має доступу до PROD-секретів;
  • Vault Token не потрапляє в логи;
  • застосунок не використовує root token;
  • відкликання секрету справді обмежує доступ;
  • зміна секрету не вимагає неконтрольованих ручних дій;
  • TLS-сертифікати перевіряються;
  • у Git, build artifacts та deployment packages немає реальних секретів.

Частину цих перевірок можна автоматизувати в CI/CD, використовуючи secret scanning (пошук потенційно розкритих секретів).

13. Що повинні врахувати різні ролі

Secrets Management — не виключно завдання DevOps або Security Engineer.

РольНа що звернути увагу

DevOpsНалаштувати доставку секретів, автентифікацію, доступність і ротацію
Architect / Tech LeadВизначити межі довіри, політики доступу та поведінку системи при відмовах
Security EngineerКонтролювати права, аудит, життєвий цикл та реакцію на компрометацію
QAПеревіряти заборону доступу, ротацію, відмови й витоки в логах
SupportРозуміти симптоми прострочених секретів та процедуру ескалації
BA / PM / POВраховувати вимоги до безпеки, доступності, аудиту та експлуатаційні ризики

Особливо важливо, щоб порядок зміни секретів був частиною експлуатаційної документації, а не залишався знанням одного розробника.

14. Checklist для production

Перед запуском системи варто переконатися, що:

  • [ ] Секрети відсутні у вихідному коді та репозиторії.
  • [ ] Для DEV, TEST, PRE-PROD і PROD використовуються незалежні облікові дані.
  • [ ] Кожен сервіс отримує тільки необхідні права.
  • [ ] Немає постійного використання адміністративних або root-токенів.
  • [ ] Налаштована перевірка TLS.
  • [ ] Секрети та токени не потрапляють у логи.
  • [ ] Існує процедура ротації та відкликання.
  • [ ] Визначено поведінку при недоступності Secrets Manager.
  • [ ] Перевірено поновлення токенів і lease.
  • [ ] Увімкнено аудит доступу та моніторинг підозрілих операцій.
  • [ ] Автоматизовано перевірку на наявність секретів у Git та CI/CD.
  • [ ] Є інструкція реагування на компрометацію секрету.
15

15. Якщо зовсім просто

Уявімо, що кожен застосунок — це співробітник компанії, а секрети — ключі від службових приміщень.

Без Secrets Management співробітнику видають зв'язку ключів назавжди.

Ключі можуть загубитися, бути скопійовані або залишитися в людини, яка вже не повинна мати доступ.

Із Secrets Management співробітник приходить до контрольованого пункту видачі ключів.

Система перевіряє, хто він, визначає, які приміщення йому дозволено відкривати, видає відповідний ключ і реєструє цю операцію.

За потреби ключ можна замінити, а доступ — відкликати.

Деякі ключі можуть бути навіть тимчасовими.

Саме так працює керування секретами у програмних системах.

16

Висновок

Secrets Management — це не просто спосіб приховати паролі від розробників.

Це архітектурний підхід, який дозволяє керувати доступом застосунків до критичних ресурсів.

Головні думки:

  1. Секрети не повинні бути частиною вихідного коду. Конфігурація також потребує відповідного захисту.
  1. Зберігання і керування — різні речі. Безпечне сховище саме по собі не вирішує питання ротації, відкликання й аудиту.
  1. Застосунок повинен мати власну ідентичність. Це дозволяє зменшити залежність від постійних паролів.
  1. Динамічні секрети зменшують ризик довгострокової компрометації. Але їхній життєвий цикл потрібно враховувати в коді та інфраструктурі.
  1. Доступність Secrets Manager — частина архітектури. Рішення повинно коректно переживати тимчасові відмови, ротацію та завершення строку дії облікових даних.

Правильна мета — не просто сховати пароль, а зробити доступ до нього контрольованим, обмеженим і керованим протягом усього життєвого циклу.
