Вступ

Уявімо звичайну корпоративну систему.

У ній є база даних із клієнтами, договорами, заявками, аваріями, обладнанням, платежами, подіями або іншою бізнес-інформацією.

Щоб отримати відповідь на просте запитання:

↳
Скільки аварійних відключень було за останні 7 днів і в яких районах їх найбільше?

користувачеві сьогодні часто потрібно:

  1. відкрити потрібну систему;
  2. знайти відповідний звіт;
  3. встановити фільтри;
  4. експортувати дані;
  5. побудувати таблицю;
  6. проаналізувати результат.

Або написати аналітику чи розробнику:

↳
Можеш зробити SQL і подивитися статистику?

А що, якщо користувач просто напише запитання природною мовою?

Скільки аварійних відключень було
за останні 7 днів і які райони
постраждали найбільше?

А система сама:

  • зрозуміє запит;
  • визначить, які дані потрібні;
  • знайде необхідні таблиці;
  • сформує SQL;
  • виконає його;
  • перевірить результат;
  • за необхідності зробить додаткові запити;
  • проаналізує дані;
  • сформує зрозумілу відповідь.

Наприклад:

↳
За останні 7 днів зафіксовано 1 247 аварійних відключень. Найбільше — у районах A, B та C. На ці три райони припадає 46% усіх випадків.

Саме тут ми переходимо від звичайної LLM до AI-агента, який працює з базою даних.

Але між:

"Було б класно дати AI доступ до БД"

і

"Це безпечно працює в PROD"

лежить величезна архітектурна прірва.

Спробуємо її пройти.

01

1. Спочатку важливе: LLM сама не вміє ходити в базу

Коли ми спілкуємося з LLM, може складатися враження, що модель щось шукає, перевіряє, аналізує бази даних і взагалі має доступ до всього.

Насправді базова LLM працює приблизно так:

Ми передаємо текст:

Скільки аварій було вчора?

Модель генерує наступні токени.

У неї немає магічного:

SELECT * FROM production;

Вона не знає:

  • де знаходиться наша БД;
  • який у неї connection string;
  • які таблиці існують;
  • які дані зараз лежать у таблицях;
  • що відбулося сьогодні;
  • хто має право бачити ці дані.

Якщо просто запитати LLM:

↳
Скільки в нас сьогодні аварій?

вона може лише відповісти на основі інформації, яка вже знаходиться в її контексті.

А якщо інформації немає — модель потенційно може почати галюцинувати.

Тому потрібен механізм, через який LLM може отримати зовнішні дані.

І тут з'являються Tools.

02

2. Tool Calling: руки AI-агента

Припустимо, ми дали моделі інструмент:

execute_sql(query)

Тепер архітектура виглядає так:

Користувач питає:

Скільки аварій було вчора?

LLM може вирішити:

Для відповіді мені потрібні дані з БД.

І викликати:

execute_sql(
    "SELECT COUNT(*)
     FROM incidents
     WHERE created_at >= CURRENT_DATE - INTERVAL '1 day'"
)

Tool виконує SQL.

База повертає:

137

Результат повертається моделі.

І модель відповідає:

↳
Вчора було зареєстровано 137 аварій.

Ось це вже значно цікавіше.

LLM не знала число 137.

Вона отримала його з корпоративної системи.

03

3. Чат-бот і AI-агент — не зовсім одне й те саме

Звичайний чат-бот часто працює за схемою:

AI-агент має можливість виконувати дії:

Тобто агент може сам вирішувати:

↳
Для відповіді мені недостатньо інформації.

Після цього:

Це називають agent loop.

04

4. Простий приклад Agent Loop

Користувач питає:

↳
Чи стало аварій цього тижня більше, ніж минулого?

Одного SQL може бути недостатньо.

Агент може спочатку отримати поточний тиждень:

SQL
SELECT COUNT(*)
FROM incidents
WHERE created_at >= date_trunc('week', CURRENT_DATE);

Результат:

842

Потім минулий:

SQL
SELECT COUNT(*)
FROM incidents
WHERE created_at >= date_trunc('week', CURRENT_DATE) - INTERVAL '7 days'
  AND created_at < date_trunc('week', CURRENT_DATE);

Результат:

711

Після цього агент сам обчислює різницю:

842 - 711 = 131

та відсоток:

131 / 711 × 100 ≈ 18.4%

І відповідає:

↳
Так. Кількість аварій зросла приблизно на 18,4% порівняно з аналогічним періодом минулого тижня.

Але агент може піти далі.

Наприклад, вирішити:

Зростання значне.
Потрібно зрозуміти, які райони дали найбільший приріст.

І виконати третій SQL.

Ось тут поведінка вже починає нагадувати роботу аналітика.

05

5. Text-to-SQL

Одне з найпопулярніших застосувань LLM для роботи з БД називається Text-to-SQL.

Ідея дуже проста:

Наприклад:

Покажи 10 районів з найбільшою
кількістю аварій за останні 30 днів.

LLM генерує:

SQL
SELECT
    district,
    COUNT(*) AS incident_count
FROM incidents
WHERE created_at >= CURRENT_DATE - INTERVAL '30 days'
GROUP BY district
ORDER BY incident_count DESC
LIMIT 10;

На демонстрації це виглядає майже магічно.

Але саме тут починаються проблеми.

06

6. Звідки LLM знає структуру нашої БД?

Припустимо, у базі є:

customers
contracts
meters
incidents
outages
payments
regions
addresses

Модель повинна знати хоча б:

table: incidents

columns:
- id
- created_at
- incident_type
- status
- region_id
- customer_id

Також потрібно знати relationships:

Без цього модель може придумати:

SQL
SELECT region_name
FROM incidents;

Хоча region_name знаходиться не в incidents, а в regions.

Тоді база відповість:

ERROR:
column "region_name" does not exist
07

7. Чи можна просто передати LLM всю schema?

Для маленької БД — іноді так.

Наприклад:

Database schema:

customers(
    id,
    name,
    region_id
)

regions(
    id,
    name
)

incidents(
    id,
    customer_id,
    created_at,
    type
)

LLM отримує це у prompt.

Але тепер уявімо enterprise-БД.

800 tables
12 000 columns
1 500 relationships

Передавати все це в кожен prompt — погана ідея.

Причини:

  • величезний контекст;
  • більше токенів;
  • більша вартість;
  • більша latency;
  • модель отримує багато непотрібної інформації;
  • важче вибрати правильні таблиці;
  • збільшується ймовірність помилки.

Тому часто потрібен окремий етап:

Наприклад, для питання про аварії агенту можна передати лише:

incidents
regions
incident_types

а не всі 800 таблиць.

08

8. Metadata важливі не менше за schema

Назва поля:

status = 4

майже нічого не говорить LLM.

Що означає 4?

Closed?
Cancelled?
Emergency?
Deleted?

Тому агенту потрібна не просто структура.

Потрібна семантика даних.

Наприклад:

incidents.status

1 = New
2 = In Progress
3 = Resolved
4 = Closed
5 = Cancelled

Або:

incident_type = 7

7 = Emergency outage

Тобто для якісної роботи AI потрібно знати не лише:

↳
де лежать дані,

а й:

↳
що ці дані означають.
09

9. Semantic Layer

Тут ми приходимо до дуже важливої концепції.

Користувач може запитати:

↳
Скільки в нас активних клієнтів?

Але в базі немає:

customer.is_active

Можливо, "активний клієнт" визначається так:

customer.deleted = false

AND

contract.status = 'ACTIVE'

AND

meter.status = 'CONNECTED'

Або ще складніше.

Для бізнесу:

Активний клієнт

— зрозумілий термін.

Для БД — це бізнес-правило.

Тому між природною мовою та фізичною моделлю БД часто потрібен Semantic Layer.

У ньому можуть бути описані:

  • бізнес-терміни;
  • KPI;
  • формули;
  • правила;
  • relationships;
  • допустимі фільтри;
  • значення статусів;
  • визначення показників.
10

10. Найпростіша архітектура

Можна зробити так:

І технічно це працюватиме.

Але це майже найнебезпечніший можливий варіант.

Тому що ми фактично говоримо моделі:

↳
Генеруй будь-який SQL, а ми його виконаємо.
11

11. А якщо LLM зробить DELETE?

Наприклад:

SQL
DELETE FROM customers;

Або:

SQL
DROP TABLE payments;

Тому перша очевидна вимога:

↳
AI-агент не повинен працювати під DB Owner.

Йому потрібен окремий користувач.

Наприклад:

ai_readonly

із правами тільки:

SELECT

і лише на дозволені об'єкти.

Але навіть цього недостатньо.

12

12. SELECT теж може бути небезпечним

Є поширена помилка:

↳
Якщо агент має тільки SELECT — він безпечний.

Не зовсім.

Уявімо таблицю:

telemetry

із 4 мільярдами записів.

LLM генерує:

SQL
SELECT *
FROM telemetry;

Формально:

DELETE — ні
UPDATE — ні
DROP — ні

Але база може сказати:

↳
Ну добре...

і почати читати мільярди рядків.

Наслідки:

  • CPU;
  • RAM;
  • disk I/O;
  • network;
  • блокування ресурсів;
  • деградація PROD;
  • проблеми для інших сервісів.

Тому:

READ ONLY ≠ SAFE
13

13. Query Guard

Між AI та БД бажано мати контрольний шар.

Query Guard може перевіряти:

✓ тільки SELECT

✓ дозволені таблиці

✓ LIMIT

✓ timeout

✓ максимальну кількість рядків

✓ заборонені функції

✓ складність query

✓ дозволені schema

✓ query cost

Наприклад, LLM генерує:

SQL
SELECT *
FROM telemetry;

Guard може відхилити запит:

Rejected:
Query must contain LIMIT.

Або автоматично обмежити:

SQL
LIMIT 1000
14

14. Timeout

Будь-який SQL від AI повинен мати обмежений час виконання.

Наприклад:

statement_timeout = 5 sec

Якщо модель випадково побудувала важкий JOIN:

SQL
SELECT ...
FROM huge_table_a a
JOIN huge_table_b b ON ...
JOIN huge_table_c c ON ...

через 5 секунд запит буде зупинено.

Без timeout агент потенційно може створити довгий важкий query.

15

15. Чи потрібно взагалі давати агенту Raw SQL?

Це одне з найважливіших архітектурних питань.

Є два підходи.

Варіант A

execute_sql(sql)

LLM має величезну свободу.

Перевага:

дуже гнучко

Недолік:

дуже небезпечно

Варіант B

Ми створюємо конкретні Tools:

get_incidents(
    region,
    date_from,
    date_to
)

get_customer(
    customer_id
)

get_payments(
    customer_id,
    period
)

get_outage_statistics(
    region,
    period
)

Тоді LLM не пише SQL.

Вона викликає:

get_outage_statistics(
    region = "Odessa",
    period = "7 days"
)

А backend сам виконує заздалегідь контрольований SQL.

16

16. Свобода проти контролю

Умовно:

Чим більше свободи ми даємо LLM, тим більше сценаріїв вона може вирішувати.

Але одночасно ростуть:

  • security risks;
  • unpredictability;
  • навантаження;
  • складність тестування;
  • складність аудиту.

Тому для enterprise-систем часто вигідніше дати агенту набір контрольованих Tools, а не прямий SQL.

17

17. AI Agent не обов'язково працює лише з БД

Тепер стає цікавіше.

Агент може мати:

SQL Tool
API Tool
Search Tool
RAG Tool
Calculator Tool
Monitoring Tool

Наприклад, користувач питає:

↳
Чому клієнту відключили послугу і чи відповідає це регламенту?

Для відповіді потрібні два різні джерела.

SQL

Отримати:

customer
contract
payments
outage reason
event history

RAG

Знайти:

регламент відключення клієнтів

Тоді:

SQL відповідає:

↳
Що сталося?

RAG:

↳
Що повинно було статися відповідно до документації?

LLM об'єднує ці два контексти.

18

18. Приклад складнішого Agent Loop

Запит:

↳
Чому в районі X цього тижня стало більше аварій?

Агент може виконати:

1. Отримати кількість аварій цього тижня.

2. Отримати кількість минулого тижня.

3. Порівняти.

4. Побачити зростання на 37%.

5. Отримати breakdown за типами.

6. Побачити, що найбільше зросли аварії типу Transformer Failure.

7. Отримати список обладнання.

8. Перевірити історію цього обладнання.

9. Сформувати висновок.

Тобто агент не просто виконав:

Він побудував план дослідження.

19

19. Self-Correction

Ще одна сильна сторона LLM.

Модель генерує:

SQL
SELECT region_name, COUNT(*)
FROM incidents
GROUP BY region_name;

База відповідає:

ERROR:
column "region_name" does not exist

Ми можемо повернути цю помилку агенту.

LLM дивиться schema і розуміє:

Ага.

incidents.region_id
regions.id
regions.name

Після цього генерує:

SQL
SELECT
    r.name,
    COUNT(*)
FROM incidents i
JOIN regions r
    ON r.id = i.region_id
GROUP BY r.name;

Тобто агент може сам виправити власний SQL.

Але тут важливо встановити обмеження.

Наприклад:

max_attempts = 3

Інакше агент може нескінченно:

query
error
query
error
query
error
...
20

20. Контекст діалогу

Розглянемо:

User:
Покажи кількість аварій за сьогодні.

Agent:
142.

Потім користувач питає:

А за вчора?

Якщо дивитися лише на другий запит:

"А за вчора?"

незрозуміло:

↳
Що саме за вчора?

Але агент має conversation context:

previous topic = incidents
metric = count

Тому розуміє:

Кількість аварій за вчора.

Саме тому агентні системи часто потребують conversation state.

21

21. Memory

Але conversation context і memory — не зовсім одне й те саме.

Контекст може жити лише в межах поточного діалогу.

Memory може зберігати довгострокову інформацію.

Наприклад:

User frequently works with region = Odessa.
Preferred report format = table.
Default period = 7 days.

Але тут виникає важливе питання:

↳
Що агент взагалі має право пам'ятати?

Не варто безконтрольно записувати в memory:

  • персональні дані;
  • результати SQL;
  • секрети;
  • токени;
  • конфіденційну інформацію.

Memory теж повинна мати governance.

22

22. Авторизація — критично важлива

Уявімо запит:

↳
Покажи зарплати всіх співробітників.

LLM технічно може знати, що існує:

employee_salary

А DB account агента може мати SELECT.

45. Основні антипатерни

❌ LLM напряму підключена до PROD

Краще використовувати контрольний backend/tool layer.

❌ DB Owner credentials

AI повинен мати мінімально необхідні права.

❌ Unrestricted SQL

Будь-який SQL від LLM повинен вважатися недовіреним.

❌ Security через Prompt

"Please don't show confidential information"

не є системою авторизації.

❌ Відсутність timeout

Один невдалий query може створити серйозне навантаження.

❌ SELECT *

Особливо на великих таблицях.

❌ Відсутність row limit

LLM не потрібно отримувати мільйон записів у context.

❌ Відсутність Audit

Потім неможливо зрозуміти, хто і які дані отримував.

❌ Вся schema в Prompt

Для великої системи це дорого, повільно та створює шум.

❌ Business Logic у Prompt

Бізнес-правила повинні виконуватися deterministic code.

❌ Довіра до даних із БД

Retrieved content теж може містити prompt injection.

❌ Необмежений Agent Loop

Агент повинен мати step/time/tool limits.

Словник термінів простими словами

  • LLM — мовна модель, яка розуміє запит і формує відповідь, але сама по собі не повинна мати необмежений доступ до бази.
  • Tool Calling — спосіб, у який модель просить застосунок викликати дозволену функцію з чіткими параметрами.
  • Agent Loop — цикл «подумати → викликати інструмент → прочитати результат → вирішити, що робити далі». Кількість кроків треба обмежувати.
  • Text-to-SQL — перетворення питання звичайною мовою на SQL-запит.
  • Schema / metadata — опис таблиць, колонок, зв’язків і типів даних, потрібний для побудови коректного запиту.
  • Semantic layer — зрозумілий бізнес-словник над технічними таблицями: наприклад, що саме означає «активний клієнт».
  • Query Guard — перевірка SQL перед виконанням: дозволені операції, таблиці, ліміти, час і вартість запиту.
  • Raw SQL — довільний SQL, сформований моделлю. Це найгнучкіший, але найризикованіший варіант.
  • RAG — пошук потрібних фрагментів знань перед відповіддю моделі.
  • Grounding — прив’язка відповіді до фактичних даних або документів, а не лише до припущень моделі.
  • Read replica — копія бази для читання, яка зменшує ризик перевантажити основну операційну базу.
  • OLTP — база для щоденних операцій; DWH — сховище, підготовлене для аналітики.
  • CDC / ETL — способи переносити зміни з робочих систем до аналітичного сховища.
  • Row-Level Security — правило, яке дозволяє користувачеві бачити лише його рядки даних.
  • Prompt injection — текст, який намагається змусити модель порушити правила або виконати небезпечну дію.
  • Audit — журнал того, хто, коли, що запитав і яку дію виконала система.
  • Human-in-the-Loop — обов’язкове підтвердження людини перед ризикованою дією.
56

👶 Якщо зовсім просто

AI-агент біля бази даних схожий на нового співробітника. Він може швидко зрозуміти запит, але йому не дають ключ від усіх дверей. Замість цього він користується набором дозволених інструментів.

Користувач ставить питання. Модель вирішує, який інструмент потрібен. Застосунок перевіряє права користувача, параметри й обмеження, виконує безпечний запит, а модель пояснює результат людською мовою.

Для читання великих обсягів даних краще використовувати read replica або аналітичне сховище. Для зміни даних — окремі бізнес-команди з перевірками, аудитом і, за потреби, підтвердженням людини.

Головне правило: модель може пропонувати дію, але доступ, перевірки й остаточне виконання контролює звичайний застосунок.

55. Головний висновок

AI-агент із доступом до бази даних — це надзвичайно потужний інструмент.

Він може перетворити:

SQL
Dashboards
Reports
Filters
Excel

на звичайний діалог:

↳
Що відбувається?
↳
Чому?
↳
Де найбільша проблема?
↳
Порівняй із минулим місяцем.
↳
Покажи клієнтів, яких це зачепило.
↳
Яка тенденція?

Для користувача це може виглядати як простий чат.

Але за цим чатом стоїть далеко не проста система.

І головна помилка, яку можна зробити:

і вирішити, що AI-агент готовий.

Насправді:

↳
AI-агент з доступом до бази даних — це не ChatGPT, якому дали connection string.

Це повноцінна інформаційна система, де LLM є лише одним із компонентів.

Між моделлю та корпоративними даними повинні знаходитися:

Authentication
Authorization
Tools
Semantic Layer
Validation
Query Guard
Limits
Audit
Observability
Security

А якщо агент ще й може змінювати дані, вимоги стають ще жорсткішими.

Тому правильне питання при проєктуванні такої системи не:

↳
Як дати AI доступ до бази?

А:

↳
Які контрольовані можливості ми хочемо дати AI, від імені якого користувача вони виконуються, до яких даних він має доступ і якими технічними механізмами ми гарантуємо, що агент не зможе вийти за ці межі?

І ось після відповіді на це питання починається справжня архітектура AI Agent.
