Вступ

Майже кожен бачив кнопку:

«Увійти через Microsoft» «Увійти через Google»

Або повідомлення:

↳
Application хоче отримати доступ до вашого профілю та календаря.

Ми натискаємо:

Allow

і застосунок отримує доступ до певних наших даних.

Але є цікаве питання:

↳
Як сторонній застосунок отримав доступ до мого календаря, якщо я ніколи не передавав йому свій пароль?

Саме цю задачу і допомагає вирішувати OAuth 2.0.

01

🔑 Як робили б без OAuth?

Уявімо застосунок Calendar Analytics, якому потрібно читати наш календар.

Найпростіша схема могла б виглядати так:

TEXT
Calendar Analytics:

Введіть:

Microsoft Login:    ________
Microsoft Password: ________

Після цього:

TEXT
Calendar Analytics
       │
       │ login + password
       ▼
Microsoft API

Технічно працювати може.

Але тепер сторонній застосунок знає наш пароль.

Причому ми хотіли дати йому лише:

↳
«Читати календар»

а фактично передали credential, який потенційно відкриває значно більше можливостей.

OAuth пропонує інший підхід:

↳
Не передавати застосунку пароль. Передати йому обмежене право виконувати конкретні дії.
02

🎟 Замість пароля — Access Token

Схематично:

TEXT
User
 │
 │ Login
 ▼
Authorization Server
 │
 │
 │ Access Token
 ▼
Application
 │
 │ Bearer Access Token
 ▼
API

Application не отримує пароль користувача.

Він отримує:

Access Token

який може мати обмежені:

  • права;
  • ресурси;
  • audience;
  • термін життя.

Наприклад, умовно:

TEXT
Token:

Resource: Calendar API
Permissions:
    calendar.read

Expires:
    15 minutes

Це набагато безпечніше, ніж передавати сторонньому застосунку пароль.

03

👥 Хто взагалі бере участь в OAuth?

У OAuth є декілька ролей.

👤 Resource Owner

Той, кому належать дані або хто може дозволити доступ.

У нашому прикладі — користувач.

📱 Client

Застосунок, який хоче отримати доступ.

Наприклад:

TEXT
Calendar Analytics

🔐 Authorization Server

Система, яка:

  • автентифікує користувача;
  • отримує його згоду, коли це потрібно;
  • видає токени.

🗄 Resource Server

API, де знаходяться ресурси.

Наприклад:

TEXT
Calendar API

У підсумку:

TEXT
           User
            👤
             │
             ▼
           Client
             │
             ▼
     Authorization Server
             │
             │ Access Token
             ▼
           Client
             │
             ▼
       Resource Server
             API
04

🚨 OAuth 2.0 — це не Login Protocol

Тут одна з найпоширеніших плутанин.

Часто можна почути:

↳
«У нас авторизація користувача через OAuth».

Але OAuth 2.0 насамперед створений для делегованого доступу до ресурсів.

Грубо кажучи:

TEXT
OAuth 2.0

ЩО застосунку
дозволено робити?

Наприклад:

TEXT
read calendar
read profile
write files
send email

А питання:

TEXT
ХТО цей користувач?

вирішується за допомогою OpenID Connect (OIDC) — identity layer поверх OAuth 2.0.

Тому коли ми бачимо:

Sign in with Microsoft

зазвичай у сценарії входу використовується:

TEXT
OAuth 2.0
    +
OpenID Connect
05

🪪 Access Token та ID Token — це різні речі

Після OIDC/OAuth flow застосунок може отримати кілька різних токенів.

Наприклад:

TEXT
Access Token
ID Token
Refresh Token

Вони мають різне призначення.

🎟 Access Token

Access Token призначений для Resource Server / API.

Наприклад:

HTTP
GET /api/orders

Authorization: Bearer eyJ...

API перевіряє token і вирішує:

↳
Чи дозволено виконати цю операцію?

🪪 ID Token

ID Token призначений Client Application.

Він повідомляє Client інформацію про результат автентифікації користувача.

Наприклад:

JSON
{
  "sub": "12345",
  "name": "Ivan",
  "iss": "https://identity.example.com"
}

Тобто:

TEXT
ID Token
    ↓
Client

а:

TEXT
Access Token
    ↓
API

Це принципова різниця.

↳
ID Token не потрібно використовувати як заміну Access Token для виклику API.
06

🔄 Authorization Code Flow

Розглянемо один із найважливіших OAuth-сценаріїв.

Користувач відкриває Application.

Application хоче отримати доступ до API від імені користувача.

1️⃣ Application перенаправляє користувача

TEXT
User
 │
 ▼
Application
 │
 │ redirect
 ▼
Authorization Server

Наприклад, передаються параметри на кшталт:

TEXT
client_id
redirect_uri
scope
state
code_challenge
07

🔐 2️⃣ Користувач входить у систему

І дуже важливий момент:

TEXT
Login
Password
MFA

користувач вводить на стороні Authorization Server.

Не в нашому Application.

Тобто:

TEXT
User
 │
 │ credentials
 ▼
Authorization Server

а не:

TEXT
User
 │
 │ password
 ▼
Third-party Application ❌
08

✅ 3️⃣ Користувач дозволяє доступ

Authorization Server може показати:

TEXT
Application requests:

✓ Read your profile
✓ Read your calendar

            [Allow]

Користувач погоджується.

09

🎫 4️⃣ Application отримує Authorization Code

Authorization Server не обов'язково повертає access token прямо через browser redirect.

Він повертає короткоживучий:

TEXT
Authorization Code

Наприклад:

TEXT
https://application/callback
    ?code=abc123

Схема:

TEXT
Authorization Server
        │
        │ Authorization Code
        ▼
      Browser
        │
        ▼
    Application
10

🔄 5️⃣ Code обмінюється на Token

Application використовує authorization code для отримання токенів:

TEXT
Application
     │
     │ Authorization Code
     ▼
Authorization Server
     │
     │ Access Token
     ▼
Application

Після цього:

TEXT
Application
     │
     │ Access Token
     ▼
Resource API
11

🤔 Навіщо потрібен Authorization Code?

Може виникнути логічне питання:

↳
Навіщо весь цей обмін? Чому просто не повернути Access Token одразу?

Одна з причин — небажано передавати access token через browser redirect там, де можна цього уникнути.

Authorization Code:

  • короткоживучий;
  • одноразовий;
  • сам по собі ще не обов'язково достатній для отримання токена.

А сучасний flow додатково захищається за допомогою PKCE.

12

🔐 Що таке PKCE?

PKCE — Proof Key for Code Exchange.

Перед початком authorization flow Client генерує випадкове значення:

TEXT
code_verifier

Наприклад:

TEXT
x7Kp92mA...

З нього формується:

TEXT
code_challenge

Authorization Server отримує challenge на початку flow.

Пізніше, коли Application обмінює:

TEXT
Authorization Code

на:

TEXT
Access Token

він повинен надати правильний:

TEXT
code_verifier

У спрощеному вигляді:

TEXT
Client

code_verifier
     │
     ▼
code_challenge
     │
     ▼
Authorization Server

Потім:

TEXT
Authorization Code
        +
code_verifier
        │
        ▼
Authorization Server
        │
        ▼
   Access Token
13

🕵️ А що, якщо Authorization Code перехопили?

Уявімо:

TEXT
Authorization Server
       │
       │ code=ABC
       ▼
      Client

Зловмисник якимось чином перехопив:

TEXT
code=ABC

Без PKCE цього могло б бути достатньо для небезпечного сценарію залежно від типу клієнта та flow.

З PKCE Authorization Server додатково запитує:

TEXT
code_verifier

А його зловмисник не отримав.

Тому:

TEXT
code=ABC
+
wrong verifier

↓

❌ Token denied
14

🎯 Що таке Scope?

Тепер повернемось до головної ідеї OAuth.

Ми не хочемо сказати:

↳
«Цей Application може робити все від мого імені».

Ми хочемо видати конкретні дозволи.

Наприклад:

TEXT
calendar.read

або:

TEXT
orders.read
orders.write

Це і є scopes.

Наприклад, токен має:

TEXT
scope:

orders.read

Client викликає:

HTTP
GET /orders

API:

TEXT
✅ Allowed

А потім:

HTTP
DELETE /orders/123

API може сказати:

TEXT
❌ Forbidden

бо необхідного permission немає.

15

🎯 А що таке Audience?

Scope відповідає приблизно на питання:

↳
Що дозволено?

Audience:

↳
Для якого API призначений цей token?

Наприклад:

TEXT
aud = billing-api

Такий token не повинен автоматично приймати:

TEXT
admin-api

навіть якщо token:

TEXT
signature    ✅
expiration   ✅
issuer       ✅

Це напряму пов'язано з темою JWT, яку ми вже розбирали.

16

♻️ Refresh Token

Access Token зазвичай має обмежений lifetime.

Наприклад:

TEXT
15 minutes

Але ми не хочемо змушувати користувача логінитися кожні 15 хвилин.

Тому може використовуватися:

Refresh Token

Схематично:

TEXT
Access Token expired
        │
        ▼
Refresh Token
        │
        ▼
Authorization Server
        │
        ▼
New Access Token

Refresh Token — дуже цінний credential.

Якщо його викрали, зловмисник потенційно може отримувати нові Access Tokens.

Тому для refresh tokens важливі:

  • захищене зберігання;
  • rotation;
  • revoke;
  • контроль lifetime;
  • detection повторного використання там, де це підтримується.
17

🖥 А що, якщо користувача взагалі немає?

До цього ми розглядали:

TEXT
User
 ↓
Application
 ↓
API

Але в мікросервісній архітектурі часто маємо:

TEXT
Service A
    │
    ▼
Service B

Наприклад, Service A раз на годину отримує інформацію із Service B.

Ніякого користувача немає.

Тоді Authorization Code Flow нам не потрібен.

Для machine-to-machine сценаріїв часто використовується:

Client Credentials Flow

18

🤖 Client Credentials Flow

Service A має власну identity:

TEXT
client_id
+
credential

і звертається:

TEXT
Service A
    │
    ▼
Authorization Server
    │
    │ Access Token
    ▼
Service A
    │
    ▼
Service B

У цьому випадку Access Token представляє сам Service A, а не конкретного користувача.

Наприклад:

TEXT
Service A

scope:
orders.read

може читати orders із Service B.

Але:

TEXT
orders.delete

йому не дозволено.

Це знову принцип:

↳
Least Privilege
19

⚠️ Client Secret — це теж Secret

У Client Credentials часто можна побачити:

TEXT
client_id
client_secret

При цьому:

client_id — зазвичай не секрет.

А:

client_secret — credential, який потрібно захищати.

Його не варто класти в:

TEXT
Git ❌
appsettings.json ❌
Wiki ❌
Chat ❌
Logs ❌

Тут ми якраз приходимо до теми Secret Management, яку можна розібрати окремо.

20

🧠 OAuth не визначає формат Access Token

Ще одна поширена помилка:

↳
OAuth Token = JWT

Не обов'язково.

OAuth визначає механізм авторизації та використання токенів, але Access Token не зобов'язаний бути JWT.

Він може бути:

TEXT
JWT

або:

TEXT
Opaque Token

Наприклад:

TEXT
8F7A92BCE21...

Для Client це взагалі не повинно бути важливо.

Client має ставитися до Access Token як до credential, який потрібно передати Resource Server.

21

🚨 Не треба будувати authorization лише на Frontend

Уявімо:

TEXT
User role = USER

Frontend приховав кнопку:

TEXT
[DELETE USER]

Чудово.

А користувач відкриває Postman і викликає:

HTTP
DELETE /api/users/123

Якщо Backend думає:

↳
«Frontend же приховав кнопку»

маємо проблему.

Authorization повинен перевірятися там, де знаходиться захищений ресурс:

TEXT
API
 │
 ├── Validate token
 ├── Validate issuer
 ├── Validate audience
 ├── Validate lifetime
 └── Check permissions/scopes

Frontend controls — це UX.

Backend authorization — це security.

22

🧩 Збираємо все разом

Для користувацького сценарію:

TEXT
                 User
                  │
                  ▼
                Client
                  │
                  │ Authorization Request
                  ▼
         Authorization Server
                  │
                  │ Authorization Code
                  ▼
                Client
                  │
                  │ Code + PKCE
                  ▼
         Authorization Server
                  │
          ┌───────┴────────┐
          ▼                ▼
     Access Token       ID Token
          │                │
          │                └──→ Client
          │
          ▼
     Resource API

Для Service-to-Service:

TEXT
Service A
    │
    │ Client Credentials
    ▼
Authorization Server
    │
    │ Access Token
    ▼
Service A
    │
    │ Bearer Token
    ▼
Service B
23

🧠 Що варто запам'ятати

OAuth 2.0 — це не просто:

TEXT
«отримати JWT»

Його головна ідея:

↳
Дати Client обмежений доступ до ресурсу без передачі йому credentials власника ресурсу.

Корисно розділяти:

TEXT
OAuth 2.0
→ delegated authorization

OpenID Connect
→ authentication / identity

Access Token
→ для API

ID Token
→ для Client

Refresh Token
→ отримання нових Access Tokens

А також:

TEXT
Authorization Code + PKCE
→ типовий користувацький сценарій

Client Credentials
→ machine-to-machine

І найголовніше:

↳
Наявність валідного токена ще не означає, що можна виконувати будь-яку операцію.

API все одно повинен перевірити:

Хто видав token?

Для якого API він призначений?

Чи не закінчився його lifetime?

Які permissions/scopes він має?

І лише після цього вирішувати:

TEXT
ALLOW

або

DENY

🔐 Security Challenge

Ситуація №1

Frontend виконав login через OpenID Connect та отримав:

TEXT
ID Token
Access Token

Для виклику:

HTTP
GET /api/orders

розробник передає:

HTTP
Authorization: Bearer <ID_TOKEN>

❓ Що тут не так?

Ситуація №2

Є:

TEXT
Billing Service
      │
      ▼
Customer Service

Billing Service кожні 10 хвилин автоматично отримує інформацію про клієнтів.

Користувача в цьому процесі немає.

❓ Чи потрібен тут Authorization Code Flow?

❓ Який OAuth flow більше підходить для такого сценарію?

І найцікавіше

У нас є Access Token:

TEXT
signature   ✅
issuer      ✅
expiration  ✅
audience    ✅

Але token має:

TEXT
scope = orders.read

Клієнт виконує:

HTTP
DELETE /orders/123

❓ Що повинен відповісти API?

І головне питання для обговорення:

❓ Де у ваших системах сьогодні закінчується Authentication і починається Authorization — і чи завжди ця межа чітко визначена?
