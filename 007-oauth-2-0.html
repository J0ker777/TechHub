01

🔑 Як робили б без OAuth?

Уявімо застосунок Calendar Analytics, якому потрібно читати наш календар.

Найпростіша схема могла б виглядати так:

Calendar Analytics:

Microsoft Login:    ________
Microsoft Password: ________

Після цього:

Технічно працювати може.

Але тепер сторонній застосунок знає наш пароль.

Причому ми хотіли дати йому лише:

↳
«Читати календар»

а фактично передали credential, який потенційно відкриває значно більше можливостей.

OAuth пропонує інший підхід:

↳
Не передавати застосунку пароль. Передати йому обмежене право виконувати конкретні дії.
02

🎟 Замість пароля — Access Token

Схематично:

Application не отримує пароль користувача.

Він отримує:

Access Token

який може мати обмежені:

  • права;
  • ресурси;
  • audience;
  • термін життя.

Наприклад, умовно:

Token:

Resource: Calendar API
Permissions:
    calendar.read

Expires:
    15 minutes

Це набагато безпечніше, ніж передавати сторонньому застосунку пароль.

  • автентифікує користувача;

  • видає токени.

API, де знаходяться ресурси.

🤔 Навіщо потрібен Authorization Code?

Може виникнути логічне питання:

↳
Навіщо весь цей обмін? Чому просто не повернути Access Token одразу?

🔐 Що таке PKCE?

PKCE — Proof Key for Code Exchange.

Перед початком authorization flow Client генерує випадкове значення:

З нього формується:

code_challenge

Authorization Server отримує challenge на початку flow.

🎯 Що таке Scope?

Тепер повернемось до головної ідеї OAuth.

Ми не хочемо сказати:

↳
«Цей Application може робити все від мого імені».

Ми хочемо видати конкретні дозволи.

Наприклад:

calendar.read

або:

orders.read
orders.write

Це і є scopes.

Наприклад, токен має:

scope:

orders.read

Client викликає:

HTTP
GET /orders

API:

✅ Allowed

А потім:

HTTP
DELETE /orders/123

API може сказати:

❌ Forbidden

бо необхідного permission немає.

🎯 А що таке Audience?

Scope відповідає приблизно на питання:

↳
Що дозволено?

Audience:

↳
Для якого API призначений цей token?

Наприклад:

aud = billing-api

Такий token не повинен автоматично приймати:

admin-api

навіть якщо token:

signature    ✅
expiration   ✅
issuer       ✅

Це напряму пов'язано з темою JWT, яку ми вже розбирали.

16

♻️ Refresh Token

Access Token зазвичай має обмежений lifetime.

Наприклад:

15 minutes

Але ми не хочемо змушувати користувача логінитися кожні 15 хвилин.

Тому може використовуватися:

Refresh Token

Схематично:

Refresh Token — дуже цінний credential.

Якщо його викрали, зловмисник потенційно може отримувати нові Access Tokens.

Тому для refresh tokens важливі:

  • захищене зберігання;
  • rotation;
  • revoke;
  • контроль lifetime;
  • detection повторного використання там, де це підтримується.

20

🧠 OAuth не визначає формат Access Token

Ще одна поширена помилка:

↳
OAuth Token = JWT

Не обов'язково.

OAuth визначає механізм авторизації та використання токенів, але Access Token не зобов'язаний бути JWT.

Він може бути:

JWT

або:

Opaque Token

Наприклад:

8F7A92BCE21...

Для Client це взагалі не повинно бути важливо.

Client має ставитися до Access Token як до credential, який потрібно передати Resource Server.

Словник термінів простими словами

  • OAuth 2.0 — протокол делегованої авторизації: застосунок отримує обмежений доступ без пароля користувача.
  • Client — застосунок, який просить доступ.
  • Authorization Server — система, що входить користувача, отримує згоду й видає токени.
  • Resource Server — API, яке приймає access token і захищає дані.
  • Access Token — короткоживучий дозвіл для виклику API.
  • Authorization Code — одноразовий проміжний код, який client обмінює на токени.
  • PKCE — доказ, що код обмінює той самий client, який почав авторизацію.
  • Scope — перелік дозволених дій; audience — API, для якого видано токен.
  • Refresh Token — довгоживучий секрет для отримання нових access tokens.
  • Bearer Token — токен, право використання якого має той, хто ним володіє.
  • Client Credentials — сценарій доступу сервісу до сервісу без користувача.
  • OpenID Connect додає до OAuth автентифікацію та ID Token з інформацією для client.
  • Client Secret — секрет застосунку, який не можна безпечно зберігати у frontend або мобільному клієнті.
24

👶 Якщо зовсім просто

OAuth дозволяє дати застосунку окрему перепустку замість пароля користувача. Перепустка має конкретні дозволи, призначена певному API й діє обмежений час.

У користувацькому сценарії браузер переходить до authorization server. Після входу client отримує одноразовий code, доводить через PKCE, що саме він почав процес, і обмінює code на access token.

API самостійно перевіряє підпис, issuer, audience, строк дії та scopes. ID token потрібен client-у для інформації про вхід, access token — API для дозволу на дію, refresh token — для безпечного оновлення доступу.
