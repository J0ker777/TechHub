Вступ

Уявімо типову архітектуру:

Service A отримує запит користувача, але для його виконання послідовно звертається до інших сервісів.

Все працює чудово.

А потім Service D перестає відповідати.

Здавалося б, впав один сервіс. Але проблема може дуже швидко поширитися на всю систему.

01

💥 Як починається каскадна відмова

Service C викликає Service D і чекає відповіді.

D не відповідає.

C продовжує чекати.

У цей момент Service B чекає на C, Service A — на B, а клієнт — на A.

Отримуємо:

Поки всі чекають, продовжують приходити нові запити.

Вони займають:

  • connections;
  • threads;
  • memory;
  • connection pool;
  • інші ресурси сервісів.

Через деякий час проблема вже не тільки в Service D.

C починає задихатися. Потім B. Потім A.

Один недоступний компонент може поступово покласти всю систему.

⏱ Timeout

Перше очевидне рішення — не чекати нескінченно.

Наприклад:

C → D timeout = 2 sec

Якщо D не відповів за дві секунди — C припиняє очікування.

Але тут виникає цікаве питання.

Припустимо:

Client timeout = 10 sec A → B = 8 sec B → C = 8 sec C → D = 8 sec

Чи має така конфігурація сенс?

Якщо кожен наступний рівень може чекати стільки ж або довше, ніж попередній, верхній рівень може вже давно завершити запит, тоді як нижні сервіси продовжують виконувати непотрібну роботу.

Тому timeout — це не просто випадкове число в конфігурації. Їх потрібно розглядати як частину загального time budget запиту.

🔁 А давайте зробимо Retry

Service D не відповів?

Спробуємо ще раз.

Звучить логічно:

request → timeout → retry → retry → retry

Але припустимо, що одночасно є 1 000 запитів.

Якщо кожен зробить ще три спроби, проблемний Service D потенційно отримає вже до:

4 000 спроб замість 1 000.

Сервіс, який і так має проблеми, отримує ще більше навантаження.

Так виникає retry storm.

Тому нормальний retry зазвичай потребує:

Exponential backoff

1s → 2s → 4s → 8s

і jitter — невеликої випадкової затримки, щоб тисячі клієнтів не повторювали запити одночасно.

І ще важливіше: retry доречний далеко не для кожної операції. Повторний POST, наприклад, може створити дубль, якщо операція не є idempotent.

🔌 Circuit Breaker

Наступний механізм — Circuit Breaker.

Якщо ми вже бачимо, що Service D стабільно не відповідає, навіщо кожному новому запиту чекати timeout?

Circuit Breaker може перейти в стан:

і тимчасово перестати відправляти запити до D.

Замість:

request → D → 5 sec → timeout

отримуємо:

request → Circuit Breaker → fail fast

Через певний час можна дозволити кілька тестових запитів:

Якщо D відновився:

і нормальна робота продовжується.

🛟 Але чи обов'язково падати взагалі?

Ось тут з'являється ще цікавіше архітектурне питання.

Припустимо, Service D відповідає за рекомендації товарів.

Чи потрібно через його недоступність повертати користувачу:

500 Internal Server Error

для всієї сторінки?

Можливо, правильніше показати сторінку без рекомендацій.

Це називається graceful degradation.

Система працює з обмеженою функціональністю, але основний бізнес-процес залишається доступним.

02

Словник термінів простими словами

  • Distributed system — система з кількох компонентів, які спілкуються мережею.
  • Dependency — сервіс або ресурс, потрібний іншому сервісу для роботи.
  • Cascading failure — збій залежності, який через очікування й навантаження поширюється далі.
  • Timeout — максимальний час очікування; time budget — час для всього ланцюжка.
  • Retry — повторна спроба тимчасово невдалої операції.
  • Exponential backoff збільшує паузу між повторами; jitter додає випадкове зміщення.
  • Retry storm — хвиля повторів, яка додатково перевантажує проблемний сервіс.
  • Idempotency — безпечне повторення операції без нового побічного ефекту.
  • Circuit Breaker тимчасово припиняє виклики несправної залежності.
  • Fail fast — швидке завершення замість довгого очікування.
  • Graceful degradation — обмежена робота замість повної відмови.
03

👶 Якщо зовсім просто

Якщо A чекає B, B чекає C, а C чекає D, то падіння D утримує ресурси всього ланцюжка. Нові запити накопичуються, і один збій може зупинити всі сервіси.

Timeout обмежує очікування, retry повторює тимчасову помилку, а circuit breaker перестає надсилати запити туди, де вже стабільно немає відповіді. Їх потрібно узгоджувати для всього ланцюжка.

Якщо залежність не критична, система може показати результат без додаткової функції. Це часто корисніше, ніж повна помилка.

🧠 Що в результаті?

У distributed system недостатньо думати:

«Що робить мій сервіс?»

Потрібно також думати:

«Що зробить мій сервіс, коли залежність перестане працювати?»

Саме тому timeout, retry, circuit breaker та graceful degradation — це не просто технічні налаштування.

Це частина архітектури системи.

Іноді найкраща реакція на проблему іншого сервісу — не намагатися врятувати його нескінченними retry, а швидко визнати його недоступним і продовжити працювати без нього.
