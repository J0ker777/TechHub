01

1. Чому одного логіна й пароля вже недостатньо

Уявімо звичайну корпоративну IT-інфраструктуру.

Співробітник користується Microsoft 365, внутрішнім порталом, системою документообігу, кількома бізнес-застосунками та мобільним додатком.

Якби кожна система самостійно відповідала за авторизацію, виникли б питання:

  • Де зберігати паролі?
  • Хто контролюватиме складність паролів?
  • Як забезпечити багатофакторну автентифікацію?
  • Що робити, якщо співробітник звільнився?
  • Як відкликати доступ одразу до всіх систем?
  • Як одному сервісу безпечно звернутися до іншого?

Можна реалізувати всі ці механізми окремо в кожній системі. Але тоді компанія отримає десятки реалізацій безпеки, кожну з яких доведеться розробляти, підтримувати й перевіряти.

Microsoft Entra ID вирішує значну частину цієї проблеми централізовано.

Microsoft Entra ID — хмарна система керування цифровими ідентичностями та доступом, або IAM (Identity and Access Management).

Вона допомагає системам визначати:

  • хто намагається увійти;
  • чи вдалося підтвердити його особу;
  • чи відповідає вхід політикам безпеки;
  • для якого застосунку або API видається токен;
  • які дозволи можна передати застосунку.

Але тут є принциповий нюанс.

Entra ID не обов'язково знає, чи може конкретний співробітник погодити заявку на 100 000 грн або переглянути дані іншого підрозділу.

Такі рішення часто повинна приймати сама бізнес-система.

Саме на цій межі між корпоративною ідентифікацією та бізнес-авторизацією і побудована сучасна архітектура доступу.

02

2. Entra ID, Active Directory та LDAP — це не одне й те саме

Перш ніж розбирати токени, потрібно усунути поширену плутанину.

Багато хто пам'ятає Azure Active Directory (Azure AD). Це попередня назва Microsoft Entra ID.

Але класичний Active Directory Domain Services (AD DS) — інша технологія.

ТехнологіяОсновне призначення
Active Directory Domain ServicesКерування доменними користувачами, комп'ютерами, групами та ресурсами локальної інфраструктури
LDAP / LDAPSПротокол доступу до служб каталогів; LDAPS — захищене TLS-з'єднання
Microsoft Entra IDХмарна ідентифікація, сучасні протоколи входу, керування доступом до застосунків та API
Entra Connect / Cloud SyncСинхронізація ідентичностей між локальним AD та Entra ID

Класичний AD широко використовує Kerberos та LDAP. Entra ID для сучасних застосунків використовує, зокрема, OpenID Connect, OAuth 2.0 і SAML.

Це не означає, що одна технологія повністю замінює іншу.

Наприклад, компанія може використовувати:

  • локальний AD для доменної інфраструктури;
  • Entra ID для Microsoft 365 та вебзастосунків;
  • синхронізацію облікових записів між ними.

Такий підхід називають Hybrid Identity (гібридна ідентифікація).

↳
Важливо: Microsoft Entra ID — не звичайний LDAP-сервер у хмарі. Не варто очікувати, що будь-який старий застосунок, який працює через LDAP, можна без змін переключити на Entra ID.
03

3. Хто відповідає за вхід, а хто — за права?

Тут потрібно розділити два поняття.

Authentication (автентифікація) — процес перевірки того, ким є користувач або сервіс.

Authorization (авторизація) — визначення того, що цьому користувачу або сервісу дозволено робити.

Приклад:

Співробітник успішно увійшов у корпоративний застосунок через Entra ID.

Це означає, що його особу підтверджено.

Але чи може він:

  • переглядати фінансові документи;
  • редагувати інформацію про клієнтів;
  • створювати нові заявки;
  • затверджувати операції;
  • відкривати адміністративну панель?

Успішний вхід сам по собі цього не визначає.

Проста аналогія: Entra ID допомагає перевірити службове посвідчення, а конкретна система вирішує, до яких кабінетів власник цього посвідчення може заходити.

Причому Entra ID також може передавати ролі та дозволи. Але остаточна перевірка доступу до конкретного бізнес-об'єкта повинна відбуватися там, де цей об'єкт захищається.

Authentication ≠ Authorization.

Це один із найважливіших принципів усієї статті.

04

4. Основні компоненти Microsoft Entra ID

Для розробника важливо знати не всі можливості адміністративної панелі, а кілька ключових понять.

ПоняттяЩо означає
TenantОкремий каталог організації в Entra ID
Tenant IDУнікальний ідентифікатор цього каталогу
UserЦифрова ідентичність користувача
GroupОб'єднання користувачів для централізованого керування
App RegistrationОпис ідентичності та налаштувань застосунку
Client IDУнікальний ідентифікатор зареєстрованого застосунку
Service PrincipalПредставлення застосунку як ідентичності в конкретному tenant
ScopeДелегований дозвіл на доступ до API
App RoleРоль, яку може використовувати застосунок для авторизації користувачів або сервісів
Enterprise ApplicationАдміністративне представлення застосунку через його Service Principal

Що таке Tenant?

Tenant — це логічна межа корпоративного каталогу.

У ньому зберігається інформація про користувачів, групи, зареєстровані застосунки, сервісні ідентичності та політики.

У великих компаній може бути кілька tenant, хоча часто достатньо одного корпоративного.

App Registration та Enterprise Application

Ці два поняття особливо часто плутають.

App Registration описує, як застосунок інтегрується з платформою ідентифікації: його Client ID, підтримувані типи облікових записів, Redirect URI, API permissions, scopes, app roles та credentials.

Enterprise Application представляє конкретний екземпляр застосунку в tenant через Service Principal. Тут можна керувати призначеннями, дозволами та доступом у цьому каталозі.

Простіше кажучи:

  • App Registration — опис застосунку.
  • Service Principal — його ідентичність у конкретній організації.

Для багатокористувацьких за організаціями (multitenant) застосунків один Application Object може мати Service Principal у різних tenant.

05

5. Як працює вхід користувача

Розглянемо приклад.

Компанія розробила корпоративний вебзастосунок для перегляду інформації про технологічні відключення.

Застосунок складається з:

  • React frontend;
  • ASP.NET Core backend;
  • REST API;
  • бази даних Microsoft SQL Server;
  • API Gateway;
  • зовнішнього захисту через WAF (Web Application Firewall — міжмережевий екран вебзастосунків).

Користувач відкриває систему, але вона не має власної форми для введення корпоративного пароля.

Замість цього вона використовує Microsoft Entra ID.

Це спрощена схема, яка показує логічну послідовність. Насправді між frontend та Entra ID відбувається окремий протокольний обмін.

Що відбувається покроково

Крок 1. Користувач відкриває React-застосунок.

Крок 2. Застосунок визначає, що користувач ще не пройшов автентифікацію.

Крок 3. Браузер перенаправляється на Microsoft Entra ID.

Крок 4. Entra ID автентифікує користувача. Якщо він уже має відповідну корпоративну сесію, повторне введення пароля може не знадобитися.

Крок 5. Перевіряються застосовні політики доступу. Наприклад, може знадобитися MFA.

Крок 6. Через стандартний протокольний механізм застосунок отримує необхідні токени.

Крок 7. Frontend виконує HTTP-запит до власного backend з Access Token.

Крок 8. Backend перевіряє токен, необхідні дозволи та бізнес-права.

Крок 9. Якщо всі перевірки успішні, система повертає дані.

Зверніть увагу: API не отримує пароль користувача і не повинен його запитувати.

Саме в цьому одна з головних переваг централізованої автентифікації.

06

6. Як саме застосунок отримує токен

Для сучасних Single Page Application (SPA — односторінкових вебзастосунків), зокрема React, типовий рекомендований механізм — Authorization Code Flow with PKCE.

PKCE — Proof Key for Code Exchange (доказ володіння ключем під час обміну коду авторизації).

Принцип такий:

  1. Застосунок формує запит на авторизацію та PKCE-параметри.
  2. Браузер відкриває Microsoft Entra ID.
  3. Після успішного входу застосунок отримує короткоживучий authorization code.
  4. Код обмінюється на токени з використанням PKCE.
  5. Access Token використовується для виклику потрібного API.

PKCE допомагає захистити процес обміну коду авторизації.

Для реалізації зазвичай використовують MSAL — Microsoft Authentication Library (бібліотека автентифікації Microsoft).

Чому не можна використовувати Client Secret у React?

Тому що код браузерного застосунку доступний користувачу.

Якщо додати Client Secret до JavaScript, його можна буде отримати з клієнтського коду або мережевих запитів.

SPA належить до категорії Public Client — клієнтів, які не можуть гарантовано зберігати секрет.

Серверний застосунок, здатний безпечно зберігати credentials, може працювати як Confidential Client.

Для систем із підвищеними вимогами до безпеки також варто розглянути Backend for Frontend (BFF) — архітектуру, у якій токени залишаються на серверній стороні, а браузер використовує захищену сесію.

07

7. SSO, MFA та Conditional Access

Три механізми, які часто згадують разом, вирішують різні задачі.

SSO — Single Sign-On

SSO (єдиний вхід) дозволяє користувачу працювати з кількома застосунками без постійного повторного введення облікових даних.

Але SSO не означає, що повторна перевірка ніколи не знадобиться.

Вона може бути викликана політикою, зміною умов доступу або необхідністю сильнішої автентифікації.

MFA — Multi-Factor Authentication

MFA (багатофакторна автентифікація) вимагає додаткового підтвердження особи.

Наприклад, за допомогою застосунку-автентифікатора або іншого дозволеного організацією способу.

Conditional Access — умовний доступ

Conditional Access дозволяє враховувати умови входу:

  • хто входить;
  • до якого ресурсу;
  • з якого пристрою;
  • з якої мережі або місця;
  • який ризик пов'язаний із входом.

Приклад політики:

↳
Для доступу до корпоративної адміністративної системи користувач повинен пройти MFA, а пристрій — відповідати вимогам організації.

Але ці механізми не працюють автоматично в кожному застосунку лише тому, що використовується Entra ID.

Політики потрібно правильно налаштувати, а частина можливостей залежить від ліцензування.

Важливо: Conditional Access не замінює перевірку бізнес-прав усередині API.

08

8. ID Token, Access Token та Refresh Token

Це ключова частина теми.

Microsoft Entra ID може видавати різні типи токенів, і кожен має власне призначення.

ТипДля чого потрібен
ID TokenПередає клієнтському застосунку інформацію про результат автентифікації користувача
Access TokenНадається конкретному захищеному ресурсу, наприклад API
Refresh TokenДозволяє отримувати нові токени без повторного повного входу, відповідно до політик платформи

Типова помилка

Розробник отримує ID Token і починає передавати його до backend як доказ права на виконання API-операцій.

Це неправильна модель.

ID Token призначений для клієнта, а не для авторизації викликів довільного API.

Backend повинен приймати Access Token, призначений саме для цього API.

Що містить Access Token

Для власного API Entra ID може видати Access Token у форматі JWT — JSON Web Token.

Приклад його декодованої частини payload:

JSON
{
  "aud": "22222222-2222-2222-2222-222222222222",
  "iss": "https://login.microsoftonline.com/11111111-1111-1111-1111-111111111111/v2.0",
  "tid": "11111111-1111-1111-1111-111111111111",
  "oid": "44444444-4444-4444-4444-444444444444",
  "azp": "33333333-3333-3333-3333-333333333333",
  "scp": "Outages.Read",
  "exp": 1791900000,
  "ver": "2.0"
}

Ідентифікатори вигадані, а приклад показує лише частину можливих claims (тверджень про ідентичність або дозволи).

Розберемо основні:

  • aud — Audience: API, для якого видано токен.
  • iss — Issuer: хто видав токен.
  • tid — Tenant ID: каталог організації.
  • oid — Object ID: ідентифікатор об'єкта користувача в tenant.
  • azp — Authorized Party: ідентифікатор клієнтського застосунку у v2-токенах.
  • scp — Scopes: делеговані дозволи.
  • exp — час завершення дії токена.
  • ver — версія формату токена.

Не всі claims гарантовано присутні в кожному типі токена.

Окремий важливий момент: для надійного зв'язування користувача із записами у власній БД зазвичай використовують стабільні ідентифікатори в контексті tenant, наприклад пару tid + oid, а не email.

Email може змінитися. Крім того, однакові за змістом дані облікового запису не означають однакову ідентичність у різних tenant.

09

9. Як backend розуміє, що токен справжній

Розглянемо запит:

HTTP
GET /api/outages?companyId=15 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
Accept: application/json

У заголовку Authorization передається Access Token.

Backend не повинен просто декодувати JWT і довіряти його вмісту.

Декодування Base64URL ще не означає, що токен справжній.

Сервер має перевірити:

  1. Криптографічний підпис.
  2. Довіреного issuer (iss).
  3. Призначення токена (aud).
  4. Термін дії (exp) та інші часові обмеження.
  5. Допустимий tenant.
  6. Необхідні scopes або app roles.
  7. Права доступу до конкретної операції та даних.

Звідки API бере ключ перевірки?

Microsoft Entra ID використовує асиметричні цифрові підписи.

Для перевірки серверу не потрібен секретний ключ Microsoft.

Публічні ключі доступні через JWKS — JSON Web Key Set (набір публічних криптографічних ключів).

Метадані постачальника ідентифікації можна отримати через OpenID Connect Discovery:

https://login.microsoftonline.com/{tenant-id}/v2.0/.well-known/openid-configuration

У відповіді буде, зокрема, jwks_uri — адреса набору ключів.

Бібліотеки автентифікації зазвичай самостійно отримують, кешують та оновлюють ці метадані.

Тому API не повинен відправляти запит до Microsoft Entra ID для перевірки кожного JWT.

Водночас потрібно враховувати ротацію ключів, недоступність сервісу метаданих та особливості кешування.

І ще один нюанс: клієнтський застосунок не повинен намагатися самостійно інтерпретувати Access Token для Microsoft Graph або іншого стороннього API. Формат токена контролює його цільовий ресурс.

10

10. Scope, App Role та Group: чим вони відрізняються

Уявімо, що ми розробляємо API для системи відключень.

Хочемо дозволити:

  • операторам читати інформацію;
  • диспетчерам редагувати інциденти;
  • сервісам імпортувати нові відключення.

Можна використати різні механізми дозволів.

Scope — делегований доступ

Наприклад:

Outages.Read

Це означає, що клієнт отримав делегований дозвіл викликати певну функціональність API від імені користувача.

Але scope сам по собі не доводить, що користувач має право бачити всі дані.

App Role — роль застосунку

Наприклад:

Outages.Dispatcher

Роль можна призначити користувачу або групі, якщо вона визначена для такого використання.

Також можна визначити роль для сервісного застосунку:

Outages.Import

У відповідному токені призначені ролі можуть передаватися в claim roles.

Group — корпоративна група

Наприклад:

Dispatchers-West

Група може використовуватися для централізованого призначення доступу або ролей.

Але групи не завжди потрібно передавати безпосередньо в токені.

У великих організаціях користувач може входити в сотні груп. Через обмеження розміру токена Entra ID іноді передає спеціальну ознаку замість повного списку. Тоді застосунку може знадобитися отримати членство через Microsoft Graph.

Практичний висновок:

Scopes описують делеговані дозволи, app roles — ролі та дозволи в контексті застосунку, а groups — організаційні об'єднання.

Жоден із цих механізмів автоматично не замінює правила доступу до конкретних бізнес-даних.

11. Практична реалізація в ASP.NET Core

Подивимося, як це виглядає в .NET.

Припустімо, ми створили App Registration для backend API та налаштували делегований дозвіл Outages.Read.

Для інтеграції використовуємо бібліотеку Microsoft.Identity.Web.

Встановлення:

BASH
dotnet add package Microsoft.Identity.Web

Приклад конфігурації appsettings.json:

JSON
{
  "AzureAd": {
    "Instance": "https://login.microsoftonline.com/",
    "TenantId": "11111111-1111-1111-1111-111111111111",
    "ClientId": "22222222-2222-2222-2222-222222222222",
    "Audience": "22222222-2222-2222-2222-222222222222"
  }
}

Ідентифікатори наведені лише як приклад. ClientId і Audience тут належать API, а не frontend-застосунку.

У Program.cs налаштовуємо автентифікацію:

CSHARP
using Microsoft.AspNetCore.Authentication.JwtBearer;
using Microsoft.Identity.Web;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(
        builder.Configuration.GetSection("AzureAd"));

builder.Services.AddAuthorization();
builder.Services.AddControllers();

var app = builder.Build();

app.UseAuthentication();
app.UseAuthorization();

app.MapControllers();

app.Run();

Бібліотека виконує стандартну перевірку токенів відповідно до конфігурації.

Тепер захистимо endpoint.

CSHARP
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;
using Microsoft.Identity.Web;

[ApiController]
[Route("api/outages")]
[Authorize]
public class OutagesController : ControllerBase
{
    [HttpGet]
    [RequiredScope("Outages.Read")]
    public IActionResult Get()
    {
        return Ok(new
        {
            message = "Access granted"
        });
    }
}

Тут є два рівні перевірки:

  • [Authorize] — запит повинен бути автентифікованим.
  • [RequiredScope("Outages.Read")] — Access Token повинен містити потрібний делегований дозвіл.

Але це ще не повноцінна бізнес-авторизація.

Якщо endpoint повертає відключення конкретного підрозділу, потрібно додатково перевірити, чи має користувач доступ саме до цього підрозділу.

Наприклад, окремий сервіс авторизації може зіставляти tid і oid із внутрішніми правилами доступу.

Цю перевірку необхідно виконувати на backend, незалежно від того, які підрозділи дозволяє вибрати frontend.

↳
Важливо: наведений код демонструє сценарій користувацького доступу через scope. Для сервісного виклику без користувача потрібна перевірка application permissions, зазвичай через app roles, або явно спроєктована інша модель авторизації.

12. А як один сервіс звертається до іншого без користувача?

У корпоративних системах далеко не всі операції запускає людина.

Наприклад:

  • фоновий сервіс отримує дані із зовнішньої системи;
  • планувальник синхронізує довідники;
  • мікросервіс надсилає інформацію до Microsoft Graph;
  • інтеграційний компонент викликає інший API.

У такому випадку застосунок може автентифікуватися від власного імені.

Для цього часто використовують OAuth 2.0 Client Credentials Flow.

Тут немає користувача, який вводить пароль.

Замість цього сервіс підтверджує власну ідентичність.

Як сервіс підтверджує себе?

Основні варіанти:

СпосібОсобливості
Client SecretПростий, але потребує безпечного зберігання та ротації
CertificateДозволяє використовувати криптографічне підтвердження ідентичності
Federated CredentialДозволяє довіряти токенам іншого налаштованого постачальника ідентифікації
Managed IdentityAzure керує сервісною ідентичністю без необхідності зберігати власний секрет у коді

Для production-систем Microsoft рекомендує надавати перевагу сертифікатам або федеративним credentials перед звичайними Client Secrets.

Якщо сервіс працює в підтримуваному Azure-середовищі, Managed Identity часто є зручнішим варіантом.

Але Managed Identity не є універсальною заміною App Registration для будь-якого локального сервера або IIS.

Чим Client Credentials відрізняється від користувацького входу?

У користувацькому сценарії API працює від імені користувача.

У Client Credentials API отримує ідентичність самого застосунку.

Наприклад, сервіс OutageImporter може мати дозвіл Outages.Import, але не повинен автоматично отримувати адміністративний доступ до всіх функцій системи.

А якщо backend повинен викликати ще один API від імені користувача?

Для цього існує On-Behalf-Of Flow (OBO) — обмін токена на інший токен для downstream API зі збереженням користувацького контексту.

Передавати той самий Access Token до будь-якого іншого API не можна: токени призначені конкретним ресурсам.

13

13. Найнебезпечніша помилка: валідний JWT означає повний доступ

Розглянемо реалістичний сценарій.

Компанія має систему, у якій кожен користувач бачить дані лише своєї регіональної компанії.

Frontend показує користувачу тільки дозволені значення у фільтрі.

Але backend перевіряє лише JWT і scope.

Нормальна робота

Оператор компанії №15 виконує запит:

HTTP
GET /api/outages?companyId=15 HTTP/1.1
Authorization: Bearer <access_token>

Отримує дані своєї компанії.

Вразлива реалізація

Backend має приблизно таку логіку:

CSHARP
[Authorize]
[RequiredScope("Outages.Read")]
[HttpGet]
public IActionResult Get(int companyId)
{
    return Ok(
        repository.GetOutages(companyId)
    );
}

Здається, що все захищено.

Користувач автентифікований, токен валідний, scope присутній.

Як виникає проблема

Користувач змінює параметр запиту:

HTTP
GET /api/outages?companyId=27 HTTP/1.1
Authorization: Bearer <access_token>

Якщо backend не перевіряє доступ до компанії №27, користувач отримує чужі дані.

Цей клас проблем належить до Broken Object Level Authorization (BOLA) — порушення авторизації на рівні конкретного об'єкта. У вебзастосунках подібні проблеми також часто називають IDOR.

Правильна реалізація

Backend повинен:

  1. Перевірити JWT.
  2. Перевірити scope.
  3. Визначити користувача.
  4. Отримати його бізнес-права.
  5. Перевірити, чи дозволений доступ до companyId=27.
  6. Повернути дані лише після успішної перевірки.

Для цього можна використовувати власну таблицю дозволів, централізований сервіс авторизації або іншу погоджену модель доступу.

Важливо, щоб джерелом істини був серверний контроль, а не список значень у браузері.

Прихована кнопка ≠ заборонена операція.

Валідний JWT ≠ повний доступ до бізнес-даних.

14

14. Що відбувається після звільнення співробітника?

Ще одна поширена помилка — очікування, що блокування користувача в Entra ID миттєво зупинить усі запити до кожної внутрішньої системи.

Насправді ситуація складніша.

Access Token зазвичай має обмежений термін дії.

Поки токен дійсний, API, яке перевіряє лише його підпис та claims, може продовжувати приймати запити.

Навіть якщо обліковий запис користувача вже заблоковано.

Це пояснюється тим, що JWT часто перевіряється локально, без звернення до Entra ID під час кожного API-запиту.

Для підтримуваних сценаріїв Microsoft реалізує Continuous Access Evaluation (CAE) — безперервне оцінювання доступу, що дозволяє реагувати на важливі події та зміни політик швидше, ніж звичайне очікування завершення токена.

Але не можна вважати, що CAE автоматично працює для кожного самописного API.

Для критичних бізнес-операцій варто окремо продумати:

  • як швидко відкликаються бізнес-права;
  • як часто оновлюються кеші доступу;
  • як обробляється блокування користувача;
  • чи потрібна додаткова серверна перевірка статусу;
  • що робити з активними сесіями;
  • як поводитися з довготривалими операціями.

Деактивація облікового запису та негайне припинення кожної вже авторизованої операції — не завжди одна подія.

15. Типові проблеми в production

Навіть правильна інтеграція з Entra ID може працювати нестабільно через помилки конфігурації.

ПроблемаМожлива причина
401 UnauthorizedВідсутній, недійсний або прострочений токен
403 ForbiddenТокен прийнято, але бракує необхідних дозволів
invalid audienceПередали токен для іншого API
invalid issuerНеправильний tenant або конфігурація довіри
Redirect URI mismatchАдреса повернення не збігається із зареєстрованою
Користувач не може ввійтиConditional Access, MFA або інші обмеження
Сервіс припинив працюватиЗакінчився термін дії Client Secret чи сертифіката
Немає потрібної роліНеправильно налаштовані app roles або призначення
Немає списку груп у токеніСпрацював механізм groups overage
Помилки перевірки JWTПроблеми з issuer, audience, метаданими або ротацією ключів

Окремо потрібно враховувати вплив API Gateway і reverse proxy.

Вони можуть виконувати частину перевірок, але не повинні випадково видаляти або підміняти заголовок Authorization.

Також не варто автоматично довіряти заголовкам на кшталт X-User-Id, якщо їх може встановити зовнішній клієнт.

Що логувати?

Корисно фіксувати:

  • ідентифікатор запиту;
  • ідентифікатор tenant;
  • ідентифікатор користувача або сервісу;
  • результат автентифікації;
  • причину відмови в доступі;
  • endpoint та тип операції.

При цьому не можна записувати повні Access Tokens, Refresh Tokens, Client Secrets або приватні ключі у звичайні журнали.

Для аналізу проблем входу корисні також журнали Sign-in Logs у Microsoft Entra ID.

Важлива перевірка

Спробуйте виконати API-запит із коректним токеном, але зміненим ідентифікатором бізнес-об'єкта.

Саме цей сценарій часто знаходить серйозні помилки, які неможливо виявити простим тестуванням UI.

Також варто перевірити:

  • чи справді backend перевіряє потрібний aud;
  • чи не приймає API ID Token замість Access Token;
  • чи не покладається авторизація лише на frontend;
  • чи не надається сервісам зайвий доступ;
  • чи не потрапляють токени в логи;
  • чи працює ротація credentials;
  • чи зрозуміло поводиться система під час недоступності Entra ID або його метаданих.

17. Що повинні знати різні ролі в команді

PM / PO

Важливо розуміти:

  • які системи використовують централізовану автентифікацію;
  • хто відповідає за налаштування доступів;
  • які залежності існують від корпоративної інфраструктури;
  • що відбувається при звільненні співробітників;
  • які вимоги до MFA, доступності та аудиту потрібно закласти.

BA / системний аналітик

Потрібно чітко визначити:

  • які користувачі та сервіси працюють із системою;
  • які є ролі;
  • хто може виконувати кожну операцію;
  • чи залежить доступ від підрозділу, компанії або власника об'єкта;
  • що відбувається при зміні ролі чи блокуванні користувача.

Вимога «авторизація через Entra ID» сама по собі недостатня для опису повноцінної безпеки системи.

QA

Потрібно перевіряти позитивні, негативні та міжрольові сценарії.

Особливо важливі перевірки прав доступу до конкретних даних, поведінки після зміни дозволів і недопущення обходу обмежень через прямі API-запити.

Developer

Потрібно розуміти:

  • різницю між ID Token та Access Token;
  • JWT і його перевірку;
  • issuer, audience, scopes та app roles;
  • OAuth 2.0 і OpenID Connect;
  • безпечну роботу з credentials;
  • відмінність користувацького та сервісного доступу;
  • необхідність бізнес-авторизації на backend.

DevOps / Infrastructure / Security

Важливі питання:

  • налаштування tenant та App Registrations;
  • керування секретами й сертифікатами;
  • автоматизована ротація;
  • права Service Principals;
  • інтеграція з Azure Key Vault або корпоративним Vault;
  • журналювання без витоку токенів;
  • Conditional Access, MFA та контроль доступу;
  • налаштування reverse proxy і передачі заголовків.

19. Якщо зовсім просто

Уявімо велику компанію з єдиною прохідною та багатьма приміщеннями.

Microsoft Entra ID — це централізована система, яка допомагає перевірити, хто ви, і за яких умов можна надати вам доступ.

SSO дозволяє не проходити однакову перевірку заново в кожній системі.

MFA додає ще один спосіб підтвердити особу.

Access Token — це цифрове підтвердження, призначене конкретному сервісу.

API перевіряє, чи справжнє це підтвердження та які дозволи воно містить.

Але остаточне рішення, чи можете ви відкрити конкретний документ, змінити заявку або переглянути дані іншого підрозділу, часто залишається за бізнес-застосунком.

Entra ID допомагає встановити, хто звертається до системи та які дозволи передано. А сама система повинна правильно застосовувати ці дозволи до власних даних.

Microsoft Entra ID — не просто сервіс входу через корпоративний обліковий запис.

Це важливий компонент архітектури ідентифікації та доступу сучасних enterprise-систем.

Він дозволяє централізувати автентифікацію користувачів, підтримувати SSO та MFA, застосовувати політики доступу й забезпечувати захищену взаємодію між застосунками та API.

Проте головна архітектурна помилка — вважати, що інтеграція з Entra ID автоматично вирішує всі питання безпеки.

Правильна модель складається з трьох рівнів:

  1. Підтвердження ідентичності — хто звертається.
  2. Перевірка дозволів API — яку функціональність дозволено викликати.
  3. Бізнес-авторизація — з якими конкретно даними та операціями можна працювати.

Саме поєднання цих рівнів дозволяє будувати системи, у яких централізована ідентифікація не просто спрощує вхід, а стає частиною надійної та керованої архітектури безпеки.
