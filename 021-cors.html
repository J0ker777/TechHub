Вступ

Уявімо типову ситуацію.

Frontend працює за адресою:

TEXT
https://portal.company.ua

а API:

TEXT
https://api.company.ua

Frontend виконує запит:

JAVASCRIPT
fetch("https://api.company.ua/users")

і браузер показує помилку приблизно такого вигляду:

TEXT
Access to fetch at 'https://api.company.ua/users'
from origin 'https://portal.company.ua'
has been blocked by CORS policy.

Розробник відкриває Postman, виконує той самий запит — і отримує:

HTTP
HTTP/1.1 200 OK

API працює.

Мережа працює.

Сервер працює.

Авторизація працює.

То чому браузер блокує запит?

Щоб це зрозуміти, потрібно розібратися з Same-Origin Policy та CORS.

01

1. Спочатку розберемося з Origin

Браузер використовує поняття Origin — джерело, з якого завантажена сторінка.

Origin складається з трьох частин:

TEXT
scheme + host + port

Наприклад:

TEXT
https://portal.company.ua:443

де:

TEXT
scheme = https
host   = portal.company.ua
port   = 443

Два URL належать до одного origin лише тоді, коли всі три компоненти збігаються.

Наприклад:

TEXT
https://portal.company.ua
https://portal.company.ua/users

це один origin.

А ось:

TEXT
https://portal.company.ua
https://api.company.ua

це вже різні origin, тому що відрізняється host.

Так само різними будуть:

TEXT
http://portal.company.ua
https://portal.company.ua

через різні протоколи.

І навіть:

TEXT
https://portal.company.ua:443
https://portal.company.ua:8443

через різні порти.

02

2. Навіщо браузеру взагалі це контролювати

Уявімо, що ви авторизувалися в:

TEXT
https://bank.example

Браузер зберігає вашу сесійну cookie.

Після цього ви відкриваєте:

TEXT
https://evil.example

На сторінці знаходиться JavaScript:

JAVASCRIPT
fetch("https://bank.example/api/accounts")

Якби браузер без обмежень дозволяв JavaScript одного сайту працювати з даними іншого, шкідливий сайт міг би намагатися використовувати вашу активну сесію.

Тому браузери застосовують фундаментальний механізм безпеки:

Same-Origin Policy (SOP).

У спрощеному вигляді його ідея така:

↳
JavaScript одного origin не повинен довільно отримувати доступ до ресурсів іншого origin.

Але тут виникає проблема.

Сучасні системи дуже часто спеціально розділені:

TEXT
Frontend
https://portal.company.ua

        ↓

Backend API
https://api.company.ua

Frontend повинен мати можливість працювати з API.

Саме для керованого дозволу таких взаємодій і використовується CORS.

03

3. Що таке CORS

CORS — Cross-Origin Resource Sharing.

Це механізм, який дозволяє серверу повідомити браузеру:

↳
«Я дозволяю JavaScript з цього origin працювати з моїм ресурсом».

Наприклад, браузер виконує запит до API і передає:

HTTP
Origin: https://portal.company.ua

API може відповісти:

HTTP
Access-Control-Allow-Origin: https://portal.company.ua

Фактично сервер повідомляє браузеру:

TEXT
https://portal.company.ua

дозволено працювати з цією відповіддю.

Схематично:

TEXT
Browser
   │
   │ Origin: https://portal.company.ua
   ▼
API
   │
   │ Access-Control-Allow-Origin:
   │ https://portal.company.ua
   ▼
Browser
   │
   └── JavaScript отримує доступ до відповіді
04

4. Дуже важливий момент: CORS — не firewall

Це одна з найпоширеніших помилок.

Люди іноді думають:

↳
«Якщо ми налаштували CORS, сторонні системи не зможуть викликати наше API».

Це неправильно.

CORS — це насамперед механізм браузера.

Наприклад, API:

TEXT
https://api.company.ua/users

можна викликати через:

BASH
curl https://api.company.ua/users

або через:

TEXT
Postman

або інший backend:

TEXT
Server → API

CORS не є механізмом контролю доступу для таких клієнтів.

Тому:

TEXT
CORS ≠ Authentication
CORS ≠ Authorization
CORS ≠ Firewall
CORS ≠ API Security

CORS не замінює:

TEXT
OAuth 2.0
JWT
API Key
mTLS
WAF
Firewall
перевірку прав доступу
05

5. Чому Postman працює, а браузер — ні

Тепер можемо відповісти на головне питання.

Припустимо:

TEXT
Frontend:
https://portal.company.ua

API:
https://api.company.ua

У браузері:

JAVASCRIPT
fetch("https://api.company.ua/users")

може завершитися повідомленням:

TEXT
blocked by CORS policy

А в Postman:

HTTP
GET https://api.company.ua/users

повертає:

HTTP
200 OK

Причина проста:

Postman не є вебсторінкою, JavaScript якої браузер обмежує Same-Origin Policy.

Тому Postman не застосовує браузерну CORS-модель так, як це робить сторінка в Chrome, Edge або Firefox.

Саме тому фраза:

↳
«У мене в Postman працює»

ще не означає:

↳
«Frontend теж зможе викликати цей API».
06

6. Що таке Preflight

Тепер найцікавіше.

Іноді перед справжнім запитом браузер автоматично виконує ще один запит:

HTTP
OPTIONS

Наприклад, frontend хоче виконати:

HTTP
POST /api/orders
Authorization: Bearer eyJ...
Content-Type: application/json

Браузер може спочатку запитати API:

HTTP
OPTIONS /api/orders
Origin: https://portal.company.ua
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

Цей запит називається:

Preflight request.

Його сенс приблизно такий:

↳
«Сайт portal.company.ua хоче виконати POST і передати такі заголовки. Ти це дозволяєш?»

API відповідає:

HTTP
HTTP/1.1 204 No Content

Access-Control-Allow-Origin: https://portal.company.ua
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Authorization, Content-Type

Після цього браузер бачить:

TEXT
POST       → дозволено
Authorization → дозволено
Content-Type  → дозволено
Origin        → дозволено

і тільки тоді виконує фактичний:

HTTP
POST /api/orders

Схема виглядає так:

TEXT
Frontend
   │
   │ OPTIONS /api/orders
   ▼
API
   │
   │ CORS дозволено
   ▼
Browser
   │
   │ POST /api/orders
   ▼
API
   │
   │ 201 Created
   ▼
Frontend
07

7. Чому в Network видно два запити

Тепер стає зрозуміло, чому іноді в DevTools → Network можна побачити:

TEXT
OPTIONS /api/orders
POST    /api/orders

Розробник може подумати:

↳
«Чому frontend двічі викликає backend?»

Але frontend не обов'язково робив два запити.

Перший:

TEXT
OPTIONS

автоматично створив браузер.

Другий:

TEXT
POST

— це вже фактичний запит застосунку.

Тому при проблемах із CORS варто перевіряти не тільки POST, PUT або DELETE, а й попередній:

TEXT
OPTIONS
08

8. Основні CORS-заголовки

Найчастіше ви зустрінете такі заголовки.

Access-Control-Allow-Origin

HTTP
Access-Control-Allow-Origin: https://portal.company.ua

Визначає, якому origin дозволено доступ.

Access-Control-Allow-Methods

HTTP
Access-Control-Allow-Methods: GET, POST, PUT, DELETE

Вказує дозволені HTTP-методи для відповідного CORS-сценарію.

Access-Control-Allow-Headers

HTTP
Access-Control-Allow-Headers: Authorization, Content-Type

Визначає, які заголовки клієнт може використовувати в cross-origin запиті.

Це особливо важливо для:

HTTP
Authorization: Bearer ...

Access-Control-Allow-Credentials

HTTP
Access-Control-Allow-Credentials: true

Дозволяє браузеру працювати з credentials у відповідному cross-origin сценарії.

Наприклад, frontend може виконувати:

JAVASCRIPT
fetch("https://api.company.ua/profile", {
    credentials: "include"
});

Це особливо важливо для систем, де авторизація використовує cookies.

09

9. А що означає Access-Control-Allow-Origin: *

Можна зустріти:

HTTP
Access-Control-Allow-Origin: *

Зірочка означає:

↳
дозволити будь-який origin у сценаріях, де wildcard допустимий.

Для справді публічного ресурсу це може бути нормально.

Наприклад:

TEXT
GET /public/countries
GET /public/currencies

Але бездумно ставити:

HTTP
Access-Control-Allow-Origin: *

на всі API — погана практика.

Особливо важливо пам'ятати: wildcard * не можна просто поєднати з credentialed CORS-доступом і очікувати, що браузер це прийме.

Для API, доступного конкретному frontend, зазвичай краще явно визначити дозволені origins:

TEXT
https://portal.company.ua
https://admin.company.ua
10

10. CORS та cookies

Припустимо, frontend:

TEXT
https://portal.company.ua

працює з:

TEXT
https://api.company.ua

і авторизація побудована на cookie.

Frontend виконує:

JAVASCRIPT
fetch("https://api.company.ua/profile", {
    credentials: "include"
});

API повинен коректно підтримувати credentialed CORS і, зокрема, повертати відповідні заголовки, наприклад:

HTTP
Access-Control-Allow-Origin: https://portal.company.ua
Access-Control-Allow-Credentials: true

Але тут потрібно пам'ятати ще про:

TEXT
Secure
HttpOnly
SameSite

Тобто CORS — лише одна частина загальної браузерної моделі безпеки.

Саме тут CORS починає перетинатися з темою CSRF, але це різні механізми.

Спрощено:

TEXT
CORS
→ хто може читати/використовувати cross-origin відповіді через браузерний JavaScript

CSRF
→ як не дозволити сторонньому сайту змусити браузер користувача виконати небажану дію від його імені

Тому:

правильно налаштований CORS не означає автоматично, що система захищена від CSRF.

11

11. Типова небезпечна конфігурація

Припустимо, сервер отримує:

HTTP
Origin: https://evil.example

і автоматично відповідає:

HTTP
Access-Control-Allow-Origin: https://evil.example
Access-Control-Allow-Credentials: true

Тобто сервер фактично каже:

↳
«Я довіряю будь-якому origin, який мене попросить».

Це вже може створювати серйозні проблеми безпеки залежно від механізму автентифікації та поведінки API.

Правильніший підхід — мати явний allowlist:

TEXT
https://portal.company.ua
https://admin.company.ua

і перевіряти Origin саме за цим списком.

12

12. CORS error не завжди означає проблему CORS

Це ще одна важлива практична деталь.

Frontend отримав:

TEXT
CORS error

Перша реакція:

↳
«Треба виправляти CORS».

Не обов'язково.

Наприклад:

TEXT
Browser
   │
   │ OPTIONS
   ▼
API Gateway
   │
   X 500 Internal Server Error

Або:

TEXT
Browser
   │
   │ OPTIONS
   ▼
WAF
   │
   X OPTIONS заборонено

Або backend повернув:

HTTP
HTTP/1.1 500 Internal Server Error

але на error-response немає:

HTTP
Access-Control-Allow-Origin

У результаті браузер показує проблему CORS, хоча первинна причина може бути зовсім іншою.

Тому CORS-помилку не варто діагностувати лише за повідомленням у Console.

13

13. Як перевіряти проблему правильно

Відкриваємо:

TEXT
DevTools → Network

і дивимося весь ланцюжок.

Насамперед перевіряємо, чи є:

TEXT
OPTIONS

Якщо є — відкриваємо його.

Перевіряємо Request Headers:

HTTP
Origin
Access-Control-Request-Method
Access-Control-Request-Headers

Потім Response Headers:

HTTP
Access-Control-Allow-Origin
Access-Control-Allow-Methods
Access-Control-Allow-Headers
Access-Control-Allow-Credentials

І лише після цього дивимося фактичний:

TEXT
GET
POST
PUT
DELETE

Корисна послідовність діагностики:

TEXT
1. Який Origin у frontend?
        ↓
2. Куди йде запит?
        ↓
3. Чи це cross-origin?
        ↓
4. Чи був OPTIONS?
        ↓
5. Який статус OPTIONS?
        ↓
6. Які Access-Control-Allow-* повернув сервер?
        ↓
7. Чи відправив браузер фактичний запит?
        ↓
8. Яку відповідь повернув API?
14

14. Маленький практичний експеримент

Уявімо:

TEXT
Frontend
http://localhost:3000

API
http://localhost:5000

Frontend:

JAVASCRIPT
fetch("http://localhost:5000/api/users")
    .then(response => response.json())
    .then(data => console.log(data));

Браузер може заблокувати доступ до відповіді через CORS.

А тепер виконаємо:

BASH
curl http://localhost:5000/api/users

і отримаємо:

JSON
[
    {
        "id": 1,
        "name": "Alex"
    }
]

API працює.

Проблема не в доступності API.

Тепер API повертає:

HTTP
Access-Control-Allow-Origin: http://localhost:3000

І браузер дозволяє frontend працювати з відповіддю.

Цей простий експеримент дуже добре показує, де насправді знаходиться CORS:

TEXT
Frontend JavaScript
        │
        ▼
     Browser
        │
        │  ← CORS контролюється тут
        ▼
       API
15

15. Що потрібно запам'ятати

Якщо після статті залишити лише кілька думок, нехай це будуть ці.

Перше.

CORS означає:

TEXT
Cross-Origin Resource Sharing

і використовується для керування cross-origin взаємодіями браузерного JavaScript.

Друге.

Origin — це:

TEXT
scheme + host + port

Третє.

Основою браузерного обмеження є:

TEXT
Same-Origin Policy

а CORS дозволяє серверу контрольовано послабити ці обмеження для визначених сценаріїв.

Четверте.

CORS — не механізм автентифікації або авторизації.

TEXT
CORS ≠ OAuth
CORS ≠ JWT
CORS ≠ Firewall
CORS ≠ WAF

П'яте.

Перед деякими cross-origin запитами браузер автоматично виконує:

HTTP
OPTIONS

Це називається:

TEXT
Preflight

Шосте.

Якщо API працює в Postman, це ще не означає, що він працюватиме з frontend у браузері.

Сьоме.

Побачивши:

TEXT
blocked by CORS policy

не потрібно одразу змінювати CORS-конфігурацію.

Спочатку відкрийте:

TEXT
DevTools → Network

і подивіться, який запит насправді впав.

16

Висновок

CORS здається складним переважно тоді, коли його сприймають як ще один механізм захисту API.

Насправді модель значно простіша.

Є:

TEXT
Same-Origin Policy

яка обмежує можливості браузерного JavaScript працювати з іншими origin.

І є:

TEXT
CORS

який дозволяє серверу сказати браузеру:

↳
«Цьому origin я дозволяю таку взаємодію».

Тому коли наступного разу побачите:

TEXT
blocked by CORS policy

не починайте з:

↳
«Що зламалося на backend?»

Почніть з чотирьох питань:

TEXT
Який Origin?
      ↓
Чи був OPTIONS?
      ↓
Що відповів сервер?
      ↓
Чи дозволив браузер фактичний запит?

У більшості випадків після цього CORS перестає виглядати магією.
