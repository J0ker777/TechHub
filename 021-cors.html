Уявімо типову ситуацію.

Frontend працює за адресою:

https://portal.company.ua

а API:

https://api.company.ua

Frontend виконує запит:

JAVASCRIPT
fetch("https://api.company.ua/users")

і браузер показує помилку приблизно такого вигляду:

Access to fetch at 'https://api.company.ua/users'
from origin 'https://portal.company.ua'
has been blocked by CORS policy.

Розробник відкриває Postman, виконує той самий запит — і отримує:

HTTP
HTTP/1.1 200 OK

API працює.

Мережа працює.

Сервер працює.

Авторизація працює.

То чому браузер блокує запит?

Щоб це зрозуміти, потрібно розібратися з Same-Origin Policy — SOP (політикою однакового джерела) та CORS — Cross-Origin Resource Sharing (керованим спільним використанням ресурсів між різними джерелами).

01

1. Спочатку розберемося з Origin

Браузер використовує поняття Origin (джерело) — комбінацію, з якої завантажена сторінка.

Origin складається з трьох частин:

Origin складається з:

  • scheme — схеми протоколу;
  • host — імені хоста;
  • port — порту.

Наприклад:

https://portal.company.ua:443

де:

scheme = https
host   = portal.company.ua
port   = 443

Два URL належать до одного origin лише тоді, коли всі три компоненти збігаються.

Наприклад:

https://portal.company.ua
https://portal.company.ua/users

це один origin.

А ось:

https://portal.company.ua
https://api.company.ua

це вже різні origin, тому що відрізняється host.

Так само різними будуть:

http://portal.company.ua
https://portal.company.ua

через різні протоколи.

І навіть:

https://portal.company.ua:443
https://portal.company.ua:8443

через різні порти.

02

2. Навіщо браузеру взагалі це контролювати

Уявімо, що ви авторизувалися в:

https://bank.example

Браузер зберігає вашу сесійну cookie.

Після цього ви відкриваєте:

https://evil.example

На сторінці знаходиться JavaScript:

JAVASCRIPT
fetch("https://bank.example/api/accounts")

Якби браузер без обмежень дозволяв JavaScript одного сайту працювати з даними іншого, шкідливий сайт міг би намагатися використовувати вашу активну сесію.

Тому браузери застосовують фундаментальний механізм безпеки:

Same-Origin Policy — SOP (політика однакового джерела).

У спрощеному вигляді його ідея така:

↳
JavaScript одного origin не повинен довільно отримувати доступ до ресурсів іншого origin.

Але тут виникає проблема.

Сучасні системи дуже часто спеціально розділені:

Frontend повинен мати можливість працювати з API.

Саме для керованого дозволу таких взаємодій і використовується CORS.

03

3. Що таке CORS

CORS — Cross-Origin Resource Sharing (кероване спільне використання ресурсів між різними джерелами).

Це механізм, який дозволяє серверу повідомити браузеру:

↳
«Я дозволяю JavaScript з цього origin працювати з моїм ресурсом».

Наприклад, браузер виконує запит до API і передає:

HTTP
Origin: https://portal.company.ua

API може відповісти:

HTTP
Access-Control-Allow-Origin: https://portal.company.ua

Фактично сервер повідомляє браузеру:

https://portal.company.ua

дозволено працювати з цією відповіддю.

04

4. Дуже важливий момент: CORS — не firewall

Це одна з найпоширеніших помилок.

Люди іноді думають:

↳
«Якщо ми налаштували CORS, сторонні системи не зможуть викликати наше API».

Це неправильно.

CORS — це насамперед механізм браузера.

Наприклад, API:

https://api.company.ua/users

можна викликати через:

BASH
curl https://api.company.ua/users

або через:

Postman

або інший backend:

Server → API

CORS не є механізмом контролю доступу для таких клієнтів.

Тому:

CORS задає правила браузера для cross-origin доступу й не замінює:

  • authentication — автентифікацію;
  • authorization — авторизацію;
  • firewall або WAF;
  • загальну безпеку API.

CORS не замінює:

OAuth 2.0
JWT
API Key
mTLS
WAF
Firewall
перевірку прав доступу
05

5. Чому Postman працює, а браузер — ні

Тепер можемо відповісти на головне питання.

Припустимо:

Frontend:
https://portal.company.ua

API:
https://api.company.ua

У браузері:

JAVASCRIPT
fetch("https://api.company.ua/users")

може завершитися повідомленням:

blocked by CORS policy

А в Postman:

HTTP
GET https://api.company.ua/users

повертає:

HTTP
200 OK

Причина проста:

Postman не є вебсторінкою, JavaScript якої браузер обмежує Same-Origin Policy.

Тому Postman не застосовує браузерну CORS-модель так, як це робить сторінка в Chrome, Edge або Firefox.

Саме тому фраза:

↳
«У мене в Postman працює»

ще не означає:

↳
«Frontend теж зможе викликати цей API».
06

6. Що таке Preflight (попередній запит)

Тепер найцікавіше.

Іноді перед справжнім запитом браузер автоматично виконує ще один запит:

HTTP
OPTIONS

Наприклад, frontend хоче виконати:

HTTP
POST /api/orders
Authorization: Bearer eyJ...
Content-Type: application/json

Браузер може спочатку запитати API:

HTTP
OPTIONS /api/orders
Origin: https://portal.company.ua
Access-Control-Request-Method: POST
Access-Control-Request-Headers: authorization, content-type

Цей запит називається:

Preflight request.

Його сенс приблизно такий:

↳
«Сайт portal.company.ua хоче виконати POST і передати такі заголовки. Ти це дозволяєш?»

API відповідає:

HTTP
HTTP/1.1 204 No Content

Access-Control-Allow-Origin: https://portal.company.ua
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Authorization, Content-Type

Після цього браузер бачить:

і тільки тоді виконує фактичний:

HTTP
POST /api/orders

7. Чому в Network видно два запити

Тепер стає зрозуміло, чому іноді в DevTools → Network можна побачити:

Розробник може подумати:

↳
«Чому frontend двічі викликає backend?»

Перший:

Другий:

POST

— це вже фактичний запит застосунку.

Тому при проблемах із CORS варто перевіряти не тільки POST, PUT або DELETE, а й попередній:

08

8. Основні CORS-заголовки

Найчастіше ви зустрінете такі заголовки.

Access-Control-Allow-Origin

HTTP
Access-Control-Allow-Origin: https://portal.company.ua

Визначає, якому origin дозволено доступ.

Access-Control-Allow-Methods

HTTP
Access-Control-Allow-Methods: GET, POST, PUT, DELETE

Вказує дозволені HTTP-методи для відповідного CORS-сценарію.

Access-Control-Allow-Headers

HTTP
Access-Control-Allow-Headers: Authorization, Content-Type

Визначає, які заголовки клієнт може використовувати в cross-origin запиті.

Це особливо важливо для:

HTTP
Authorization: Bearer ...

Access-Control-Allow-Credentials

HTTP
Access-Control-Allow-Credentials: true

Дозволяє браузеру працювати з credentials у відповідному cross-origin сценарії.

Наприклад, frontend може виконувати:

JAVASCRIPT
fetch("https://api.company.ua/profile", {
    credentials: "include"
});

Це особливо важливо для систем, де авторизація використовує cookies.

09

9. А що означає Access-Control-Allow-Origin: *

Можна зустріти:

HTTP
Access-Control-Allow-Origin: *

Зірочка означає:

↳
дозволити будь-який origin у сценаріях, де wildcard допустимий.

Для справді публічного ресурсу це може бути нормально.

Наприклад:

GET /public/countries
GET /public/currencies

Але бездумно ставити:

HTTP
Access-Control-Allow-Origin: *

на всі API — погана практика.

Особливо важливо пам'ятати: wildcard * не можна просто поєднати з credentialed CORS-доступом і очікувати, що браузер це прийме.

Для API, доступного конкретному frontend, зазвичай краще явно визначити дозволені origins:

https://portal.company.ua
https://admin.company.ua
10

10. CORS та cookies

Припустимо, frontend:

https://portal.company.ua

працює з:

https://api.company.ua

і авторизація побудована на cookie.

Frontend виконує:

JAVASCRIPT
fetch("https://api.company.ua/profile", {
    credentials: "include"
});

API повинен коректно підтримувати credentialed CORS і, зокрема, повертати відповідні заголовки, наприклад:

HTTP
Access-Control-Allow-Origin: https://portal.company.ua
Access-Control-Allow-Credentials: true

Але тут потрібно пам'ятати ще про:

Secure
HttpOnly
SameSite

Тобто CORS — лише одна частина загальної браузерної моделі безпеки.

Саме тут CORS починає перетинатися з темою CSRF, але це різні механізми.

Спрощено:

  • CORS: чи дозволено браузерному JavaScript працювати з cross-origin відповіддю?
  • CSRF: чи може сторонній сайт змусити браузер виконати небажану дію від імені користувача?

Тому:

правильно налаштований CORS не означає автоматично, що система захищена від CSRF.

11

11. Типова небезпечна конфігурація

Припустимо, сервер отримує:

HTTP
Origin: https://evil.example

і автоматично відповідає:

HTTP
Access-Control-Allow-Origin: https://evil.example
Access-Control-Allow-Credentials: true

Тобто сервер фактично каже:

↳
«Я довіряю будь-якому origin, який мене попросить».

Це вже може створювати серйозні проблеми безпеки залежно від механізму автентифікації та поведінки API.

Правильніший підхід — мати явний allowlist:

https://portal.company.ua
https://admin.company.ua

і перевіряти Origin саме за цим списком.

15. Що потрібно запам'ятати

Якщо після статті залишити лише кілька думок, нехай це будуть ці.

Перше.

CORS означає:

Cross-Origin Resource Sharing

і використовується для керування cross-origin взаємодіями браузерного JavaScript.

Друге.

Origin — це:

scheme + host + port

Третє.

Основою браузерного обмеження є:

Same-Origin Policy

а CORS дозволяє серверу контрольовано послабити ці обмеження для визначених сценаріїв.

CORS ≠ OAuth
CORS ≠ JWT
CORS ≠ Firewall

16

Висновок

CORS здається складним переважно тоді, коли його сприймають як ще один механізм захисту API.

Насправді модель значно простіша.

Є:

Same-Origin Policy

яка обмежує можливості браузерного JavaScript працювати з іншими origin.

І є:

CORS

який дозволяє серверу сказати браузеру:

↳
«Цьому origin я дозволяю таку взаємодію».

Тому коли наступного разу побачите:

blocked by CORS policy

не починайте з:

↳
«Що зламалося на backend?»

Почніть з чотирьох питань:

У більшості випадків після цього CORS перестає виглядати магією.

17

👶 Якщо зовсім просто

🏢 Браузер перевіряє адресу сторінки й адресу API

Уявіть бізнес-центр із охороною. Сторінка завантажена з офісу portal.company.ua, а дані потрібно взяти з іншого офісу — api.company.ua. Навіть якщо обидва належать одній компанії, для браузера це різні origin, бо їхні host відрізняються.

Origin складається зі схеми протоколу, хоста й порту. Якщо хоча б одна частина інша, взаємодія вважається cross-origin (між різними джерелами). Шлях після хоста не входить до origin, тому /users і /orders на тому самому сайті не створюють різні origin.

🛡 Що роблять SOP і CORS

Same-Origin Policy — базове правило браузера, яке обмежує доступ JavaScript однієї сторінки до даних з іншого origin. CORS дозволяє серверу контрольовано сказати браузеру: «Ось цьому origin я дозволяю працювати з моєю відповіддю».

CORS застосовує браузер. curl, Postman і серверний код не є сторінкою JavaScript під контролем браузерної Same-Origin Policy, тому той самий API-запит може працювати там і давати CORS-помилку у frontend.

✉️ Що таке preflight

Для деяких cross-origin запитів браузер спочатку надсилає OPTIONS. Це preflight — попередня перевірка дозволу на майбутній метод і заголовки. Якщо сервер не дозволив запит, браузер не надсилає фактичний POST, PUT чи інший запит, який потребував preflight.

Не кожен cross-origin запит має preflight. Так звані simple requests (прості запити, що відповідають обмеженим умовам щодо методу й заголовків) можуть піти одразу. Якщо відповідь не містить потрібного дозволу CORS, браузер не відкриє її JavaScript. Сам запит при цьому міг уже дійти до сервера та виконати дію.

Ця різниця важлива для діагностики й безпеки: повідомлення CORS не завжди означає, що сервер нічого не отримав.

🍪 Що змінюють cookies і credentials

Якщо cross-origin запит повинен містити cookie або інші credentials (облікові дані браузерної сесії), frontend явно вмикає відповідний режим, а сервер повертає Access-Control-Allow-Credentials: true та конкретний дозволений origin.

Для credentialed response (відповіді із залученням облікових даних) wildcard * не може замінити конкретне значення Access-Control-Allow-Origin. Крім CORS, поведінку cookie визначають SameSite, Secure, домен, шлях та інші атрибути.

🔐 Чого CORS не робить

CORS не перевіряє пароль, JWT або роль користувача. Він не замінює firewall, WAF, авторизацію та серверну перевірку прав. API все одно повинен вважати кожен вхідний запит недовіреним і самостійно вирішувати, чи дозволена операція.

CORS також не є повним захистом від CSRF. Деякі запити можуть бути відправлені браузером навіть тоді, коли сторонній JavaScript не отримає доступу до відповіді. Для операцій зі cookie потрібен окремий CSRF-захист і коректні атрибути cookie.

🔎 Як розібрати CORS-помилку

Спочатку відкрийте DevTools → Network, а не лише Console. Знайдіть OPTIONS, якщо він був, перевірте його статус і CORS-заголовки. Потім з’ясуйте, чи браузер надіслав фактичний запит і що повернули API Gateway, WAF або backend.

Помилка може виникнути через неправильний allowlist (список дозволених origin), відсутній заголовок на error-response, заборонений OPTIONS, редирект, помилку API або невідповідність дозволених методів і заголовків. Додавати * навмання — погана діагностика й потенційно небезпечна конфігурація.

Якщо сервер динамічно повертає дозволений origin із allowlist, кеші також повинні розрізняти відповіді за заголовком Origin; для цього часто потрібен Vary: Origin.

👥 Що потрібно різним ролям

PM/BA: CORS визначає, які браузерні frontend можуть працювати з API, але не визначає права конкретного користувача. У вимогах важливо перелічити дозволені середовища й origin: production, admin-портал, тестові стенди та локальну розробку.

QA: перевіряйте дозволений і заборонений origin, прості запити, preflight, cookies, помилкові відповіді та фактичну появу обох запитів у Network. Робота в Postman не підтверджує правильну браузерну конфігурацію.

Dev/Architect: підтримуйте точний allowlist, відповідайте на preflight без побічних бізнес-дій, додавайте CORS-заголовки до потрібних успішних і помилкових відповідей та не віддзеркалюйте довільний Origin. Авторизація й CSRF-захист залишаються окремими шарами.
