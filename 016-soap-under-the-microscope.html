SOAP часто сприймають дуже просто:

↳
«Це API, де запити передаються в XML».

Або:

↳
«Це те, через що ми інтегруємося із SAP».

Це близько до правди, але не зовсім.

SOAP — Simple Object Access Protocol (протокол обміну структурованими повідомленнями) — це не SAP і не SoapUI.

Для передачі даних SOAP використовує XML — Extensible Markup Language (розширювану мову розмітки), часто працює поверх HTTP або HTTPS, а контракт сервісу зазвичай описується через WSDL — Web Services Description Language (мову опису вебсервісу).

У корпоративних системах SOAP зустрічається й сьогодні: SAP, банківські системи, ERP, державні сервіси, старі та нові enterprise-інтеграції.

Тому варто розібратися, що насправді стоїть за фразою:

↳
«Наша система викликає SOAP-сервіс».

02

2. Як виглядає SOAP-запит

Типовий SOAP Request може виглядати так:

XML
<soapenv:Envelope
    xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
    xmlns:cus="http://company.local/customer">

   <soapenv:Header/>

   <soapenv:Body>
      <cus:GetCustomer>
         <cus:CustomerId>12345</cus:CustomerId>
      </cus:GetCustomer>
   </soapenv:Body>

</soapenv:Envelope>

На перший погляд — багато XML.

Але структура досить проста:

Envelope містить:

  • Header — службову інформацію;
  • Body — бізнес-операцію.
03

3. Envelope — конверт SOAP-повідомлення

Envelope — кореневий елемент SOAP-повідомлення.

Можна провести аналогію зі звичайним листом.

Є конверт, а всередині:

  • службова інформація;
  • саме повідомлення.

У SOAP це:

Просто XML:

XML
<GetCustomer>
    <CustomerId>12345</CustomerId>
</GetCustomer>

ще не обов'язково є SOAP-повідомленням.

SOAP має свою визначену структуру.

04

4. Header — службова інформація

У Header можуть передаватися:

  • інформація про безпеку;
  • токени;
  • цифрові підписи;
  • correlation ID;
  • timestamp;
  • службові параметри.

У простому випадку Header може бути порожнім:

XML
<soapenv:Header/>

А в складніших enterprise-інтеграціях він може містити, наприклад, WS-Security.

При цьому автентифікація не обов'язково знаходиться саме в SOAP Header.

Можуть використовуватися:

  • HTTP Basic Authentication;
  • сертифікати;
  • mTLS;
  • WS-Security;
  • інші механізми.
05

5. Body — сама бізнес-операція

Найцікавіша частина — Body.

XML
<soapenv:Body>

   <cus:GetCustomer>
      <cus:CustomerId>12345</cus:CustomerId>
   </cus:GetCustomer>

</soapenv:Body>

Тут:

GetCustomer

— операція.

А:

CustomerId = 12345

— її параметр.

Як дуже груба аналогія, у REST ми могли б мати:

HTTP
GET /customers/12345

А в SOAP бізнесова дія описується XML-структурою всередині Body.

06

6. Namespace — маленька деталь, яка може зламати весь запит

Подивімося ще раз:

XML
xmlns:cus="http://company.local/customer"

Це namespace.

Тому:

XML
<cus:GetCustomer>

означає не просто:

GetCustomer

а операцію GetCustomer із конкретного namespace.

Для людини такі XML можуть виглядати майже однаково:

XML
<GetCustomer>

і:

XML
<cus:GetCustomer>

А для SOAP-сервісу це можуть бути різні речі.

Через неправильний namespace можна отримати помилку навіть тоді, коли назва операції здається правильною.

Це одна з типових проблем SOAP.

07

7. Як SOAP потрапляє до SAP

SOAP-повідомлення потрібно передати мережею.

Найчастіше для цього використовується HTTP або HTTPS.

Наприклад:

HTTP
POST /services/CustomerService HTTP/1.1
Host: sap.company.local
Content-Type: text/xml; charset=utf-8
SOAPAction: "GetCustomer"

А нижче йде XML:

XML
<soapenv:Envelope>
   ...
</soapenv:Envelope>

Тобто:

SOAP не замінює HTTP.

SOAP-повідомлення часто просто передається всередині HTTP Request.

Саме тут ця тема безпосередньо пов'язана з попередньою статтею «HTTP-запит під мікроскопом».

08

8. Endpoint — куди відправляється запит

Щоб викликати сервіс, потрібно знати його адресу.

Наприклад:

https://sap.company.local/services/CustomerService

Це SOAP endpoint.

Клієнт відправляє Request саме на нього.

Важливо не плутати:

WSDL URL

і:

SOAP Endpoint

WSDL описує сервіс.

Endpoint приймає запити.

09

9. SOAPAction

У SOAP 1.1 часто можна зустріти HTTP header:

HTTP
SOAPAction: "GetCustomer"

Або:

HTTP
SOAPAction: "http://company.local/customer/GetCustomer"

Він допомагає серверу зрозуміти, яку операцію потрібно виконати.

Через неправильний SOAPAction може виникнути цікава ситуація:

endpoint правильний;

HTTP працює;

XML виглядає правильно;

але потрібна операція не виконується.
10

10. WSDL — контракт SOAP-сервісу

Тепер одна з найважливіших частин SOAP.

WSDL — Web Services Description Language.

Це XML-документ, який описує сервіс.

У спрощеному вигляді він відповідає на питання:

Які операції існують?

Які параметри вони приймають?

Що повертають?

Які типи даних використовуються?

Який SOAP binding використовується?

Де знаходиться endpoint?

Наприклад, із WSDL клієнт може дізнатися, що сервіс підтримує:

CustomerService може містити операції:

  • GetCustomer;
  • CreateCustomer;
  • UpdateCustomer;
  • GetCustomerStatus.

Це одна з сильних сторін SOAP:

контракт сервісу формалізований.

11

11. XSD — структура даних

Разом із WSDL часто використовується XSD — XML Schema Definition.

XSD описує:

  • типи полів;
  • обов'язкові та необов'язкові поля;
  • вкладені структури;
  • повторювані елементи;
  • допустимі формати.

Наприклад:

XML
<xs:element
    name="CustomerId"
    type="xs:string"/>

означає, що CustomerId має тип string.

А:

XML
<xs:element
    name="MiddleName"
    type="xs:string"
    minOccurs="0"/>

означає, що MiddleName необов'язковий.

Через XSD SOAP-сервіс може досить жорстко визначати структуру Request і Response.

13. SOAP Response

SAP може повернути приблизно таку відповідь:

XML
<soapenv:Envelope
    xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
    xmlns:cus="http://company.local/customer">

   <soapenv:Body>

      <cus:GetCustomerResponse>

         <cus:Customer>
            <cus:CustomerId>12345</cus:CustomerId>
            <cus:Name>Іван Петренко</cus:Name>
            <cus:Status>Active</cus:Status>
         </cus:Customer>

      </cus:GetCustomerResponse>

   </soapenv:Body>

</soapenv:Envelope>

SOAP-клієнт отримує XML, десеріалізує його і перетворює у звичайний об'єкт програми.

14

14. SOAP Fault — помилка SOAP-рівня

Якщо операцію неможливо виконати, сервер може повернути SOAP Fault.

Наприклад:

XML
<soapenv:Fault>

   <faultcode>
      soapenv:Server
   </faultcode>

   <faultstring>
      Customer not found
   </faultstring>

</soapenv:Fault>

SOAP Fault може містити:

  • код;
  • опис;
  • додаткові деталі.

І тут важливо розуміти різницю між рівнями помилок.

18. SOAP 1.1 і SOAP 1.2

Існують різні версії SOAP.

Найчастіше:

SOAP 1.1

SOAP 1.2

Наприклад, SOAP 1.1 часто використовує:

HTTP
Content-Type: text/xml

А SOAP 1.2:

HTTP
Content-Type: application/soap+xml

Відрізняються також namespaces і правила роботи з action.

Тому іноді Request може виглядати правильним, але сервер його не приймає через неправильну версію SOAP.

19. SOAP і безпека

HTTPS

Client Certificate

mTLS

WS-Security

UsernameToken

XML Signature

20. SOAP vs REST

SOAP і REST часто порівнюють, хоча технічно це різні категорії.

SOAP — протокол.

REST — архітектурний стиль.

Спрощено:

SOAPREST
Зазвичай XMLЧасто JSON
WSDLЧасто OpenAPI
Формальний контрактКонтракт залежить від реалізації
Сильна типізаціяЗалежить від API
WS-* стандартиПростіші web-механізми
Часто enterpriseДуже поширений у web/API
Більш багатослівнийЗазвичай компактніший

Неправильно мислити так:

SOAP — старий і поганий.

REST — новий і хороший.

SOAP досі використовується там, де важливі:

  • формальні контракти;
  • enterprise interoperability;
  • schema-first підхід;
  • складні security-механізми;
  • сумісність із великими корпоративними системами.

22. Що потрібно запам'ятати

Якщо залишити після статті лише кілька ключових думок, то ось вони.

SOAP — не просто XML.

Це протокол структурованого обміну повідомленнями.

WSDL — контракт сервісу.

Він описує operations, типи даних, binding та endpoint.

XSD визначає структуру XML.

Типи, обов'язкові поля та вкладені структури.

SOAP часто працює поверх HTTP/HTTPS.

Тому проблема SOAP-інтеграції може насправді бути мережевою, TLS або HTTP-проблемою.

SOAP Request складається з Envelope, Header і Body.

А бізнес-операція знаходиться переважно в Body.

Namespace має значення.

Візуально схожий XML може мати зовсім інше значення для сервісу.

SOAP Fault — окремий рівень помилки.

Не потрібно плутати його з HTTP-помилкою.

SoapUI — лише інструмент тестування.

У production той самий SOAP Request зазвичай формує код.

SAP може надавати SOAP-сервіс, але SOAP не є технологією SAP.

25

👶 Якщо зовсім просто

SOAP можна уявити як формальний обмін листами між двома системами. WSDL описує адресу сервісу, доступні операції та форму даних. XML — це формат листа. Envelope є конвертом, Header містить службову інформацію, а Body — саму бізнес-команду.

Namespace (простір імен XML) пояснює, до якого словника належить елемент. XSD — XML Schema Definition (опис структури XML) — задає поля, типи та обов’язковість. Навіть правильні за змістом дані можуть бути відхилені через неправильний namespace, тип або структуру.

HTTP status і SOAP Fault відповідають за різні рівні. HTTP показує результат транспортування, а Fault описує помилку SOAP або бізнес-операції. Тому 200 OK не завжди означає успішний бізнес-результат, а технічна діагностика повинна перевіряти і HTTP, і XML-відповідь.

SoapUI допомагає вручну прочитати WSDL, сформувати запит і відокремити проблему сервісу від проблеми коду клієнта. Якщо запит із SoapUI працює, а із застосунку ні, потрібно порівняти endpoint, SOAPAction, версію SOAP, заголовки, namespaces, серіалізацію та автентифікацію.

PM/BA важливо узгодити операції, поля, помилки й версію контракту. QA — тестувати позитивні відповіді, Fault, HTTP-помилки, неправильні namespaces і граничні дані. Dev/Architect — контролювати генерацію клієнта, сумісність контракту, безпечні заголовки та спостережуваність інтеграції.
