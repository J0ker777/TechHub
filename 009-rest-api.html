01

🌐 REST — це не просто JSON через HTTP

REST — Representational State Transfer.

Це архітектурний стиль, описаний Роєм Філдінгом.

REST не говорить:

↳
«Усі endpoint повинні виглядати саме так».

Але задає набір архітектурних обмежень і принципів.

У практичному API design одна з найкорисніших ідей REST звучить так:

↳
Думайте про ресурси, а не про функції.

Наприклад, у нас є:

Customer
Order
Payment
Invoice

Це ресурси.

Тому замість:

HTTP
POST /getCustomer

ми можемо сказати:

HTTP
GET /customers/123

А замість:

HTTP
POST /deleteCustomer

використати:

HTTP
DELETE /customers/123

URL описує ресурс.

HTTP method — що ми хочемо з ним зробити.

02

🔨 Один ресурс — різні операції

Наприклад:

HTTP
GET /customers/123
↳
Отримати customer 123.
HTTP
POST /customers
↳
Створити нового customer.
HTTP
PUT /customers/123
↳
Замінити представлення customer 123.
HTTP
PATCH /customers/123
↳
Частково змінити customer 123.
HTTP
DELETE /customers/123
↳
Видалити customer 123.

Зверніть увагу: URL практично не змінюється.

/customers
/customers/123

Змінюється HTTP method.

03

🧠 URL краще описує «що», а не «що зробити»

Порівняємо.

RPC-style

HTTP
POST /getCustomer
POST /createCustomer
POST /updateCustomer
POST /deleteCustomer

У URL зашита дія:

get
create
update
delete

Resource-oriented

HTTP
GET    /customers/123
POST   /customers
PATCH  /customers/123
DELETE /customers/123

Тут:

API стає більш передбачуваним.

Побачивши:

HTTP
GET /orders/987

розробнику не потрібно читати документацію, щоб приблизно зрозуміти, що станеться.

04

📚 Collection та Resource

Корисно розрізняти:

/customers

і:

/customers/123

Перше — collection.

Друге — конкретний resource.

Наприклад:

HTTP
GET /customers

отримати список.

HTTP
GET /customers/123

отримати одного.

HTTP
POST /customers

створити нового в collection.

05

🔗 А якщо ресурси пов'язані?

Customer має orders.

Можна зробити:

HTTP
GET /customers/123/orders

Це читається природно:

↳
Покажи orders customer 123.

А конкретне замовлення:

HTTP
GET /orders/987

Але тут теж не потрібно перетворювати URL на копію структури Database:

/customers/123/orders/987/items/44/product/78/category/9

REST API описує зручну модель ресурсів для consumer, а не обов'язково структуру таблиць.

06

❓ Filtering

У нас мільйон orders.

Не дуже хороша ідея:

HTTP
GET /orders

повертати весь мільйон.

Потрібні filters:

HTTP
GET /orders?status=active

або:

HTTP
GET /orders?customerId=123&status=active

Тобто:

/orders

залишається ресурсом/collection,

а query parameters описують, яку його частину ми хочемо отримати.

07

📄 Pagination

Припустимо:

Orders = 5 000 000

Client точно не потрібно отримувати все одним response.

Наприклад:

HTTP
GET /orders?page=2&pageSize=50

А response:

JSON
{
  "items": [
    ...
  ],
  "page": 2,
  "pageSize": 50,
  "total": 152340
}

Є різні моделі pagination — offset, cursor тощо.

Але головна ідея:

↳
API повинен проектуватися з урахуванням реального обсягу даних, а не лише тестових 20 записів.
08

🔃 Sorting

Наприклад:

HTTP
GET /orders?sort=createdAt

або:

HTTP
GET /orders?sort=-createdAt

де - умовно означає descending.

Можна отримати:

Filtering
+
Sorting
+
Pagination

в одному запиті:

HTTP
GET /orders
    ?status=active
    &sort=-createdAt
    &page=1
    &pageSize=50
09

🆚 POST vs PUT

Тут починається одна з улюблених тем для суперечок.

Припустимо, створюємо order.

Зазвичай:

HTTP
POST /orders
JSON
{
  "customerId": 123,
  "productId": 456
}

Server створює:

Order ID = 987

і відповідає:

HTTP
201 Created
Location: /orders/987

У цьому сценарії ID ресурсу визначив Server.

10

🔄 PUT

Тепер:

HTTP
PUT /customers/123

з body:

JSON
{
  "name": "Ivan",
  "email": "ivan@example.com"
}

У REST-практиці PUT зазвичай розглядають як повну заміну представлення ресурсу за відомим URI.

Тобто Client знає:

/customers/123

і передає нове представлення цього ресурсу.

11

🩹 PATCH

А якщо потрібно змінити лише email?

HTTP
PATCH /customers/123
JSON
{
  "email": "new@example.com"
}

Ідея:

↳
Змінити частину ресурсу.

Це часто краще передає намір, ніж відправляти весь Customer для зміни одного поля.

Конкретна семантика PATCH body при цьому теж повинна бути визначена контрактом.

12

🔁 Що таке Idempotency?

Дуже важливе поняття.

Уявімо:

HTTP
DELETE /customers/123

Виконали один раз:

Customer deleted

Виконали повторно.

Стан системи в сенсі цільового ресурсу залишається:

Customer does not exist

Це idempotent operation.

Спрощено:

↳
Повторення тієї самої операції не повинно додатково змінювати кінцевий стан після першого успішного застосування.
13

⚠️ POST зазвичай не idempotent

Наприклад:

HTTP
POST /orders

виконали:

Order 1001 created

Клієнт не отримав response через network timeout.

Він не знає:

Order створився?
чи ні?

І повторює:

HTTP
POST /orders

Server:

Order 1002 created

Тепер маємо два замовлення.

Саме тому в критичних операціях може використовуватися Idempotency Key:

HTTP
POST /orders
Idempotency-Key: 7a8f91...

При повторному request:

HTTP
POST /orders
Idempotency-Key: 7a8f91...

Server розуміє:

↳
Я вже обробляв цю операцію.

Це особливо важливо для:

Payments
Orders
Financial Operations
External Integrations
14

💥 REST не означає CRUD один-в-один

Ось тут дуже важливий момент.

Іноді REST розуміють так:

GET    = SELECT
POST   = INSERT
PUT    = UPDATE
DELETE = DELETE

і намагаються буквально виставити Database через HTTP.

Але API — це бізнес-контракт, а не HTTP-обгортка над таблицями.

Наприклад, у нас є Order.

Бізнес-операція:

↳
Скасувати замовлення.

Можна зробити:

HTTP
POST /orders/123/cancel

Хтось скаже:

↳
«У REST не повинно бути дієслів!»

Можна змоделювати це через ресурс:

HTTP
POST /orders/123/cancellations

Але інколи перший варіант може бути значно зрозумілішим для команди та consumers.

І це приводить до важливої думки:

↳
Хороший API важливіший за релігійно "чистий" REST.
15

🧩 REST — це більше, ніж красиві URL

REST має кілька архітектурних constraints.

Один із найважливіших:

16

Stateless

Це означає, що кожен request повинен містити достатньо інформації для його обробки.

Наприклад:

HTTP
GET /orders/123
Authorization: Bearer eyJ...

Server не повинен вимагати прихованого контексту попереднього HTTP-запиту, щоб зрозуміти цей request.

Це не означає:

↳
«Server не може мати Database або session state взагалі».

Йдеться про те, що кожен request має бути самодостатнім з точки зору протоколу взаємодії.

🚦 Status Codes — частина API Contract

Ми вже говорили про це в HTTP.

REST API повинен використовувати зрозумілу HTTP semantics.

Наприклад:

HTTP
GET /customers/123

Customer існує:

HTTP
200 OK

Не існує:

HTTP
404 Not Found

Створили:

HTTP
201 Created

Request невалідний:

HTTP
400 Bad Request

Користувач не автентифікований:

HTTP
401 Unauthorized

Не має прав:

HTTP
403 Forbidden

Конфлікт стану:

HTTP
409 Conflict
19

💣 Не треба завжди повертати 200

Наприклад:

HTTP
200 OK
JSON
{
  "success": false,
  "errorCode": 401,
  "message": "Unauthorized"
}

Client тепер повинен знати:

↳
HTTP status не дивись. Шукай наш власний status усередині JSON.

Ми фактично створили:

хоча HTTP вже має потрібну семантику.

20

🧾 Error Response теж повинен мати контракт

Поганий варіант:

JSON
{
  "error": "Something went wrong"
}

Трохи краще мати стабільну структуру:

JSON
{
  "code": "CUSTOMER_NOT_FOUND",
  "message": "Customer was not found",
  "traceId": "a82f91..."
}

Тоді:

Для стандартизованого опису HTTP API errors також існує формат Problem Details (application/problem+json).

👥 І тут API перестає бути лише задачею розробника

Наприклад, аналітик описує:

↳

Словник термінів простими словами

  • REST — принципи організації API навколо ресурсів і стандартної поведінки HTTP.
  • Resource — сутність: користувач, замовлення або платіж.
  • Endpoint — адреса API разом із методом, наприклад GET /orders/42.
  • HTTP method — дія над ресурсом: GET читає, POST створює або запускає операцію, PUT/PATCH змінюють, DELETE видаляє.
  • Idempotency — повторення того самого запиту не створює додаткового ефекту.
  • Stateless — кожен запит містить усе потрібне; сервер не покладається на пам’ять про попередній запит.
  • Authentication перевіряє особу; authorization — її дозволи.
  • API contract — погоджені адреси, параметри, формати, статуси й помилки.
  • Error code уточнює причину помилки; Trace ID допомагає знайти запит у логах.
  • OpenAPI — формальний опис контракту для документації та клієнтського коду.
  • Versioning — спосіб змінювати API, не ламаючи чинних клієнтів.
  • Controller приймає HTTP-запит; бізнес-рішення залишаються в сервісах і доменній логіці.
26

👶 Якщо зовсім просто

REST API схожий на каталог предметів із передбачуваними командами. Адреса показує, з яким ресурсом ми працюємо, метод — що хочемо зробити, а status code — чим усе завершилося.

Хороший API однаково поводиться в однакових ситуаціях. Він перевіряє особу та права, не приховує помилки за статусом 200 і повертає стабільний формат для автоматичної обробки.

Контракт проєктують до controller: визначають ресурси, правила, помилки, повторні запити та сумісність. Тоді frontend, backend, QA і бізнес говорять про одну поведінку.
