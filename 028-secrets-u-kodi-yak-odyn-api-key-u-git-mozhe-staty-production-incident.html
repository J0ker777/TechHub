Вступ

Уявімо звичайну ситуацію.

Розробник тестує інтеграцію із зовнішнім API.

Щоб швидше перевірити код, він тимчасово пише:

CSHARP
var apiKey = "prod-8f2a91c7-super-secret-key";

var client = new ApiClient(apiKey);

Потім:

git add .
git commit -m "Add API integration"
git push

Через кілька хвилин він помічає проблему.

«Ой. Ключ потрапив у Git».

Виправляє:

CSHARP
var apiKey = configuration["ApiKey"];

і робить новий commit.

Тепер у коді секрету немає.

Проблема вирішена?

Ні.

І ось тут починається найцікавіше.

01

🕵️ Git пам'ятає

Git — це не просто сховище поточної версії файлів.

Він зберігає історію змін.

Тобто:

Commit 1

apiKey = "prod-secret-key";

потім:

Commit 2

apiKey = configuration["ApiKey"];

У поточній версії секрету вже немає.

Але:

git log

і перегляд старого commit усе ще дозволяють його знайти.

Тому:

↳
Видалити secret із наступного commit ≠ прибрати скомпрометований secret.

Якщо секрет потрапив у Git, його варто розглядати як скомпрометований.

02

🔑 Що взагалі вважати Secret?

Очевидно:

Password

Але список набагато більший:

API Keys
Database Passwords
Connection Strings
Private Keys
Client Secrets
Access Tokens
Refresh Tokens
Storage Keys
SAS Tokens
Webhook Secrets
Certificates / private key material

Наприклад:

JSON
{
  "ConnectionStrings": {
    "MainDb": "Server=prod-db;User=admin;Password=P@ssw0rd!"
  }
}

Це теж secret.

І appsettings.json у Git — не найкраще місце для нього.

03

🙈 А якщо репозиторій приватний?

Частий аргумент:

↳
«У нас private repository. Його бачить тільки команда».

Це, звичайно, краще за public repository.

Але private ≠ secret storage.

Доступ до репозиторію можуть мати:

Developers
DevOps
Contractors
CI/CD
Service Accounts
Automation
Backup Systems

Репозиторій також може:

  • клонуватися на ноутбуки;
  • потрапляти в backup;
  • копіюватися;
  • форкатися;
  • використовуватися CI/CD агентами.

І головне:

↳
Secret живе довше, ніж ми пам'ятаємо, кому колись був доступний repository.

додамо до:

Але .env сам по собі не є Secret Management System.

Developer Laptop
Server

Backup

І якщо його просто скопіювати на Production:

/opt/application/.env

ми лише перенесли проблему з Git на файлову систему.

👤 А розробнику потрібен Production password?

Ще одне важливе питання.

Припустимо, розробник підтримує сервіс:

Billing Service

Чи потрібно йому знати:

У хорошій схемі — бажано, щоб ні.

  • копіювання;
  • передачі в чаті;
  • збереження на ноутбуці;
  • використання Production credentials у DEV.

09

🔄 Secret Rotation

Припустимо, у нас є:

API_KEY = abc123

і він використовується вже три роки.

Ніхто точно не пам'ятає:

Хто його бачив?
Де він зберігався?
Хто його копіював?
На яких серверах він залишився?

Саме тому важлива rotation.

Наприклад:

У зрілішій системі це може бути автоматизовано.

10

🚨 А що робити, якщо secret уже потрапив у Git?

Перша реакція часто:

Delete secret
Commit
Push

Але цього недостатньо.

Найважливіший крок:

↳
ROTATE / REVOKE SECRET

Тобто старий ключ потрібно зробити недійсним.

Наприклад:

і створити новий:

xyz789

Лише після цього має сенс займатися очищенням Git history, якщо це необхідно.

Пріоритет:

1. Revoke / Rotate
2. Assess exposure
3. Replace
4. Clean history if needed
5. Investigate

Тому що поки ми красиво чистимо repository, зловмисник потенційно продовжує використовувати старий credential.

12

⚠️ А що з логами?

Припустимо, у Git усе правильно.

Secrets лежать у Vault.

А потім розробник додає:

CSHARP
logger.LogInformation(
    "Calling API with token {Token}",
    token);

І тепер:

Secret чудово захищений у Vault...

...до моменту, коли застосунок записав його в лог.

Те саме може статися з:

Authorization header
Cookies
JWT
Connection Strings
Request Body
Personal Data

Тому logging policy — теж частина security.

15

Словник термінів простими словами

  • Secret — конфіденційне значення, яке дає доступ: пароль, API key, token, private key або connection string.
  • Credential — дані, якими користувач чи застосунок підтверджує право на доступ.
  • Git history — історія commit-ів; видалення секрету з поточного файлу не прибирає його зі старих версій.
  • Secret Manager / Vault — спеціальне сховище, яке захищає секрети та контролює їх видачу.
  • Application Identity — посвідчення застосунку, за яким сховище визначає дозволені секрети.
  • Least privilege — кожен користувач і сервіс отримує лише мінімально потрібний доступ.
  • Secret rotation — керована заміна старого секрету новим.
  • Revocation — відкликання секрету, після якого він більше не працює.
  • Secret scanning — автоматичний пошук ключів і паролів у файлах та commit-ах.
  • False positive — рядок, схожий на секрет, але ним не є.
  • Audit log — журнал доступу до секретів.
  • Redaction / masking — приховування секретних частин у логах та інтерфейсах.
16

👶 Якщо зовсім просто

Secret у Git схожий на опублікований пароль. Навіть після нового commit-а копія може залишитися в історії, clone-ах, кешах і системах збірки. Тому такий secret вважають скомпрометованим.

Секрети зберігають у спеціальному сховищі. Застосунок підтверджує власну identity, отримує лише потрібне значення і не записує його в код, конфігурацію, чат або лог.

Якщо секрет уже витік, його відкликають або обмежують, створюють новий, оновлюють застосунки, перевіряють роботу й досліджують використання старого ключа. Простого очищення Git недостатньо.

17

🧠 Що варто запам'ятати

Secret не повинен бути частиною:

Source Code
Git
Documentation
Chat
Logs
Docker Image
Deployment Package

По можливості застосунок повинен отримувати його через контрольований механізм:

А доступ повинен будуватися за принципом:

↳
Least Privilege

Сервіс отримує тільки ті secrets, які реально потрібні йому для роботи.

І головне:

↳
Якщо secret потрапив у Git — недостатньо його видалити. Вважайте його скомпрометованим і змініть або відкличте.

🔐 Security Challenge

Розробник випадково зробив commit:

PROD_DB_PASSWORD=SuperSecret123

Через 2 хвилини він це помітив.

Repository приватний.

Commit уже був:

push

Розробник видалив пароль і зробив:

git commit
git push

У поточній версії коду пароля більше немає.

❓ Чи потрібно змінювати Production password?

А тепер складніше.

Усі Production secrets правильно зберігаються у Vault.

Але застосунок випадково пише:

Authorization: Bearer eyJhbGci...

у централізований ELK.

❓ Чи можемо ми після цього сказати, що наші secrets захищені?

І головне питання:

❓ Якби сьогодні потрібно було за одну годину змінити абсолютно всі credentials конкретного Production-сервісу — чи знаємо ми, де вони знаходяться, хто їх використовує і що саме потрібно перезапустити?
