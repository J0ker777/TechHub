Вступ

Коли розробник закінчує задачу, робота над зміною насправді ще далеко не завершена.

Код потрібно перевірити, зібрати, протестувати, перевірити на вразливості, сформувати артефакт, доставити його на потрібне середовище, правильно застосувати конфігурацію, перевірити працездатність і лише після цього вважати реліз успішним.

У невеликому проєкті все це іноді роблять вручну:

  1. розробник збирає застосунок;
  2. передає файли;
  3. хтось копіює їх на сервер;
  4. змінює конфігурацію;
  5. перезапускає сервіс;
  6. перевіряє, чи він запустився.

Поки система маленька, це може навіть працювати.

Але зі збільшенням кількості сервісів, розробників, середовищ і релізів дуже швидко з'являються проблеми:

  • хтось забув виконати тест;
  • хтось зібрав неправильну версію;
  • на TEST перевіряли один build, а на PROD потрапив інший;
  • конфігурація PROD випадково потрапила в TEST;
  • у repository опинився пароль;
  • після deployment сервіс формально запустився, але фактично не працює;
  • незрозуміло, який commit зараз знаходиться на PROD;
  • неможливо швидко повернути попередню версію.

CI/CD з'явився саме для того, щоб зробити цей процес повторюваним, контрольованим і максимально автоматизованим.

01

1. Що таке CI/CD

CI/CD — це набір практик та автоматизованих процесів, які дозволяють провести зміну програмного забезпечення від вихідного коду до працюючої версії в потрібному середовищі.

Абревіатура складається з двох основних частин:

CI — Continuous Integration безперервна інтеграція.

CD — Continuous Delivery / Continuous Deployment безперервна доставка або безперервне розгортання.

Спрощено весь процес можна представити так:

Developer
    │
    ▼
   Git
    │
    ▼
Pull Request
    │
    ▼
┌────────────── CI ──────────────┐
│                                │
│ Build                          │
│ Unit Tests                     │
│ SAST                           │
│ Dependency Scan                │
│ Packaging                      │
│                                │
└───────────────┬────────────────┘
                │
                ▼
            Artifact
                │
                ▼
┌────────────── CD ──────────────┐
│                                │
│ DEV                            │
│  ↓                             │
│ TEST                           │
│  ↓                             │
│ PRE-PROD                       │
│  ↓                             │
│ PROD                           │
│                                │
└────────────────────────────────┘

Але важливо розуміти:

↳
CI/CD — це не просто скрипт, який копіює файли на сервер.

Це цілий керований процес доставки програмного забезпечення.

02

2. Continuous Integration — CI

Уявімо, що над одним сервісом працюють п'ять розробників.

Кожен змінює код:

Developer A ── feature/login
Developer B ── feature/payment
Developer C ── feature/profile
Developer D ── bugfix/timeout
Developer E ── feature/report

Якщо всі працюватимуть ізольовано протягом декількох тижнів, у момент об'єднання змін може виявитися, що вони несумісні.

Саме звідси походить поняття Continuous Integration.

Ідея проста:

↳
Зміни потрібно регулярно інтегрувати в загальну кодову базу та автоматично перевіряти.

Типовий CI-процес виглядає приблизно так:

Developer
    │
    │ git push
    ▼
Repository
    │
    ▼
Pull Request
    │
    ▼
Pipeline
    │
    ├── Restore dependencies
    ├── Build
    ├── Unit Tests
    ├── Static Analysis
    ├── Dependency Scan
    └── Package

Якщо будь-яка критична перевірка не пройдена:

Pipeline = FAILED

і зміна не повинна рухатися далі.

03

3. Що відбувається після git push

Розглянемо типовий сценарій.

Розробник створив:

feature/payment-status

Вніс зміни та виконав:

BASH
git add .
git commit -m "Add payment status endpoint"
git push

Після цього створюється Pull Request.

Наприклад:

feature/payment-status
          │
          │ Pull Request
          ▼
        develop

Сам факт того, що код компілюється на комп'ютері розробника, ще нічого не гарантує.

CI pipeline повинен незалежно перевірити цей код.

04

4. Build

Перший очевидний етап — збірка.

Наприклад, для .NET:

BASH
dotnet restore
dotnet build --configuration Release

Для Node.js це може бути:

BASH
npm ci
npm run build

На цьому етапі вже можуть бути виявлені:

  • помилки компіляції;
  • відсутні dependencies;
  • неправильні версії бібліотек;
  • проблеми конфігурації build;
  • несумісність компонентів.

Тобто знамените:

↳
«А в мене локально працює»

для CI не є аргументом.

Pipeline виконує збірку у стандартизованому середовищі.

05

5. Automated Tests

Після успішної збірки запускаються автоматизовані тести.

Наприклад:

BASH
dotnet test

Pipeline може виконувати різні типи тестів.

Unit Tests

Перевіряють окремі функції або компоненти.

Наприклад:

CalculatePrice(100, 10%) → 90

Integration Tests

Перевіряють взаємодію компонентів:

Service
   │
   ├── Database
   ├── RabbitMQ
   └── External API

API Tests

Можуть автоматично перевіряти:

HTTP
GET /api/orders/123

та очікувати:

HTTP
200 OK

і певну структуру відповіді.

Якщо критичний тест не проходить:

Tests FAILED
      │
      ▼
Pipeline FAILED
      │
      X
Deployment

Код не повинен рухатися далі.

06

6. Security checks

CI/CD може бути частиною не лише процесу розробки, а й процесу безпеки.

Наприклад, pipeline може запускати:

Source Code
    │
    ├── SAST
    ├── SCA
    ├── Secret Scan
    └── License Scan

SAST

Static Application Security Testing аналізує вихідний код і намагається знайти потенційні вразливості.

Наприклад:

SQL Injection
Path Traversal
Command Injection
Hardcoded Password
Insecure Cryptography

SCA

Software Composition Analysis перевіряє сторонні бібліотеки.

Наприклад, застосунок використовує:

Library X 1.2.0

і для цієї версії відома критична CVE.

Pipeline може заблокувати build або deployment.

07

7. Quality Gate

Не кожна знайдена проблема обов'язково повинна блокувати pipeline.

Тому часто використовують поняття:

Quality Gate.

Наприклад, правила можуть бути такими:

Critical vulnerability → FAIL

High vulnerability     → FAIL

Medium vulnerability   → WARNING

Low vulnerability      → WARNING

Або:

Unit Tests < 100% success
        ↓
      FAIL

Таким чином рішення:

можна / не можна

приймається не вручну кожного разу, а відповідно до визначених правил.

08

8. Artifact — один із найважливіших елементів CI/CD

Після того як код:

✓ зібрався
✓ пройшов тести
✓ пройшов security checks

потрібно сформувати результат збірки.

Цей результат називається artifact.

Artifact може бути:

.zip
.tar.gz
.jar
.war
.exe
.dll
NuGet package
npm package
Docker image

Наприклад:

payment-service-2.4.1.zip

Це вже конкретна версія програми, яку можна розгортати.

09

9. Build once, deploy many

Це одна з найважливіших ідей правильно побудованого CI/CD.

Уявімо неправильний процес:

Source Code
   │
   ├── Build for TEST
   │       ↓
   │     TEST
   │
   └── Build for PROD
           ↓
         PROD

На перший погляд усе нормально.

Але виникає фундаментальна проблема.

На TEST перевіряли:

Build A

а на PROD потрапив:

Build B

Навіть якщо вони були створені з одного Git commit, це вже дві різні операції збірки.

Можуть відрізнятися:

  • dependencies;
  • версії build tools;
  • environment;
  • timestamps;
  • generated files;
  • package versions.

Тому правильніша модель:

              Build
                │
                ▼
        Artifact v2.4.1
                │
        ┌───────┼─────────┐
        ▼       ▼         ▼
       TEST  PRE-PROD    PROD

Тобто:

↳
Ми один раз створюємо artifact і просуваємо саме його через середовища.

Наприклад:

Commit:
8f31a9c

        ↓

Build:
20260901.153

        ↓

Artifact:
payment-service-2.4.1

        ↓

TEST
        ↓
PRE-PROD
        ↓
PROD

Саме цей artifact був протестований.

Саме цей artifact був перевірений.

Саме цей artifact повинен потрапити на PROD.

10

10. Але ж TEST і PROD мають різні налаштування

Так.

І тут часто виникає плутанина.

Різними повинні бути configuration, а не application artifact.

Наприклад:

Artifact
payment-service-2.4.1
        │
        ├── TEST configuration
        │
        ├── PRE-PROD configuration
        │
        └── PROD configuration

Для TEST:

DB_HOST=test-db
API_URL=https://test-api.example

Для PROD:

DB_HOST=prod-db
API_URL=https://api.example

Але application artifact залишається тим самим.

Це дозволяє сказати:

↳
На PROD розгорнута саме та версія програми, яку ми перевірили на TEST та PRE-PROD.
11

11. Secrets — окрема історія

Припустимо, застосунку потрібен пароль до бази даних.

Найгірший варіант:

YAML
DB_USER: production_user
DB_PASSWORD: SuperSecretPassword123

і цей файл знаходиться в Git.

Це означає, що секрет:

Git history
     │
     ├── Developer
     ├── Pipeline
     ├── Backup
     └── Repository clone

може поширитися набагато ширше, ніж очікувалося.

Навіть якщо потім видалити пароль із поточної версії файлу, він може залишитися в історії Git.

Тому secrets повинні зберігатися окремо.

Наприклад:

Application
     │
     ▼
Secret Store / Vault
     │
     ▼
DB Password

Pipeline може отримати необхідний секрет під час deployment, не записуючи його у repository.

12

12. Continuous Delivery

Після CI у нас є перевірений artifact.

Тепер його потрібно доставити.

Починається CD.

Наприклад:

Artifact
   │
   ▼
 DEV
   │
   ▼
 TEST
   │
   ▼
PRE-PROD
   │
   ▼
 PROD

Але це не означає, що кожен успішний commit автоматично повинен потрапляти на PROD.

Тут важливо розрізняти два поняття.

13

13. Continuous Delivery vs Continuous Deployment

Назви дуже схожі, але сенс різний.

Continuous Delivery

Система автоматично доводить software до стану:

↳
«Готово до deployment на PROD».

Але перед PROD може бути ручне підтвердження.

Artifact
   │
   ▼
 TEST
   │
   ▼
PRE-PROD
   │
   ▼
[APPROVAL]
   │
   ▼
 PROD

Людина підтверджує:

Deploy

Continuous Deployment

Якщо всі автоматичні перевірки пройдені:

Commit
   ↓
Build
   ↓
Tests
   ↓
Security
   ↓
Artifact
   ↓
TEST
   ↓
Validation
   ↓
PROD

deployment виконується автоматично.

Без ручного підтвердження.

Для критичних enterprise-систем частіше можна зустріти Continuous Delivery із контрольованим approval перед PROD.

14

14. Approvals та Gates

Перед deployment можуть існувати додаткові умови.

Наприклад:

PRE-PROD
    │
    ▼
Security Gate
    │
    ▼
QA Approval
    │
    ▼
Release Approval
    │
    ▼
PROD

Approval означає:

↳
відповідальна особа підтверджує можливість переходу на наступний етап.

Gate — це автоматична умова.

Наприклад:

Critical vulnerabilities = 0

або:

Integration tests = PASSED

або:

Health Check = OK

Тільки після виконання умов pipeline продовжується.

15

15. Pipeline as Code

Колись pipelines часто налаштовували вручну через UI.

Сучасний підхід — описувати pipeline як код.

Наприклад, у YAML.

Спрощений приклад:

YAML
trigger:
  branches:
    include:
      - main

steps:

- script: dotnet restore
  displayName: Restore dependencies

- script: dotnet build --configuration Release
  displayName: Build

- script: dotnet test
  displayName: Run tests

- script: dotnet publish --configuration Release
  displayName: Publish application

Це означає:

main changed
     │
     ▼
restore
     │
     ▼
build
     │
     ▼
test
     │
     ▼
publish

Перевага Pipeline as Code у тому, що pipeline:

  • версіонується;
  • проходить code review;
  • має історію змін;
  • може бути відтворений;
  • знаходиться поруч із кодом;
  • може змінюватися через Pull Request.

Тобто зміна процесу deployment стає такою ж контрольованою зміною, як і зміна application code.

16

16. Git і CI/CD

CI/CD дуже тісно пов'язаний із Git workflow.

Наприклад:

feature/*
    │
    ▼
Pull Request
    │
    ▼
develop
    │
    ▼
release
    │
    ▼
main

Але конкретна модель може бути іншою.

Наприклад:

GitFlow
GitHub Flow
Trunk-Based Development
Release Flow

CI/CD не вимагає конкретної Git-моделі.

Головне, щоб було зрозуміло:

яка зміна
     ↓
з якого commit
     ↓
створила який artifact
     ↓
і куди цей artifact був deployed
17

17. Pull Request як Quality Gate

Pull Request — це не просто кнопка Merge.

PR може бути важливим елементом CI.

Наприклад:

Developer
    │
    ▼
Pull Request
    │
    ├── Reviewer
    ├── Build
    ├── Unit Tests
    ├── SAST
    ├── Dependency Scan
    └── Policy Check
            │
            ▼
          Merge

Branch Policy може вимагати:

✓ мінімум 1 reviewer
✓ successful build
✓ successful tests
✓ відсутність merge conflicts
✓ security checks

І лише після цього дозволити merge.

18

18. Версіонування

У CI/CD надзвичайно важливо точно знати, яка версія де знаходиться.

Наприклад:

2.4.1

У Semantic Versioning це умовно:

MAJOR.MINOR.PATCH

Наприклад:

2.4.1
│ │ │
│ │ └── Patch
│ └──── Minor
└────── Major

Але самої версії іноді недостатньо.

Корисно мати зв'язок:

Version
   │
   ▼
Build
   │
   ▼
Commit

Наприклад:

Version: 2.4.1
Build:   20260901.153
Commit:  8f31a9c

Тоді, побачивши помилку на PROD, можна визначити:

яка версія працює
        ↓
яким pipeline вона створена
        ↓
з якого commit
        ↓
які зміни входили в цей commit

Це називається traceability.

19

19. Що зараз працює на PROD?

На це питання хороша CI/CD система повинна дозволяти відповісти дуже швидко.

Не:

↳
«Зараз запитаємо у розробника».

Не:

↳
«Здається, реліз минулого четверга».

Не:

↳
«У папці лежить final_v2_new_fixed.zip».

А конкретно:

Environment: PROD
Service: payment-service

Version: 2.4.1
Build: 20260901.153
Commit: 8f31a9c
Deployed: 2026-09-01 18:42
Pipeline: Release #481

Це принципово важливо при:

  • інцидентах;
  • аудитах;
  • rollback;
  • аналізі дефектів;
  • security incidents.
20

20. Database migrations

Deployment application — це ще не вся історія.

Дуже часто нова версія вимагає зміни бази даних.

Наприклад:

SQL
ALTER TABLE customers
ADD COLUMN external_id VARCHAR(100);

Тоді pipeline може виглядати так:

Deploy application
       │
       ▼
Database migration
       │
       ▼
Health Check

Але тут виникає серйозна проблема.

Що буде, якщо application можна повернути назад, а структура бази вже змінилася?

Наприклад:

Application v2
       │
       ▼
Migration DB v2
       │
       ▼
ERROR
       │
       ▼
Rollback Application → v1

Але:

Database = v2
Application = v1

і стара версія application може вже не вміти працювати з новою структурою.

Тому database migrations повинні проектуватися з урахуванням deployment та rollback.

21

21. Rollback

Що робити, якщо після deployment на PROD виникла проблема?

Наприклад:

v2.4.1
   │
   ▼
PROD
   │
   ▼
ERROR

Один із варіантів:

v2.4.1
   │
   X
   │
   ▼
v2.4.0

Тобто повернути попередній artifact.

Якщо artifacts правильно зберігаються, pipeline вже має:

payment-service-2.4.0
payment-service-2.4.1

і не потрібно:

шукати старий код
        ↓
переключати branch
        ↓
збирати його заново
        ↓
сподіватися, що вийде те саме

Можна використати вже відомий artifact.

22

22. Rollback чи Roll-forward?

Rollback не завжди є найкращим рішенням.

Іноді проблему простіше виправити новою версією.

Наприклад:

2.4.1 → ERROR

замість:

2.4.1 → 2.4.0

робимо:

2.4.1
  ↓
fix
  ↓
2.4.2

Це називається roll-forward.

Вибір залежить від:

  • характеру проблеми;
  • стану бази;
  • сумісності API;
  • часу виправлення;
  • критичності інциденту.

Головне — стратегія повинна бути продумана до інциденту, а не під час нього.

23

23. Deployment ≠ успішний реліз

Pipeline повідомив:

Deployment succeeded

Чи означає це, що система працює?

Ні.

Це може означати лише:

файли скопійовані

або:

процес запущений

Але application може:

  • не підключатися до БД;
  • не бачити RabbitMQ;
  • не мати доступу до Vault;
  • отримувати помилки від зовнішнього API;
  • не мати потрібної конфігурації.

Тому після deployment потрібна перевірка.

24

24. Health Check

Наприклад, сервіс має endpoint:

HTTP
GET /health

і повертає:

JSON
{
  "status": "Healthy"
}

Pipeline може зробити:

Deploy
   │
   ▼
Wait 10 sec
   │
   ▼
GET /health
   │
   ├── 200 OK ─────→ SUCCESS
   │
   └── ERROR ──────→ FAILED

Більш розвинений health check може перевіряти:

Application
    │
    ├── Database        ✓
    ├── RabbitMQ        ✓
    ├── Redis           ✓
    └── External API    ✓

Тобто deployment завершується не тоді, коли файли опинилися на сервері, а коли є достатні підстави вважати нову версію працездатною.

25

25. Smoke Tests

Після deployment можна виконати базові функціональні перевірки.

Наприклад:

GET /health           → 200
GET /api/version      → 2.4.1
GET /api/customers/1  → 200
POST /api/orders      → 201

Це називають Smoke Tests.

Їх мета — швидко визначити:

↳
система після deployment взагалі виконує основні функції чи ні?
26

26. Zero-downtime deployment

Простий deployment може виглядати так:

Stop application
       ↓
Deploy
       ↓
Start application

У цей момент користувачі можуть отримувати:

503 Service Unavailable

Для деяких систем це прийнятно.

Для систем, які повинні працювати 24/7, — ні.

Тоді застосовують інші deployment strategies.

27

27. Rolling Deployment

Уявімо три instance:

Load Balancer
   │
   ├── App 1 v1
   ├── App 2 v1
   └── App 3 v1

Оновлюємо їх поступово:

App 1 → v2
App 2 → v1
App 3 → v1

потім:

App 1 → v2
App 2 → v2
App 3 → v1

і нарешті:

App 1 → v2
App 2 → v2
App 3 → v2

Користувачі продовжують працювати під час deployment.

Але тут з'являється нова вимога:

↳
v1 та v2 певний час повинні вміти працювати одночасно.

Це особливо важливо для API та database migrations.

28

28. Blue/Green Deployment

Є два однакових середовища:

BLUE  → v1
GREEN → v2

Користувачі зараз працюють із:

Traffic → BLUE

Нову версію розгортаємо в GREEN:

BLUE  → v1 ← users
GREEN → v2 ← testing

Перевіряємо GREEN.

Якщо все добре:

Traffic
   │
   ▼
 GREEN → v2

BLUE залишається доступним для швидкого повернення.

Перевага — дуже швидке переключення.

Недолік — потрібно фактично підтримувати два середовища.

29

29. Canary Deployment

Ще цікавіший варіант.

Спочатку нову версію отримує невелика частина користувачів:

Users
 │
 ├── 95% → v1
 │
 └──  5% → v2

Спостерігаємо:

Errors
Latency
CPU
Memory
Business metrics

Якщо все добре:

25% → v2

потім:

50% → v2

і нарешті:

100% → v2

Це дозволяє зменшити blast radius проблемного релізу.

30

30. Логи та моніторинг після deployment

CI/CD не повинен існувати окремо від observability.

Після deployment важливо бачити:

New Version
     │
     ▼
Logs
Metrics
Errors
Health

Наприклад:

Error rate:
0.2% → 7.8%

одразу після deployment.

Це сильний сигнал, що нова версія має проблему.

Тому зрілий release process виглядає не так:

Deploy → SUCCESS → додому

а приблизно так:

Deploy
   ↓
Health Check
   ↓
Smoke Tests
   ↓
Logs
   ↓
Metrics
   ↓
Stabilization period
   ↓
Release successful
31

31. CI/CD і відповідальність команди

Іноді CI/CD помилково вважають виключно зоною відповідальності DevOps.

Це не зовсім так.

DevOps може реалізовувати та підтримувати інфраструктуру pipeline, але сам pipeline описує процес доставки продукту, у якому беруть участь різні ролі.

32

32. Що повинен розуміти Developer

Developer повинен розуміти CI/CD досить глибоко.

Зокрема:

  • що запускає pipeline;
  • як виконується build;
  • які tests запускаються;
  • чому pipeline впав;
  • як формується artifact;
  • як application отримує configuration;
  • де знаходяться secrets;
  • як виконуються migrations;
  • як працюють health checks;
  • як версія потрапляє на середовище;
  • що відбувається під час rollback.

Позиція:

↳
«Це DevOps, мене не стосується»

не працює.

Якщо код розробника проходить через pipeline, розробник повинен розуміти цей шлях.

33

33. Що повинен розуміти QA

QA не обов'язково повинен уміти будувати складний pipeline.

Але він повинен розуміти:

що саме зараз розгорнуто на TEST

і:

який artifact він тестує

QA повинен мати можливість відповісти:

Яку версію я тестував?

Який build?

Чи саме цей build піде на PROD?

Чи пройшли automated tests?

Чи виконалися migrations?

Чи успішно пройшов deployment?

Інакше може виникнути ситуація:

QA протестував Build A
            │
            ▼
        "Все добре"

PROD отримав Build B

Тоді саме поняття перевірки перед релізом частково втрачає сенс.

34

34. Що повинен розуміти BA

Business Analyst не зобов'язаний писати YAML pipeline.

Але якщо BA бере участь у прийманні функціоналу, аналізі дефектів або релізі, йому корисно розуміти:

  • що таке environment;
  • що таке build;
  • що таке artifact;
  • що означає deployment;
  • чому TEST і PROD можуть поводитися по-різному;
  • як визначити версію;
  • що таке configuration;
  • що deployment може бути успішним технічно, але функціонал — непрацездатним.

Наприклад, користувач каже:

↳
«На PROD немає функції, яку ми тестували».

Перші питання повинні бути не лише про бізнес-логіку.

Потрібно також перевірити:

Яка версія на PROD?

Яка версія була на TEST?

Чи однаковий artifact?

Чи правильно застосована конфігурація?

Чи була feature включена?
35

35. Що повинен розуміти PM

PM також не потрібно писати pipeline.

Але PM, який відповідає за delivery, повинен розуміти сам процес доставки.

Наприклад:

Code Complete

не означає:

Ready for PROD

Між ними може бути:

Code Complete
     ↓
Pull Request
     ↓
Code Review
     ↓
Build
     ↓
Tests
     ↓
Security
     ↓
Artifact
     ↓
TEST
     ↓
QA
     ↓
PRE-PROD
     ↓
Approval
     ↓
PROD

Якщо PM не розуміє цього ланцюжка, йому складно реально оцінювати готовність релізу.

36

36. Що повинен розуміти DevOps

Для DevOps це вже глибока технічна зона.

Необхідно розуміти:

  • pipeline architecture;
  • runners/agents;
  • artifacts;
  • repositories;
  • credentials;
  • service connections;
  • environments;
  • approvals;
  • deployment strategies;
  • infrastructure;
  • secrets management;
  • monitoring;
  • rollback;
  • networking;
  • permissions;
  • audit;
  • availability.

DevOps повинен зробити процес максимально:

repeatable
predictable
secure
observable
recoverable
37

37. Типова погана схема релізу

Розглянемо умовний приклад.

Developer
   │
   ▼
Build locally
   │
   ▼
ZIP
   │
   ▼
Telegram / Share
   │
   ▼
Administrator
   │
   ▼
Copy to server
   │
   ▼
Edit config manually
   │
   ▼
Restart

Які тут проблеми?

Практично на кожному кроці.

Незрозуміло:

з якого commit build
хто його створив
які tests пройшли
які dependencies використовувалися
чи перевіряла його security
чи саме цей build тестував QA
що змінили у config
хто виконав deployment
як повернути попередню версію

Це не означає, що ручний deployment завжди заборонений.

Але що більше ручних неконтрольованих операцій — то більший операційний ризик.

38

38. «А ми автоматизували deployment»

Інша крайність.

Команда каже:

↳
«У нас є CI/CD».

А pipeline виглядає так:

Build
   ↓
Copy files
   ↓
Restart service

Це вже автоматизація, але зрілим CI/CD такий процес назвати складно.

Хороший pipeline може включати:

Source
   ↓
Build
   ↓
Unit Tests
   ↓
SAST
   ↓
SCA
   ↓
Artifact
   ↓
Deploy
   ↓
Migration
   ↓
Health Check
   ↓
Smoke Tests
   ↓
Monitoring

Тобто важлива не наявність YAML-файлу.

Важливий контрольований delivery process.

39

39. Типові помилки CI/CD

1. Збирати PROD окремо

TEST Build ≠ PROD Build

Ми вже розібрали, чому це погано.

2. Зберігати secrets у repository

password=123456

Pipeline не робить такий підхід безпечним.

3. Виконувати половину deployment вручну

Наприклад:

Pipeline → files

а потім:

зайти на сервер
скопіювати config
виконати SQL
перезапустити service

Такі операції складно повторювати гарантовано однаково.

4. Не зберігати artifacts

Якщо потрібно зробити rollback, команда змушена заново збирати старий код.

Це погіршує відтворюваність.

5. Не мати traceability

Не можна швидко відповісти:

Commit → Build → Artifact → PROD

6. Вважати deployment успішним лише тому, що pipeline зелений

Deploy SUCCESS

ще не означає:

Application HEALTHY

7. Не продумати database rollback

Application повернули.

Database — ні.

Система не запускається.

8. Не перевіряти dependencies

Ваш код може бути безпечним.

Але:

Application
   │
   └── vulnerable-library

створює вразливість у всьому application.

9. Робити pipeline, який ніхто не розуміє

Pipeline написав один DevOps.

Через рік він пішов.

Ніхто не знає:

чому тут цей script
чому тут sleep 60
що буде, якщо його прибрати
звідки береться password
чому PROD працює тільки після restart

Pipeline — теж код.

Він потребує:

  • структури;
  • документації;
  • review;
  • підтримки.
40

40. CI/CD ≠ DevOps

Ці поняття часто використовують як синоніми.

Але це неправильно.

CI/CD — це набір практик і процесів автоматизованої інтеграції та доставки software.

DevOps — значно ширший підхід до взаємодії development та operations.

DevOps охоплює:

Development
Infrastructure
Automation
Monitoring
Operations
Incident Management
Security
Delivery

CI/CD є важливою частиною цього світу, але не всім DevOps.

41

41. Повний приклад

Тепер зберемо все разом.

Розробник реалізував:

feature/customer-search

Крок 1

Виконує:

BASH
git push

Крок 2

Створює Pull Request.

feature/customer-search
        ↓
      develop

Крок 3

Запускається CI:

Restore
   ↓
Build
   ↓
Unit Tests
   ↓
SAST
   ↓
SCA

Усе пройдено:

✓ Build
✓ Tests
✓ Security

Крок 4

Reviewer перевіряє код.

PR Approved

Крок 5

Зміна потрапляє в цільову гілку.

Крок 6

Створюється release artifact:

customer-service-3.7.0

Пов'язаний із:

Commit: a8c921f
Build: 20260901.221

Крок 7

Artifact розгортається на TEST.

customer-service-3.7.0
          ↓
         TEST

Крок 8

Pipeline виконує:

Health Check
Smoke Tests

Крок 9

QA тестує:

Version 3.7.0
Build 20260901.221

Крок 10

Той самий artifact переходить у PRE-PROD:

3.7.0
  ↓
PRE-PROD

Крок 11

Виконуються додаткові перевірки.

Крок 12

Отримано approval на PROD.

Крок 13

Той самий artifact:

customer-service-3.7.0

розгортається на PROD.

Крок 14

Автоматично перевіряються:

Health
API
Dependencies

Крок 15

Перевіряються:

Logs
Metrics

Після цього реліз можна вважати завершеним.

42

42. Що ми отримали

Тепер для PROD можна побудувати повний ланцюжок:

PROD
 │
 ▼
Version 3.7.0
 │
 ▼
Artifact customer-service-3.7.0
 │
 ▼
Build 20260901.221
 │
 ▼
Commit a8c921f
 │
 ▼
Pull Request #482
 │
 ▼
Developer changes

І в інший бік:

Commit
   ↓
PR
   ↓
Build
   ↓
Artifact
   ↓
TEST
   ↓
PRE-PROD
   ↓
PROD

Це і є контрольований software delivery process.

43

43. Хороший CI/CD не означає «автоматизувати все»

Не кожна система повинна мати:

Commit → PROD

за п'ять хвилин.

Для одного продукту це може бути чудовою моделлю.

Для іншого потрібні:

QA
Security Approval
Business Approval
Maintenance Window
Change Request

і це нормально.

Мета CI/CD не полягає в тому, щоб прибрати людей із процесу.

Мета полягає в тому, щоб:

↳
усунути непотрібні ручні операції та зробити необхідні контрольні точки явними, повторюваними і перевірюваними.
44

44. CI/CD не виправляє поганий процес

Це теж важливий момент.

Якщо процес виглядає так:

незрозуміло хто погоджує
незрозуміло хто тестує
незрозуміло що релізимо
немає критеріїв готовності
немає rollback plan

автоматизація не вирішить проблему магічно.

Можна просто отримати:

↳
дуже швидкий автоматизований поганий процес.

Спочатку потрібно зрозуміти:

WHAT
WHO
WHEN
UNDER WHICH CONDITIONS

і вже після цього:

AUTOMATE
45

45. Чекліст зрілого CI/CD

Для свого проєкту можна поставити такі питання.

Source

  • Чи весь application code знаходиться у version control?
  • Чи використовуються Pull Requests?
  • Чи налаштовані branch policies?
  • Чи можна визначити commit для кожного release?

Build

  • Чи build виконується автоматично?
  • Чи відтворюваний build?
  • Чи використовується однаковий процес збірки?

Tests

  • Чи запускаються Unit Tests?
  • Чи є Integration Tests?
  • Чи можуть невдалі tests заблокувати release?

Security

  • Чи є SAST?
  • Чи перевіряються dependencies?
  • Чи є Quality Gates?
  • Чи перевіряється repository на secrets?

Artifact

  • Чи формується versioned artifact?
  • Чи зберігаються старі artifacts?
  • Чи можна однозначно пов'язати artifact із commit?

Environments

  • Чи розділені:
DEV
TEST
PRE-PROD
PROD
  • Чи використовують вони один і той самий artifact?

Configuration

  • Чи відділена configuration від application?
  • Чи немає environment-specific build?

Secrets

  • Чи винесені secrets із Git?
  • Чи контролюється доступ до них?

Deployment

  • Чи deployment автоматизований?
  • Чи зрозуміло, хто може запускати PROD deployment?
  • Чи є approvals?

Database

  • Чи автоматизовані migrations?
  • Чи продумана backward compatibility?
  • Чи є план rollback?

Validation

  • Чи є health checks?
  • Чи є smoke tests?
  • Чи перевіряються logs та metrics після deployment?

Recovery

  • Чи можна швидко виконати rollback?
  • Чи відомо, який попередній artifact був стабільним?

Audit

  • Чи можна відповісти:
Хто?
Що?
Коли?
Яку версію?
З якого commit?
На яке середовище?
З яким результатом?

Якщо на більшість цих питань є чіткі відповіді — процес уже має хорошу основу.

46. Головна думка

CI/CD іноді сприймають як:

↳
«DevOps написав YAML, який щось там деплоїть».

Але насправді CI/CD описує один із найважливіших процесів у розробці програмного забезпечення:

↳
як зміна перетворюється з коду розробника на працюючий функціонал у користувача.

Між:

git commit

та:

PROD

повинен існувати контрольований ланцюжок:

CODE
  ↓
REVIEW
  ↓
BUILD
  ↓
TEST
  ↓
SECURITY
  ↓
ARTIFACT
  ↓
DEPLOY
  ↓
VERIFY
  ↓
MONITOR

І для кожного кроку бажано мати відповідь:

Хто його виконує?

Що буде, якщо перевірка не пройдена?

Чи можемо ми повернутися назад?

Саме тому CI/CD — це не лише тема для DevOps.

Developer повинен розуміти, як збирається і доставляється його код.

QA — яку саме версію він тестує.

BA — чому функціонал на різних середовищах може поводитися по-різному.

PM — що Development Done ще не означає Ready for PROD.

Security — де і як застосовуються security gates.

DevOps — як зробити весь цей процес надійним, безпечним і повторюваним.

А команда в цілому повинна мати можливість у будь-який момент пройти весь шлях:

PROD
  ↓
Version
  ↓
Artifact
  ↓
Build
  ↓
Commit
  ↓
Pull Request
  ↓
Change

і у зворотному напрямку:

Change
  ↓
Commit
  ↓
Build
  ↓
Artifact
  ↓
TEST
  ↓
PRE-PROD
  ↓
PROD

Якщо цей ланцюжок прозорий, відтворюваний і контрольований — CI/CD виконує свою головну задачу.

Коротко

CI відповідає на питання:

↳
Чи можемо ми автоматично довести, що зміна достатньо якісна для подальшого руху?

CD відповідає на питання:

↳
Чи можемо ми контрольовано доставити перевірену версію в потрібне середовище?

А один із найважливіших принципів усього процесу:

↳
Build once — deploy many.

Ми не повинні окремо створювати «версію для TEST» і «версію для PROD».

Ми створюємо один перевірений artifact, знаємо, з якого commit він отриманий, і просуваємо саме його:

            Artifact
               │
               ▼
              TEST
               │
               ▼
           PRE-PROD
               │
               ▼
              PROD

Тоді фраза:

↳
«Ми протестували цю версію перед релізом»

дійсно означає, що на PROD потрапила саме та версія, яку тестували.
