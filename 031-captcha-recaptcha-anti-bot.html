01

1. CAPTCHA є, а бот усе одно працює

Уявімо корпоративний вебсайт, на якому користувачі можуть реєструватися, залишати звернення та переглядати інформацію.

Одного дня команда помітила підозрілу активність: за годину через контактну форму надійшли тисячі однакових повідомлень.

Розробники додали CAPTCHA — перевірку з галочкою «Я не робот».

Спаму стало менше. Здавалося, проблему вирішено.

Але через кілька днів автоматизовані повідомлення знову почали надходити.

Під час аналізу з'ясувалося, що бот узагалі не відкривав вебсторінку. Він напряму викликав API:

HTTP
POST /api/contact HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "email": "bot@example.com",
  "message": "Автоматизоване повідомлення"
}

Сервер приймав запит і створював звернення.

Проблема була не в CAPTCHA, а в тому, що Backend не перевіряв її результат.

Цей приклад добре демонструє, чому недостатньо просто додати CAPTCHA на сторінку. Потрібно розуміти, як вона працює, що саме перевіряє та які має обмеження.

02

2. Що таке CAPTCHA?

CAPTCHA — Completely Automated Public Turing test to tell Computers and Humans Apart.

Українською — повністю автоматизований публічний тест для розрізнення комп'ютерів і людей.

Основна ідея: запропонувати перевірку, яку людині відносно легко пройти, а автоматизованій програмі — складніше.

Найвідоміші приклади — введення спотворених символів, вибір фотографій зі світлофорами або галочка «Я не робот».

Але сучасна CAPTCHA може взагалі не показувати завдання. Замість цього система аналізує технічні характеристики клієнта, результати перевірок браузера та інші сигнали.

Від чого захищає CAPTCHA?

ЗагрозаДії бота
SpamМасово надсилає повідомлення
Fake RegistrationСтворює фальшиві акаунти
Credential StuffingПеревіряє викрадені логіни й паролі
Password SprayingПеребирає поширені паролі
ScrapingАвтоматично збирає інформацію
ScalpingМасово скуповує товари чи бронює квитки
Form AbuseЗловживає формами та бізнес-операціями

CAPTCHA може зменшувати ризики таких зловживань, але не гарантує їх повного блокування.

Важливо: не всі боти шкідливі. Пошукові роботи, системи моніторингу та дозволені інтеграції також використовують автоматизацію.

Тому мета захисту — відрізняти дозволену активність від небажаної.

03

3. Які бувають CAPTCHA?

Спочатку CAPTCHA використовували завдання, які людям було значно простіше виконувати, ніж комп'ютерам.

Із розвитком OCR, комп'ютерного зору та штучного інтелекту ці завдання поступово втрачали ефективність.

OCR — Optical Character Recognition (оптичне розпізнавання символів).

Основні види

ТипПринцип роботиОсновне обмеження
Text CAPTCHAРозпізнавання спотворених символівOCR може автоматизувати розпізнавання
Image CAPTCHAВибір зображень за умовоюComputer Vision здатний розв'язувати частину завдань
Audio CAPTCHAРозпізнавання аудіозаписуSpeech-to-Text може автоматизувати перевірку
Checkbox CAPTCHAГалочка та можливі додаткові перевіркиСама галочка не доводить, що клієнт — людина
Invisible CAPTCHAФонова перевірка клієнтаРезультат залежить від якості аналізу сигналів
Proof of WorkВиконання обчислювального завданняБот також може виконати обчислення

Як розвивалися підходи

Це умовна схема еволюції. Сьогодні різні підходи використовуються паралельно.

Чим цікавий Proof of Work?

Proof of Work (PoW) — доказ виконаної обчислювальної роботи.

Замість розпізнавання символів браузер виконує певне обчислювальне завдання.

Для одного запиту витрати можуть бути невеликими. Але якщо програма намагається автоматизувати тисячі операцій, сумарні витрати зростають.

Головне обмеження: PoW не доводить, що перед системою людина. Він лише підвищує вартість автоматизації.

04

4. CAPTCHA та reCAPTCHA — у чому різниця?

Ці поняття часто використовують як синоніми, але це неправильно.

CAPTCHA — загальна назва класу технологій.

reCAPTCHA — конкретна технологія Google.

Основні версії reCAPTCHA

ВерсіяЯк працюєРезультат
reCAPTCHA v1Розпізнавання текстуІсторична версія, більше не працює
reCAPTCHA v2 CheckboxГалочка та можливе додаткове завданняРезультат перевірки
reCAPTCHA v2 InvisibleПеревірка без обов'язкової галочкиРезультат перевірки
reCAPTCHA v3Оцінка ризику взаємодіїScore від 0 до 1

Найважливіша відмінність — між v2 та v3.

reCAPTCHA v2

Користувач проходить перевірку, після чого браузер отримує спеціальний токен.

Token (токен) — значення, яке передається серверу для підтвердження результату перевірки.

Backend надсилає токен до сервісу reCAPTCHA та отримує відповідь.

Наприклад:

JSON
{
  "success": true,
  "challenge_ts": "2026-10-10T10:30:00Z",
  "hostname": "example.com"
}

Тут:

  • success — результат перевірки токена;
  • challenge_ts — час, пов'язаний із перевіркою;
  • hostname — домен, на якому виконувалася CAPTCHA.

Для класичної reCAPTCHA токен має строк дії дві хвилини та може бути перевірений лише один раз.

Джерело: Google — Verifying the user's response.

reCAPTCHA v3

reCAPTCHA v3 використовує оцінку ризику.

Score — числовий показник, який допомагає оцінити ймовірність легітимної взаємодії.

У класичній reCAPTCHA v3:

  • 1.0 — висока ймовірність легітимної взаємодії;
  • 0.0 — висока ймовірність автоматизації.

Приклад:

JSON
{
  "success": true,
  "score": 0.32,
  "action": "contact_submit",
  "hostname": "example.com"
}

Тут виникає цікава ситуація.

success = true, але score = 0.32.

Це не суперечність.

Перший параметр означає, що токен успішно перевірений.

Другий — що сама взаємодія оцінюється як підозріла.

Action — назва операції, для якої виконувалася перевірка.

Наприклад: login, register, contact_submit.

Backend повинен перевіряти, що отриманий action відповідає очікуваній бізнес-операції.

Джерело: Google — reCAPTCHA v3.

05

5. Практичний експеримент: reCAPTCHA v2 проти v3

Розглянемо одну форму звернення на example.com.

Користувач заповнює:

JSON
{
  "email": "user@example.com",
  "message": "Потрібна консультація"
}

Frontend надсилає запит:

HTTP
POST /api/contact HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "email": "user@example.com",
  "message": "Потрібна консультація",
  "captchaToken": "<captcha-token>"
}

Варіант А. reCAPTCHA v2

Backend перевіряє токен і отримує:

JSON
{
  "success": true,
  "hostname": "example.com"
}

Після перевірки необхідних параметрів Backend може перейти до виконання бізнес-операції.

Модель:

Токен дійсний → дозволено перейти до наступних серверних перевірок.

Варіант Б. reCAPTCHA v3

Тепер використовуємо v3 з операцією:

action = contact_submit

Backend отримує:

JSON
{
  "success": true,
  "score": 0.32,
  "action": "contact_submit",
  "hostname": "example.com"
}

Токен успішно перевірений, але оцінка ризику низька.

Тому Backend застосовує налаштовану політику.

Наприклад:

ScoreРішення
0.70–1.00Створити звернення
0.40–0.69Передати на модерацію
0.00–0.39Відхилити

Це умовні пороги для навчального прикладу, а не універсальні рекомендації Google.

У реальній системі значення потрібно визначати за статистикою трафіку та характером бізнес-операцій.

Головна різниця

reCAPTCHA v2 переважно повідомляє результат перевірки.

reCAPTCHA v3 додатково надає оцінку ризику, яку Backend використовує для вибору подальших дій.

Водночас обидва механізми потребують серверної перевірки токена.

Примітка: приклади вище використовують класичний SiteVerify. Для нових інтеграцій Google Cloud рекомендує API CreateAssessment, який має інший формат відповідей.

Джерело: Google Cloud — Verify reCAPTCHA responses.

6. Сучасні альтернативи reCAPTCHA

Google — не єдиний постачальник CAPTCHA.

РішенняОсновний підхідОсобливість
Google reCAPTCHAЗавдання та оцінка ризикуv2, v3, Google Cloud API
Cloudflare TurnstileПеревірка клієнтського середовищаManaged, Non-Interactive, Invisible
hCaptchaПеревірочні завдання та аналіз ризикуРізні режими перевірки
Friendly CaptchaОбчислювальні завдання й оцінка ризикуВикористання криптографічних перевірок
Власна CAPTCHAЗалежить від реалізаціїПовний контроль і власна відповідальність за захист

Cloudflare Turnstile

Підтримує три режими:

Managed — система визначає, чи потрібна додаткова інтерактивна перевірка.

Non-Interactive — перевірка виконується без дій користувача.

Invisible — перевірка не відображається у вигляді окремого компонента.

Turnstile повертає токен, який потрібно перевірити на Backend.

Токен має строк дії 300 секунд і призначений для одноразової перевірки.

Джерело: Cloudflare Turnstile.

hCaptcha

Використовує перевірочні завдання та додаткові механізми оцінки ризику.

Результат перевірки також підтверджується сервером через API провайдера.

Джерело: hCaptcha Documentation.

Friendly Captcha

Використовує криптографічні обчислювальні завдання та інші сигнали ризику.

Це приклад того, що CAPTCHA не обов'язково повинна містити зображення або текст.

Джерело: Friendly Captcha Documentation.

Як вибрати рішення?

Порівнювати варто не лише зовнішній вигляд.

Важливі критерії:

  • ефективність проти потрібних типів автоматизації;
  • складність інтеграції з Backend;
  • доступність SDK та документації;
  • наявність оцінки ризику;
  • затримка перевірки;
  • вартість і тарифні обмеження;
  • захист даних та політика конфіденційності;
  • можливості тестування й моніторингу.

Немає рішення, яке буде оптимальним абсолютно для всіх систем.

07

7. Як CAPTCHA працює технічно

Повернемося до нашого прикладу з формою звернення.

У системі є чотири компоненти:

Browser — браузер користувача.

Backend — сервер бізнес-логіки.

CAPTCHA Provider — сервіс перевірки.

Database — база даних звернень.

Архітектура

Що відбувається покроково?

Крок 1. Ініціалізація

Frontend завантажує компонент CAPTCHA.

Для цього використовується sitekey — публічний ідентифікатор інтеграції.

Його можна передавати браузеру.

Крок 2. Перевірка клієнта

CAPTCHA Provider виконує перевірку та повертає токен.

Крок 3. Відправлення форми

Frontend додає токен до HTTP-запиту.

Крок 4. Серверна перевірка

Backend передає токен CAPTCHA Provider.

Для цього використовується secret key — секретний ключ, який повинен зберігатися лише на серверній стороні.

Крок 5. Прийняття рішення

Backend перевіряє результат, домен, операцію та score, якщо він доступний.

Крок 6. Виконання операції

Лише після успішного проходження всіх необхідних перевірок Backend створює звернення в Database.

Приклад HTTP-запиту до reCAPTCHA

Для класичного SiteVerify:

HTTP
POST /recaptcha/api/siteverify HTTP/1.1
Host: www.google.com
Content-Type: application/x-www-form-urlencoded

secret=<server-secret>&response=<captcha-token>

Тут:

  • secret — секретний ключ інтеграції;
  • response — токен, отриманий від браузера.

Backend не повинен приймати рішення лише на основі факту наявності токена.

Його необхідно перевірити через CAPTCHA Provider.

08

8. Приклад перевірки CAPTCHA на Backend

Розглянемо спрощену реалізацію для ASP.NET Core / .NET 8.

Приклад використовує класичну reCAPTCHA v3 та SiteVerify.

Для демонстрації вважаємо, що:

  • сайт працює на example.com;
  • операція називається contact_submit;
  • умовний поріг score дорівнює 0.70;
  • HttpClient передається через Dependency Injection;
  • секрет зберігається в серверній конфігурації.
CSHARP
using System.Net.Http.Json;

public sealed record RecaptchaResponse(
    bool Success,
    double? Score,
    string? Action,
    string? Hostname
);

public sealed class CaptchaVerifier
{
    private readonly HttpClient _client;
    private readonly string _secret;

    public CaptchaVerifier(
        HttpClient client,
        IConfiguration configuration)
    {
        _client = client;

        _secret = configuration["Captcha:Secret"]
            ?? throw new InvalidOperationException(
                "CAPTCHA secret is missing");
    }

    public async Task<bool> VerifyAsync(
        string token,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(token))
            return false;

        using var content = new FormUrlEncodedContent(
            new Dictionary<string, string>
            {
                ["secret"] = _secret,
                ["response"] = token
            });

        using var response = await _client.PostAsync(
            "https://www.google.com/recaptcha/api/siteverify",
            content,
            cancellationToken);

        response.EnsureSuccessStatusCode();

        var result = await response.Content
            .ReadFromJsonAsync<RecaptchaResponse>(
                cancellationToken: cancellationToken);

        return result is not null
            && result.Success
            && result.Hostname == "example.com"
            && result.Action == "contact_submit"
            && result.Score >= 0.70;
    }
}

Що робить цей код?

Спочатку перевіряє, чи передано токен.

Потім викликає API reCAPTCHA, передаючи серверний секрет і токен.

Після отримання відповіді перевіряє чотири умови:

  1. Токен успішно перевірено.
  2. Домен відповідає очікуваному.
  3. action відповідає бізнес-операції.
  4. score не нижчий за налаштований поріг.

Якщо хоча б одна умова не виконується, метод повертає false.

Це навчальний приклад, а не готова production-реалізація.

Тут не показані налаштування таймаутів, обробка мережевих помилок, логування, Rate Limiting та інтеграція з Database.

Також метод повертає лише bool, тому не реалізує наш сценарій середнього ризику з модерацією. У повній системі варто повертати структурований результат перевірки.

09

9. Чому CAPTCHA на Frontend недостатньо

Припустимо, розробник реалізував перевірку лише у JavaScript:

JAVASCRIPT
if (captchaCompleted) {
    submitForm();
}

Це керує поведінкою інтерфейсу, але не забезпечує серверний контроль.

Бот може напряму викликати:

HTTP
POST /api/contact HTTP/1.1
Host: example.com
Content-Type: application/json

{
  "email": "test@example.com",
  "message": "Запит без CAPTCHA"
}

Якщо Backend створює звернення, захист можна обійти.

Як має бути правильно

Важливий принцип:

Frontend validation ≠ Backend security control.

Тобто перевірка в інтерфейсі не замінює перевірку на сервері.

Так само CAPTCHA не замінює:

  • Authentication — автентифікацію, тобто перевірку ідентичності.
  • Authorization — авторизацію, тобто перевірку прав доступу.
  • Валідацію вхідних даних.
  • Захист від CSRF та інших вебатак.
  • Контроль бізнес-правил.

Наприклад, користувач може успішно пройти CAPTCHA, але не мати права видаляти чужі записи.

10

10. CAPTCHA, Rate Limiting та Anti-Bot — це різні механізми

CAPTCHA — не єдиний спосіб протидії автоматизації.

Для захисту вебзастосунків використовують декілька технологій.

МеханізмПризначення
CAPTCHAПеревірка клієнта
Rate LimitingОбмеження кількості запитів
HoneypotВиявлення певних автоматизованих дій
WAFФільтрація та захист HTTP-трафіку
Anti-Bot ProtectionВиявлення та обмеження автоматизації
API AuthorizationКонтроль прав доступу

Rate Limiting — обмеження частоти запитів.

Наприклад, система може дозволяти визначену кількість спроб реєстрації за певний час.

Honeypot — пастка для автоматизованих клієнтів. Наприклад, приховане поле форми, яке простий бот може помилково заповнити.

WAF — Web Application Firewall — міжмережевий екран вебзастосунку.

WAF може містити функції Anti-Bot, але сам факт використання WAF не означає, що такий захист уже налаштований.

Що таке Anti-Bot Protection?

Anti-Bot Protection — ширша система виявлення автоматизованого трафіку.

Вона може використовувати:

  • Browser Fingerprinting;
  • Behavioral Analysis;
  • IP Reputation;
  • Machine Learning;
  • JavaScript Challenges;
  • CAPTCHA;
  • Rate Limiting.

Тобто CAPTCHA може бути частиною Anti-Bot, але не охоплює всі його можливості.

Як працює сучасний Anti-Bot?

Browser Fingerprinting

Browser Fingerprinting — формування відбитка браузера.

Система аналізує характеристики клієнта: браузер, операційну систему, параметри JavaScript та інші доступні ознаки.

Це допомагає виявляти підозрілі середовища, але не гарантує унікальної ідентифікації користувача.

Behavioral Analysis

Behavioral Analysis — аналіз поведінки.

Наприклад, звичайний користувач переглядає кілька сторінок, а автоматизований клієнт послідовно запитує тисячі записів.

Такий характер активності може вказувати на парсинг.

Але швидкість запитів сама по собі не доводить, що клієнт є ботом.

Machine Learning

Machine Learning — машинне навчання.

Моделі аналізують сукупність сигналів і формують оцінку ризику.

На її основі система може дозволити запит, вимагати додаткову CAPTCHA або застосувати обмеження.

11

11. Типові помилки та обмеження CAPTCHA

Навіть сучасна CAPTCHA не гарантує абсолютного захисту.

AI-моделі можуть розв'язувати частину перевірочних завдань. Існують сервіси розв'язування CAPTCHA, а складні боти можуть працювати через повноцінні браузери.

Тому важливо не лише правильно вибрати технологію, а й коректно інтегрувати її.

Найпоширеніші помилки

ПомилкаЧому виникає проблемаПравильний підхід
CAPTCHA лише на FrontendAPI можна викликати напрямуСерверна перевірка
Secret key у JavaScriptСекрет стає доступним клієнтамЗберігати на Backend
Перевіряється лише successНе враховується scoreПеревіряти всі потрібні параметри
Не перевіряються hostname та actionВтрачається контроль контекстуПеревіряти очікувані значення
Не враховано строк дії токенаПрострочені токени викликають відмовиПередбачити оновлення токена
Немає обробки таймаутівЗовнішній сервіс може бути недоступнийВизначити політику відмов
CAPTCHA замінює інші контролиЧастина загроз залишаєтьсяКомбінувати механізми

Що робити, якщо CAPTCHA Provider недоступний?

Для нашої форми звернення визначимо правило:

Якщо перевірка недоступна, Backend не створює звернення та повертає контрольовану помилку.

Наприклад:

503 Service Unavailable

Це називають підходом Fail Closed — операція не дозволяється, якщо необхідний контроль безпеки не може бути виконаний.

В інших системах може застосовуватися інша політика, але вона повинна бути визначена заздалегідь.

Не слід автоматично вважати CAPTCHA успішною через помилку зовнішнього сервісу.

Повторні запити

Є ще один нюанс.

Припустимо, CAPTCHA пройдена, але під час створення звернення виник таймаут.

Користувач повторює запит із тим самим токеном.

Оскільки токен одноразовий, повторна перевірка може завершитися відмовою.

При цьому перша бізнес-операція могла вже виконатися.

Тому потрібно окремо контролювати повторення бізнес-операцій.

Для цього може застосовуватися Idempotency Key — ідентифікатор, який допомагає не виконувати одну бізнес-операцію повторно.

Важливо: Idempotency Key не замінює CAPTCHA, а вирішує іншу проблему — дублювання операцій.

12

12. Як це перевірити

Тестування CAPTCHA не повинно обмежуватися натисканням галочки.

Потрібно перевіряти Frontend, Backend, інтеграцію з провайдером і фактичний результат бізнес-операції.

Повернемося до:

POST /api/contact

Для прикладу використовуємо умовну політику reCAPTCHA v3:

  • score >= 0.70 — створити звернення;
  • 0.40 <= score < 0.70 — передати на модерацію;
  • score < 0.40 — відхилити.

Тестові сценарії

Початкові умовиДіяОчікуваний результатОзнака помилки
Валідний токен, score 0.92Надіслати формуHTTP 201, запис CreatedЗапис відсутній або дубльований
Валідний токен, score 0.55Надіслати формуHTTP 202, PendingReviewЗвернення створено без модерації
Валідний токен, score 0.18Надіслати формуHTTP 403, запис відсутнійЗвернення створено
Токен відсутнійНадіслати формуHTTP 403, запис відсутнійAPI прийняв запит
Токен некоректнийНадіслати формуHTTP 403, запис відсутнійОперацію виконано
Токен простроченийНадіслати формуВідмова, повторна перевіркаОперацію виконано
Токен уже використанийПовторити запитВідмова, без нового зверненняСтворено дублікат

CAPTCHA Provider недоступнийНадіслати формуHTTP 503, запис відсутнійПеревірку пропущено

HTTP-статуси відповідають нашому навчальному API-контракту.

Що ще потрібно перевірити?

Паралельні запити. Надіслати два запити з одним токеном та переконатися, що він не може бути успішно перевірений двічі.

Таймаут. Змоделювати недоступність CAPTCHA Provider і перевірити, що Backend коректно завершує операцію.

Відновлення. Після відновлення провайдера повторити операцію з новим токеном.

Прямий API-запит. Спробувати відправити форму без використання frontend.

Фактичний стан Database. Переконатися, що відхилені запити не створили записи.

Останній пункт особливо важливий.

HTTP 403 сам по собі не доводить, що бізнес-операція не була виконана.

Автоматизація тестування

Для Unit та Integration Testing доцільно використовувати тестовий адаптер CAPTCHA Provider.

Він може повертати заздалегідь визначені результати:

JSON
{
  "success": true,
  "score": 0.55,
  "action": "contact_submit",
  "hostname": "example.com"
}

Так можна перевірити бізнес-логіку без проходження реальних CAPTCHA.

Окремо потрібно перевіряти інтеграцію з API провайдера за допомогою передбачених ним тестових механізмів.

13. Що контролювати в Production

CAPTCHA часто залежить від зовнішнього сервісу.

Тому потрібно контролювати не лише ефективність блокування, а й стабільність інтеграції.

Основні метрики

МетрикаПризначення
Verification Success RateЧастка успішних перевірок
Verification Failure RateЧастка невдалих перевірок
Provider LatencyЧас відповіді провайдера
Provider AvailabilityДоступність сервісу
Rejected RequestsКількість відхилених запитів
Risk Score DistributionРозподіл score
Business Operation Success RateЧастка успішних бізнес-операцій

Різке зростання кількості невдалих перевірок може означати як активність ботів, так і технічну проблему.

Тому метрики потрібно аналізувати разом.

Що логувати?

Корисно зберігати:

  • час перевірки;
  • тип бізнес-операції;
  • результат CAPTCHA;
  • категорію помилки;
  • score, якщо він доступний;
  • час відповіді провайдера;
  • ідентифікатор HTTP-запиту;
  • результат бізнес-операції.

Не потрібно логувати повні CAPTCHA-токени або секретні ключі.

Для DEV, TEST та PROD варто використовувати окремі конфігурації й ключі.

14

14. Коли CAPTCHA доречна?

CAPTCHA добре підходить для захисту конкретних операцій, виконання яких можна поставити в залежність від додаткової перевірки.

Наприклад, реєстрації, відправлення звернень, коментарів або відновлення пароля.

Але не всі задачі слід вирішувати CAPTCHA.

ЗадачаЩо розглядати
Контактна формаCAPTCHA + Rate Limiting
РеєстраціяCAPTCHA + перевірка акаунта
АвторизаціяRisk Scoring + Rate Limiting + MFA
Масовий парсингAnti-Bot + обмеження доступу до API
Публічний APIКвоти та Rate Limiting
Складна браузерна автоматизаціяAnti-Bot із поведінковим аналізом

MFA — Multi-Factor Authentication (багатофакторна автентифікація).

Це орієнтири для вибору механізмів, а не універсальні готові конфігурації.

Особливо важливо розуміти обмеження CAPTCHA під час захисту від парсингу.

Якщо інформація доступна будь-якому анонімному користувачу, гарантувати повну неможливість її автоматизованого збору не можна.

У такому випадку потрібно застосовувати ширші механізми контролю трафіку.

15

15. Що повинні знати різні ролі

PM / PO. CAPTCHA знижує ризик автоматизованих зловживань. Потрібно визначити, які операції захищати та що робити при відмові перевірки.

BA / System Analyst. Важливо описати правила запуску CAPTCHA, обробку результатів і поведінку системи в негативних сценаріях.

QA. Потрібно тестувати API, токени, повторні запити, таймаути та фактичний стан Database, а не лише інтерфейс.

Developer. Необхідно розуміти життєвий цикл токена, серверну перевірку, безпечне зберігання секретів і обробку помилок.

DevOps / Support. Важливо контролювати доступність провайдера, конфігурації середовищ, метрики та логи.

Tech Lead / Architect. Потрібно визначити місце CAPTCHA в загальній архітектурі безпеки та врахувати залежність від зовнішнього сервісу.

16

16. Практичний checklist

Перед впровадженням CAPTCHA перевір:

  • [ ] Визначено операції, які потребують захисту.
  • [ ] Обрано відповідний тип CAPTCHA.
  • [ ] Реалізовано серверну перевірку токена.
  • [ ] Перевіряються необхідні параметри відповіді.
  • [ ] Secret key зберігається лише на сервері.
  • [ ] Передбачено обробку прострочених і повторно використаних токенів.
  • [ ] Визначено поведінку під час недоступності провайдера.
  • [ ] Налаштовано необхідні додаткові механізми захисту.
  • [ ] Реалізовано логування та моніторинг.
  • [ ] QA перевірив негативні сценарії та стан Database.
  • [ ] Тестові ключі не використовуються в PROD.
17

17. Якщо зовсім просто

Уявімо вхід до офісної будівлі.

Спочатку охоронець просить відвідувача виконати невелике завдання.

Це схоже на класичну CAPTCHA.

Пізніше в будівлі встановлюють розумнішу систему. Тепер охоронець може отримувати оцінку того, наскільки підозрілим виглядає відвідувач, і проводити додаткові перевірки лише за необхідності.

Це нагадує сучасні CAPTCHA з оцінкою ризику.

Але навіть якщо відвідувач успішно пройшов перевірку на вході, це не означає, що він має право заходити в будь-який кабінет.

Для цього потрібні окремі права доступу.

Так само працює вебзастосунок.

CAPTCHA допомагає перевірити клієнта та оцінити ризик автоматизації.

Backend перевіряє результат і вирішує, чи можна продовжити операцію.

А Authentication та Authorization окремо визначають, хто звертається до системи та що йому дозволено робити.

І навіть найкраща система перевірки не може гарантувати, що ніхто ніколи її не обійде.

Тому CAPTCHA — один із механізмів захисту, а не абсолютна гарантія безпеки.

Головне, що потрібно запам'ятати: CAPTCHA недостатньо просто показати на сторінці. Її результат необхідно перевірити на сервері та правильно використати для прийняття рішення.

18

Підсумок

CAPTCHA еволюціонувала від текстових завдань до систем, які використовують перевірку браузера, поведінкові сигнали та оцінку ризику.

При цьому незмінними залишаються основні принципи:

CAPTCHA — не конкретний продукт, а клас технологій. reCAPTCHA, Turnstile, hCaptcha та Friendly Captcha реалізують різні підходи до перевірки клієнтів.

Серверна перевірка є обов'язковою. Без неї CAPTCHA на frontend може не захищати бізнес-операцію.

Успішна перевірка токена не завжди означає низький ризик. Для рішень із score необхідно застосовувати власну політику.

CAPTCHA не замінює інші механізми безпеки. Authentication, Authorization, Rate Limiting та Anti-Bot Protection вирішують різні завдання.

Абсолютного захисту від автоматизації не існує. Ефективність залежить від конкретної загрози, правильної реалізації та поєднання механізмів.
