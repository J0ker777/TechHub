Уявімо типову задачу.

У компанії є:

  • 10 000 внутрішніх документів;
  • технічна документація;
  • регламенти;
  • інструкції;
  • Wiki;
  • API documentation.

І виникає ідея:

↳
«Давайте завантажимо все це в AI і навчимо модель відповідати на наші питання».

Звучить логічно.

Але перше питання, яке варто поставити:

А модель взагалі потрібно навчати?

У багатьох випадках — ні.

Саме тут з'являються два поняття, які часто плутають:

RAG та Fine-tuning.

01

🧠 Що взагалі знає LLM?

Коли ми запитуємо модель:

Що таке Circuit Breaker?

вона відповідає на основі знань та закономірностей, отриманих під час навчання.

Але якщо запитати:

Який у нашій компанії процес
публікації сервісу в Production?

модель цього може просто не знати.

Наш внутрішній регламент не був частиною її навчальних даних.

Що робити?

Найочевидніша думка:

↳
«Давайте донавчимо модель на наших документах».

Але часто це неправильний інструмент для цієї задачі.

02

📚 Підхід №1 — RAG

RAG означає:

Retrieval-Augmented Generation

Ідея дуже проста.

Ми не змушуємо модель запам'ятовувати наші документи.

Замість цього перед відповіддю знаходимо потрібну інформацію та передаємо її моделі як контекст.

Схематично:

Наприклад, користувач запитує:

Який процес релізу в Production?

Система знаходить відповідний фрагмент внутрішнього регламенту:

Production deployment requires...

і формує запит до LLM приблизно так:

Використовуй наступний документ:

[Relevant document fragment]

Питання:
Який процес релізу в Production?

LLM отримує потрібні знання безпосередньо під час виконання запиту.

03

🔎 Але як знайти потрібний документ?

Можна використовувати звичайний keyword search.

Але в RAG часто використовують embeddings.

Текст перетворюється у числовий вектор.

Умовно:

Цей вектор описує певні семантичні характеристики тексту.

Тому система може знайти схожий за змістом документ навіть тоді, коли слова не збігаються буквально.

Наприклад:

Question:
"Як змінити пароль?"

може знайти:

Document:
"Password reset procedure"

хоча формулювання різні.

05

💥 «Ми завантажили PDF у Vector DB — у нас є RAG»

Технічно — можливо.

Але якість такого RAG може бути дуже поганою.

Наприклад, PDF містить таблицю:

Environment | Deployment | Approval
DEV         | Automatic  | No
TEST        | Pipeline   | Team Lead
PROD        | Pipeline   | Change Manager

Парсер прочитав її як:

Environment Deployment Approval
DEV Automatic PROD Pipeline
No TEST Team Lead Change Manager

Embedding побудований.

Vector DB працює.

LLM чудова.

Але вхідні дані вже зіпсовані.

06

✂️ Chunking теж має значення

Уявімо речення:

Для Production deployment
потрібне погодження Security
та Change Manager.

А chunking розділив його так:

Chunk 1:
Для Production deployment
потрібне погодження
Chunk 2:
Security та Change Manager.

Користувач запитує:

Хто погоджує Production deployment?

Retrieval повертає лише Chunk 1.

LLM бачить:

↳
«Для Production deployment потрібне погодження...»

А чиє саме — контексту вже немає.

Модель може сказати:

↳
«Потрібне погодження відповідальної команди».

Звучить переконливо.

Але цього в документі не було.

07

⚠️ І тут виникає важлива думка

Коли RAG дає неправильну відповідь, ми часто кажемо:

↳
«LLM галюцинує».

Але проблема може бути зовсім не в LLM.

Можливо:

Parsing ❌

або:

Chunking ❌

або:

Retrieval ❌

Модель просто отримала неправильний контекст.

Тому якість AI-системи:

AI Quality ≠ LLM Quality

Швидше:

AI Quality =
Data
+ Parsing
+ Retrieval
+ Context
+ Prompt
+ LLM
+ Evaluation

Іноді заміна моделі дає набагато менший ефект, ніж покращення retrieval.

08

🎯 А що тоді таке Fine-tuning?

Fine-tuning — зовсім інший підхід.

Ми беремо вже навчену модель і додатково тренуємо її на підготовлених прикладах.

Умовно:

Наприклад, маємо багато прикладів:

Input:
Помилка SQL connection timeout.

Output:
{
  "category": "DATABASE",
  "severity": "HIGH"
}
Input:
JWT signature validation failed.

Output:
{
  "category": "SECURITY",
  "severity": "HIGH"
}

Ми хочемо, щоб модель стабільно виконувала певну задачу або дотримувалася потрібного стилю/формату.

Тут fine-tuning уже може бути доречним.

09

📚 А можна Fine-tuning використати для документів?

Можна навчати модель на доменних даних, але якщо задача звучить як:

↳
«Модель повинна знати актуальну версію наших 10 000 документів».

Fine-tuning часто буде невдалим рішенням.

Чому?

Уявімо, сьогодні регламент каже:

Production deployment
requires approval A.

Ми підготували dataset.

Навчили модель.

Через місяць регламент змінився:

Production deployment
requires approval A + B.

Що робити?

Знову:

А завтра змінився ще один документ.

Для бази знань, яка постійно змінюється, це незручно.

10

🔄 А що буде з RAG?

Документ змінився.

Ми:

І наступний запит уже може використовувати актуальну інформацію.

Саму LLM перенавчати не потрібно.

Саме тому для корпоративних knowledge systems RAG часто є природним вибором.

11

⚖️ RAG vs Fine-tuning

Дуже спрощено:

Тому корисна ментальна модель:

↳
RAG — «що модель повинна знати прямо зараз?»
↳
Fine-tuning — «як модель повинна поводитися?»

Це спрощення, але для вибору архітектури воно дуже корисне.

12

14

🔐 А як щодо прав доступу?

У корпоративному RAG є ще одна проблема, про яку легко забути.

Уявімо:

Але обидва документи знаходяться в одному Vector DB.

Якщо retrieval не враховує permissions:

Тобто security потрібно застосовувати до retrieval, а не лише до UI.

AI не повинен отримати документ, який користувач не має права бачити.

15

Словник термінів простими словами

  • RAG — пошук потрібних матеріалів і додавання їх до контексту перед відповіддю моделі.
  • Fine-tuning — додаткове навчання моделі на прикладах для зміни її поведінки або формату.
  • Embedding — числове представлення змісту тексту для пошуку схожих фрагментів.
  • Vector DB — сховище, яке швидко знаходить близькі embeddings.
  • Retrieval — вибір фрагментів, найбільш пов’язаних із питанням.
  • Chunking — поділ документа на частини, придатні для пошуку та контексту.
  • Parsing — витягування тексту й структури з PDF, HTML чи іншого формату.
  • Context — знайдені фрагменти та інші дані, які модель бачить разом із питанням.
  • Training dataset — перевірений набір прикладів для fine-tuning.
  • Grounding — прив’язка відповіді до конкретних джерел.
  • Information leak — показ даних людині без потрібного дозволу.
16

👶 Якщо зовсім просто

RAG працює як бібліотекар: знаходить потрібні сторінки й кладе їх поруч із питанням. Документ можна оновити в індексі без перенавчання моделі, а у відповіді показати джерело.

Fine-tuning працює як тренування стилю та навички. Він допомагає моделі стабільніше виконувати певну задачу, але не є зручним сховищем актуальних корпоративних документів.

Часто потрібні обидва підходи: fine-tuning визначає, як відповідати, а RAG — на основі чого. Пошук обов’язково має враховувати права користувача.
