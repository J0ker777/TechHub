Уявімо звичайний вебзастосунок.

Користувач авторизувався:

Браузер отримав cookie (невеликий фрагмент даних, який сайт зберігає у браузері):

session=abc123

Тепер користувач відкриває свій профіль і змінює email.

Все нормально.

Server (сервер) бачить cookie та розуміє:

А тепер уявімо іншу ситуацію.

Користувач усе ще авторизований у своєму кабінеті.

Але в іншій вкладці відкриває:

evil.example

Він:

  • ❌ не вводить пароль;
  • ❌ не передає cookie;
  • ❌ не відкриває свій профіль;
  • ❌ не натискає Change Email.

А через декілька секунд email у кабінеті змінюється.

😐

Виникає цікаве питання:

↳
Як сторонній сайт зміг виконати операцію від імені авторизованого користувача, навіть не знаючи його пароля та cookie?

Це і є основа:

01

Cross-Site Request Forgery — CSRF

CSRF — Cross-Site Request Forgery (підробка міжсайтового запиту).

02

🧠 Що таке CSRF?

CSRF — Cross-Site Request Forgery — це атака, за якої зловмисник змушує браузер уже авторизованого користувача відправити небажаний request (HTTP-запит) до іншого сайту.

Наприклад:

  • 📧 змінити email;
  • 🔑 змінити пароль;
  • 👤 створити користувача;
  • 🗑️ видалити запис;
  • ⚙️ змінити налаштування;
  • 💰 виконати операцію.

Головна особливість:

↳
Зловмиснику не обов'язково знати пароль або красти session cookie (cookie активної сесії користувача).

Браузер користувача вже авторизований.

І саме це attacker (зловмисник) намагається використати.

03

🍪 До чого тут Cookie?

Після Login (входу в систему) server може повернути:

HTTP
Set-Cookie: session=abc123

Браузер зберігає cookie.

Після цього користувач відкриває:

/profile

і browser (браузер) відправляє:

HTTP
GET /profile HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

Server знаходить сесію:

і повертає його профіль.

Зручно.

Але є важлива деталь.

04

🤖 Cookie додає Browser

Користувач не пише вручну:

HTTP
Cookie: session=abc123

під час кожного request.

Це робить browser.

І саме тут знаходиться основна ідея CSRF.

↳
Якщо сторонній сайт зможе змусити browser створити потрібний request, browser за певних умов може сам додати до нього cookie користувача.

Attacker не потрібно знати значення cookie.

Йому потрібно змусити Victim Browser (браузер жертви) відправити потрібний request.

05

😈 Подивимося на атаку

У нашому application є endpoint (адреса API або вебоперації):

HTTP
POST /profile/change-email

Нормальний request:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123
Content-Type: application/x-www-form-urlencoded

email=denis@example.com

Server бачить:

session=abc123

і виконує:

Email changed ✅

Тепер attacker створює на своєму сайті звичайну HTML form (HTML-форму):

HTML
<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="attacker@example.com">

    <button type="submit">
        Click me
    </button>

</form>

Що відбудеться, якщо авторизований користувач відкриє цю сторінку та натисне кнопку?

А якщо cookie дозволено використовувати в такому сценарії:

Server отримує:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

email=attacker@example.com

💥

06

🤔 Що бачить Server?

Server бачить:

POST /profile/change-email
Cookie: session=abc123

Перевіряє session:

І думає:

Denis змінює свій email

Але насправді Denis нічого такого не робив.

Request створив:

evil.example

а відправив browser користувача.

Тому:

↳
Valid Session (валідна сесія) ≠ User wanted this operation (користувач справді хотів виконати цю операцію).

Це одна з найважливіших думок для розуміння CSRF.

07

🧩 Вся атака одним малюнком

Attacker при цьому:

  • ❌ не знає Password (пароль);
  • ❌ не знає Session ID (ідентифікатор сесії);
  • ❌ не читає Cookie;
  • ❌ не входить у Account (обліковий запис).

Він використовує вже авторизований browser користувача.

08

📨 Але ж у нас POST

Іноді можна почути:

↳
У нас зміни тільки через POST. Тому CSRF немає.

Але POST (HTTP-метод для передавання даних і виконання операцій) сам по собі не означає:

↳
«Цей request створив саме наш сайт».

HTML form прекрасно вміє робити POST:

HTML
<form method="POST">

Наприклад, attacker може створити:

HTML
<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="attacker@example.com">

    <button type="submit">
        Подивитися фото
    </button>

</form>

Користувач знаходиться на:

evil.example

натискає кнопку, і browser формує POST-request до:

cabinet.example.com

Далі browser перевіряє правила cookie для cabinet.example.com.

Якщо вони дозволяють передати cookie в цьому cross-site (міжсайтовому) сценарії, browser може додати:

HTTP
Cookie: session=abc123

У результаті Backend (серверна частина застосунку) бачить:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123
Content-Type: application/x-www-form-urlencoded

email=attacker@example.com

Для Backend це може виглядати як абсолютно нормальний авторизований request.

Тому:

↳
POST ≠ CSRF Protection

POST визначає тип HTTP-операції.

Але він не доводить, що request був ініційований саме нашим application.

Інакше кажучи:

Саме тому POST + Valid Session ще недостатньо для захисту від CSRF.

Потрібні додаткові механізми:

09

🚨 А якщо зміна виконується через GET?

Тут може бути ще цікавіше.

Уявімо:

HTTP
GET /user/delete?id=123

видаляє користувача.

GET (HTTP-метод отримання ресурсу) концептуально не повинен використовуватися для таких операцій.

Attacker може розмістити:

HTML
<img src="https://cabinet.example.com/user/delete?id=123">

Browser бачить:

HTML
<img>

і думає:

↳
Потрібно завантажити картинку.

У результаті:

Тому GET не повинен виконувати операції, які змінюють дані.

Концептуально:

10

🌐 А браузер не забороняє чужим сайтам працювати з нашим?

Так, у browser є багато security mechanisms (механізмів безпеки).

Наприклад:

SOP — Same-Origin Policy (політика одного джерела).

Вона не дозволяє одному сайту просто читати дані іншого сайту.

Наприклад:

evil.example

не може просто прочитати:

cabinet.example.com/profile

Але для CSRF attacker часто і не потрібно читати відповідь.

Йому потрібно Send Request (відправити запит), а не Read Response (прочитати відповідь).

Тому:

↳
Не можу прочитати response ≠ Не можу спричинити request.

Це дуже важлива різниця.

11

⚠️ А CORS?

Тут часто виникає плутанина.

CORS — Cross-Origin Resource Sharing (механізм керування доступом між різними origin — джерелами вебсторінок) контролює cross-origin взаємодію JavaScript із ресурсами іншого origin.

А CSRF використовує іншу ідею:

Тому:

↳
CORS ≠ CSRF Protection

CORS може впливати на конкретну атаку.

Але просто сказати:

↳
«У нас CORS → CSRF немає»

не можна.

12

🔒 А HTTPS?

HTTPS — HyperText Transfer Protocol Secure (захищений HTTP) дуже важливий.

Він шифрує з'єднання між browser та server:

Але CSRF request теж може піти через HTTPS.

Тому:

↳
HTTPS ≠ CSRF Protection

HTTPS захищає канал передачі.

CSRF використовує легітимний browser і легітимний HTTPS-канал для виконання небажаної операції.

13

🍪 А HttpOnly?

Cookie може мати атрибут:

HTTP
HttpOnly

HttpOnly (заборона JavaScript читати cookie) означає, що JavaScript не може просто прочитати її через:

JAVASCRIPT
document.cookie

Це хороший security mechanism.

Але CSRF attacker і не обов'язково потрібно читати cookie.

Browser може використати її сам.

Але:

↳
HttpOnly ≠ CSRF Protection
14

🛡 Як тоді захищатися?

Є декілька механізмів.

Найважливіші для розуміння:

Розберемо їх окремо.

15

🍪 SameSite Cookie

Cookie може мати параметр:

SameSite

SameSite (правило використання cookie між сайтами) допомагає browser вирішувати, коли cookie можна відправляти в cross-site сценаріях.

Наприклад:

HTTP
Set-Cookie: session=abc123;
            Secure;
            HttpOnly;
            SameSite=Lax

SameSite допомагає browser вирішити:

↳
Чи можна відправляти цю cookie, якщо request виник у контексті іншого сайту?

Основні режими:

  • Strict
  • Lax
  • None

🛡 Strict

SameSite=Strict

Найсильніше обмежує cookie в cross-site сценаріях.

⚖️ Lax

SameSite=Lax

Компроміс між безпекою та зручністю.

Багато небезпечних cross-site сценаріїв обмежуються, але деякі звичайні переходи між сайтами залишаються можливими.

🌍 None

SameSite=None

Cookie може використовуватися в cross-site сценаріях.

При SameSite=None cookie також повинна бути:

Secure

Secure (передавати cookie лише через HTTPS) не є CSRF-захистом сам по собі, але не дозволяє передавати таку cookie через незахищений HTTP.

Тому якщо бачимо:

HTTP
SameSite=None; Secure

потрібно особливо уважно розуміти, навіщо application потрібна cross-site cookie і який CSRF-захист використовується.

16

🎟️ CSRF Token

Ще один дуже поширений механізм —

CSRF Token (спеціальний непередбачуваний маркер для перевірки легітимності запиту).

Server генерує випадкове непередбачуване значення:

f8d93a7c...

і додає його у форму:

HTML
<form action="/profile/change-email" method="POST">

    <input
        type="hidden"
        name="csrf_token"
        value="f8d93a7c...">

    <input name="email">

</form>

Коли користувач відправляє форму, server отримує:

  • Session Cookie;
  • CSRF Token.

і перевіряє обидва.

17

😈 Чому attacker стає складніше?

Attacker може створити свою HTML form:

HTML
<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        name="email"
        value="attacker@example.com">

</form>

Browser потенційно може додати cookie.

Але attacker не знає правильний:

csrf_token

Якщо він відправить:

csrf_token=123

server повинен отримати:

Session      → VALID ✅
CSRF Token   → INVALID ❌

і не виконати операцію.

Тобто:

18

🌍 Перевірка Origin

Browser також може передавати інформацію про Origin (джерело, з якого ініційований запит).

Наприклад:

HTTP
Origin: https://cabinet.example.com

Server очікує:

cabinet.example.com

і отримує:

cabinet.example.com

Результат:

✅ Request from expected Origin

А тепер:

HTTP
Origin: https://evil.example

Server бачить:

Expected:
cabinet.example.com

Received:
evil.example

❌

і може відхилити request.

Тобто server отримує ще одну можливість запитати:

↳
Звідки взагалі прийшла ця операція?
19

🧱 Захист повинен бути на Server

Це дуже важливо.

Можна зробити у Frontend (клієнтській частині застосунку):

  • Button disabled — вимкнути кнопку;
  • Hidden menu — приховати меню;
  • JavaScript validation — зробити перевірку через JavaScript.

Але attacker не зобов'язаний використовувати ваш Frontend.

Він створює:

Тому рішення:

ALLOW

або:

DENY

повинен приймати Server.

20

🧪 Як це тестувати?

Тепер подивимося на CSRF очима QA — Quality Assurance (фахівця з контролю якості) або Developer.

У нас є:

Відкриваємо:

і знаходимо request.

Наприклад:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

email=test@example.com

Ставимо просте питання:

↳
Що заважає сторонньому сайту відправити такий самий request?
21

🔎 Перевіряємо Cookie

Дивимося:

Secure?
HttpOnly?

Особливо нас цікавить:

SameSite

тому що він безпосередньо впливає на поведінку cookie у cross-site сценаріях.

22

🎟️ Шукаємо CSRF Token

Він може бути, наприклад, у body (тілі HTTP-запиту):

csrf_token=f8d93a7c...

або header (HTTP-заголовку):

HTTP
X-CSRF-Token: f8d93a7c...

Якщо token є, можна перевірити:

або:

Server повинен відхилити request із неправильним token.

Найважливіше:

Operation NOT executed ❌
23

💣 Робимо простий CSRF PoC

PoC — Proof of Concept (демонстраційний приклад, який підтверджує можливість проблеми).

Один із найзрозуміліших способів перевірки — створити просту HTML-сторінку.

Наприклад:

HTML
<!DOCTYPE html>
<html>
<body>

<h1>CSRF Test</h1>

<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="csrf-test@example.com">

    <button type="submit">
        Test
    </button>

</form>

</body>
</html>

Далі:

↳
⚠️ Такі перевірки потрібно проводити лише на системах, які ви маєте право тестувати, бажано на DEV/TEST та з безпечною тестовою операцією.
24

🔍 Що перевіряємо?

Нас цікавить весь flow (послідовність виконання процесу):

Останній пункт найважливіший.

Наприклад:

  • Email реально змінився?
  • User реально створився?
  • Role реально змінилася?
  • Object реально видалився?
25

⚠️ Не дивимося тільки на HTTP Status

HTTP Status (код результату HTTP-запиту) сам по собі не дає повної відповіді.

Наприклад:

HTTP
200 OK

ще не означає:

CSRF successful

Server міг повернути сторінку Login або повідомлення про помилку.

Тому правильніше перевіряти:

26

🎯 Що тестувати першочергово?

Усе, що щось змінює.

Наприклад:

  • 📧 Change Email;
  • 🔑 Change Password;
  • 👤 Create User;
  • 🗑️ Delete User;
  • 🛡️ Change Role;
  • ⚙️ Change Settings;
  • 💰 Financial Operation.

І окремо варто шукати:

GET

які чомусь змінюють дані.

27

📦 А якщо API працює з JSON?

API — Application Programming Interface (інтерфейс взаємодії між програмними компонентами).

Наприклад:

HTTP
POST /api/profile
Content-Type: application/json

{
    "email": "new@example.com"
}

JSON — JavaScript Object Notation (текстовий формат представлення структурованих даних).

Звичайна HTML form не вміє просто відправити довільний:

application/json

request.

Тому класична CSRF-атака через HTML form стає складнішою.

Але робити висновок:

↳
JSON → CSRF impossible

не потрібно.

Все одно потрібно дивитися на:

  • Authentication (автентифікацію);
  • Cookies;
  • CORS;
  • Accepted Requests (які запити приймає сервер);
  • CSRF Protection.

Тобто:

↳
JSON може ускладнити конкретний сценарій атаки, але сам по собі не є CSRF-захистом.
28

🚨 Типові помилки

❌ «У нас POST»

↳
POST ≠ CSRF Protection

❌ «У нас HTTPS»

↳
HTTPS ≠ CSRF Protection

❌ «Cookie має HttpOnly»

↳
HttpOnly ≠ CSRF Protection

❌ «У нас CORS»

↳
CORS ≠ CSRF Protection

❌ «Frontend не дозволяє це зробити»

Attacker не використовує ваш Frontend.

❌ «Endpoint ніхто не знає»

Його можна побачити через:

Прихований endpoint — не security mechanism.

29

🛡 Як виглядає нормальний захист?

Не існує однієї чарівної галочки:

CSRF Protection = ON

Захист може складатися з декількох рівнів:

При цьому важливо розуміти:

  • HTTPS;
  • HttpOnly;
  • SameSite;
  • CORS;
  • CSRF Token;
  • Origin.

— це різні механізми.

Вони вирішують різні security problems (проблеми безпеки).

Тому хороше питання:

↳
Від якої конкретно атаки нас захищає цей механізм?

🧠 Що варто запам'ятати

CSRF — це не про те, що attacker обов'язково вкрав Password або Cookie.

Ідея інша:

Attacker використовує той факт, що browser уже авторизований.

Тому:

↳
Valid Session ≠ User wanted this operation

І це, мабуть, головна думка всієї статті.

32

🕵️ CSRF Challenge

Уявімо корпоративний application:

https://cabinet.company.com

Користувач авторизувався.

Browser отримав:

HTTP
Set-Cookie: session=ABC123;
            Secure;
            HttpOnly;
            SameSite=None

У application є:

HTTP
POST /profile/change-email

Request:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.company.com
Cookie: session=ABC123

email=new@company.com

При цьому:

  • CSRF Token ❌
  • Origin Check ❌

Attacker створив:

HTML
<form
    action="https://cabinet.company.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="attacker@example.com">

    <button type="submit">
        Open photo
    </button>

</form>

Авторизований користувач відкриває сторінку attacker та натискає кнопку.

❓ Питання №1

Attacker не знає:

session=ABC123

Чому attack усе одно потенційно може спрацювати?

❓ Питання №2

Cookie має:

HttpOnly

Чи захищає це від CSRF?

❓ Питання №3

Що тут означає:

SameSite=None

і чому на це варто звернути увагу?

❓ Питання №4

Server додав:

CSRF Token

Що тепер повинен знати attacker, крім параметрів самої операції?

❓ Питання №5

Server почав перевіряти:

HTTP
Origin: https://cabinet.company.com

А request прийшов із:

https://evil.example

Що повинен зробити Server?

❓ І останнє

У нас є:

  • HTTPS;
  • Secure;
  • HttpOnly.

але немає нормального захисту від небажаних cross-site requests.

Чи можна сказати:

Ні.

Саме тут проявляється головна ідея CSRF:

↳
Server повинен розуміти не тільки, хто авторизований, а й захищати критичні операції від requests, які користувач насправді не ініціював.

І якщо після цієї статті при перегляді нового endpoint виникає питання:

↳
«А що заважає іншому сайту змусити мій browser відправити такий самий request?»

— значить основна ідея CSRF зрозуміла. 🛡️

33

👶 Якщо зовсім просто

Уявімо, що після входу в корпоративний кабінет browser отримав спеціальний пропуск:

session=ABC123

Цей пропуск — cookie.

Коли ви працюєте із сайтом, вам не потрібно щоразу вводити логін і пароль.

Browser сам додає цей пропуск до потрібних requests.

Умовно:

Це дуже зручно.

Але саме цю зручність намагається використати CSRF.

Зловмиснику не обов'язково красти ваш пароль.

Не обов'язково красти cookie.

І навіть не обов'язково входити у ваш account.

Його задача інша:

↳
Змусити ваш уже авторизований browser відправити потрібний йому request.

Наприклад, ви авторизовані в:

cabinet.company.com

а потім відкрили інший сайт.

Цей сайт створює форму, яка відправляє:

HTTP
POST /profile/change-email

на ваш корпоративний application.

Browser бачить request до cabinet.company.com.

І якщо правила cookie це дозволяють, може сам додати вашу session cookie.

У результаті схема виглядає так:

Ось це і є головна проблема CSRF.

Server бачить:

користувач авторизований

але цього недостатньо, щоб сказати:

користувач справді хотів виконати цю дію

Тому дуже важлива формула всієї статті:

↳
Valid Session ≠ User wanted this operation

📨 Чому POST не рятує?

Тому що стороння HTML-сторінка теж може створити форму:

HTML
<form method="POST" action="https://cabinet.company.com/profile/change-email">

Тобто POST говорить server, яку операцію виконують, але сам по собі не доводить, звідки ця операція прийшла і чи справді користувач хотів її виконати.

Саме тому:

↳
POST потрібен для правильного проєктування API, але POST — не CSRF-захист.

🍪 Чим допомагає SameSite?

SameSite встановлює правила для browser:

↳
Чи можна передавати цю cookie, якщо request виник через інший сайт?

Чим суворіші правила SameSite, тим менше можливостей у стороннього сайту використати авторизовану cookie користувача.

Але конкретне значення потрібно вибирати відповідно до архітектури application.

🎟️ Чим допомагає CSRF Token?

CSRF Token — це додаткове значення, яке server очікує разом із request.

Browser може автоматично додати cookie.

А правильний CSRF Token attacker знати не повинен.

Тому:

Тобто одного факту:

користувач авторизований

вже недостатньо.

🌍 Чим допомагає Origin?

Origin дозволяє server перевірити, звідки прийшов request.

Наприклад:

cabinet.company.com

— очікуваний origin.

А:

evil.example

— зовсім інший сайт.

Якщо критична операція повинна приходити лише з нашого application, така перевірка може стати ще одним рівнем захисту.

🔒 А HTTPS, HttpOnly та CORS?

Вони потрібні.

Але вони вирішують інші проблеми.

Дуже спрощено:

  • HTTPS — захищає дані під час передачі мережею;
  • HttpOnly — не дозволяє JavaScript просто прочитати cookie;
  • CORS — контролює певні cross-origin взаємодії;
  • SameSite — впливає на відправлення cookie між сайтами;
  • CSRF Token — допомагає підтвердити легітимність request;
  • Origin Validation — дозволяє перевірити джерело request.

Тому не варто думати:

HTTPS є
+
HttpOnly є
=
CSRF закритий

Так це не працює.

Кожен механізм вирішує свою задачу.

🧪 Що повинен запам'ятати QA?

Якщо endpoint щось змінює:

email
password
role
user
settings
financial data

потрібно поставити просте питання:

↳
Що заважає сторонньому сайту змусити мій browser відправити такий самий request?

Після цього перевіряємо:

  • яка cookie використовується;
  • який SameSite;
  • чи є CSRF Token;
  • чи перевіряється Origin;
  • що станеться без token;
  • що станеться з неправильним token;
  • чи можна створити простий PoC;
  • чи реально після request змінилися дані.

👨‍💻 Що повинен запам'ятати Developer?

Недостатньо зробити:

POST
+
Authentication

і вважати операцію захищеною.

Для cookie-based authentication потрібно окремо подумати про CSRF.

Наприклад:

При цьому конкретний набір механізмів залежить від архітектури application.

🧑‍💼 А що з цього потрібно PM/BA?

Не обов'язково пам'ятати всі HTTP headers або правила SameSite.

Важливо розуміти сам ризик.

Якщо користувач авторизований у системі, це ще не означає, що кожна операція, яка прийшла з його browser, була свідомо виконана ним.

Особливо важливі операції:

  • зміна пароля;
  • зміна email;
  • керування користувачами;
  • зміна ролей;
  • зміна прав;
  • критичні налаштування;
  • фінансові операції.

Для них питання CSRF-захисту повинно бути частиною проєктування та тестування.

🎯 Вся стаття в одній схемі

Тому якщо залишити одну фразу, яку потрібно винести з цієї статті, то це:

↳
CSRF — це ситуація, коли зловмисник не краде вашу авторизацію, а намагається використати вже авторизований браузер, щоб виконати небажану дію від вашого імені.

А головне питання під час розробки або тестування:

↳
«Що заважає іншому сайту змусити browser авторизованого користувача відправити такий самий request?»

Якщо на це питання є чітка технічна відповідь — ми вже значно краще розуміємо, як application захищається від CSRF. 🛡️
