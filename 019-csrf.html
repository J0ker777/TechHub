Уявімо звичайний вебзастосунок.

Користувач авторизувався:

User
 ↓
Login
 ↓
Server
 ↓
Session Cookie 🍪

Браузер отримав cookie:

session=abc123

Тепер користувач відкриває свій профіль і змінює email.

Browser
   ↓
POST /profile/change-email
   ↓
Cookie: session=abc123
   ↓
Server
   ↓
Email changed ✅

Все нормально.

Server бачить cookie та розуміє:

session=abc123
      ↓
   User Denis

А тепер уявімо іншу ситуацію.

Користувач усе ще авторизований у своєму кабінеті.

Але в іншій вкладці відкриває:

evil.example

Він:

❌ не вводить пароль
❌ не передає cookie
❌ не відкриває свій профіль
❌ не натискає "Change Email"

А через декілька секунд email у кабінеті змінюється.

😐

Виникає цікаве питання:

↳
Як сторонній сайт зміг виконати операцію від імені авторизованого користувача, навіть не знаючи його пароля та cookie?

Це і є основа:

01

Cross-Site Request Forgery — CSRF

02

🧠 Що таке CSRF?

CSRF — Cross-Site Request Forgery — це атака, за якої зловмисник змушує браузер уже авторизованого користувача відправити небажаний request до іншого сайту.

Наприклад:

📧 змінити email
🔑 змінити пароль
👤 створити користувача
🗑️ видалити запис
⚙️ змінити налаштування
💰 виконати операцію

Головна особливість:

↳
Зловмиснику не обов'язково знати пароль або красти session cookie.

Браузер користувача вже авторизований.

І саме це attacker намагається використати.

03

🍪 До чого тут Cookie?

Після Login server може повернути:

HTTP
Set-Cookie: session=abc123

Браузер зберігає cookie.

Після цього користувач відкриває:

/profile

і browser відправляє:

HTTP
GET /profile HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

Server знаходить сесію:

abc123
   ↓
User Denis

і повертає його профіль.

Зручно.

Але є важлива деталь.

04

🤖 Cookie додає Browser

Користувач не пише вручну:

HTTP
Cookie: session=abc123

під час кожного request.

Це робить browser.

User
 ↓
clicks button
 ↓
Browser
 ↓
creates Request
 ↓
adds Cookie 🍪
 ↓
Server

І саме тут знаходиться основна ідея CSRF.

↳
Якщо сторонній сайт зможе змусити browser створити потрібний request, browser за певних умов може сам додати до нього cookie користувача.

Attacker не потрібно знати значення cookie.

Йому потрібно змусити:

Victim Browser

відправити потрібний request.

05

😈 Подивимося на атаку

У нашому application є endpoint:

HTTP
POST /profile/change-email

Нормальний request:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123
Content-Type: application/x-www-form-urlencoded

email=denis@example.com

Server бачить:

session=abc123

і виконує:

Email changed ✅

Тепер attacker створює на своєму сайті звичайну HTML form:

HTML
<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="attacker@example.com">

    <button type="submit">
        Click me
    </button>

</form>

Що відбудеться, якщо авторизований користувач відкриє цю сторінку та натисне кнопку?

evil.example
     ↓
HTML Form
     ↓
Browser
     ↓
POST /profile/change-email
     ↓
cabinet.example.com

А якщо cookie дозволено використовувати в такому сценарії:

Browser
   ↓
adds session Cookie 🍪
   ↓
Server

Server отримує:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

email=attacker@example.com

💥

06

🤔 Що бачить Server?

Server бачить:

POST /profile/change-email
        +
session=abc123

Перевіряє session:

abc123
 ↓
Denis

І думає:

Denis змінює свій email

Але насправді Denis нічого такого не робив.

Request створив:

evil.example

а відправив:

Denis Browser

Тому:

Valid Session
      ≠
User wanted this operation

Це одна з найважливіших думок для розуміння CSRF.

07

🧩 Вся атака одним малюнком

User logs into
cabinet.example.com
        ↓
Browser stores Cookie 🍪
        ↓
User opens
evil.example
        ↓
evil.example creates Request
        ↓
Browser sends Request
        ↓
Browser may add Cookie 🍪
        ↓
Server sees valid Session
        ↓
Operation executed 💥

Attacker при цьому:

❌ не знає Password
❌ не знає Session ID
❌ не читає Cookie
❌ не входить у Account

Він використовує вже авторизований browser користувача.

08

📨 Але ж у нас POST

Іноді можна почути:

У нас зміни тільки через POST.
Тому CSRF немає.

Але HTML form вміє робити:

HTML
<form method="POST">

Тому:

POST ≠ CSRF Protection

POST — це HTTP method.

Він не доводить, що request прийшов саме з нашого application.

09

🚨 А якщо зміна виконується через GET?

Тут може бути ще цікавіше.

Уявімо:

HTTP
GET /user/delete?id=123

видаляє користувача.

Attacker може розмістити:

HTML
<img src="https://cabinet.example.com/user/delete?id=123">

Browser бачить:

HTML
<img>

і думає:

↳
Потрібно завантажити картинку.

У результаті:

Browser
   ↓
GET /user/delete?id=123
   ↓
Server
   ↓
User deleted 💥

Тому GET не повинен виконувати операції, які змінюють дані.

Концептуально:

GET
 ↓
отримати дані

POST / PUT / PATCH / DELETE
 ↓
змінити дані
10

🌐 А браузер не забороняє чужим сайтам працювати з нашим?

Так, у browser є багато security mechanisms.

Наприклад:

Same-Origin Policy — SOP

Вона не дозволяє одному сайту просто читати дані іншого сайту.

Наприклад:

evil.example

не може просто прочитати:

cabinet.example.com/profile

Але для CSRF attacker часто і не потрібно читати відповідь.

Йому потрібно:

Send Request

а не:

Read Response

Тому:

Не можу прочитати response
          ≠
Не можу спричинити request
11

⚠️ А CORS?

Тут часто виникає плутанина.

CORS контролює cross-origin взаємодію JavaScript із ресурсами іншого origin.

А CSRF використовує іншу ідею:

Attacker
   ↓
не обов'язково читає Response
   ↓
йому достатньо змусити Browser
відправити потрібний Request

Тому:

CORS ≠ CSRF Protection

CORS може впливати на конкретну атаку.

Але просто сказати:

У нас CORS
↓
CSRF немає

не можна.

12

🔒 А HTTPS?

HTTPS дуже важливий.

Він захищає з'єднання:

Browser
   🔒
 HTTPS
   🔒
Server

Але CSRF request теж може піти через HTTPS.

evil.example
      ↓
Browser
      ↓
HTTPS
      ↓
cabinet.example.com

Тому:

HTTPS ≠ CSRF Protection
13

🍪 А HttpOnly?

Cookie може мати:

HTTP
HttpOnly

Це означає, що JavaScript не може просто прочитати її через:

JAVASCRIPT
document.cookie

Це хороший security mechanism.

Але CSRF attacker і не обов'язково потрібно читати cookie.

Browser може використати її сам.

Тому:

HttpOnly
   ↓
Cookie harder to steal with JavaScript ✅

але:

HttpOnly ≠ CSRF Protection
14

🛡 Як тоді захищатися?

Є декілька механізмів.

Найважливіші для розуміння:

🍪 SameSite
      +
🎟️ CSRF Token
      +
🌍 Origin Check

Розберемо їх окремо.

15

🍪 SameSite Cookie

Cookie може мати параметр:

SameSite

Наприклад:

HTTP
Set-Cookie: session=abc123;
            Secure;
            HttpOnly;
            SameSite=Lax

SameSite допомагає browser вирішити:

↳
Чи можна відправляти цю cookie, якщо request виник у контексті іншого сайту?

Основні режими:

Strict
Lax
None

Дуже спрощено:

🛡 Strict

SameSite=Strict

Найсильніше обмежує cookie в cross-site сценаріях.

⚖️ Lax

SameSite=Lax

Компроміс між безпекою та зручністю.

Багато небезпечних cross-site сценаріїв обмежуються, але деякі звичайні переходи між сайтами залишаються можливими.

🌍 None

SameSite=None

Cookie може використовуватися в cross-site сценаріях.

При SameSite=None cookie також повинна бути:

Secure

Тому якщо бачимо:

HTTP
SameSite=None; Secure

потрібно особливо уважно розуміти, навіщо application потрібна cross-site cookie і який CSRF-захист використовується.

16

🎟️ CSRF Token

Ще один дуже поширений механізм —

CSRF Token

Server генерує випадкове непередбачуване значення:

f8d93a7c...

і додає його у форму:

HTML
<form action="/profile/change-email" method="POST">

    <input
        type="hidden"
        name="csrf_token"
        value="f8d93a7c...">

    <input name="email">

</form>

Коли користувач відправляє форму, server отримує:

Session Cookie
      +
CSRF Token

і перевіряє обидва.

Session valid?
      ↓
     YES
      ↓
CSRF Token valid?
      ↓
     YES
      ↓
Execute operation ✅
17

😈 Чому attacker стає складніше?

Attacker може створити свою HTML form:

HTML
<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        name="email"
        value="attacker@example.com">

</form>

Browser потенційно може додати cookie.

Але attacker не знає правильний:

csrf_token

Якщо він відправить:

csrf_token=123

server повинен отримати:

Session      → VALID ✅
CSRF Token   → INVALID ❌

і не виконати операцію.

Тобто:

Cookie 🍪
 ↓
Browser може додати сам

CSRF Token 🎟️
 ↓
Attacker не повинен знати
18

🌍 Перевірка Origin

Browser також може передавати інформацію про origin, з якого був ініційований request.

Наприклад:

HTTP
Origin: https://cabinet.example.com

Server очікує:

cabinet.example.com

і отримує:

cabinet.example.com
✅ Request from expected Origin

А тепер:

HTTP
Origin: https://evil.example

Server бачить:

Expected:
cabinet.example.com

Received:
evil.example

❌

і може відхилити request.

Тобто server отримує ще одну можливість запитати:

↳
Звідки взагалі прийшла ця операція?
19

🧱 Захист повинен бути на Server

Це дуже важливо.

Можна зробити у Frontend:

Button disabled
Hidden menu
JavaScript validation

Але attacker не зобов'язаний використовувати ваш Frontend.

Він створює:

Own HTML
   ↓
Own Form
   ↓
Request
   ↓
Your Server

Тому рішення:

ALLOW

або:

DENY

повинен приймати Server.

20

🧪 Як це тестувати?

Тепер подивимося на CSRF очима QA або Developer.

У нас є:

Profile
   ↓
Change Email
   ↓
Save

Відкриваємо:

DevTools
   ↓
Network

і знаходимо request.

Наприклад:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.example.com
Cookie: session=abc123

email=test@example.com

Ставимо просте питання:

↳
Що заважає сторонньому сайту відправити такий самий request?
21

🔎 Перевіряємо Cookie

Дивимося:

Secure?
HttpOnly?
SameSite?

Особливо нас цікавить:

SameSite

тому що він безпосередньо впливає на поведінку cookie у cross-site сценаріях.

22

🎟️ Шукаємо CSRF Token

Він може бути, наприклад, у body:

csrf_token=f8d93a7c...

або header:

HTTP
X-CSRF-Token: f8d93a7c...

Якщо token є, можна перевірити:

Remove Token
     ↓
Send Request

або:

Change Token
     ↓
Send Request

Server повинен відхилити request із неправильним token.

Найважливіше:

Operation NOT executed ❌
23

💣 Робимо простий CSRF PoC

Один із найзрозуміліших способів перевірки — створити просту HTML-сторінку.

Наприклад:

HTML
<!DOCTYPE html>
<html>
<body>

<h1>CSRF Test</h1>

<form
    action="https://cabinet.example.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="csrf-test@example.com">

    <button type="submit">
        Test
    </button>

</form>

</body>
</html>

Далі:

Login у TEST application
        ↓
залишаємо Session активною
        ↓
відкриваємо PoC
з іншого Origin
        ↓
натискаємо Test
        ↓
дивимося Request
        ↓
перевіряємо результат
↳
⚠️ Такі перевірки потрібно проводити лише на системах, які ви маєте право тестувати, бажано на DEV/TEST та з безпечною тестовою операцією.
24

🔍 Що перевіряємо?

Нас цікавить весь flow:

Was Request sent?
        ↓
Was Cookie attached?
        ↓
Did Server accept Request?
        ↓
Was operation executed?

Останній пункт найважливіший.

Наприклад:

Email реально змінився?
User реально створився?
Role реально змінилася?
Object реально видалився?
25

⚠️ Не дивимося тільки на HTTP Status

Наприклад:

HTTP
200 OK

ще не означає:

CSRF successful

Server міг повернути сторінку Login або повідомлення про помилку.

Тому правильніше перевіряти:

State BEFORE
     ↓
Request
     ↓
State AFTER
26

🎯 Що тестувати першочергово?

Усе, що щось змінює.

Наприклад:

📧 Change Email
🔑 Change Password
👤 Create User
🗑️ Delete User
🛡️ Change Role
⚙️ Change Settings
💰 Financial Operation

І окремо варто шукати:

GET

які чомусь змінюють дані.

27

📦 А якщо API працює з JSON?

Наприклад:

HTTP
POST /api/profile
Content-Type: application/json

{
    "email": "new@example.com"
}

Звичайна HTML form не вміє просто відправити довільний:

application/json

request.

Тому класична CSRF-атака через HTML form стає складнішою.

Але робити висновок:

JSON
 ↓
CSRF impossible

не потрібно.

Все одно потрібно дивитися на:

Authentication
Cookies
CORS
Accepted Requests
CSRF Protection

Тобто:

↳
JSON може ускладнити конкретний сценарій атаки, але сам по собі не є CSRF-захистом.
28

🚨 Типові помилки

❌ «У нас POST»

POST ≠ CSRF Protection

❌ «У нас HTTPS»

HTTPS ≠ CSRF Protection

HttpOnly ≠ CSRF Protection

CORS ≠ CSRF Protection

Attacker не використовує ваш Frontend.

Його можна побачити через:

DevTools
   ↓
Network

Прихований endpoint — не security mechanism.

29

🛡 Як виглядає нормальний захист?

Не існує однієї чарівної галочки:

CSRF Protection = ON

Захист може складатися з декількох рівнів:

🍪 Secure Cookie
       +
🍪 HttpOnly
       +
🛡️ SameSite
       +
🎟️ CSRF Token
       +
🌍 Origin Validation
       ↓
Better Protection

При цьому важливо розуміти:

HTTPS
HttpOnly
SameSite
CORS
CSRF Token
Origin

— це різні механізми.

Вони вирішують різні security problems.

Тому хороше питання:

↳
Від якої конкретно атаки нас захищає цей механізм?
30

✅ Простий CSRF Checklist

Коли бачимо операцію:

Change something

перевіряємо:

🍪 Cookie
   ↓
What is SameSite?

🎟️ CSRF Token
   ↓
Does it exist?
Is it validated?

🌍 Origin
   ↓
Is it checked?

🧪 PoC
   ↓
Can another site cause this Request?

🔍 Result
   ↓
Did the data actually change?

Цього вже достатньо, щоб почати нормальне тестування CSRF.

31

🧠 Що варто запам'ятати

CSRF — це не про те, що attacker обов'язково вкрав:

Password

або:

Cookie

Ідея інша:

Attacker
    ↓
Victim Browser
    ↓
Request
    ↓
Cookie 🍪
    ↓
Server
    ↓
💥 Operation

Attacker використовує той факт, що browser уже авторизований.

Тому:

Valid Session
      ≠
User wanted this operation

І це, мабуть, головна думка всієї статті.

32

🕵️ CSRF Challenge

Уявімо корпоративний application:

https://cabinet.company.com

Користувач авторизувався.

Browser отримав:

HTTP
Set-Cookie: session=ABC123;
            Secure;
            HttpOnly;
            SameSite=None

У application є:

HTTP
POST /profile/change-email

Request:

HTTP
POST /profile/change-email HTTP/1.1
Host: cabinet.company.com
Cookie: session=ABC123

email=new@company.com

При цьому:

CSRF Token ❌
Origin Check ❌

Attacker створив:

HTML
<form
    action="https://cabinet.company.com/profile/change-email"
    method="POST">

    <input
        type="hidden"
        name="email"
        value="attacker@example.com">

    <button type="submit">
        Open photo
    </button>

</form>

Авторизований користувач відкриває сторінку attacker та натискає кнопку.

❓ Питання №1

Attacker не знає:

session=ABC123

Чому attack усе одно потенційно може спрацювати?

❓ Питання №2

Cookie має:

HttpOnly

Чи захищає це від CSRF?

❓ Питання №3

Що тут означає:

SameSite=None

і чому на це варто звернути увагу?

❓ Питання №4

Server додав:

CSRF Token

Що тепер повинен знати attacker, крім параметрів самої операції?

❓ Питання №5

Server почав перевіряти:

HTTP
Origin: https://cabinet.company.com

А request прийшов із:

https://evil.example

Що повинен зробити Server?

❓ І останнє

У нас є:

HTTPS
+
Secure
+
HttpOnly

але немає нормального захисту від небажаних cross-site requests.

Чи можна сказати:

Authentication працює
       ↓
значить Request безпечний

Ні.

Саме тут проявляється головна ідея CSRF:

↳
Server повинен розуміти не тільки, хто авторизований, а й захищати критичні операції від requests, які користувач насправді не ініціював.

І якщо після цієї статті при перегляді нового endpoint виникає питання:

↳
«А що заважає іншому сайту змусити мій browser відправити такий самий request?»

— значить основна ідея CSRF зрозуміла. 🛡️
