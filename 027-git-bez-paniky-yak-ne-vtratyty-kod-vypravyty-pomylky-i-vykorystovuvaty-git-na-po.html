Вступ

Git є майже в кожному сучасному проєкті.

Розробник пише код:

BASH
git add .
git commit -m "fix"
git push

І більшу частину часу цього достатньо.

Проблеми починаються, коли:

  • зробив commit не в ту гілку;
  • випадково видалив зміни;
  • виконав reset --hard;
  • потрібно забрати один commit з іншої гілки;
  • після pull з'явився конфлікт;
  • хтось зробив force push;
  • потрібно знайти commit, який зламав систему;
  • локальна історія перетворилася на десяток fix, fix2, final, final-final;
  • Git повідомляє про detached HEAD, а що це означає — не дуже зрозуміло.

У такі моменти Git починає виглядати як магія.

Насправді більшість проблем стають зрозумілими, якщо знати кілька базових принципів.

Головна думка цієї статті:

↳
Git — це не просто commit, push і pull. Це машина часу для коду.

Розберімося, як вона працює.

01

1. Git і GitHub — не одне й те саме

Почнемо з дуже поширеної плутанини.

Git — це Distributed Version Control System (розподілена система контролю версій).

Вона зберігає історію змін проєкту та дозволяє:

  • створювати commits;
  • створювати branches;
  • порівнювати версії;
  • повертатися до попередніх станів;
  • об'єднувати зміни;
  • працювати паралельно кільком розробникам.

А GitHub, GitLab, Azure DevOps та подібні платформи — це сервіси, на яких може зберігатися remote repository (віддалений репозиторій).

Git може чудово працювати взагалі без GitHub.

Наприклад:

BASH
git init

І у вас уже є локальний Git-репозиторій.

02

2. Найважливіша схема Git

Щоб нормально працювати з Git, важливо розуміти чотири області.

Working Directory

Working Directory (робоча директорія) — файли, які ви зараз редагуєте.

Наприклад:

app.js
config.json
README.md

Ви змінили app.js.

Git бачить зміну, але вона ще не стала частиною історії.

Перевірити це можна:

BASH
git status

Staging Area

Staging Area (область підготовки змін) — проміжна зона перед commit.

Коли виконуємо:

BASH
git add app.js

ми говоримо Git:

↳
Цю версію app.js я хочу включити в наступний commit.

Це важливий момент.

git add не зберігає зміни в історію.

Він лише готує їх до commit.

Local Repository

Після:

BASH
git commit -m "Add authentication"

Git створює commit у Local Repository (локальному репозиторії).

Тепер зміни вже є частиною історії.

Але вони все ще можуть існувати лише на вашому комп'ютері.

Remote Repository

Коли виконуємо:

BASH
git push

локальні commits передаються до Remote Repository (віддаленого репозиторію).

Наприклад, в Azure DevOps або GitHub.

03

3. Що насправді таке commit

Commit часто сприймають як:

↳
«Я зберіг змінені файли».

Але корисніше думати про нього як про snapshot (знімок стану проєкту).

Умовно:

Кожен commit має унікальний ідентифікатор — commit hash (хеш commit).

Наприклад:

68b4990

або повний SHA:

68b4990e3e3d17...

Подивитися історію:

BASH
git log

Але зазвичай зручніше:

BASH
git log --oneline

Наприклад:

68b4990 Fix authentication
317c4f3 Add authenticated article
e21ac98 Create article page

Git фактично створив для нас ланцюжок точок у часі.

І саме тому до них можна повертатися.

04

4. Branch — це не копія проєкту

Branch (гілка) часто уявляється як окрема копія всього коду.

Але концептуально branch значно простіший.

Це покажчик на commit.

Наприклад:

main просто вказує на останній commit.

Створимо нову гілку:

BASH
git switch -c feature-login

Отримаємо:

Після нового commit у feature-login:

Тобто створення branch — дуже дешева операція.

Git не копіює весь проєкт.

Він створює новий покажчик.

05

5. А що тоді таке HEAD?

Тепер можна зрозуміти одну з найбільш загадкових речей у Git.

HEAD (покажчик поточної позиції) показує, де ви зараз перебуваєте в історії.

Наприклад:

HEAD
 ↓
main
 ↓
68b4990

Тобто:

HEAD → main → commit

Якщо переключитися:

BASH
git switch feature-login

отримаємо:

HEAD → feature-login → commit

Тому коли Git говорить про HEAD, це не якась магічна сутність.

Це просто відповідь на питання:

↳
«Де я зараз знаходжуся?»
06

6. Що таке detached HEAD

Іноді можна зробити:

BASH
git checkout 68b4990

або:

BASH
git switch --detach 68b4990

Тоді HEAD вказуватиме безпосередньо на commit:

HEAD → 68b4990

а не:

HEAD → main → 68b4990

Це називається Detached HEAD (HEAD, від'єднаний від гілки).

Сам по собі цей стан не є помилкою.

Ви можете дивитися код, запускати його, тестувати стару версію.

Але якщо почнете створювати commits, вони не належатимуть звичайній branch.

Якщо хочете продовжити роботу:

BASH
git switch -c experiment

І commit отримає нормальну гілку.

07

7. git fetch і git pull — не одне й те саме

Ми часто пишемо:

BASH
git pull

не задумуючись, що саме відбувається.

git fetch

BASH
git fetch

отримує інформацію про зміни з remote repository, але не змінює вашу поточну робочу гілку автоматично.

Тобто це відносно безпечний спосіб сказати:

↳
«Git, покажи, що змінилося на сервері».

Після цього можна подивитися:

BASH
git log HEAD..origin/main --oneline

git pull

git pull робить більше.

Спрощено:

git pull = git fetch + інтеграція змін

Залежно від налаштувань це може бути merge або rebase.

Тому pull — не просто «завантажити зміни».

Він може змінити вашу локальну історію.

08

8. Я змінив файл і хочу все повернути

Уявімо:

BASH
git status

показує:

modified: app.js

Ви зрозуміли, що зміни не потрібні.

Можна виконати:

BASH
git restore app.js

Git поверне файл до стану останнього commit.

А якщо потрібно скасувати всі незбережені зміни:

BASH
git restore .

⚠️ Тут потрібно бути обережним.

Незбережені зміни можуть бути втрачені.

09

9. Я випадково зробив git add

Наприклад:

BASH
git add config.json

але файл не повинен потрапити в наступний commit.

Не потрібно видаляти файл.

Використовуємо:

BASH
git restore --staged config.json

Файл залишиться зміненим, але буде прибраний зі Staging Area.

Це чудово демонструє, навіщо розуміти:

Working Directory
        ↓
Staging Area
        ↓
Repository
10

10. Я зробив commit і відразу побачив помилку

Класика.

Зробили:

BASH
git commit -m "Add authentication"

І через десять секунд:

↳
Забув один файл.

Додаємо його:

BASH
git add forgotten-file.js

і:

BASH
git commit --amend

Amend (внесення змін до останнього commit) дозволяє замінити останній commit новою версією.

Можна також змінити повідомлення:

BASH
git commit --amend -m "Add authentication and validation"

Але є важливий нюанс.

amend змінює commit hash.

Тому якщо commit уже був опублікований і ним користуються інші розробники, потрібно розуміти наслідки переписування історії.

11

11. reset і revert — дуже різні речі

Це одна з найважливіших тем Git.

Уявімо історію:

A → B → C → D

Commit D поганий.

Є два принципово різні підходи.

git revert

BASH
git revert D

Git не видаляє D.

Він створює новий commit, який скасовує зміни D.

A → B → C → D → E
                ↑
           revert D

Історія залишається.

Саме тому revert зазвичай добре підходить для вже опублікованої спільної історії.

git reset

Наприклад:

BASH
git reset --hard C

Покажчик branch переміститься назад:

A → B → C

D більше не буде частиною звичайної історії цієї branch.

Тобто:

↳
revert додає історію, а reset пересуває історію.

Це принципова різниця.

12

12. Три види reset

Git має:

BASH
git reset --soft
git reset --mixed
git reset --hard

Розглянемо просто.

--soft

BASH
git reset --soft HEAD~1

Commit скасовується, але зміни залишаються у Staging Area.

Корисно, якщо потрібно переробити commit.

--mixed

BASH
git reset HEAD~1

або:

BASH
git reset --mixed HEAD~1

Commit скасовується, зміни залишаються у Working Directory, але вже не в Staging Area.

--hard

BASH
git reset --hard HEAD~1

Git пересуває branch і приводить робочі файли до відповідного стану.

Це вже небезпечна операція.

Саме тут можна втратити незбережені зміни.

13

13. «Я зробив reset --hard. Все пропало!»

Не обов'язково.

Тут з'являється одна з найкорисніших команд Git:

BASH
git reflog

Reflog — Reference Log (локальний журнал переміщень посилань Git).

Наприклад:

68b4990 HEAD@{0}: reset: moving to 68b4990
91d23ab HEAD@{1}: commit: Add authentication
73ad112 HEAD@{2}: commit: Add login page

Звичайний:

BASH
git log

може вже не показувати втрачений commit.

А reflog часто показує.

Тоді можна створити branch:

BASH
git branch recovery 91d23ab

або перейти до commit і відновити потрібні зміни.

↳
💡 Git набагато складніше безповоротно зламати, ніж здається.

Якщо commit уже існував, часто його ще можна знайти через reflog.

Але це не означає, що reflog — резервна копія назавжди. Git з часом може очистити недосяжні об'єкти.

14

14. Простий лайфхак перед небезпечною операцією

Перед великим reset, rebase або іншим експериментом можна витратити кілька секунд:

BASH
git branch backup-before-reset

Все.

Тепер поточний commit має додатковий покажчик.

Можна експериментувати значно спокійніше.

Або одразу створити експериментальну branch:

BASH
git switch -c experiment

Це один із найпростіших способів не боятися Git.

15

15. git stash — сховати незакінчену роботу

Уявімо ситуацію.

Ви працюєте над feature.

Робота ще не готова.

Раптом приходить повідомлення:

↳
PROD лежить. Терміново потрібен hotfix.

А переключити branch Git не дозволяє через локальні зміни.

Тут допомагає stash (тимчасове сховище змін):

BASH
git stash

Після цього можна переключитися:

BASH
git switch main

зробити hotfix, а потім повернутися:

BASH
git switch feature
git stash pop

Подивитися список:

BASH
git stash list

Краще давати stash зрозумілу назву:

BASH
git stash push -m "WIP authentication"

WIP — Work In Progress (робота в процесі).

Важливо:

↳
Stash — зручна тимчасова кишеня, але не довгострокове сховище роботи.
16

16. git cherry-pick — забрати один commit

Уявімо:

у develop уже є багато нової функціональності.

Але серед commits є один важливий bugfix, який потрібно перенести в release.

Merge всієї develop робити не можна.

Тоді:

BASH
git cherry-pick <commit>

Cherry-pick (вибіркове перенесення commit) бере зміни конкретного commit і застосовує їх у поточній branch.

Наприклад:

BASH
git switch release
git cherry-pick 91d23ab

Дуже корисний інструмент для release/hotfix сценаріїв.

17

17. git bisect — знайти commit, який усе зламав

Уявімо:

у вас 500 commits.

Сьогодні функція не працює.

Три місяці тому точно працювала.

Який із 500 commits винен?

Перевіряти кожен?

Ні.

Git має bisect (бінарний пошук проблемного commit).

Починаємо:

BASH
git bisect start

Говоримо:

BASH
git bisect bad

Поточна версія погана.

Потім вказуємо старий хороший commit:

BASH
git bisect good <commit>

Git вибере commit приблизно посередині.

Ви перевіряєте програму та відповідаєте:

BASH
git bisect good

або:

BASH
git bisect bad

Git знову ділить діапазон.

Замість перевірки сотень commits може знадобитися лише кілька перевірок.

А після завершення:

BASH
git bisect reset
18

18. git blame — не для пошуку винного

Команда:

BASH
git blame app.js

показує, який commit останнім змінював кожен рядок файлу.

Назва blame провокує використовувати її як:

↳
Хто написав цю дурницю?!

Але значно корисніше питання:

↳
Чому цей код тут з'явився?

Знайшли commit.

Потім:

BASH
git show <commit>

І вже можна побачити:

  • які ще файли змінювалися;
  • повідомлення commit;
  • контекст зміни;
  • пов'язаний PR або задачу, якщо процес це підтримує.

Тому git blame — це скоріше інструмент археології коду, а не пошуку винних.

19

19. git diff — команда, яку варто використовувати частіше

Найпростіший варіант:

BASH
git diff

показує незастейджені зміни.

Але є ще:

BASH
git diff --staged

Він показує:

↳
Що саме зараз потрапить у наступний commit?

Це дуже корисно виконувати перед:

BASH
git commit

Можна порівняти branches:

BASH
git diff main..feature

або commits:

BASH
git diff <commit1> <commit2>

Git дозволяє не просто дивитися історію, а ставити їй конкретні запитання.

20

20. Нормальний git log

Звичайний:

BASH
git log

іноді незручний.

Спробуйте:

BASH
git log --oneline --graph --decorate --all

Він показує:

  • commits;
  • branches;
  • merges;
  • HEAD;
  • структуру історії.

Якщо команда подобається, можна створити alias (псевдонім команди):

BASH
git config --global alias.tree "log --oneline --graph --decorate --all"

Після цього:

BASH
git tree

І отримуємо компактне дерево репозиторію.

21

21. Як знайти, коли з'явився конкретний код

Ще один дуже корисний трюк.

Наприклад, потрібно зрозуміти:

↳
У якому commit з'явилася CalculatePrice()?

Можна:

BASH
git log -S "CalculatePrice"

Git шукатиме commits, у яких змінювалася кількість входжень цього тексту.

А якщо потрібен пошук за шаблоном у diff, є:

BASH
git log -G "Calculate.*"

Це дуже корисно при дослідженні старого коду.

Особливо коли ніхто вже не пам'ятає, чому певна логіка взагалі існує.

22

22. Interactive Rebase — прибираємо історію перед PR

Під час розробки історія може виглядати так:

Add authentication
fix
fix typo
fix again
really fix
final
final2

Для локальної роботи це нормально.

Але перед Pull Request (запитом на включення змін) іноді хочеться привести commits до зрозумілого вигляду.

Тут допомагає Interactive Rebase (інтерактивне перебудування історії):

BASH
git rebase -i HEAD~6

Git покаже приблизно:

pick 81ab123 Add authentication
pick 91ac234 fix
pick 31bc345 fix typo
pick 73dc456 fix again
pick 19ef567 final
pick 88fa678 final2

Можна використовувати:

pick
reword
edit
squash
fixup
drop

Наприклад, squash дозволяє об'єднати commits.

У результаті замість шести технічних commits може залишитися один зрозумілий:

Add authentication

Але тут діє важливе правило:

↳
⚠️ Не переписуйте історію спільної branch, якщо не розумієте наслідків.

Rebase змінює commit hashes.

23

23. Force push: краще знати --force-with-lease

Після rebase іноді потрібно оновити remote branch.

Перше, що приходить на думку:

BASH
git push --force

Але --force фактично говорить:

↳
Запиши мою версію branch незалежно від того, що зараз знаходиться на сервері.

Це може затерти чужі зміни.

Безпечніший варіант:

BASH
git push --force-with-lease

Force with lease (примусове оновлення з перевіркою стану remote branch) додатково перевіряє, чи не змінилася віддалена branch відносно очікуваного вами стану.

Якщо хтось уже встиг додати туди нові commits, Git може відмовитися перезаписувати branch.

Тому практичне правило:

↳
Якщо force push справді необхідний, зазвичай варто спочатку подумати про --force-with-lease.
24

24. Кілька маленьких Git-лайфхаків

Швидко повернутися на попередню branch

BASH
git switch -

Працює приблизно як кнопка «назад».

Подивитися commit

BASH
git show <commit>

Наприклад:

BASH
git show 68b4990

Побачимо сам commit і його зміни.

Перед видаленням untracked-файлів спочатку подивитися

Untracked files (файли, які Git ще не відстежує) можна знайти через:

BASH
git status

Для очищення існує:

BASH
git clean

Але не поспішайте видаляти.

Спочатку:

BASH
git clean -n

-n виконує dry run (пробний запуск без реального видалення).

Git покаже, що було б видалено.

І тільки після перевірки можна вирішувати, чи потрібне фактичне очищення.

Подивитися авторів commits

BASH
git shortlog -sn

Покаже кількість commits за авторами.

Але кількість commits не варто сприймати як метрику продуктивності розробника.

Один commit може містити зміну одного символу, а інший — складний рефакторинг.

25

25. Ще один сильний інструмент — git worktree

Є ситуація.

Ви працюєте над великою feature.

У Working Directory купа змін.

І раптом потрібно швидко подивитися іншу branch або зробити hotfix.

Можна використовувати stash.

А можна використати Git Worktree (додаткова робоча директорія одного репозиторію).

Наприклад:

BASH
git worktree add ../project-hotfix main

Git створить другу робочу директорію:

project/
project-hotfix/

При цьому обидві використовують один Git repository.

Тепер в одному вікні IDE можна продовжувати feature, а в іншому — працювати з hotfix.

Подивитися worktrees:

BASH
git worktree list

Для розробника, який часто перемикається між задачами, це може бути дуже зручно.

26

26. Що робити, якщо виник merge conflict

Merge Conflict (конфлікт злиття) виникає, коли Git не може автоматично визначити, яку версію змін залишити.

Наприклад, два розробники змінили один фрагмент.

Git може показати:

<<<<<<< HEAD
timeout = 30
=======
timeout = 60
>>>>>>> feature

Це не означає, що Git зламався.

Він говорить:

↳
Я бачу дві різні зміни і не можу сам вирішити, яка правильна.

Розробник повинен:

  1. зрозуміти обидві зміни;
  2. залишити правильний результат;
  3. видалити службові маркери;
  4. додати виправлений файл:
BASH
git add config.txt
  1. завершити merge або rebase.

Головне правило:

↳
Не вирішуйте conflict механічним натисканням «Accept ours» або «Accept theirs», якщо не розумієте, що саме відкидаєте.
27

27. Git-рятувалка

Коли щось пішло не так, не потрібно пам'ятати сотні Git-команд.

Достатньо розуміти, на якому рівні виникла проблема.

СитуаціяЩо згадати
Хочу побачити стан репозиторіюgit status
Змінив файл і передумавgit restore
Випадково додав файл у staginggit restore --staged
Треба змінити останній commitgit commit --amend
Треба безпечно скасувати опублікований commitgit revert
Треба пересунути локальну історіюgit reset
Після reset «все пропало»git reflog
Треба тимчасово сховати роботуgit stash
Потрібен один commit з іншої branchgit cherry-pick
Треба знайти commit, який приніс buggit bisect
Треба зрозуміти історію рядкаgit blame
Треба знайти появу конкретного кодуgit log -S
Треба привести commits до ладуgit rebase -i
Потрібен force pushgit push --force-with-lease
Треба паралельно працювати з двома branchesgit worktree
28

28. Найважливіше — не вчити команди напам'ять

Git має величезну кількість команд і параметрів.

Немає сенсу пам'ятати їх усі.

Набагато важливіше зрозуміти модель:

Коли ця модель зрозуміла, команди перестають бути магічними.

restore, reset, revert, checkout, switch, rebase — це просто різні способи керувати файлами, покажчиками та історією.

29

Якщо зовсім просто

Уявіть, що Git — це машина часу для вашого коду.

Ви пишете код у Working Directory.

git add говорить:

↳
«Ось ці зміни хочу зберегти».

git commit створює точку в історії:

↳
«Запам'ятай проєкт у такому стані».

Branch — це закладка:

↳
«Ось тут зараз знаходиться ця лінія розробки».

HEAD говорить:

↳
«А ось тут зараз знаходжуся я».

git push відправляє вашу історію на сервер.

git revert говорить:

↳
«Створи нову зміну, яка скасує стару».

git reset говорить:

↳
«Пересунь мою закладку назад».

git reflog говорить:

↳
«Покажи, де моя закладка була раніше».

git cherry-pick:

↳
«Візьми ось цю одну зміну з іншої історії».

git bisect:

↳
«Допоможи знайти момент, коли все зламалося».

git stash:

↳
«Потримай мої незакінчені зміни, я скоро повернуся».

А git worktree:

↳
«Дай мені ще один робочий стіл для цього ж проєкту».

Тому головний Git-лайфхак — не знати 100 команд.

Головний лайфхак — розуміти, що Git зараз робить з вашими файлами та історією.

І перш ніж панікувати через «втрачений» код:

BASH
git status

а якщо проблема вже пов'язана з історією:

BASH
git reflog

Дуже часто код нікуди не зник.

Просто потрібно знайти, де Git його залишив.
