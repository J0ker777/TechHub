01

1. Чому тестування — це не просто натискання кнопок

Уявімо корпоративну систему, у якій користувач створює заявку.

Він відкриває вебсторінку, заповнює форму та натискає кнопку «Створити».

Система повідомляє:

«Заявку успішно створено».

Чи означає це, що все працює правильно?

Не обов'язково.

Можливо:

  • інтерфейс показав успішне повідомлення, але заявка не збереглася в базі;
  • заявка створилася двічі;
  • API дозволив виконати операцію користувачу без необхідних прав;
  • повідомлення не потрапило до RabbitMQ;
  • інший сервіс не отримав інформацію;
  • після повторного запиту виникла помилка.

Інтерфейс може виглядати абсолютно справним, хоча всередині система працює неправильно.

Саме тому тестування — це не лише перевірка того, що бачить користувач, а й перевірка поведінки системи на різних рівнях.

У цій статті розберемося, які бувають види тестування, чим вони відрізняються, як поєднуються та як побудувати ефективну стратегію перевірок.

02

2. Одна система — багато точок перевірки

Розглянемо типову архітектуру корпоративного вебзастосунку.

Спрощена архітектура. У реальних системах зв'язки можуть бути складнішими, а повідомлення RabbitMQ можуть обробляти інші сервіси.

На кожному з цих рівнів можна виконувати перевірки.

Точка перевіркиЩо перевіряємо
UIПоведінку інтерфейсу
APIЗапити, відповіді, контракти, доступ
ServiceБізнес-логіку
DatabaseЗбереження та цілісність даних
RabbitMQПублікацію й обробку повідомлень
RedisКешування та термін дії даних
Увесь процесНаскрізну роботу системи

Важливо розуміти: це точки перевірки, а не повністю незалежні види тестування. Наприклад, API-тест може одночасно бути інтеграційним, функціональним та регресійним.

03

3. Основні рівні та точки тестування

3.1. Unit Testing — модульне тестування

Unit Testing перевіряє невелику одиницю програмної логіки: функцію, метод або клас.

Наприклад, система розраховує знижку для клієнта:

  • сума до 1 000 грн — без знижки;
  • від 1 000 грн — 5%;
  • від 10 000 грн — 10%.

Ми можемо перевірити цю логіку без браузера, HTTP-запитів або реальної бази даних.

CSHARP
[Theory]
[InlineData(500, 0)]
[InlineData(1000, 50)]
[InlineData(10000, 1000)]
public void CalculateDiscount_ReturnsExpected(
    decimal amount,
    decimal expected)
{
    var result = DiscountCalculator.Calculate(amount);

    Assert.Equal(expected, result);
}

У цьому прикладі використовується xUnit для .NET.

Переваги: швидке виконання, проста діагностика помилок, можливість запускати сотні або тисячі тестів.

Обмеження: успішні Unit-тести не гарантують, що всі компоненти правильно взаємодіють між собою.

Зазвичай такі тести пишуть Developers.

3.2. API Testing — тестування програмного інтерфейсу

API (Application Programming Interface — програмний інтерфейс застосунку) дозволяє перевіряти систему без використання графічного інтерфейсу.

Наприклад, створюємо заявку:

HTTP
POST /api/requests
Authorization: Bearer <token>
Content-Type: application/json

{
  "customerId": 123,
  "amount": 1500
}

Очікуємо:

HTTP
HTTP/1.1 201 Created
Location: /api/requests/456
JSON
{
  "id": 456,
  "status": "Created"
}

Але перевірити тільки код 201 недостатньо.

Хороший API-тест може перевіряти:

  • HTTP status code (код результату запиту);
  • структуру JSON;
  • обов'язкові поля;
  • правила валідації;
  • авторизацію та права доступу;
  • бізнес-обмеження;
  • поведінку при повторному запиті;
  • коректність повідомлень про помилки.

Наприклад:

СценарійОчікувана поведінка
Коректний запит201 Created
Некоректні дані400 Bad Request або 422 Unprocessable Content
Немає автентифікації401 Unauthorized
Недостатньо прав403 Forbidden
Ресурс не знайдено404 Not Found
Конфлікт стану409 Conflict

Конкретні коди залежать від контракту API. Наприклад, 422 використовується не в кожній системі.

Важливий нюанс: якщо API повернуло правильний JSON, це ще не доводить, що заявка дійсно збереглася або всі наступні операції виконалися.

3.3. Integration Testing — інтеграційне тестування

Integration Testing перевіряє, чи правильно взаємодіють кілька компонентів.

Наприклад:

Що потрібно перевірити?

  1. Order Service сформував коректне повідомлення.
  2. Повідомлення було опубліковане в RabbitMQ.
  3. Billing Service отримав його.
  4. Сервіс правильно обробив дані.
  5. Результат зберігся в базі.

А що станеться, якщо RabbitMQ тимчасово недоступний?

А якщо повідомлення доставили двічі?

А якщо Billing Service упав під час обробки?

Саме тут з'являються важливі сценарії:

  • Retry — повторна спроба;
  • Idempotency — ідемпотентність, тобто повторна обробка не повинна створювати небажаних додаткових ефектів;
  • Dead Letter Queue (DLQ) — черга повідомлень, які не вдалося обробити;
  • Timeout — обмеження часу очікування.

Інтеграційні тести можуть виконуватися автоматично, зокрема з використанням тестових контейнерів та реальних залежностей.

3.4. Database Testing — тестування бази даних

Тут перевіряють не зовнішню відповідь системи, а правильність роботи з даними.

Наприклад, після створення заявки:

SQL
SELECT Id, CustomerId, Status
FROM Requests
WHERE Id = 456;

Можна перевірити:

  • чи створився запис;
  • чи правильний статус;
  • чи не виникли дублікати;
  • чи збереглися зв'язки;
  • чи дотримуються обмеження цілісності;
  • чи коректно працюють транзакції.

Окремо перевіряють міграції структури БД, складні SQL-запити та процедури.

Важливо: не кожен API-тест повинен напряму звертатися до бази. Інакше тести стають залежними від внутрішньої реалізації, а зміна схеми БД може ламати перевірки навіть без зміни бізнес-поведінки.

Прямі перевірки БД варто використовувати там, де вони справді потрібні.

3.5. UI Testing — тестування інтерфейсу

UI (User Interface — інтерфейс користувача) Testing перевіряє, як працює застосунок з погляду користувача.

Наприклад:

  1. Відкрити сторінку авторизації.
  2. Увести логін і пароль.
  3. Натиснути «Увійти».
  4. Перевірити відкриття особистого кабінету.

Для автоматизації вебінтерфейсів часто використовують Playwright або Selenium.

UI-тести особливо корисні для перевірки:

  • форм;
  • навігації;
  • відображення даних;
  • повідомлень про помилки;
  • взаємодії з елементами;
  • критичних користувацьких сценаріїв.

Проте вони часто повільніші за модульні та API-тести, а також можуть бути чутливими до змін інтерфейсу.

3.6. E2E Testing — наскрізне тестування

E2E (End-to-End — від початку до кінця) перевіряє повний сценарій роботи системи.

Наприклад:

Такий тест перевіряє не окремий метод чи API, а завершення бізнес-процесу.

При цьому E2E не обов'язково означає UI-автоматизацію. Наскрізний сценарій іноді запускають через API та перевіряють результат через публічні інтерфейси системи.

Головна цінність E2E: перевірити, що компоненти разом забезпечують очікуваний результат для бізнесу.

Головний недолік: такі тести зазвичай дорожчі в підтримці, повільніші та складніші для діагностики.

04

4. Види тестування за метою

Ми вже розглянули, де можна тестувати систему.

Тепер розберемо, навіщо проводять перевірки.

ВидОсновне питання
FunctionalЧи правильно працює функція?
SmokeЧи система загалом придатна до подальшого тестування?
SanityЧи працює конкретна змінена частина?
RegressionЧи не зламали попередню функціональність?
SecurityЧи захищена система?
PerformanceНаскільки швидко та стабільно вона працює?
LoadЯк поводиться під очікуваним навантаженням?
StressЩо станеться за межами нормального навантаження?
UsabilityНаскільки зручно користуватися?
CompatibilityЧи працює в різних середовищах?

Розглянемо найважливіші.

Functional Testing — функціональне тестування

Перевіряє відповідність функціональності вимогам.

Наприклад:

↳
Якщо клієнт натиснув «Скасувати заявку», її статус повинен змінитися на Cancelled.

Це можна перевірити через UI або API.

Smoke Testing — базова перевірка працездатності

Smoke Testing (димове тестування) — невеликий набір перевірок, який дозволяє швидко зрозуміти, чи придатна система до подальшого тестування.

Наприклад, після розгортання нової версії:

  • застосунок відкривається;
  • авторизація працює;
  • головна сторінка завантажується;
  • критичний API відповідає;
  • базовий бізнес-сценарій виконується.

Smoke не перевіряє всю функціональність. Його задача — швидко виявити критичні проблеми.

Sanity Testing — цільова перевірка змін

Sanity Testing — швидка перевірка конкретної зміненої функціональності.

Наприклад, розробник виправив помилку розрахунку знижки.

QA перевіряє, що нова логіка працює і пов'язані сценарії не мають очевидних проблем.

Різниця між Smoke та Sanity умовна й може залежати від процесів команди:

  • Smoke — широка, але поверхнева перевірка системи;
  • Sanity — вузька перевірка певної зміни.

Regression Testing — регресійне тестування

Regression Testing перевіряє, чи нові зміни не зламали те, що раніше працювало.

Наприклад, команда змінила механізм авторизації.

Після цього потрібно перевірити не тільки новий сценарій входу, а й:

  • оновлення токенів;
  • вихід із системи;
  • доступ до API;
  • роботу ролей;
  • доступ до адміністративних функцій.

Регресійні перевірки — один із головних кандидатів на автоматизацію, особливо якщо вони стабільні та регулярно повторюються.

Security Testing — тестування безпеки

Security Testing перевіряє, чи може система протистояти несанкціонованим діям.

Приклади:

  • доступ до чужих даних;
  • обхід авторизації;
  • SQL Injection — ін'єкція SQL;
  • XSS — міжсайтове виконання сценаріїв;
  • CSRF — підробка міжсайтових запитів;
  • неправильна перевірка JWT;
  • витік конфіденційної інформації.

Частину таких перевірок можна автоматизувати на рівні API, частину виконують спеціалізованими інструментами SAST/DAST (статичний та динамічний аналіз безпеки).

Автоматизоване сканування не замінює повноцінне тестування на проникнення.

Performance, Load та Stress Testing

Ці терміни часто плутають.

Performance Testing — тестування продуктивності. Перевіряє час відповіді, пропускну здатність, використання ресурсів та інші характеристики продуктивності.

Load Testing — навантажувальне тестування. Перевіряє поведінку системи під очікуваним навантаженням, наприклад при 1 000 одночасних активних користувачах.

Stress Testing — стрес-тестування. Перевіряє поведінку за межами нормального навантаження, відмовостійкість та відновлення після перевантаження.

Load та Stress — це різновиди тестування продуктивності, а не повністю незалежні категорії.

Для API-систем важливо перевіряти не лише середній час відповіді, а й, наприклад, p95 і p99 — час, у який вкладаються відповідно 95% та 99% запитів.

05

5. Чому один тест може належати до кількох категорій

Ось одна з найважливіших ідей статті.

Тестування можна класифікувати за кількома незалежними ознаками.

Приклад класифікації одного тесту:

ОзнакаЗначення
Спосіб виконанняAutomated
Точка перевіркиAPI
МетаFunctional
Набір перевірокRegression

Це автоматизований функціональний API-тест, який регулярно запускається у складі регресійного набору.

Інший тест може бути:

Manual → UI → E2E → Smoke

Тобто ручна перевірка критичного наскрізного сценарію через інтерфейс у межах Smoke-набору.

Тому запитання «Що краще — API чи Regression?» некоректне. Це різні характеристики тестування.

06

6. Test Pyramid — піраміда тестування

Одна з найпоширеніших помилок — намагатися автоматизувати всі перевірки через браузер.

Наприклад, Manual QA має 300 тест-кейсів, які виконує через UI.

Приходить Automation QA та переносить усі 300 сценаріїв у Playwright.

Формально компанія отримала автоматизацію.

Але чи стала стратегія тестування ефективною?

Не обов'язково.

Частина перевірок могла б виконуватися через API значно швидше, а частина бізнес-логіки — перевірятися модульними тестами.

Концептуальна піраміда, подана вертикальними рівнями для зручного читання з телефона. Зверху — менше тестів із ширшим охопленням, знизу — більше швидких тестів. Реальні пропорції залежать від архітектури та ризиків системи.

Ідея Test Pyramid полягає в тому, щоб мати багато швидких, ізольованих перевірок на нижніх рівнях і менше дорогих наскрізних тестів.

При цьому не існує універсальної пропорції на кшталт «70% Unit, 20% API, 10% UI», яка однаково підходить усім системам.

Для API-first (систем, де API є основним інтерфейсом взаємодії) велика кількість API та інтеграційних перевірок може бути цілком виправданою.

Головне правило: перевіряти поведінку на найнижчому рівні, який дає достатню впевненість, і доповнювати її наскрізними перевірками критичних процесів.

07

7. Практичний приклад: як тестувати створення заявки

Припустимо, у нас є система, де користувач створює заявку, а інший сервіс отримує повідомлення та виконує подальшу обробку.

Що потрібно тестувати?

РівеньПриклад перевірки
UnitПравильно визначається початковий статус заявки
APIPOST /requests повертає правильний результат
DatabaseЗаявка збереглася без дублювання
IntegrationПодія RequestCreated передана та оброблена
SecurityКористувач не може створити заявку від чужого імені
E2EКористувач створив заявку й побачив результат обробки
PerformanceСистема витримує очікувану кількість запитів

Зверни увагу: це не обов'язково сім окремих тестів. Деякі перевірки можна поєднати, а деякі потрібно виконувати окремо для точної діагностики.

Що робити, якщо RabbitMQ недоступний?

Тут виникає окремий клас сценаріїв.

Наприклад:

  • заявка успішно записалася в базу;
  • RabbitMQ тимчасово недоступний;
  • подія не була опублікована;
  • користувач отримав повідомлення про успіх.

Чи правильна така поведінка?

Відповідь залежить від архітектури та бізнес-вимог.

Якщо система гарантує доставку подій, потрібно перевіряти відповідний механізм, наприклад Transactional Outbox (транзакційний вихідний журнал), який дозволяє надійно передавати події після збереження даних.

Це приклад того, чому QA має розуміти архітектуру, а не лише інтерфейс системи.

08

8. Хто повинен відповідати за тестування

Тестування — відповідальність усієї команди, але різні ролі мають різні основні завдання.

РольОсновний внесок
DeveloperUnit, компонентні та частина інтеграційних тестів
Manual QAДослідницьке, функціональне, UI та E2E тестування
Automation QAАвтоматизація API, Integration, UI та E2E
BA / POКритерії приймання, бізнес-сценарії
DevOpsІнфраструктура запуску тестів, CI/CD
Security EngineerСпеціалізовані перевірки безпеки

Це не жорсткі межі. Наприклад, Automation QA може писати компонентні тести, а Developer — автоматизувати API-перевірки.

Важливо, щоб команда домовилася, хто забезпечує покриття кожного критичного ризику.

Чому Automation QA — це не просто розробник Playwright-тестів

Playwright — інструмент. Він не визначає стратегію тестування.

Хороший Automation QA повинен розуміти:

  • архітектуру системи;
  • HTTP, REST API та JSON;
  • авторизацію й автентифікацію;
  • роботу з базами даних;
  • асинхронні процеси;
  • принципи стабільних тестів;
  • CI/CD — безперервну інтеграцію та доставку;
  • причини нестабільності автоматизованих перевірок.

Наприклад, якщо тест перевіряє лише розрахунок суми заявки, навіщо відкривати браузер, авторизуватися, переходити на сторінку й натискати кнопки?

Можливо, це краще перевірити через API або Unit-тест.

Але якщо потрібно перевірити, що користувач може правильно заповнити форму, — UI-тест цілком виправданий.

09

9. Як обрати правильний рівень тестування

Спробуй обрати, де краще виконати кожну перевірку.

Мініпрактикум

Питання 1. Потрібно перевірити формулу розрахунку комісії.

  • A. UI
  • B. Unit
  • C. E2E

Питання 2. Потрібно перевірити, що API відхиляє запит без прав доступу.

  • A. API
  • B. UI
  • C. Load

Питання 3. Потрібно перевірити, що повідомлення з RabbitMQ обробляє інший сервіс.

  • A. Unit
  • B. Integration
  • C. Usability

Питання 4. Потрібно перевірити повний процес створення та погодження заявки.

  • A. E2E
  • B. Unit
  • C. Database

<details> <summary><strong>Показати правильні відповіді та пояснення</strong></summary>

  1. B. Unit. Ізольовану бізнес-логіку найефективніше перевіряти швидким модульним тестом.
  2. A. API. Перевірка авторизації на рівні API дозволяє напряму протестувати серверне правило доступу.
  3. B. Integration. Ми перевіряємо взаємодію компонентів, включно з брокером повідомлень.
  4. A. E2E. Наскрізний тест перевіряє завершення бізнес-сценарію через необхідні компоненти.

</details>

10

10. Типові помилки в організації тестування

Помилка №1. Усе тестуємо через UI.

Це створює повільні та складні в підтримці набори тестів. Частину сценаріїв варто перенести на API або нижчі рівні.

Помилка №2. Якщо API повернув 200 — усе добре.

Правильний HTTP-код не гарантує правильного бізнес-результату. Потрібно перевіряти контракт, дані та очікувані ефекти.

Помилка №3. Unit-тести пройшли — систему можна випускати.

Unit-тести не перевіряють усі інтеграції, конфігурацію та реальну взаємодію компонентів.

Помилка №4. Автоматизуємо всі тест-кейси без аналізу.

Не кожен тест потрібно автоматизувати. Варто оцінювати ризик, частоту виконання, стабільність і вартість підтримки.

Помилка №5. Тести запускаються тільки перед релізом.

Базові автоматизовані перевірки бажано інтегрувати в CI/CD, щоб проблеми виявлялися якомога раніше.

11

11. Як організувати перевірки в CI/CD

CI/CD — Continuous Integration / Continuous Delivery (безперервна інтеграція та доставка) — дозволяє запускати автоматизовані перевірки на різних етапах розробки.

Один із можливих варіантів:

Це приклад, а не універсальний обов'язковий процес.

Частину тестів можна запускати на кожному Pull Request, інші — після розгортання в TEST, за розкладом або перед релізом.

Важливо, щоб швидкі перевірки давали зворотний зв'язок рано, а критичні наскрізні сценарії перевірялися до виходу змін у продуктивне середовище.

12

12. Якщо зовсім просто

Уяви, що ти перевіряєш автомобіль.

  • Unit Testing — перевірити окремий датчик.
  • Integration Testing — перевірити, що датчик правильно взаємодіє з електронним блоком керування.
  • API Testing — перевірити команди та відповіді електронної системи через її інтерфейс.
  • UI Testing — перевірити кнопки й показники на панелі.
  • E2E Testing — сісти за кермо, завести автомобіль і перевірити, що весь процес працює.
  • Smoke Testing — швидко переконатися, що автомобіль заводиться й основні системи працюють.
  • Regression Testing — після ремонту переконатися, що нічого іншого не зламалося.
  • Performance Testing — перевірити характеристики роботи за різних умов.
  • Security Testing — перевірити захист від несанкціонованого доступу.

Жодна з цих перевірок не замінює всі інші.

Головна думка: якісне тестування — це не максимальна кількість тестів і не автоматизація кожного натискання кнопки. Це правильно підібрані перевірки, які дають команді впевненість у працездатності, надійності та безпеці системи.

13

Підсумок

Після цієї статті варто запам'ятати три речі.

Перше: UI, API, Integration та E2E описують різні точки або масштаби перевірки системи.

Друге: Functional, Smoke, Regression, Security та Performance пояснюють, з якою метою ми тестуємо.

Третє: Manual та Automated описують спосіб виконання тестів, а не їхню якість чи рівень.

Найкраща стратегія — не обирати один «правильний» вид тестування, а комбінувати їх відповідно до архітектури, бізнес-ризиків та вартості перевірок.
