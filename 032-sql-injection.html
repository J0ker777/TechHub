01

1. Вразливість, якій десятки років

Уявіть звичайну корпоративну систему.

Вона має API для пошуку клієнтів. Користувач вводить електронну адресу, система звертається до бази даних і повертає результат.

Нічого незвичайного.

А тепер уявіть, що замість електронної адреси користувач передає спеціально сформований текст, який змінює логіку SQL-запиту.

У результаті система може повернути не одного клієнта, а тисячі записів.

Іноді для цього достатньо одного неправильно обробленого параметра.

Це і є SQL Injection (SQL-ін'єкція) — вразливість, яка дозволяє стороннім даним впливати на структуру SQL-запиту.

SQL — Structured Query Language (мова структурованих запитів) — використовується для роботи з реляційними базами даних.

SQL Injection відома десятиліттями. Проте її продовжують знаходити в сучасних вебзастосунках, корпоративних системах та API.

Причина проста:

↳
Проблема не в SQL і не у віці технології. Проблема виникає тоді, коли застосунок перестає розрізняти дані користувача та SQL-код.

Розберемося, як саме це відбувається.

02

2. Як працює SQL Injection

Розглянемо максимально простий приклад.

Припустимо, у системі є таблиця Users.

Користувач шукає обліковий запис за електронною адресою.

Застосунок формує SQL-запит:

SQL
SELECT Id, Email
FROM Users
WHERE Email = 'user@example.com';

Цілком нормальна операція.

Але розробник вирішив формувати запит простим об'єднанням рядків.

CSHARP
var sql =
    $"SELECT Id, Email FROM Users WHERE Email = '{email}'";

На перший погляд усе працює.

Поки користувач передає звичайну адресу.

А що буде, якщо замість адреси передати:

SQL
' OR 1=1 --

Тоді сформований SQL виглядатиме приблизно так:

SQL
SELECT Id, Email
FROM Users
WHERE Email = '' OR 1=1 --';

Розберемо, що сталося.

  • ' — закриває рядкове значення.
  • OR 1=1 — додає умову, яка завжди істинна.
  • -- — починає SQL-коментар, через що решта рядка не виконується як код.

У цьому прикладі використовується синтаксис коментарів, характерний, зокрема, для Microsoft SQL Server.

Що отримали?

Замість пошуку одного користувача запит потенційно поверне всі записи таблиці.

Звісно, конкретний результат залежить від структури запиту, СУБД та прав доступу.

Але головне вже сталося: користувач змінив логіку SQL.

Як виглядає процес атаки

Зверніть увагу на важливий момент.

База даних не знає, що частину SQL сформував зловмисник.

Для неї це звичайний запит, який надіслав застосунок.

І саме тому SQL Injection настільки небезпечна.

03

3. Наскільки небезпечною може бути SQL Injection

Існує поширена думка, що SQL Injection — це можливість отримати зайві записи з таблиці.

Насправді потенційні наслідки значно серйозніші.

3.1. Витік конфіденційної інформації

Якщо запит вразливий, зловмисник за певних умов може отримати доступ до інформації, яку система не повинна йому показувати.

Наприклад:

  • персональні дані клієнтів;
  • фінансову інформацію;
  • внутрішні ідентифікатори;
  • службові довідники;
  • дані облікових записів.

Особливо небезпечно, коли один обліковий запис бази даних використовується багатьма функціями застосунку.

3.2. Обхід авторизації

У деяких реалізаціях SQL Injection дозволяє обійти перевірку облікових даних або обмеження доступу.

Але це не означає, що будь-яка ін'єкція автоматично дозволяє увійти адміністратором.

Усе залежить від архітектури механізму автентифікації та конкретної вразливості.

У сучасних системах паролі повинні перевірятися через безпечні механізми роботи з їхніми хешами, а не порівнюватися як звичайний текст у SQL.

3.3. Зміна або видалення інформації

Якщо обліковий запис застосунку має відповідні права, наслідками можуть стати:

  • зміна записів;
  • пошкодження довідників;
  • видалення даних;
  • порушення цілісності інформації.

3.4. Порушення доступності

Небезпечний запит може створити надмірне навантаження на базу даних.

У гіршому випадку це призведе до деградації продуктивності або недоступності сервісу.

Важливий висновок:

Масштаб наслідків SQL Injection значною мірою залежить від того, які права має обліковий запис, під яким застосунок підключається до бази даних.

Саме тому принцип мінімальних привілеїв настільки важливий.

04

4. Які бувають SQL Injection

Не кожна SQL-ін'єкція виглядає як простий приклад із OR 1=1.

Іноді застосунок узагалі не повертає результат SQL-запиту користувачеві.

Але це ще не означає, що система захищена.

4.1. In-band SQL Injection

In-band (атака через той самий канал) — результат ін'єкції повертається через той самий канал, яким було надіслано запит.

Наприклад:

Користувач звертається до API, а у відповіді отримує дані, які не повинен бачити.

До цієї категорії належать, зокрема, атаки, що використовують повідомлення про помилки або операцію UNION для отримання інформації.

Це один із найзрозуміліших різновидів SQL Injection.

4.2. Blind SQL Injection

Blind SQL Injection (сліпа SQL-ін'єкція) — атака, за якої результат SQL-запиту безпосередньо не відображається користувачу.

Наприклад, API повертає лише:

JSON
{
  "found": true
}

або:

JSON
{
  "found": false
}

На перший погляд, нічого небезпечного.

Але якщо зловмисник може змінювати SQL-умови та спостерігати за відповідями, він іноді здатний поступово отримувати інформацію про дані.

Тобто відсутність SQL-помилок у відповіді ще не означає відсутності вразливості.

4.3. Time-based SQL Injection

Time-based (атака за часом відповіді) — різновид Blind SQL Injection.

У цьому випадку інформацію намагаються отримати не через текст відповіді, а через затримки її виконання.

Наприклад, певна SQL-умова може впливати на час обробки запиту.

Аналізуючи повторювані відмінності, зловмисник може робити висновки про поведінку бази даних.

Особливо складно виявляти такі атаки, коли застосунок повертає однакові відповіді незалежно від результату SQL.

4.4. Second-order SQL Injection

Second-order (SQL-ін'єкція другого порядку) — один із найцікавіших варіантів.

Уявімо ситуацію:

  1. Користувач передає спеціально сформований текст.
  2. Застосунок безпечно зберігає його в базі.
  3. Через деякий час інший компонент читає цей текст.
  4. Компонент використовує його для небезпечного формування SQL.

Вразливість виникає не під час збереження, а під час подальшої обробки.

Це особливо актуально для систем із багатьма інтеграціями.

Дані, отримані з власної бази, не стають автоматично безпечними.

До речі, існують і Out-of-band SQL Injection — атаки, де для отримання інформації використовується інший канал взаємодії. Вони залежать від можливостей СУБД і мережевої конфігурації.

05

5. SQL Injection — це не лише форма авторизації

Коли говорять про SQL Injection, найчастіше показують поле логіна.

Проте в реальних корпоративних системах потенційних точок значно більше.

Наприклад:

  • параметри пошуку в API;
  • фільтри списків;
  • динамічне сортування;
  • формування звітів;
  • експорт інформації;
  • адміністративні інструменти;
  • імпорт даних;
  • інтеграції з іншими системами.

Розглянемо звичайний API:

HTTP
GET /api/customers?search=ivan

Застосунок отримує параметр search та формує SQL.

Якщо значення безпосередньо додається до тексту запиту, існує ризик SQL Injection.

І неважливо, звідки надійшло значення:

  • через GET;
  • через POST;
  • із JSON;
  • через чергу повідомлень;
  • з іншої бази даних;
  • із зовнішньої інтеграції.

Головне — як саме застосунок використовує ці дані при формуванні SQL.

06

6. Чому ORM не гарантує захисту

ORM — Object-Relational Mapping (об'єктно-реляційне відображення) — технологія, яка дозволяє працювати з даними через об'єкти та класи замість ручного написання SQL для кожної операції.

Наприклад:

  • Entity Framework Core;
  • Laravel Eloquent;
  • Hibernate.

Вони значно зменшують ризик SQL Injection за правильного використання.

Але це не означає, що застосунок автоматично захищений.

Проблеми можуть виникнути, коли розробник переходить до виконання SQL, сформованого вручну.

6.1. Приклад із Dapper

Dapper — легковаговий інструмент для відображення результатів SQL-запитів у .NET-об'єкти.

Подивимося на небезпечний приклад:

CSHARP
var sql = $"""
    SELECT Id, Email
    FROM Users
    WHERE Email = '{email}'
    """;

var users = connection.Query<User>(sql);

Тут використовується інтерполяція рядків.

Якщо email надходить від користувача, він може вплинути на структуру SQL.

Правильна реалізація:

CSHARP
var sql = """
    SELECT Id, Email
    FROM Users
    WHERE Email = @Email
    """;

var users = connection.Query<User>(
    sql,
    new { Email = email }
);

Тепер значення передається як окремий параметр.

Навіть якщо користувач введе спеціальні символи, вони оброблятимуться як дані, а не як SQL-команди.

Це називається Parameterized Query (параметризований запит).

І це основний механізм захисту від SQL Injection.

6.2. Entity Framework Core

Entity Framework Core зазвичай автоматично параметризує значення в LINQ-запитах.

Наприклад:

CSHARP
var user = await context.Users
    .Where(x => x.Email == email)
    .FirstOrDefaultAsync();

Це безпечний спосіб передавання значення email у SQL-запит.

Але розробник може використовувати SQL безпосередньо.

Наприклад, небезпечний варіант:

CSHARP
var sql =
    $"SELECT * FROM Users WHERE Email = '{email}'";

var users = await context.Users
    .FromSqlRaw(sql)
    .ToListAsync();

Проблема знову полягає в ручному формуванні SQL.

Натомість можна використати:

CSHARP
var users = await context.Users
    .FromSql($"SELECT * FROM Users WHERE Email = {email}")
    .ToListAsync();

У цьому випадку FromSql отримує інтерпольований рядок як FormattableString і параметризує значення.

Метод FromSql доступний починаючи з EF Core 7. Для попередніх версій використовується FromSqlInterpolated.

Важливий нюанс: якщо спочатку сформувати SQL як звичайний рядок із підставленими значеннями, а потім передати його у FromSqlRaw, автоматичного захисту не буде.

6.3. Laravel

У Laravel Query Builder та Eloquent значення умов зазвичай параметризуються.

Безпечний приклад:

PHP
$user = User::query()
    ->where('email', $email)
    ->first();

Але небезпечне формування SQL усе ще можливе:

PHP
$sql = "SELECT * FROM users WHERE email = '$email'";

$users = DB::select($sql);

Правильніше передавати значення окремо:

PHP
$users = DB::select(
    'SELECT * FROM users WHERE email = ?',
    [$email]
);

Отже, навіть сучасний фреймворк не захистить від усіх помилок розробника.

07

7. Неочевидна проблема: динамічне сортування

Уявімо API, яке підтримує сортування:

HTTP
GET /api/customers?sortBy=name&sortDirection=asc

Розробник хоче дозволити користувачеві вибирати поле та напрямок сортування.

І формує SQL:

CSHARP
var sql = $"""
    SELECT Id, Name, CreatedAt
    FROM Customers
    ORDER BY {sortBy} {sortDirection}
    """;

Це небезпечно.

Чому просто не використати SQL-параметри?

Тому що параметри SQL призначені для значень, а не для заміни назв колонок, таблиць чи ключових слів.

Наприклад, передати назву колонки через @SortBy як звичайне значення не вийде.

Як правильно?

Використовувати Allowlist (список дозволених значень).

CSHARP
var column = sortBy switch
{
    "name" => "[Name]",
    "created" => "[CreatedAt]",
    _ => "[Name]"
};

var direction = descending ? "DESC" : "ASC";

var sql = $"""
    SELECT Id, Name, CreatedAt
    FROM Customers
    ORDER BY {column} {direction}
    """;

Тепер застосунок не вставляє довільний текст користувача.

Він обирає SQL-фрагменти із заздалегідь визначеного набору.

Це важливий приклад, оскільки навіть за активного використання параметризованих запитів розробники можуть припускатися помилок у динамічних частинах SQL.

08

8. Як правильно захищатися від SQL Injection

Ефективний захист складається з кількох рівнів.

Рівень 1. Параметризовані запити

Це головний механізм захисту.

Prepared Statements (підготовлені запити) дозволяють відокремити структуру SQL від значень параметрів.

Тоді користувацьке значення не може змінити структуру запиту через звичайний механізм прив'язування параметрів.

Саме такий підхід рекомендує OWASP — Open Worldwide Application Security Project (міжнародна спільнота з безпеки застосунків).

Рівень 2. Перевірка вхідних даних

Input Validation (перевірка вхідних даних) дозволяє контролювати:

  • тип значення;
  • допустимий формат;
  • максимальну довжину;
  • допустимі діапазони;
  • перелік дозволених операцій.

Наприклад, якщо API очікує числовий ідентифікатор, немає сенсу приймати довільний текст.

Але важливо розуміти:

Валідація не замінює параметризовані запити.

Іноді цілком легітимні дані містять спеціальні символи.

Наприклад, прізвище:

O'Reilly

Такі значення мають коректно оброблятися, а не блокуватися лише через наявність апострофа.

Рівень 3. Мінімальні права в базі даних

Least Privilege (принцип мінімальних привілеїв) означає, що кожен компонент повинен мати лише ті права, які необхідні для його роботи.

Наприклад:

Сервіс, який лише читає довідник, не повинен мати можливості змінювати або видаляти записи.

А обліковий запис застосунку не повинен отримувати адміністративні права без обґрунтованої необхідності.

Це не усуває SQL Injection, але здатне суттєво обмежити наслідки атаки.

Рівень 4. WAF

WAF — Web Application Firewall (міжмережевий екран вебзастосунків).

Його завдання — аналізувати HTTP-трафік та виявляти підозрілі запити.

Наприклад, WAF може виявляти типові ознаки SQL Injection і блокувати відповідні запити.

Серед таких рішень — Imperva, Cloudflare WAF та інші.

Але є важливий нюанс.

WAF аналізує зовнішні запити, а не гарантує правильність SQL, який сформує застосунок.

Крім того, небезпечні дані можуть потрапити до системи через внутрішню інтеграцію або вже перебувати в базі даних.

Тому WAF — додатковий рівень захисту, а не заміна правильного програмування.

Як виглядає багаторівневий захист

Ключовий принцип: основний захист від SQL Injection повинен забезпечуватися в коді застосунку.

Додаткові рівні зменшують ризики, але не виправляють небезпечне формування SQL.

09

9. А як щодо Stored Procedures?

Stored Procedure (збережена процедура) — SQL-логіка, яка зберігається та виконується на стороні бази даних.

Іноді можна почути:

↳
У нас усі операції виконуються через процедури, тому SQL Injection неможлива.

Це не зовсім так.

Якщо процедура використовує параметризовані операції та правильно обробляє дані, вона може бути безпечною.

Але якщо всередині процедури формується динамічний SQL через об'єднання рядків, ризик повертається.

Тобто перенесення SQL-логіки із застосунку в базу даних саме по собі не гарантує безпеки.

Важливий не тільки спосіб виклику процедури, а й те, як вона працює всередині.

10

10. Як виявляти SQL Injection під час розробки та тестування

Захист бажано перевіряти на кількох етапах SDLC — Software Development Life Cycle (життєвого циклу розробки програмного забезпечення).

10.1. Code Review

Code Review (перевірка коду) — один із найефективніших способів виявити потенційно небезпечні місця.

Особливу увагу варто звертати на:

  • формування SQL через інтерполяцію рядків;
  • конкатенацію SQL-фрагментів;
  • використання FromSqlRaw;
  • динамічні ORDER BY;
  • побудову SQL у збережених процедурах;
  • використання значень із зовнішніх інтеграцій.

Не кожне використання динамічного SQL є вразливістю.

Але кожне таке місце потребує розуміння походження даних.

10.2. SAST

SAST — Static Application Security Testing (статичний аналіз безпеки коду).

Такі інструменти аналізують вихідний код або інші програмні артефакти без виконання застосунку.

Наприклад, Fortify може виявляти потенційно небезпечні потоки даних, коли значення користувача потрапляє до SQL-запиту.

Але результати потребують аналізу.

Інструмент може не помітити складну вразливість або повідомити про проблему, якої фактично немає.

10.3. DAST

DAST — Dynamic Application Security Testing (динамічне тестування безпеки).

На відміну від SAST, цей підхід передбачає перевірку запущеного застосунку.

Інструменти надсилають тестові запити та аналізують поведінку системи.

Зокрема, вони можуть перевіряти:

  • чи змінюється результат залежно від спеціальних значень;
  • чи повертає сервер SQL-помилки;
  • чи проявляються нетипові відмінності у відповідях;
  • чи доступні дані, які не повинні повертатися.

Такі перевірки потрібно виконувати лише в дозволених середовищах і з контрольованими тестовими даними.

10.4. Що може зробити QA

QA не обов'язково повинен бути спеціалістом із проникнення в системи, щоб помічати потенційні проблеми.

Під час тестування API варто перевіряти:

1. Спеціальні символи

Що відбудеться, якщо передати значення з апострофом?

Чи працює система коректно?

2. Некоректні типи

Що буде, якщо замість числа передати рядок?

3. Довгі значення

Чи контролюється допустима довжина параметрів?

4. Помилки бази даних

Чи не повертає API користувачеві текст SQL, назви таблиць або інші внутрішні деталі?

5. Динамічне сортування

Чи можна передати довільну назву колонки?

6. Авторизація

Чи перевіряються права доступу незалежно від параметрів SQL-запиту?

Важливо: відсутність SQL-помилок або коректна обробка спеціальних символів ще не доводить, що SQL Injection неможлива.

Для впевненості потрібна також перевірка реалізації запитів.

11

11. Типові помилки, які створюють ризик

Помилка №1. «Ми перевіряємо всі значення регулярними виразами»

Регулярні вирази можуть бути корисними для перевірки формату.

Але це не гарантує безпечного формування SQL.

Правильний механізм — параметризація.

Помилка №2. «Ми екрануємо апострофи»

Екранування залежить від конкретної СУБД, контексту запиту та правил обробки рядків.

Воно значно менш надійне, ніж передавання значень окремими параметрами.

Помилка №3. «У нас Entity Framework»

ORM зменшує ризики, але розробник усе одно може виконати небезпечний SQL.

Помилка №4. «У нас стоїть WAF»

WAF може заблокувати частину атак.

Але помилка в коді залишиться.

Помилка №5. «Ці дані вже є в нашій базі»

Навіть дані з внутрішньої БД можуть бути небезпечними, якщо пізніше використовуються для побудови SQL.

Помилка №6. «У застосунку немає SQL Injection, бо ми не працюємо з SQL напряму»

Варто перевірити, чи немає ручних SQL-запитів у бібліотеках доступу до даних, звітах, фонових процесах, інтеграціях та збережених процедурах.

12

12. Практичний чекліст для команди

Перед релізом функціональності, яка працює з базою даних, корисно перевірити кілька питань.

Для Developer:

  • Чи всі значення передаються через SQL-параметри?
  • Чи є місця, де SQL формується динамічно?
  • Чи використовуються списки дозволених значень для назв колонок і сортування?
  • Чи безпечно працюють збережені процедури?

Для QA:

  • Чи перевірена обробка некоректних параметрів?
  • Чи не повертаються внутрішні SQL-помилки?
  • Чи протестовані пошук, фільтрація та сортування?
  • Чи передбачені перевірки безпеки API?

Для Tech Lead та Architect:

  • Чи є стандарти безпечної роботи з SQL?
  • Чи обмежені права облікових записів БД?
  • Чи охоплені перевірками фонові процеси та інтеграції?
  • Чи використовується SAST у процесі розробки?

Для DevOps та Security Engineer:

  • Чи працюють автоматизовані перевірки безпеки?
  • Чи налаштований моніторинг підозрілих подій?
  • Чи контролюються привілеї облікових записів?
  • Чи є додатковий захист зовнішніх API?

Для PM/PO та BA:

  • Чи враховані вимоги безпеки під час постановки задач?
  • Чи передбачений час на перевірки?
  • Чи оцінено ризик витоку або модифікації даних?
  • Чи погоджені критерії приймання функціональності?

Безпека SQL — це не тільки питання розробника.

Це частина якості всієї системи.

13

13. Якщо зовсім просто

Уявіть ресторан.

Ви робите замовлення:

«Принесіть мені каву».

Офіціант повинен сприйняти це як замовлення.

А тепер уявіть, що ви написали на папірці:

«Принесіть каву, а також відчиніть усі двері ресторану».

І офіціант почав виконувати все, що написано, наче це офіційні інструкції керівництва.

Ось приблизно так працює SQL Injection.

Застосунок повинен передавати базі даних значення, яке ввів користувач.

Але через неправильну реалізацію частина цього значення може бути сприйнята як команда.

Параметризовані запити вирішують головну проблему: вони відокремлюють інструкції від даних.

Тому користувач може передати практично будь-який текст, але він не повинен змінювати структуру SQL-запиту.

14

Висновок

SQL Injection — одна з найвідоміших вразливостей програмного забезпечення.

І водночас одна з тих, від яких давно існують ефективні способи захисту.

Сучасні фреймворки, ORM, засоби статичного аналізу та WAF значно спрощують побудову захищених застосунків.

Але жодна з цих технологій не усуває необхідності правильно працювати з даними.

П'ять головних висновків:

  1. SQL Injection виникає, коли недовірені дані можуть змінити структуру SQL-запиту.
  2. Параметризовані запити — основний механізм захисту.
  3. ORM зменшує ризики, але не гарантує безпеку неправильного використання SQL.
  4. WAF, валідація та мінімальні права створюють додаткові рівні захисту.
  5. Перевіряти необхідно не тільки зовнішні API, а й інтеграції, фонові процеси та повторне використання даних.

І найголовніше:

↳
Найкращий спосіб захиститися від SQL Injection — не намагатися розпізнати небезпечний текст, а побудувати систему так, щоб користувацький текст ніколи не міг стати SQL-командою.
