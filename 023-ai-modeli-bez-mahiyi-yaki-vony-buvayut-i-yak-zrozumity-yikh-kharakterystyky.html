01

1. ChatGPT — це не AI-модель

Почнемо з поширеної плутанини.

ChatGPT — це продукт.

Усередині такого продукту можуть бути:

┌────────────────────────────┐
│          ChatGPT           │
│                            │
│  Chat                      │
│  Files                     │
│  Search                    │
│  Memory                    │
│  Tools                     │
│  Agents                    │
│                            │
│            ↓               │
│        AI MODEL            │
└────────────────────────────┘

AI-модель — лише одна частина системи.

Спрощено:

MODEL
  ↓
API / Runtime
  ↓
Application
  ↓
Tools / RAG / Agents
  ↓
User

Одна й та сама модель потенційно може використовуватися:

  • у чаті;
  • через API;
  • у корпоративній системі;
  • у IDE;
  • локально на комп'ютері;
  • в AI-агенті;
  • у системі аналізу документів.

Тому порівнювати, наприклад, ChatGPT і Llama без уточнення контексту не зовсім коректно: в одному випадку ми говоримо про готовий продукт, в іншому — про сімейство моделей.

02

2. Не кожна AI-модель — це LLM

Сьогодні терміни AI та LLM часто використовують майже як синоніми.

Але LLM — лише один із класів AI-моделей.

Спрощено екосистему можна представити так:

AI MODELS
│
├── Language Models
│
├── Reasoning Models
│
├── Coding Models
│
├── Vision / Multimodal Models
│
├── Embedding Models
│
├── Speech-to-Text
│
├── Text-to-Speech
│
└── Image / Video Generation

Кожен тип вирішує свою задачу.

03

3. Що таке LLM

LLM означає:

Large Language Model

або:

велика мовна модель.

Основна задача такої моделі — працювати з послідовністю токенів і прогнозувати їх продовження.

Дуже спрощено:

Вхідний текст
      ↓
Tokenizer
      ↓
Tokens
      ↓
LLM
      ↓
Наступний token
      ↓
Наступний token
      ↓
...
      ↓
Відповідь

Саме на цьому механізмі базується величезна кількість можливостей:

  • відповіді на питання;
  • генерація тексту;
  • переклад;
  • написання коду;
  • аналіз документів;
  • узагальнення;
  • класифікація;
  • робота з інструкціями.

Тобто модель не дістає готову відповідь із величезної бази відповідей.

Вона генерує послідовність токенів.

04

4. Що таке token

LLM не бачить текст так, як його бачить людина.

Перед передачею в модель текст проходить через tokenizer.

Наприклад:

"Створи REST API для користувачів"

перетворюється на послідовність токенів:

[token]
[token]
[token]
[token]
...

Токен не обов'язково дорівнює одному слову.

Це може бути:

  • слово;
  • частина слова;
  • символ;
  • послідовність символів.

Спрощена схема:

TEXT
 ↓
TOKENIZER
 ↓
TOKENS
 ↓
MODEL
 ↓
TOKENS
 ↓
TEXT

Саме тому в AI API часто зустрічаємо поняття:

input tokens
output tokens

Токени використовуються для визначення розміру контексту, обмеження відповіді та часто — для розрахунку вартості API.

05

5. General-purpose моделі

Це універсальні моделі.

Вони можуть виконувати широкий спектр задач:

текст
код
аналіз
переклад
пояснення
структурування
робота з документами

До відомих сімейств належать, наприклад:

GPT
Claude
Gemini
Qwen
Llama
Mistral
DeepSeek
Gemma

Але навіть усередині одного сімейства можуть бути різні моделі:

велика
мала
швидка
reasoning
coding
vision

Тому назва сімейства ще не говорить, яка конкретно модель краще підходить під задачу.

06

6. Coding models

Окремий важливий напрям — моделі, оптимізовані для програмування.

Типові задачі:

Code Generation
Code Completion
Bug Fixing
Code Review
Refactoring
Test Generation
Repository Analysis

Наприклад, ми можемо дати моделі:

JAVASCRIPT
function getUser(id) {
    ...
}

і попросити:

Знайди потенційні проблеми безпеки.

Або:

Реалізуй цей endpoint.

Але сьогодні межа між coding і general-purpose моделями стає все менш чіткою.

Сильна універсальна модель також може дуже добре працювати з кодом.

Тому напис Coder у назві — корисна характеристика спеціалізації, але не гарантія того, що ця модель автоматично буде кращою за всі універсальні моделі.

07

7. Reasoning models

Для частини задач просто швидко продовжити текст недостатньо.

Наприклад:

складна математика
архітектура системи
debugging
планування
аналіз великої кількості умов
складні логічні задачі

Для цього використовуються reasoning-моделі або reasoning-режими.

Умовно звичайну генерацію можна представити так:

Prompt
  ↓
Model
  ↓
Answer

А reasoning-підхід:

Prompt
  ↓
Model
  ↓
Additional reasoning / compute
  ↓
Answer

Ключова ідея:

↳
Модель може витратити більше обчислень на задачу перед формуванням фінальної відповіді.

Це називають, зокрема:

inference-time compute

або:

test-time compute

Більше обчислень може допомогти на складних задачах, але зазвичай означає більшу затримку та/або вартість.

І важливий нюанс: внутрішній процес міркування моделі не обов'язково показується користувачу.

08

8. Vision та Multimodal

Раніше мовні моделі переважно працювали з текстом.

Сучасні моделі можуть працювати з кількома типами інформації.

Наприклад:

TEXT
IMAGE
AUDIO
VIDEO
DOCUMENT

Такі моделі називають:

Multimodal

або можна зустріти позначення:

Vision
VL
Vision-Language

Наприклад:

Фото інтерфейсу
       ↓
Vision Model
       ↓
"На формі відсутня кнопка..."

Або:

Architecture Diagram
        ↓
Multimodal Model
        ↓
Architecture Analysis

Це особливо корисно для:

  • аналізу скриншотів;
  • документів;
  • схем;
  • фотографій;
  • UI;
  • графіків.
09

9. Що означає 7B, 14B, 32B, 70B

Тепер переходимо до однієї з найпомітніших характеристик.

Біля назв моделей часто можна побачити:

7B
14B
32B
70B

B означає:

Billion

тобто мільярд.

Отже:

7B  ≈ 7 мільярдів параметрів
14B ≈ 14 мільярдів параметрів
32B ≈ 32 мільярди параметрів
70B ≈ 70 мільярдів параметрів
10

10. Що таке параметри

Модель можна дуже спрощено представити як величезну математичну функцію.

Усередині неї знаходиться величезна кількість числових коефіцієнтів:

0.1827
-0.7421
1.3928
0.0041
...

Це і є параметри моделі.

Під час навчання:

Training Data
      ↓
Training
      ↓
Parameters change
      ↓
Trained Model

Модель поступово змінює ці значення.

У результаті мільярди параметрів кодують закономірності, які модель навчилася використовувати.

11

11. Більше параметрів = краща модель?

Одна з головних помилок:

70B > 32B > 14B > 7B

і звідси висновок:

70B завжди краща.

Це неправильно.

На якість моделі впливають:

Architecture
+
Training Data
+
Data Quality
+
Training Process
+
Post-training
+
Fine-tuning
+
Reasoning techniques
+
Context handling
+
Tool use

Тому сучасна добре навчена модель меншого розміру може перевершувати значно більшу старішу модель в конкретних задачах.

Кількість параметрів потрібно сприймати як технічну характеристику, а не як показник IQ.

12

12. Dense models

Тут з'являється ще один важливий нюанс.

Моделі можуть мати різну архітектуру.

Один із варіантів:

Dense

Дуже спрощено, у Dense-моделі для обробки кожного токена задіюється вся мережа.

Наприклад:

32B Dense

Token
  │
  ▼
┌───────────────────┐
│███████████████████│
│        32B        │
└───────────────────┘

Тому якщо бачимо:

32B Dense

можна приблизно говорити про модель із 32 млрд параметрів, що беруть участь в обчисленні.

13

13. MoE — Mixture of Experts

Інший підхід:

MoE

або:

Mixture of Experts

Тут модель складається з набору умовних «експертів».

Спеціальний механізм — router — визначає, які експерти потрібно використати для конкретного токена.

Спрощено:

                   ┌─ Expert 1
                   │
                   ├─ Expert 2 ← active
                   │
Token → Router ────┼─ Expert 3
                   │
                   ├─ Expert 4
                   │
                   ├─ Expert 5 ← active
                   │
                   └─ Expert 6

Тобто не всі параметри моделі обов'язково активуються одночасно.

Саме тому біля MoE можна побачити щось на кшталт:

Total Parameters: 100B
Active Parameters: 10B

Це означає:

100B

параметрів є в моделі загалом,

але приблизно:

10B

використовуються для конкретного проходу відповідно до архітектури моделі.

14

14. Навіщо потрібен MoE

Ідея MoE полягає в тому, щоб отримати переваги дуже великої моделі, не використовуючи всі її параметри для кожного токена.

Умовно:

Dense:

Token
 ↓
████████████████
all network

MoE:

Token
 ↓
Router
 ↓
██   ██
selected experts

Це може суттєво зменшити обчислення порівняно з Dense-моделлю такого самого загального розміру.

Але є важливий нюанс.

↳
Active parameters і розмір моделі в пам'яті — не одне й те саме.

Навіть якщо модель має відносно мало active parameters, ваги інших експертів усе одно потрібно десь зберігати.

Це стане особливо важливим, коли в другій статті говоритимемо про VRAM.

15

15. Base та Instruct

У назвах open-weight моделей можна побачити:

Model-Base

та:

Model-Instruct

Різниця принципова.

Base

Base-модель пройшла основне навчання.

Її базова задача — добре прогнозувати продовження послідовності.

Наприклад:

Київ — столиця...

модель прогнозує:

України

Але Base-модель не обов'язково добре поводитиметься як чат-асистент.

Instruct

Instruct-модель додатково налаштована виконувати інструкції.

Наприклад:

Поясни OAuth 2.0.

Знайди помилку в коді.

Напиши SQL-запит.

Поверни результат у JSON.

Тому для:

chat
assistant
coding assistant
agent

часто потрібна саме Instruct/Chat-модель.

16

16. Context Window

Ще одна характеристика:

8K
32K
128K
256K
1M

Це розмір контекстного вікна.

Контекст — інформація, доступна моделі під час поточного inference.

Спрощено:

┌──────────────────────────────────┐
│ SYSTEM PROMPT                    │
│                                  │
│ CHAT HISTORY                     │
│                                  │
│ DOCUMENTS                        │
│                                  │
│ CODE                             │
│                                  │
│ RAG RESULTS                      │
│                                  │
│ USER QUESTION                    │
│                                  │
│ GENERATED RESPONSE               │
└──────────────────────────────────┘

             CONTEXT

Усе це займає токени.

17

17. Context — це не довгострокова пам'ять

Наприклад:

Context = 128K

не означає:

↳
AI назавжди пам'ятає 128 000 токенів нашого спілкування.

Це означає, що модель може обробити певний обсяг інформації в рамках конкретного контексту.

Довгострокова пам'ять у готовому AI-продукті може бути реалізована зовсім іншими механізмами.

Наприклад:

Database
Vector Search
User Profile
Conversation Summary
RAG

А потрібна інформація вже потім додається в контекст моделі.

18

18. Чи означає більший context кращу модель?

Також ні.

Припустимо:

Model A → 32K
Model B → 256K

З цього не можна зробити висновок:

Model B > Model A

Великий контекст корисний для:

  • великих документів;
  • codebase;
  • логів;
  • довгих чатів;
  • RAG;
  • контрактів;
  • великих звітів.

Але важливе інше питання:

↳
Наскільки добре модель знаходить і використовує потрібну інформацію всередині цього контексту?

Максимальний context window та якість long-context reasoning — різні характеристики.

19

19. Temperature

При генерації відповіді модель оцінює ймовірності наступних токенів.

Умовно:

"Столиця Франції —"

Paris      96%
London      1%
Berlin    0.5%
Rome      0.2%
...

Параметр:

temperature

впливає на розподіл і вибір наступних токенів.

Дуже спрощено:

низька temperature
        ↓
більш передбачувана генерація

вища temperature
        ↓
більше варіативності

Для задач на кшталт:

JSON
classification
data extraction

часто потрібна стабільніша поведінка.

Для:

brainstorming
creative writing
ideas

може бути корисна більша варіативність.

Конкретні рекомендовані значення залежать від моделі та API.

20

20. Top-P

Інший параметр генерації:

top_p

Спрощено уявімо:

Token A    50%
Token B    25%
Token C    10%
Token D     5%
Token E     3%
...

Top-P дозволяє обмежити набір кандидатів найбільш імовірними токенами до певної сумарної ймовірності.

Для базового розуміння достатньо запам'ятати:

↳
Temperature і Top-P не додають моделі нових знань. Вони впливають на те, як модель вибирає наступні токени.
21

21. Fine-tuning

Уявімо, що є універсальна модель:

GENERAL MODEL

Ми хочемо спеціалізувати її.

Наприклад:

General Model
      ↓
Special Dataset
      ↓
Fine-tuning
      ↓
Specialized Model

Fine-tuning змінює параметри моделі.

Його можна використовувати, наприклад, для:

  • спеціального стилю відповідей;
  • певного формату;
  • доменної поведінки;
  • спеціалізованих задач.

Але тут виникає дуже важлива плутанина.

22

22. Fine-tuning ≠ RAG

Припустимо, компанія має:

10 000 внутрішніх документів

і хоче, щоб AI відповідав на питання за ними.

Перша думка:

↳
Давайте навчимо модель на наших документах.

Але часто це не найкращий шлях.

Fine-tuning

DATA
 ↓
TRAINING
 ↓
MODEL WEIGHTS CHANGE

RAG

User Question
      ↓
Search
      ↓
Knowledge Base
      ↓
Relevant Information
      ↓
LLM Context
      ↓
Answer

При RAG ваги LLM не потрібно змінювати.

Ми знаходимо потрібну інформацію та передаємо її моделі в контекст.

Це особливо важливо для інформації, яка:

часто змінюється
має права доступу
повинна мати джерело
міститься в документах
23

23. Embedding Models

Але як знайти потрібний документ за змістом?

Тут з'являється ще один клас моделей:

Embedding Model

Її задача — не генерувати текст.

Вона перетворює інформацію на числовий вектор.

Наприклад:

"RabbitMQ cluster"

        ↓

Embedding Model

        ↓

[0.17, -0.42, 0.81, 0.13, ...]

Інший текст:

"налаштування кластера RabbitMQ"

отримає інший вектор, але він може бути математично близьким до першого.

Це дозволяє виконувати:

Semantic Search
Similarity Search
RAG
Recommendations

Тому AI-система може використовувати одразу кілька моделей:

Embedding Model
       +
Reranker
       +
LLM

24. Speech models

Ще один окремий клас — моделі для роботи з голосом.

Наприклад:

Speech-to-Text

перетворює:

AUDIO
 ↓
TEXT

Відомий приклад такого підходу — Whisper.

А Text-to-Speech робить зворотне:

TEXT
 ↓
AUDIO

Тому голосовий AI-асистент може складатися з кількох компонентів:

CALL
 ↓
Speech-to-Text
 ↓
TEXT
 ↓
LLM
 ↓
TEXT
 ↓
Text-to-Speech
 ↓
VOICE

Отже, «голосовий AI» — це не обов'язково одна модель.

Це може бути цілий pipeline.

25

25. Tool Calling

LLM має фундаментальне обмеження.

Вона не знає актуальний стан ваших систем, якщо ці дані їй не передати.

Наприклад, користувач питає:

Який статус замовлення 12345?

Модель не повинна вигадувати відповідь.

Замість цього вона може викликати інструмент:

get_order_status(
    order_id = 12345
)

Схема:

User
 ↓
LLM
 ↓
Tool Call
 ↓
API
 ↓
Business System
 ↓
Result
 ↓
LLM
 ↓
Answer

Це називають:

Tool Calling

або залежно від платформи:

Function Calling

Це одна з основ сучасних AI-агентів.

26

26. LLM та AI Agent — не одне й те саме

Звичайна LLM:

Prompt
 ↓
Model
 ↓
Answer

AI Agent може виглядати приблизно так:

             ┌── Search
             │
             ├── Database
User → LLM ──┼── API
             │
             ├── Files
             │
             └── Other Tools
                   │
                   ▼
                 Result
                   │
                   ▼
                  LLM
                   │
                   ▼
                 Answer

Тобто:

↳
LLM — це модель. Agent — система, яка використовує модель для прийняття рішень і роботи з інструментами.

Тому якість AI-агента залежить не тільки від самої LLM.

27

27. Structured Output

Для інтеграцій дуже важливо, щоб модель могла повертати не просто текст:

Користувача знайдено. Його ID — 123.

а структурований результат:

JSON
{
  "userId": 123,
  "status": "active"
}

Тому при виборі моделі для корпоративної системи можуть бути важливими:

Instruction Following
Structured Output
JSON
Tool Calling
Function Calling

Модель може чудово писати статті, але погано виконувати строгий формат.

Для AI-агента це може бути критично.

28

28. Open-weight моделі

Частину моделей можна завантажити та запускати на власній інфраструктурі.

Їх часто називають:

open-source models

але точніше в багатьох випадках говорити:

open-weight

Тобто доступні ваги моделі.

Це не обов'язково означає, що відкриті:

training dataset
training code
training process
license without restrictions

Тому для корпоративного використання потрібно перевіряти ліцензію конкретної моделі.

29. Cloud та Local — це вже спосіб використання

Одну модель можна отримувати як сервіс:

Application
     ↓
Internet
     ↓
AI Provider
     ↓
Model

або запускати на власній інфраструктурі:

Application
     ↓
Local AI Server
     ↓
GPU
     ↓
Model

Cloud дає:

простий старт
масштабування
доступ до великих моделей
відсутність власного GPU

Local дає:

контроль
offline
privacy
контроль інфраструктури

Але Local додає нові питання:

Який GPU?

Скільки VRAM?

Що таке Q4?

Що таке GGUF?

Чому 32B модель не влазить у відеокарту?

Чому вона запустилася, але працює повільно?

Це вже тема наступної статті.

30

30. Benchmark

Як зрозуміти, наскільки модель хороша?

Для цього існують benchmark — стандартизовані набори тестів.

Вони можуть перевіряти:

Coding
Math
Reasoning
Knowledge
Long Context
Tool Use
Agentic Tasks

У результаті отримуємо умовно:

Model A → 78
Model B → 81
Model C → 74

Здається, все просто:

81 > 78 > 74

Отже, беремо Model B?

Не обов'язково.

31

31. Чому benchmark недостатньо

Припустимо, benchmark перевіряє складні математичні задачі.

А ваша задача:

аналізувати API logs

або:

генерувати SQL

або:

працювати з корпоративними документами українською мовою

Результат математичного benchmark може мати обмежену практичну цінність.

Тому benchmark краще використовувати для:

100 моделей
      ↓
benchmark
      ↓
5 кандидатів
      ↓
власні тести
      ↓
1–2 моделі

39

Висновок

Універсальної «найкращої AI-моделі» не існує.

Модель для coding assistant і модель для голосового оператора можуть мати зовсім різні вимоги.

Модель для корпоративного RAG і модель для генерації зображень взагалі вирішують різні задачі.

А число:

70B

саме по собі ще дуже мало говорить про реальну користь моделі.

Правильний підхід виглядає так:

TASK
 ↓
REQUIREMENTS
 ↓
MODEL TYPE
 ↓
MODEL CANDIDATES
 ↓
BENCHMARKS
 ↓
YOUR TESTS
 ↓
MODEL

Тому замість питання:

↳
«Яка AI-модель найкраща?»

краще поставити:

↳
«Яка AI-модель найкраще підходить для цієї конкретної задачі?»

Але після вибору моделі виникає наступне питання.

Припустимо, ми знайшли:

32B Instruct
128K Context

і хочемо запустити її локально.

Чи вистачить відеокарти на 16 GB?

А на 24 GB?

Чому модель на 32 мільярди параметрів може займати 64 GB, а після квантизації — значно менше?

Що таке:

FP16
BF16
FP8
Q8
Q5
Q4
GGUF
VRAM
KV Cache
Memory Bandwidth
Tensor Cores

І чому дві відеокарти з однаковими 24 GB VRAM можуть запускати ту саму модель із зовсім різною швидкістю?

Про це — у другій частині: «Локальний AI без магії: GPU, VRAM, квантизація і як зрозуміти, яку модель потягне ваш комп'ютер».
